# wax 사용 매뉴얼

wax는 기능 하나를 **기획 → 설계 → 구현 → 검토 → 보고**로 나누어 진행하고, 문서와 완료 근거를 프로젝트에 남깁니다.

이 매뉴얼은 wax 0.14.0 기준입니다. 설치한 버전은 플러그인 폴더에서 `node bin/wax.mjs --version`으로 확인합니다. 버전마다 바뀐 점은 배포본의 `CHANGELOG.md`와 [변경 이력](https://wax.me2shop.com/changelog/)에 있습니다.

쓰는 방법은 두 가지입니다. 터미널의 AI 세션에서 단계 명령을 하나씩 실행하거나(3·4절, 다른 도구는 5절), 대시보드에서 한 줄로 요청해 선택한 도구가 끝까지 진행하게 합니다(6-3절). 어느 쪽이든 기록은 같은 `.wax/`에 남습니다.

## 1. 무엇이 필요한가요?

Node.js 22 이상과 로그인된 Claude Code, Codex, Antigravity CLI, GitHub Copilot CLI, Grok Build 또는 Gemini CLI 중 하나가 필요합니다. wax는 공개 저장소 [cafein-network/wax](https://github.com/cafein-network/wax)에서 각 도구의 마켓플레이스로 바로 설치하거나, [wax 사이트](https://wax.me2shop.com/#download)에서 ZIP으로 내려받을 수 있습니다. 배포본에는 플러그인 소스·테스트·매뉴얼이 들어 있습니다. wax 코드에는 AGPL-3.0 라이선스(무료로 쓰고 고치고 배포할 수 있으며, 배포 시 소스 제공 조건 준수, 수정본을 네트워크로 제공하면 원격 사용자에게 대응 소스 제공)가 적용되며 AI 도구와 API의 사용 요금·한도는 별도입니다.

**0.14.0 공개 저장소 안내.** 0.14.0부터 공개 저장소 `cafein-network/wax`를 새 이력으로 다시 만들었습니다. 설치 주소는 그대로입니다. 0.13.x 이하에서 등록한 마켓플레이스의 업데이트가 이력 불일치로 실패하면 그 도구에서 `wax` 마켓플레이스 등록을 지우고 다시 등록하세요(9절, INSTALL.md의 "업데이트 및 직접 개선"). 작업 프로젝트의 `.wax`와 `docs/wax`는 그대로 둡니다. 0.13.x 이하의 GitHub 릴리스 ZIP과 출처 증명은 더 이상 제공하지 않으며, 변경 내역은 `CHANGELOG.md`와 [변경 이력](https://wax.me2shop.com/changelog/)에 남아 있습니다.

## 2. 코드 내려받기

ZIP을 **모두 압축 풀기**로 해제한 뒤 내부에 `package.json`과 `bin/wax.mjs`가 있는 `wax` 폴더를 찾습니다. `.claude-plugin` 숨김 폴더도 포함되어 있어야 합니다. 플러그인은 `npm install` 없이 실행됩니다.

Windows·WSL 예제와 업데이트 방법은 ZIP 안의 `INSTALL.md`를 참고하세요. 이 매뉴얼에서 `/path/to/wax`은 예시 경로입니다. 반드시 압축을 푼 실제 절대 경로로 바꾸세요.

아래 예제에서 `/path/to/my-app`은 **실제로 코딩할 프로젝트 디렉터리**로 바꾸세요. 해당 디렉터리는 먼저 존재해야 합니다. 플러그인 소스 디렉터리와 작업할 프로젝트를 구분하세요.

## 3. Claude Code에서 첫 작업 시작

작업할 프로젝트에서 wax 플러그인을 로드합니다. 이 방식은 해당 Claude 세션에 적용되므로 새 세션을 열 때 같은 옵션을 사용하세요.

```sh
cd /path/to/my-app
claude --plugin-dir "/path/to/wax"
```

다른 컴퓨터에서는 `--plugin-dir` 뒤의 경로도 실제 위치로 바꾸세요. npm 설치 없이 동작합니다.

매번 `--plugin-dir`을 붙이지 않으려면 한 번만 설치합니다: `claude plugin marketplace add "/path/to/wax"` 뒤 `claude plugin install wax@wax`. 압축을 푼 폴더가 그대로 마켓플레이스이며, Codex(`codex plugin marketplace add` → `codex plugin add wax@wax`)와 GitHub Copilot CLI(`copilot plugin marketplace add` → `copilot plugin install wax@wax`)도 같은 폴더로 한 번 설치합니다. 업데이트·제거는 설치 안내(INSTALL.md)의 "한 번 설치" 절을 보세요.

처음에는 Claude 대화창에서 시작 명령을 한 번 실행합니다.

```text
/wax:init
```

설정 질문 없이 기본 이름으로 바로 참여하고 대시보드를 엽니다. 작업은 진행 중인 것이 하나면 그 작업, 아니면 없음으로 정합니다. PM이 없는 프로젝트에서는 init한 세션이 PM이 되고(`--no-pm`이면 지정하지 않음), 이미 PM이 있으면 그대로 유지합니다. 이름·작업·PM 옵션을 명시하면 그대로 적용합니다. 끝나면 이 세션이 팀 채널에 참여해 가상 사무실에 캐릭터로 나타나고, 다른 AI 세션이 참여하는 방법(`/wax:join`)을 알려 줍니다. init과 join은 대기 상태로 참여하며, 실제 단계 작업을 시작할 때 작업 중으로 바뀝니다. 대시보드를 나중에 다시 열 때도 `/wax:init`을 실행합니다.

자동 진행은 대시보드의 요청과 보고 화면(`/start`)에서 한 줄로 요청합니다(6-3절). 터미널에서 각 단계를 직접 관리하려면 다음처럼 기능을 요청합니다.

```text
/wax:plan email-login 이메일과 비밀번호로 로그인하는 기능을 만들어줘
```

wax가 기존 코드를 확인하고 요구사항·범위·수용 기준을 정리합니다. 결정이 필요한 질문에 답한 뒤 결과를 확인하세요. 한 명령은 그 단계의 작업을 수행하며, 모든 후속 단계를 한꺼번에 실행하지 않습니다.

## 4. 단계를 차례로 진행

| 명령 | 하는 일 |
| --- | --- |
| `/wax:init` | 시작하기: 팀 채널 참여, 맡을 작업, 대시보드 열기, PM 지정을 한 번에 |
| `/wax:join` | 다른 AI 세션이 팀 채널에 참여(이름·작업만 정함) |
| `/wax:plan email-login …` | 새 기능의 문제·범위·수용 기준 정리 |
| `/wax:design email-login` | 구조·데이터·수정 파일·검증 방법 설계 |
| `/wax:implement email-login` | 호스트의 도구로 실제 코드 수정 및 관련 검사 실행 |
| `/wax:review email-login` | 설계와 실제 결과 비교, 테스트 근거와 미검증 항목 기록 |
| `/wax:report email-login` | 결과·검증·사용법·남은 과제 정리 |
| `/wax:status email-login` | 현재 단계와 완료 근거 확인 |
| `/wax:iterate email-login 만료 토큰 처리 개선` | 이전 주기를 보관하고 구현 단계로 돌아가기 |

예를 들어 첫 기획을 마친 후 다음 명령을 한 번씩 실행합니다.

```text
/wax:design email-login
/wax:implement email-login
/wax:review email-login
/wax:report email-login
```

현재 단계의 문서와 완료 근거가 있어야 다음 단계로 넘어갑니다. 구현은 실제로 통과한 테스트(`wax test`)나 커밋(`wax evidence`) 근거를, 검토는 통과한 테스트 근거와 확인된 통과 판정을 함께 연결해야 완료됩니다. 문서만 고치는 작업처럼 실행할 검증이 없으면 `--no-proof <사유>`로 사유를 남기고 넘어가며, 그 사유는 완료 기록과 다른 도구가 읽는 인수인계 문맥에 그대로 남습니다. 검토는 수용 기준 표에 더해 구조 → 기능 → 효율 → 표현 순서로 점검합니다. 역할별 흐름과 권한(화면에서 숨기는 데 그치지 않고 서버에서도 막히는지), 되돌릴 수 없는 동작의 확인·취소 경로, 수치·집계와 원본 데이터의 일치, 실제에 가까운 데이터 양에서의 찾기·속도, 로딩·오류·빈 화면을 보고, 해당하지 않으면 해당 없음과 이유를 적습니다. 발견한 문제에는 누가 왜 곤란한지를 함께 적습니다. 해결되지 않은 문제나 미검증 기준이 남으면 검토를 완료하지 않고 그 이유를 알려줍니다.

기능 ID는 영문 소문자·숫자로 시작하며 소문자·숫자·하이픈만 포함하는 1~64자입니다. `email-login`, `dashboard`, `payment-v2`처럼 정하세요.

### 개선 주기(iterate)

검토에서 문제가 발견됐다면 다음과 같이 개선합니다.

```text
/wax:iterate email-login 만료된 인증 토큰을 거부하도록 개선
/wax:implement email-login
/wax:review email-login
/wax:report email-login
```

### 수용 기준 추적

기획은 수용 기준을 한 줄에 하나씩 `- AC-1: <기준> — 검증: <방법>`처럼 줄 맨 앞에 ID를 붙여 적습니다(줄 맨 앞의 `AC-<번호>`만 ID로 읽고, 본문 중간의 언급은 선언으로 보지 않습니다). 기획에 AC ID가 있으면 검토를 완료할 때 `--checks-file` JSON 배열에 ID마다 `{"id": "ac-1", "status": "pass", "detail": "<확인 내용>", "proofIds": ["<근거 ID>"]}` 항목을 넣어야 합니다. `pass`는 현재 주기의 통과한 테스트나 커밋 근거가 연결되어야 인정되고, 빠졌거나 `unverified`이거나 근거 없는 기준이 남으면 검토가 완료되지 않습니다. 정말 검증할 수 없는 기준만 `--ac-unverified <사유>`로 남기고 넘어가며, `fail`이 하나라도 있으면 사유와 관계없이 거절하므로 `wax iterate`로 고칩니다. 추적표(AC → 상태 → 근거)는 `wax status <id>`의 `acceptanceTrace`, `wax context <id>`, 보고 단계 프롬프트에 나타납니다. AC ID가 없는 기존 기획은 이전과 똑같이 동작합니다.

### 검토자 분리

단계를 완료한 세션 이름은 `wax complete ... --author <이름>`으로 완료 기록(`completed`)과 이력(`history`)에 남습니다. 구현을 완료했거나 현재 주기의 구현 근거(`wax test`·`wax evidence --author`)를 남긴 세션이 검토까지 완료하면 기본(`WAX_REVIEW_SEPARATION=warn`)으로는 완료하되 경고를 남깁니다. 경고는 CLI 오류 출력(`wax: 경고: …`), 완료 기록의 `warning`, 대시보드 기록 타임라인의 단계 완료 항목, 자동 진행 요청 대화와 인수인계 문맥에 보입니다. `WAX_REVIEW_SEPARATION=enforce`로 실행한 세션과 대시보드는 구현한 세션의 검토 완료와 `--author` 없는 검토 완료를 거절합니다(대시보드 자동 진행은 한 세션이 모든 단계를 맡으므로 검토에서 멈춥니다). `off`는 확인하지 않습니다. 팀 전체에 적용하려면 모든 세션과 대시보드를 같은 설정으로 시작하세요. 이름은 세션이 스스로 밝히는 값이라 보안 경계가 아니라 실수를 막는 장치입니다. 이전 기록에는 완료 세션이 없으며 그대로 읽고 가져올 수 있습니다.

### 근거 신선도

`wax test`·`wax evidence`는 근거를 남길 때 작업 트리 지문(`tree`)을 함께 저장합니다. 지문은 HEAD 커밋과, HEAD와 다르거나 추적되지 않은(무시 목록 제외) 파일별 Git blob ID입니다(`.wax/`는 제외). 이후 `wax context`는 근거마다 "이후 바뀐 파일 N개"를, 머리말에는 현재 주기의 검토 근거(없으면 구현 근거) 이후 바뀐 파일을 보여 주고, `wax status <id>`는 같은 내용을 `evidenceFreshness`로, 보고 단계 지시문(`wax prompt report`, 대시보드 자동 진행)은 "검토 근거 이후 바뀐 파일 N개: …"로 알립니다. 대시보드 근거 카드에도 "이후 바뀐 파일 N개"가 붙고 마우스를 올리면 파일 목록이 보입니다. 이 표시는 판정이 아니라 관찰이며 단계 진행을 막지 않습니다. 바뀐 파일이 근거와 관련 있으면 테스트를 다시 실행하세요. 바뀐·추적되지 않은 파일이 200개를 넘거나 합계 64MB를 넘거나 Git 명령이 5초 안에 끝나지 않으면 멈추지 않고 지문을 "미확인"으로 남깁니다. Git이 없는 프로젝트와 이 기능 이전의 근거에는 지문이 없어 "이후 변경 미확인"으로 표시되며, 그대로 읽고 백업·복원할 수 있습니다.

### 작업 인수인계

새 세션에서 기존 작업을 이어받을 때는 먼저 다음 명령으로 인수인계 문맥을 읽으세요.

```sh
node /path/to/wax/bin/wax.mjs --project /path/to/my-app context login --budget 3000
```

`login`은 기존 작업 ID입니다. 목표, 현재 단계와 다음 행동, 화이트보드 결정과 답변·결정이 연결되지 않은 질문, 실행 근거, 개선 사유와 단계 문서 발췌를 보여 줍니다. 각 항목의 `.wax/features/<id>.json#/...` 또는 `.wax/chat/board/<id>.jsonl#<노트 ID>` 참조로 원본을 확인할 수 있습니다. 단계 스킬과 `work`에서도 작업 전에 이 명령을 읽도록 안내합니다.

`--budget`은 유니코드 문자 수이며 토큰 수가 아닙니다. 기본 3,000자, 범위 1,000~100,000자입니다. 끝의 표시/전체 개수와 `…`는 생략된 항목과 원문이 있음을 알려 줍니다. 출력은 규칙에 따른 발췌이므로 최신 `status`, 전체 단계 `prompt`와 필요한 원본도 확인하세요. 질문은 해당 작업 보드 범위이며, 답변이 연결돼도 실제 해결을 보장하지 않습니다. 손상된 보드 기록은 제외 개수를 표시하고, 안전하지 않은 저장 경로나 손상된 작업 파일은 오류로 알립니다.

조회는 읽기 전용이며 외부 AI를 호출하지 않습니다. 과거 주기의 테스트와 현재 주기의 테스트를 구분하고 실행 당시 커밋·작업 트리 상태를 표시합니다. 기록된 통과는 현재 코드의 통과를 보장하지 않으므로 변경 후에는 필요한 테스트를 다시 실행하세요.

### 단계별 소요 시간과 실행 기록

wax는 작업 이력으로 단계마다 걸린 시간을 계산합니다. 단계에 들어간 때부터 완료한 때까지의 실제 경과 시간이며, 개선 주기로 구현에 다시 들어간 구간은 같은 단계에 더합니다. 대시보드 **작업 진행**의 작업마다 단계별 시간과 합계가 나오고, 진행 중인 단계는 "12분째"처럼 표시합니다. `wax status <id>` JSON에는 `durations`로 들어갑니다. 보관한 기간과 백업·복원 사이의 공백은 세지 않고, 시각이 없거나 거꾸로 간 예전 기록은 건너뜁니다. 비용·토큰은 작업 단계와 맞출 기록이 없어 넣지 않습니다.

단계 방문마다 언제, 어느 세션·도구가, 어떤 근거로, 무엇을 바꾸며 지나갔는지는 `wax trace <id>`(Markdown)나 `wax trace <id> --json`, 대시보드의 실행 기록 패널에서 봅니다(6절 "대시보드에서 기록 확인하기"). 둘 다 읽기 전용이며 AI를 부르지 않습니다.

### 화면 캡처와 시안 비교

화면이 있는 작업은 캡처를 근거로 남깁니다. `wax capture <작업ID> --check <검증 ID> --file <파일> [-- <캡처 명령>]`은 캡처를 `.wax/artifacts/`에 보관하고, 캡처마다 찍은 조건을 라벨로 붙일 수 있습니다.

- `--viewport <너비>x<높이>`: 화면 크기(예: `1280x800`, 각 16384 이하)
- `--scroll top|bottom|<픽셀>`: 스크롤 위치
- `--state <이름>`: 화면 상태. 영문 소문자로 시작하는 32자 이하 이름(예: `default`, `hover`, `focus`, `open`, `loading`, `error`, `empty`)

웹 프로젝트(6-8절)의 설계·검토 안내는 360·768·1280과 시안보다 넓은 1920 폭을 상태별로 찍고, 화면 변화가 스크롤·클릭·호버·시간 중 무엇 때문인지 적게 합니다. 라벨은 PR 설명 초안, `wax trace`, 대시보드 실행 기록 패널에 함께 보입니다.

`wax compare <작업ID> [--json]`은 검토 캡처(`ui-review`)를 폭·스크롤·상태가 모두 같은 설계 캡처(`design-preview`)와 짝지어 보여 줍니다. 기준은 이 프로젝트에서 찍은 설계 캡처뿐입니다. 라벨마다 가장 최근 캡처를 쓰고, 기준은 검토한 주기 이하에서 가장 최근 설계 주기의 캡처를 고릅니다. 짝이 없는 캡처(시안 없음, 다시 캡처하지 않은 시안)와 라벨 없는 예전 캡처는 짝짓지 않고 따로 적으며, 디자인실 인계 미리보기는 라벨 없는 참고로 표시합니다. 두 PNG의 크기가 같으면 서로 다른 픽셀 비율을 보여 주지만 관찰값일 뿐 일치 판정이 아니고, 크기가 다르면 다르다고만 적습니다. 대시보드 실행 기록 패널의 마지막 검토 방문에 두 캡처가 나란히(휴대폰 폭에서는 위아래로) 나오고, PR 설명 초안에도 요약이 들어갑니다. 읽기 전용이며 AI를 부르지 않습니다. 검토 안내는 설계 캡처와 같은 라벨로 찍고 `wax compare`를 읽어 남은 차이를 숨기지 않고 적게 합니다.

### PR 설명 초안

`wax pr-body <작업ID> [--out <파일>] [--json]`은 작업 기록만으로 PR 설명 Markdown 초안을 만듭니다. 제안 PR 제목, 작업 단계와 주기, 저장된 보고 문서, 수용 기준 표, 현재 주기의 테스트·커밋 근거와 화면 캡처, 시안 비교 요약, 근거 없이 완료한 단계의 사유, 근거 신선도가 들어갑니다. 빠진 기록은 빠졌다고 적고 지어내지 않습니다. 기록 속 `@이름`은 코드 표기로 바꿔 GitHub 알림이 가지 않게 합니다. 표준 출력이나 `--out` 파일에만 쓰고(이미 있는 파일은 덮어쓰며, 디렉터리나 심볼릭 링크는 거절), `gh`나 네트워크를 부르지 않으며 PR을 만들지 않습니다.

보고 단계 안내는 보고를 완료한 뒤 이 초안을 만들지 제안하고, `gh pr create --draft --body-file <파일>`은 사용자가 승인할 때만 실행하게 합니다. PR 만들기·push·병합은 늘 사람이 정합니다. PM 루프(6-6절)도 보고가 끝난 작업에 초안 파일 카드만 내고 PR 결정은 사람에게 남깁니다.

## 5. Gemini CLI에서 사용 (기존 사용자)

개인 사용자는 Google 안내에 따라 Antigravity CLI(5-2절)를 권장합니다. 이 절은 API 인증이나 기업 라이선스로 Gemini CLI를 계속 쓰는 경우입니다.

**인증 안내(2026-10-20 확인):** 2026-06-18부터 개인 Google 로그인에 포함되던 Gemini CLI 이용이 종료됐으며 무료·Google AI Pro·Ultra 모두 해당합니다. 계속 이용하려면 지원되는 API 인증 또는 기존 Gemini Code Assist Standard·Enterprise 라이선스가 필요합니다. Google 전환 공지는 유료 API 키 이용을 명시하고 개인 사용자에게 Antigravity CLI 이전을 안내합니다. Standard·Enterprise 신규 구독 판매도 2026-10-09 중단됐고 기존 구독은 계약과 별도 종료 일정에 따릅니다. wax 설치는 AI 이용 권한을 제공하지 않습니다. [개인 계정 종료 안내](https://developers.google.com/gemini-code-assist/docs/deprecations/code-assist-individuals) · [API·Antigravity 전환 안내](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/) · [기업 구독 일정](https://docs.cloud.google.com/gemini/docs/codeassist/sunset)

처음 한 번 확장을 연결합니다.

```sh
gemini extensions link "/path/to/wax"
cd /path/to/my-app
gemini
```

새 Gemini 세션에서 Claude와 같은 명령을 사용합니다. 처음에는 `/wax:init`으로 시작하고, 이어서 `/wax:plan`, `/wax:design` 등을 실행합니다. 확장 연결이나 명령 파일 변경 후에는 세션을 다시 시작하세요. 이 프로젝트에서 Gemini TOML 문법은 검사했지만 실제 Gemini 호스트 실행은 아직 검증하지 않았습니다.

설치 버전은 플러그인 폴더에서 `node bin/wax.mjs --version`으로 확인합니다.

## 5-1. Codex에서 사용

터미널에서 공개 마켓플레이스를 한 번 등록하고 설치합니다. Codex용 목록은 `.agents/plugins/marketplace.json`에 있으며 ZIP에도 포함됩니다.

```sh
codex plugin marketplace add cafein-network/wax
codex plugin add wax@wax
```

`already added from a different source`가 나오면 먼저 `codex plugin marketplace list`로 이전 ZIP 경로나 Git 주소를 확인합니다. 공개 저장소로 전환하려면 아래 명령을 한 줄씩 실행하고, 앞 명령이 성공했을 때만 다음으로 넘어갑니다. 마켓플레이스 등록 제거는 작업 프로젝트의 소스나 `.wax` 기록을 삭제하지 않습니다.

```sh
codex plugin marketplace remove wax
codex plugin marketplace add cafein-network/wax
codex plugin add wax@wax
```

등록 출처가 이미 공개 GitHub 저장소인데 `plugin wax was not found in marketplace wax`가 나오면 `codex plugin marketplace upgrade wax`로 갱신한 뒤 `codex plugin list --marketplace wax --available --json`에서 `wax@wax`를 확인하고 다시 설치합니다. ZIP 출처라면 새 ZIP을 같은 경로에 풉니다. 여전히 목록에 없으면 `codex --version`, 마켓플레이스 목록과 플러그인 목록 결과를 함께 확인하세요. 설치 뒤에는 새 Codex 세션을 시작합니다. 자세한 내용은 [설치 안내](../INSTALL.md)의 오류 해결 절을 참고하세요.

특정 프로젝트에만 연결하려면 다음 프로젝트 연결기를 사용합니다. Antigravity CLI(5-2절)·Grok Build(5-4절)도 같은 연결기를 씁니다. 압축을 푼 원본은 계속 같은 위치에 두세요.

```sh
node "/path/to/wax/scripts/install-project.mjs" --project "/path/to/my-app"
node "/path/to/wax/scripts/install-project.mjs" --project "/path/to/my-app" --check
cd /path/to/my-app
codex
```

Codex의 `/skills`에서 13개 스킬을 확인하고 대화창에서 사용합니다. `$`는 스킬 호출, `@`는 파일 첨부입니다. 배정받은 일은 `$wax:work <업무ID>`로 실행하며, wax 팀 채널의 `@이름` 알림과 구분하세요. 다음 예시는 셸 터미널 명령이 아닙니다.

```text
$wax:init
$wax:plan email-login 이메일 로그인 구현
$wax:design email-login
$wax:implement email-login
$wax:review email-login
$wax:report email-login
$wax:status email-login
$wax:iterate email-login 만료 토큰 처리 개선
```

연결기는 프로젝트의 `.agents/skills/wax-*`(Codex·Antigravity CLI·GitHub Copilot CLI)와 `.grok/skills/wax-*`(Grok Build)에 같은 원본 스킬을 연결합니다. 한 위치라도 같은 이름의 다른 스킬이 있으면 어디에도 쓰지 않고 멈춥니다. 기존 다른 스킬이나 도구 설정을 덮어쓰지 않으며 같은 연결을 반복해도 됩니다. 0.13.4까지 안내한 `scripts/install-codex.mjs`도 같은 연결기를 실행합니다. Windows는 디렉터리 junction, Linux·WSL은 심볼릭 링크를 사용합니다. 원본 경로가 바뀌면 설치 확인이 실패하므로 기존 링크를 확인한 뒤 다시 연결하세요. 새 스킬이 보이지 않으면 Codex를 재시작합니다.

현재 단계의 문서·완료 근거와 `.wax/features` 기록은 다른 호스트와 공유합니다. Codex 자체의 로그인·도구 권한을 사용합니다.

## 5-2. Antigravity CLI에서 사용

Antigravity CLI(`agy`)는 프로젝트의 `.agents/skills`에서 스킬을 읽으므로 5-1절의 프로젝트 연결기를 그대로 사용합니다. Codex용으로 이미 연결했다면 추가 설치가 필요 없습니다. 개인 Google 계정으로 쓰던 Gemini CLI 사용자도 이 방법으로 옮겨 오면 됩니다.

```sh
node "/path/to/wax/scripts/install-project.mjs" --project "/path/to/my-app" --check
cd /path/to/my-app
agy
```

새 세션의 `/skills`에서 13개 스킬을 확인합니다. Antigravity CLI는 스킬을 슬래시 명령으로 바꾸므로 `/plan email-login 이메일 로그인 구현`, `/design email-login`처럼 스킬 이름으로 호출합니다. 실제 표시 이름은 `/skills` 목록을 따르며, 이름이 겹치면 "wax plan 단계를 실행해줘"처럼 요청할 수 있습니다. 시작 명령 `/init`이 Antigravity CLI 자체 명령과 겹치면 "wax init 스킬로 시작해줘"처럼 요청하세요.

`agy plugin install`이나 `agy plugin import gemini`는 파일을 다른 위치로 복사·변환하므로 스킬이 함께 제공되는 CLI를 찾지 못할 수 있습니다. 프로젝트 연결 방식을 사용하세요. 실제 Antigravity CLI 세션 실행은 아직 검증하지 않았습니다.

## 5-3. GitHub Copilot CLI에서 사용

GitHub Copilot CLI(`copilot`)에는 한 번만 설치합니다. Microsoft Copilot이 아니라 GitHub Copilot 구독으로 쓰는 터미널 도구입니다. 압축을 푼 wax 폴더를 로컬 마켓플레이스로 등록하면 모든 프로젝트에서 wax 스킬을 씁니다.

```sh
copilot plugin marketplace add "/path/to/wax"
copilot plugin install wax@wax
```

로컬 마켓플레이스는 폴더를 복사하지 않고 바로 읽습니다. 새 버전은 같은 경로의 폴더 내용을 바꾸면 다음 세션부터 적용됩니다. 처음에는 "wax init 스킬로 시작해줘"로 시작합니다. 스킬은 "wax plan 스킬로 email-login 이메일 로그인 기획해줘", "wax design 스킬로 email-login 설계해줘"처럼 이름을 밝혀 요청합니다(`/status` 같은 GitHub Copilot CLI 자체 명령과 이름이 겹치기 때문). 팀 채널에서 세션 종류는 `copilot`, 기본 이름은 `copilot-<폴더 이름>`입니다.

프로젝트에 `.agents/skills`(5-1절)를 연결해 둔 경우에도 충돌하지 않습니다. 같은 이름의 스킬은 프로젝트 쪽이 우선하고 한 벌만 보입니다.

## 5-4. Grok Build에서 사용

Grok Build(`grok`)는 xAI의 터미널 코딩 도구로, 공식 프로젝트 스킬 위치인 `.grok/skills`를 읽습니다. 5-1절의 프로젝트 연결기가 이 위치에도 연결하므로 같은 명령을 실행한 뒤 시작합니다.

```sh
node "/path/to/wax/scripts/install-project.mjs" --project "/path/to/my-app" --check
cd /path/to/my-app
grok
```

새 세션의 `/skills`에서 13개 스킬을 확인합니다. Grok Build에는 `/plan`(플랜 모드)·`/code-review` 같은 자체 명령이 있으므로 GitHub Copilot CLI처럼 "wax init 스킬로 시작해줘", "wax plan 스킬로 email-login 이메일 로그인 기획해줘"처럼 스킬 이름을 밝혀 요청합니다. 팀 채널에서 세션 종류는 `grok`, 기본 이름은 `grok-<폴더 이름>`입니다. Grok Build는 Claude Code 플러그인도 읽으므로 Claude Code에 wax를 설치했다면 연결 없이 보일 수 있으며, 같은 이름의 스킬은 우선순위가 높은 위치 하나만 쓰입니다. 대시보드 첫 화면의 자동 진행 도구에는 아직 Grok Build가 없습니다. 실제 Grok Build 세션 실행은 아직 검증하지 않았습니다.

## 6. 팀 대시보드: AI 세션 협업과 일일 업무보고

대시보드는 어느 코딩 도구의 세션이든 한 화면에서 같은 방식으로 보여 줍니다. 팀 패널의 각 세션에는 **다음 명령**이 그 도구의 문법으로 나옵니다. 배정된 업무가 있으면 work, 없으면 맡은 작업의 현재 단계, 맡은 작업이 끝났으면 status이며, 복사 버튼으로 그 세션에 그대로 붙여 넣을 수 있습니다. 업무 배정 폼에서 담당 세션을 고르면 그 세션이 실행할 명령을 미리 보여 주고, 가상 사무실에서 캐릭터를 눌러도 같은 다음 명령이 나옵니다. 도움말(`/help`)의 "도구별로 부르는 방법" 표에 모든 명령이 정리되어 있습니다.

세션은 참여할 때 `wax chat join --model <모델>`로 자기 모델을 밝힐 수 있습니다(같은 도구에서도 모델을 바꿀 수 있기 때문). 대시보드와 인사기록 카드에 "도구 · 모델"로 표시되며, 세션이 스스로 밝힌 값입니다.

여러 코딩 도구 세션(Claude Code·Codex·Antigravity CLI·GitHub Copilot CLI·Grok Build·Gemini CLI)이 같은 프로젝트에서 일할 때, 각 세션의 AI가 **팀원**으로 참여합니다. 대화·업무 배정·일일 보고는 프로젝트의 `.wax/chat/`에 저장되고, 로컬 대시보드에서 실시간으로 확인합니다. 상세 기록과 팀 채널은 기록을 보여 줍니다. 요청과 보고 화면(`/start`)에서 사용자가 요청을 보내면 선택한 CLI의 별도 세션이 작업합니다. 가상 사무실의 안내 NPC(진행 소식을 전하는 제이크, 도움말·사무실을 안내하는 써니, 디자인실 제작 순서를 안내하는 제니)는 프로젝트 기록과 현재 시각으로 말합니다. 리나의 도구 소식은 서버가 공식 공개 릴리스를 소스마다 1시간 간격으로 확인합니다. 프로젝트·설치 버전·세션 정보는 보내지 않으며, 조회 실패 시 마지막 자료를 유지하고 실패한 소스만 5분부터 최대 1시간까지 간격을 늘려 다시 시도합니다. 호출 한도 응답의 대기 시간을 따르고 수동 새로고침은 1분에 한 번으로 제한합니다. `WAX_TOOL_NEWS=off`로 외부 조회를 끌 수 있습니다. NPC 안내와 캐릭터 잡담은 화면 연출이라 기록되지 않습니다. 자세한 내용은 대시보드의 **도움말**(`/help`)을 보세요.

### 대시보드 열기

```sh
node "/path/to/wax/bin/wax.mjs" --project "/path/to/my-app" dashboard
```

`http://127.0.0.1:4330/`을 엽니다(`--port`나 `WAX_DASHBOARD_PORT`로 변경). AI 세션에서는 `/wax:init`(Codex `$wax:init`, Antigravity `/init`)이 대시보드를 바로 열어 줍니다. 첫 화면은 팀 채널이고, **＋ 새 요청**을 누르면 요청과 보고 화면(`/start`)의 시작 가이드가 열립니다. 0.13.5까지의 `/?mode=…`·`/?request=…` 주소는 `/start`로 이어집니다. 따로 대시보드 명령은 없고, 나중에 다시 열 때도 init을 실행합니다. 이미 켜져 있으면 주소만 알려 주고, 꺼져 있으면 세션이 백그라운드로 실행하거나 따로 실행할 명령을 안내합니다. `dashboard --status`로 실행 여부만 확인할 수 있습니다. 화면 사용법은 대시보드 상단의 **도움말**(`/help`)에 정리되어 있습니다. 서버는 이 컴퓨터(127.0.0.1)에서만 열립니다. 웹에서 쓰는 사람 이름은 `WAX_CHAT_USER`로 정합니다(기본 "대표"). 화면 언어는 오른쪽 위의 언어 선택(한국어·English)으로 바꾸며 이 브라우저에 기억됩니다. 처음에는 브라우저 언어가 한국어면 한국어, 아니면 영어로 열리고 주소에 `?lang=ko`·`?lang=en`을 붙여 정할 수도 있습니다. 화면 문구만 바뀌고 메시지·문서·보고서처럼 사람과 AI가 쓴 내용은 쓴 그대로 보여 줍니다.

### 브라우저 알림

팀 채널·요청과 보고·상세 기록 화면 위쪽의 **알림 켜기**를 누르면 브라우저가 알림 권한을 묻습니다(페이지를 열 때는 묻지 않음). 그 뒤 탭을 보고 있지 않을 때 다음 일을 브라우저 알림으로 받습니다.

- AI 세션의 질문
- 새 실행 승인 요청
- 작업 단계 완료
- 새 트리거 제안과 알림만 하는 트리거(6-5절)
- 사람이 결정할 PM 루프 카드와 PM 루프 정지(6-6절). auto가 카드 없이 처리하는 행동은 알리지 않습니다.

알림을 누르면 그 탭으로 돌아와 해당 메시지·승인·작업을 엽니다. 탭을 보고 있는 동안, 내가 쓴 글, 화면을 열거나 다시 연결하기 전부터 있던 기록은 알리지 않고, 같은 일은 한 번만 알립니다. 가려진 동안 쌓인 수는 탭 제목 앞에 `(2)`처럼 붙고 탭을 다시 보면 사라집니다. 켜고 끈 선택은 이 브라우저에만 저장되며, 브라우저가 알림을 막았거나 지원하지 않으면 버튼에 **알림 차단됨**·**알림 미지원**으로 표시됩니다. 막혔다면 주소창의 사이트 설정에서 알림을 허용한 뒤 새로고침하세요. 대시보드 탭이 열려 있어야 알림이 옵니다.

### 대시보드에서 기록 확인하기

상단 통계 카드를 누르면 관련 작업·업무·타임라인으로 이동합니다. **먼저 확인할 일**은 현재 막힌 업무, 선택한 날짜의 실패한 테스트 근거, 오래된 미해결 질문 순으로 표시합니다. 같은 작업·단계의 이후 통과 기록이 있으면 이전 실패는 이 목록에서 빠지고 타임라인에는 남습니다. 실패 기록만으로 현재 작업 전체가 실패했다고 판단하지 마세요.

**원문 보기**는 요약에서 생략된 질문·결정의 전체 본문을, **실행 근거 보기**는 저장된 실제 명령·종료 코드·출력을 기존 문서 창에서 보여 줍니다. 버튼을 눌러도 명령을 다시 실행하지 않습니다. 최근 결정과 테스트 근거는 선택한 날짜 기준이며, 업무와 미해결 질문은 현재 전체 기록 기준입니다.

**실행 기록.** **작업 진행**의 각 작업 옆 **실행 기록**을 누르거나 `/manage?feature=<작업ID>`로 열면, 작업이 단계를 지나간 과정을 단계 방문마다 세로 타임라인으로 보여 줍니다. 방문마다 시작·끝·걸린 시간(단계별 소요 시간과 같은 계산), 결과(단계 완료·구현으로 되돌림과 그 이유·진행 중, 요청이 연결되어 있으면 질문·막힘), 완료한 세션과 실행 도구, 그때의 커밋, 완료 근거와 사유, 연결한 테스트·커밋 근거와 기록 이후 바뀐 파일, 검토의 수용 기준 결과, 앞 방문 끝 커밋과 이번 방문 끝 커밋 사이에 바뀐 파일(커밋 기준)이 펼쳐집니다. 되돌린 반복은 같은 단계를 다시 방문한 줄로 보입니다. **Markdown 내려받기**는 같은 내용을 PR 설명 초안과 같은 규칙(@이름·HTML 무력화)으로 내려받고, CLI에서는 `wax trace <id>`(Markdown)나 `wax trace <id> --json`으로 봅니다. 읽기 전용이며 AI를 부르지 않습니다. 단계를 완료하거나 되돌릴 때 이력에 그때의 커밋(`head`), 커밋 안 된 변경 여부(`dirty`, `.wax/` 제외), 아는 경우 실행 도구(`tool`, 대시보드 자동 진행)가 함께 남으며, Git이 없거나 이 기능 이전의 기록은 해당 칸을 비워 둡니다. 토큰·비용은 Claude Code 사용량 기록과 단계 방문을 맞출 세션 기록이 없어 보여 주지 않습니다.

날짜를 빠르게 바꿔도 마지막으로 선택한 날짜의 응답만 적용됩니다. 갱신 실패 시 마지막 성공 기록과 재시도 버튼을 유지합니다. 재연결 시 세션 정보를 다시 읽으며, 입력 중인 배정 내용과 새 작업 정보는 배경 갱신으로 지우지 않습니다.

### 세션끼리 대화하기

처음 한 세션은 `/wax:init`으로 시작하고, 다른 AI 세션은 `/wax:join`(Codex `$wax:join`, Antigravity `/join`, GitHub Copilot CLI·Grok Build "wax join 스킬로 참여해줘")으로 참여합니다. init이나 join을 건너뛰어도 세션에서 처음 실행한 wax 명령이 자동으로 참여시킵니다. 같은 이름이 이미 활동 중이면(같은 폴더에서 같은 도구 세션을 둘 이상 띄운 경우) `claude-my-app-2`처럼 번호를 붙여 참여하고 그 이름을 알려 줍니다. init을 여러 번 해서 지난 세션이 이름을 잡고 있으면 `/wax:init --reset`(join도 같음)으로 지난 세션을 정리한 뒤 기본 이름으로 참여합니다. 듣는 중이거나 작업 중인 세션은 남기며, PM·업무는 이름에 남아 그 이름으로 참여한 새 세션이 이어받습니다. 참여한 세션은 wax 단계 명령을 실행할 때 단계를 시작하면 상태를 "작업 중"으로 바꾸고 그 작업 채널의 최근 메시지를 읽습니다. 단계를 마치면 맡은 업무의 상태(완료·막힘)에 결과를 기록합니다. 참여자 이름은 기본적으로 `도구-폴더이름`(예: `my-app` 폴더의 Claude 세션은 `claude-my-app`)입니다. 폴더 이름에서 영문·한글 등 글자·숫자·공백·`_`·`.`·`-`가 아닌 문자는 `-`로 바꾸고 40자 안으로 줄입니다. 같은 도구의 세션을 여러 개 쓰거나 이름을 바꾸려면 아무 wax 명령에나 `--name <이름>`을 붙입니다(예: `/wax:join --name claude-front`). 그 세션은 이후 명령에서도 그 이름을 쓰고, 바로 채널에 참여합니다. 이전 이름으로 참여한 적이 있으면 그 이름은 "자리 비움"으로 바뀝니다. 이름은 세션 대화 안에서만 기억하므로 새 세션에서는 다시 지정합니다.

맡을 작업도 함께 정할 수 있습니다. `/wax:join --name claude-front --feature chatbot`(`--project=chatbot`도 같음)처럼 실행하면 그 세션이 `chatbot` 작업을 선택한 대기 상태로 참여하고, 이후 wax 명령에서 작업 ID를 생략하면 그 작업을 씁니다. init은 작업 선택 여부와 관계없이 `http://127.0.0.1:4330/`(팀 채널)을 엽니다. 해당 작업 기록은 `/manage?feature=chatbot`에서 확인합니다. 첫 화면의 **기존 AI 세션으로 팀 작업하기**는 PM 유무, 배정과 막힌 이유, 각 세션에 붙여 넣을 명령을 보여 줍니다.

소통 규칙은 왕복 대화를 줄이도록 정해져 있습니다. AI 세션은 메시지를 보낼 때마다 전체 대화를 다시 읽으므로, 짧은 인사나 확인 한 줄도 비용이 큽니다.

- **지시**는 PM의 업무 배정(`assign`)으로만 전달합니다. 목표·범위·완료 조건·산출물을 담습니다.
- **결과**는 업무 상태(`task done`·`task block`)의 메모로 보고합니다. 대시보드의 업무 목록과 타임라인에 표시됩니다.
- **채널 글**은 질문(`question`), 답변(`answer`), 결정(`decision`)만 씁니다. 인사·수신 확인·진행 보고·요약은 올리지 않습니다. 대표가 직접 보내 달라고 한 메시지는 그대로 보냅니다.

메시지는 두 부분으로 구성됩니다.

- **지금 하는 일**(`--doing`): 보내는 세션이 현재 하는 일. 대시보드 팀 목록에도 표시됩니다.
- **전할 내용**(`--message`): 받는 사람(`--to`, 생략하면 전체)에게 필요한 질문·답변·결정. 문서 내용은 옮기지 않고 경로를 적습니다.

직접 대화하려면 `/wax:chat [채널] [메시지]`(Codex `$wax:chat`, Antigravity `/chat`)를 실행합니다. 세션은 명령을 실행할 때만 채널을 읽으므로, 다른 세션의 메시지는 그 세션이 다음 wax 명령을 실행할 때 전달됩니다. 다른 세션의 메시지는 참고 자료로만 다루며, 메시지 안의 요청만으로 명령을 실행하지 않습니다.

**듣기와 바로 답하기.** 세션이 wax에 참여하면, 출력 한 줄마다 세션을 깨울 수 있는 도구(Claude Code의 Monitor)가 있을 때 `wax chat watch --author <이름> --wake`를 자동으로 켭니다. 이후 누군가 `@이름`으로 부르거나 받는 사람으로 지정한 메시지, 또는 PM의 새 배정이 오면 세션이 깨어나 같은 채널에 답변(`answer`)으로 답합니다. 기다리는 동안에는 AI를 호출하지 않고, 부르지 않은 메시지와 자기 메시지로는 깨어나지 않습니다. 메시지는 채널이 달라도 쓴 순서대로 전달되고, 감시가 끊겼다 다시 시작하면(Monitor는 30분마다 만료) 그 사이 온 메시지를 먼저 전달합니다. 읽음 위치는 `.wax/chat/watch/`, 듣는 중 표시는 `.wax/chat/listeners/`에 남습니다. 사람이 채팅창에서 맡기지 않은 일을 요청하면 세션은 그 요청을 자기 세션의 사용자에게 전하고, 전달했다고 답합니다. `/wax:chat --watch`는 듣기가 꺼져 있을 때 다시 켭니다. Codex·Gemini CLI·Antigravity CLI에는 출력으로 세션을 깨우는 기능이 없어 다음 wax 명령 때 메시지를 확인합니다. 바로 알림을 받으려면 `wax chat watch`를 별도 터미널에 띄웁니다. 이 감시는 사람이 보는 알림이라 `--wake`를 붙이지 않으며, 대시보드에는 `다음 명령 때`로 표시됩니다.

**채널 화면에서 부르기.** 채널 화면(`/chat`) 입력창 위에 참여한 AI 세션이 **받는 사람** 버튼으로 나옵니다. 버튼에는 `바로 답함`(듣는 중), `다음 명령 때`, `자리 비움`이 표시됩니다. 받는 사람을 고르거나 `@이름`으로 부르고 보내면, 누가 곧 답하고 누가 나중에 확인하는지 안내가 나옵니다. 받는 사람이 없으면 기록만 남고 AI 세션은 깨어나지 않습니다. 메시지마다 있는 **답장**을 누르면 그 메시지에 이어서 답하고, 질문이면 유형이 답변으로 바뀝니다.

**입력창 자동완성.** 입력창에서 `@`를 치면 참여한 세션, `/`를 치면 wax 명령, `#`을 치면 작업이 목록으로 나옵니다. 화살표로 고르고 Enter나 Tab으로 넣으며, Esc로 닫습니다. `@이름`을 고르면 그 세션이 받는 사람으로도 선택됩니다. `/명령`은 받는 사람이 한 명이면 그 도구의 문법(Claude Code `/wax:review`, Codex `$wax:review` 등)으로, 아니면 `wax review`로 넣고, 작업 스레드나 작업 채널에서는 작업 ID도 채웁니다.

**작업 탭.** 채널 왼쪽의 **작업** 탭은 요청·업무 배정·이어진 대화·실행 승인을 **답변 필요 · 진행 중 · 완료**로 나눠 오늘·어제·지난 7일·지난 30일·이전으로 묶어 보여 줍니다. 위의 **작업 찾기**는 모든 상태에서 제목·내용·담당·ID를 찾습니다. 별 버튼으로 고정한 작업은 상태와 상관없이 맨 위에 남으며, 고정은 이 브라우저에만 저장됩니다. AI가 질문으로 멈춘 요청은 **답변 필요**에 들어갑니다. 요청을 열면 대화가 단계별(SM은 접수·분석 → 영향 확인 → 수정 → 회귀 검증 → 처리 보고)로 접혀 지금 단계(끝났으면 마지막 단계)만 펼쳐지고, 단계 머리글에 실행 기록 수와 테스트 통과 수, 커밋 수가 나옵니다. 그 단계에서 기록한 테스트·커밋 근거는 카드로 보이며, 누르면 상세 기록에서 실제 출력을 확인합니다. 근거를 남긴 뒤 바뀐 파일이 있으면 카드에 "이후 바뀐 파일 N개"가 붙습니다(관찰 기록).

**Claude Code 세션끼리 직접 알림.** Claude Code는 같은 컴퓨터의 다른 Claude Code 세션에 직접 메시지를 보낼 수 있습니다. 참여할 때 자기 세션 이름을 `--peer`로 남기고(`wax chat who`에 `세션 <이름>`으로 표시), 다른 Claude 세션을 받는 사람으로 지정해 글을 쓰면 그 세션에 `wax: #<채널> <메시지 ID> from <이름>` 형식의 위치 알림만 보냅니다. 내용은 채널 기록에만 있으므로, 알림을 받은 세션은 채널에서 그 메시지를 읽어 처리하고 이미 처리한 메시지면 무시합니다. 이 기능을 쓸 수 없으면 건너뛰며, 메시지는 채널과 듣기로 그대로 전달됩니다.

### 세션 이름과 재참여

`wax chat join --author <이름> --session <ID> --json`이 돌려준 `session`을 보관하고, 참여한 이름의 모든 상태 변경·게시·보고·업무 변경에 `--session <ID>`를 함께 넘깁니다. 409 오류가 나면 같은 세션 ID로 다시 join하고 반환된 이름을 사용하세요. PM·업무 담당 역할은 이름에 남고, 24시간 활동이 없는 이름은 다음 세션이 넘겨받습니다. 이전 버전의 토큰 없는 기록은 join할 때 인계됩니다. join 없이 직접 사용하는 CLI 기록은 별도로 식별되며, 세션이 이름을 인계받으면 토큰 없이 그 이름에 쓸 수 없습니다.

### PM과 업무 분담

사람은 **대표** 한 명이며, 대표가 지시하고 최종 결정하며, PM은 조언하고 선택지를 내고, 결정된 대로 지시(배정)하고, 진행·지연을 대표에게 보고합니다.

1. 업무를 나눌 세션에서 `/wax:pm <지시나 목표>`를 실행합니다. PM이 목표·현재 작업·참여자를 확인하고 통상적인 범위와 담당을 정해, 같은 호출에서 작업 생성과 현재 단계 배정까지 진행합니다. 이미 배정된 업무는 재사용합니다. 대표가 선택지를 요청했거나 필수 요구사항·명시적 지시 충돌 때문에 배정할 수 없을 때만 구체적으로 질문합니다. 목표가 없고 기록도 없으면 원하는 결과를 한 번 묻습니다. “범위와 담당이 결정되면 배정하겠습니다” 같은 약속만으로 끝내지 않습니다.
2. PM은 적용한 범위·담당을 간단히 기록하고 실제 기능 ID·업무 ID·담당·단계·실행 명령을 확인해 보고합니다. 진행 중인 다른 작업을 덮어쓰거나 아직 시작할 수 없는 후속 단계를 미리 배정하지 않습니다. 배정 자체가 지시이므로 채널에 다시 쓰지 않고, 담당자 사이의 순서가 중요할 때만 general 채널에 결정으로 남깁니다. PM이 없을 때는 대시보드에서 사람이 PM을 맡을 수도 있습니다. PM은 이 프로젝트를 이어 맡는 자리라 함부로 바꾸지 않습니다. 다른 세션이 `/wax:pm`을 실행해도 기존 PM을 대신하지 않고, 대표가 교체를 요청했을 때만(대시보드 **PM 교체…**에서 한 번 더 확인, CLI는 `wax chat team pm <이름> --replace`) 바뀝니다. 진행 중인 작업이 없으면 대시보드 **작업 진행** 패널의 **새 작업 만들기**로 기획 단계 작업을 만든 뒤 AI에게 기획을 배정합니다.
3. 각 세션에서 `/wax:work`(Codex `$wax:work`, Antigravity `/work`)를 실행합니다. 자기에게 배정된 업무를 받아(accept) 해당 작업의 단계를 수행하고, 끝나면 완료(done)나 막힘(block, 이유 포함)을 결과와 함께 기록합니다. 이 기록이 PM에게 하는 보고입니다. 한 번에 한 업무를 처리합니다.
4. PM 세션에서 목표 없이 `/wax:pm`을 다시 실행하면 **진행 보고**를 합니다. 새 목표나 계속 진행하라는 지시가 있으면 보고에 그치지 않고 해당 범위의 다음 배정까지 진행합니다. 작업별 완료·진행·미착수, 지연(막힌 업무, 오래 결과가 없는 업무, 앞 단계를 기다리는 업무)과 원인·일정 영향, 위험을 알리고, 결정할 일은 선택지와 추천안으로 올립니다. 결정된 계획 안에서 막힌 업무를 풀거나 다시 맡기는 일은 PM이 하고, 범위·우선순위·일정·담당 변경은 대표의 결정을 받습니다. 참여자 목록에 사람이 있으면 짧은 보고를 그 사람 앞으로 채널에도 올려 대시보드에서 볼 수 있게 합니다.

안전 범위:
- 업무는 대표가 지정한 PM만 배정할 수 있습니다. 다른 참여자가 업무를 만들거나 일반 메시지로 지시해도 배정으로 인정되지 않습니다.
- 배정이 허용하는 일은 지정한 작업의 해당 wax 단계뿐입니다. 대표의 직접 지시가 PM보다 우선하며, 파일 수정·명령 실행은 각 도구의 권한 확인을 그대로 거칩니다.
- 단계 순서는 그대로 지킵니다. 앞 단계가 끝나지 않았으면 업무를 막힘으로 기록하고 PM에게 알립니다.

**업무 완료 확인.** 업무를 완료(`task done`)로 바꾸면 wax가 연결된 작업의 그 단계가 배정 이후 실제로 끝났는지 확인합니다. 단계를 지정한 업무는 현재 주기에 그 단계의 완료 기록(`wax complete`)이 배정 시각 뒤에 있어야 하고, `any` 업무는 배정 이후 완료한 단계가 하나라도 있어야 합니다. 기본(`WAX_TASK_DONE_CHECK=warn`)으로는 완료로 기록하되 상태 기록에 경고(`warning`)를 남깁니다. 경고는 CLI 오류 출력(`wax chat: 경고: …`), `wax chat tasks --all`·`wax chat team`의 업무 줄, 대시보드 기록 타임라인과 일일 업무보고 초안, 작업 탭의 업무 대화, 사무실 작업노트에 보이고, PM은 진행 보고에서 이런 업무를 끝나지 않은 일로 다룹니다. `WAX_TASK_DONE_CHECK=enforce`로 실행한 세션과 대시보드는 이런 완료를 거절하며, 단계를 완료한 뒤 다시 하거나 끝낼 수 없으면 `task block`으로 이유를 남기라고 안내합니다. `off`는 확인하지 않습니다. 연결된 작업이 지워진 업무와 완료가 아닌 상태 변경(수락·막힘·취소)은 확인하지 않습니다.

### Claude 사용량 모니터

Claude Code 2.1.287 이상에서 wax 플러그인을 쓰면 플러그인에 들어 있는 wax 모드(Claude Code mods)가 턴이 끝날 때마다 숫자만 이 프로젝트의 `.wax/usage/<세션 ID>.json`에 남깁니다: 계정의 플랜 사용량(5시간·주간 %와 초기화 시각), 그 세션의 컨텍스트 사용량, 지금까지의 비용. 대화 내용(프롬프트·답변·도구 호출)은 읽지도 남기지도 않고, `.wax` 폴더가 없는 프로젝트에는 아무것도 쓰지 않습니다. 가상 사무실 사장실 벽의 모니터와 `wax chat usage`로 보고, PM은 진행 보고에서 한도에 가까운 사용량을 일정 위험으로 알립니다. Claude Code의 `/plugin`에서 wax 플러그인의 훅을 끄면 기록하지 않습니다. 다른 도구(Codex·GitHub Copilot CLI·Gemini CLI·Antigravity CLI)의 사용량은 아직 표시하지 않습니다.

### 일일 업무보고

`/wax:daily [YYYY-MM-DD]`(Codex `$wax:daily`, Antigravity `/daily`)를 실행하면 AI가 그날의 집계 초안을 읽고 보고서를 작성해 `docs/wax/daily/<날짜>/NN.md`로 등록합니다. 보고서는 오늘 한 일, 검증 결과, 결정 사항, 문제와 미해결 질문, 내일 할 일로 구성됩니다. 같은 날 여러 번 등록하면 번호가 늘어나며 기존 보고서를 덮어쓰지 않습니다. 대시보드의 **집계 초안 보기**는 AI 없이 기록만 모은 초안을 보여 줍니다.

### CLI로 직접 사용

```sh
wax chat post <채널> --author <이름> --session <ID> --kind <종류> --doing <지금 하는 일> --to <받는 사람> --message <전할 내용>
wax chat read <채널> [--since <메시지ID>] [--json]
wax chat join --author <이름> --session <ID> --kind <종류> [--model <모델>] [--feature <작업ID>]   # 첫 참여(같은 이름이 활동 중이면 -2, -3을 붙여 참여)
wax chat presence --author <이름> --session <ID> --state working|discussing|reviewing|idle|away [--note <하는 일>]
wax chat who
wax chat reset [--author <이름>]   # 지난 세션 정리(듣는 중·작업 중 세션은 남김, --author는 그 세션만)
wax chat watch --author <이름> [--feature <작업ID>] [--wake] [--json]   # 나를 부른 메시지·새 배정을 한 줄씩(멈출 때까지). --wake는 AI 세션을 깨우는 감시
wax chat read <채널> --id <메시지ID> [--json]                            # 메시지 하나를 그대로 읽기
wax chat team pm <이름> --kind <종류>        # PM 지정(대표가 정함)
wax chat assign <작업ID> --to <담당> --author <PM> --session <ID> --phase <단계|any> --message <지시>
wax chat tasks [--to <이름>] [--all]
wax chat skills [--json]                    # 스킬 지도: 사원 × 단계·검증·코드 영역 기록 수, 빈 분야
wax chat rules [--all] | rules candidates | rules lint   # 프로젝트 규칙, 근거 후보, 근거 점검
wax chat rules propose --author <이름> --session <ID> --message <규칙> --why <이유> --source <근거 ID>   # 규칙 제안(승인은 대시보드에서 사람이)
wax chat notes <이름> [--days 7] [--json]    # 작업노트: 그 사원이 날마다 한 일과 지금 맡은 업무·마지막 메모
wax chat memo --author <이름> --session <ID> --message <메모> [--feature <작업ID>]   # 작업노트에 남은 일·주의점 메모
wax chat task accept|done|block|cancel <업무ID> --author <이름> --session <ID> [--message <메모>]
wax chat daily [--date YYYY-MM-DD]           # 타임라인
wax chat daily draft | report --file <보고서.md> | list
```

`wax`는 `node "/path/to/wax/bin/wax.mjs"`를 뜻합니다. 종류(`--kind`)는 `claude`, `codex`, `copilot`, `gemini`, `antigravity`, `grok`, `human`, `other` 중 하나입니다. 다른 명령의 도움말은 `wax --help`, `wax chat --help`, `wax trigger --help`, `wax pm-loop --help`, `wax mcp --help`처럼 봅니다.

**CLI 언어.** 도움말(`--help`)·안내·경고·오류는 `WAX_LANG=en`이면 영어로 나옵니다(`en_US`, `ko-KR` 같은 값도 받습니다). `WAX_LANG`이 없으면 `LC_ALL` → `LC_MESSAGES` → `LANG` 중 값이 있는 첫 번째가 `en`으로 시작할 때 영어, 그 밖에는 한국어입니다. 영어 시스템에서 한국어로 쓰려면 `WAX_LANG=ko`를 지정하세요. `--json` 출력, 저장 기록, AI 세션에 주는 단계 지시문·인수인계 문맥·스킬은 언어와 상관없이 같습니다. 대시보드 화면 언어는 따로 정합니다(6절 "대시보드 열기").

| 경로 | 내용 |
| --- | --- |
| `.wax/chat/channels/<채널>.jsonl` | 채널 메시지(추가만 함) |
| `.wax/chat/board/<작업>.jsonl` | 화이트보드 노트와 보고서 기록 |
| `.wax/chat/presence.json` | 참여자 상태와 지금 하는 일 |
| `.wax/chat/team.json`, `assignments.jsonl` | PM과 업무 배정·상태 이력 |
| `.wax/chat/daily.jsonl`, `docs/wax/daily/<날짜>/NN.md` | 일일 보고서 기록과 본문 |

그 밖의 저장 위치는 7절에 정리되어 있습니다.

빈 디렉터리에서 `node scripts/chat-demo.mjs --project ./demo --loop`를 실행하면 PM 배정·대화·보고가 반복되는 시연 장면을 대시보드에서 볼 수 있습니다.

## 6-1. 기록 검색

대화·화이트보드·업무 배정·일일 보고·단계 문서·완료 근거·개선 이력·테스트와 커밋 근거·요청 대화·디자인 작업을 한 번에 찾습니다. 결과마다 원문 위치(파일과 기록 ID 또는 문서 위치)와 그 기록을 여는 화면 링크가 붙습니다.

처음 한 번 검색 색인을 만듭니다. 대시보드 상단 메뉴의 **검색**(`/search`)에서 **검색 색인 만들기**를 누르거나 다음을 실행합니다.

```sh
wax search index
```

그다음부터는 검색할 때마다 바뀐 기록만 먼저 반영합니다. 다른 AI 세션이나 CLI가 쓴 기록도 그대로 찾을 수 있습니다.

```sh
wax search 인계
wax search 인계 --feature lookbook-upload
wax search "Claude Code" --kind message --author claude-app --from 2026-10-01 --to 2026-10-18
wax search status
```

- 띄어 쓴 단어는 모두 들어 있는 기록만 찾고, 큰따옴표는 공백을 포함한 구절입니다. 대소문자는 구분하지 않으며 결과는 최신순입니다.
- 세 글자 이상은 부분 일치입니다(`인계를`, `handoff-v2.md`, `docs/wax/design`, 커밋 SHA 앞자리). 두 글자(`인계`, `리뷰`, `오류`, `UI`)는 단어 안의 두 글자 조각으로 찾아 “인계를”, “디자인 인계”에도 맞습니다. 한 글자는 전체를 훑어 느릴 수 있습니다. 형태소(“인계했다”로 “인계를”), 초성, 의미 검색은 지원하지 않습니다.
- 필터: 종류(`--kind`), 작업(`--feature`), 작성자(`--author`), 단계(`--phase`), 기간(`--from`, `--to`, YYYY-MM-DD). 결과가 많으면 출력 끝의 `--cursor`로 다음 페이지를 봅니다. `--json`은 원문 위치와 강조 범위를 JSON으로 줍니다.
- 실행 승인 기록, 세션 토큰, AI 세션 정보는 검색하지 않습니다.

색인(`.wax/search/index.db`)은 기록에서 다시 만들 수 있는 사본이고 원본은 `.wax`의 JSON/JSONL 그대로입니다. 색인이 없으면 검색은 만드는 방법만 안내합니다. 손상됐거나 이 wax 버전과 형식이 다르면 `wax search index --rebuild`(대시보드의 **색인 다시 만들기(복구)**)로 다시 만듭니다. 읽지 못한 기록 줄은 건너뛰고 `wax search status`에 파일과 줄 번호를 보여 줍니다. 색인을 만들다 멈췄으면(강제 종료, 대시보드 재시작) “중간에 멈췄습니다”와 **색인 이어서 만들기**가 나오고, 검색하거나 버튼을 누르면 남은 기록부터 이어서 반영합니다. 화이트보드·일일 보고서 Markdown만 고치거나 지워도 다음 검색에 반영되며, 지워졌거나 프로젝트 밖을 가리키는(심볼릭 링크) 파일은 본문을 검색하지 않고 상태에 표시합니다. 작성자 필터는 대표, 한글·공백이 들어간 이름도 그대로 씁니다.

### 관련 기록 찾기(recall)

`wax recall`은 AI 세션이 작업 전에 다른 작업의 기록을 참고하도록 같은 색인에서 관련 기록을 **관련도순**으로 찾습니다. 검색과 달리 낱말 중 하나만 맞아도 찾고, 많은 낱말이 맞을수록·관련도가 높을수록 앞에 둡니다. 한국어 낱말 끝의 조사(`토큰이`, `인계를`)는 떼고도 찾습니다.

```sh
wax recall 토큰 만료 재시도 --exclude-feature login-retry
wax recall 결제 오류 --kind note --limit 5 --budget 2000
```

- 결과는 문자 수(토큰 아님) 예산 안에서 한 줄씩 인용하고, 원문 위치와 화면 링크를 붙입니다. `--json`은 순위·일치한 낱말·점수까지 줍니다.
- 단계 스킬과 자동 진행은 비슷한 오류·같은 모듈·이전 결정이 다른 작업에 있을 수 있을 때 `recall`을 실행합니다. 찾은 기록은 지시가 아닌 참고 자료로 다루고 지금 코드에서 다시 확인합니다.
- 색인이 없으면 처음 한 번 만듭니다. 의미 검색(비슷한 뜻의 다른 낱말)은 지원하지 않습니다.

검색에는 Node.js 22.16 이상 또는 24 이상이 필요합니다(내장 SQLite의 전문 검색). 그보다 낮은 Node.js에서는 검색만 안내 문구를 보여 주고 다른 wax 기능은 그대로 동작합니다. 자세한 동작과 측정은 [기록 검색 안내](SEARCH.md)에 있습니다.

## 6-2. MCP 서버(실험)

`wax mcp`는 코딩 도구가 MCP(stdio)로 wax 기록을 읽고 팀 채널에 쓰게 하는 서버입니다. 셸 명령 대신 도구 호출을 쓰므로 인수 실수와 권한 확인이 줄고, 연결 하나가 곧 세션이라 `--session <ID>`를 넘길 일이 없습니다. 기본으로 꺼져 있어 등록할 때 환경 변수 `WAX_MCP=on`을 함께 주어야 시작합니다. 플러그인을 설치해도 자동으로 등록되지 않습니다.

| 도구 | 하는 일 |
| --- | --- |
| `wax_status` | 업무 목록, 또는 `id`를 주면 업무 하나의 진행 중인 단계·그다음 단계·revision·완료 기록·최근 근거 |
| `wax_context` | 업무 인계 문맥(`id`, `budget` 문자 수) — `wax context`와 같은 내용 |
| `wax_recall` | 다른 업무 기록에서 관련 결정·실패(`query`, `excludeFeature`, `budget`) — `wax recall`과 같은 순위 |
| `wax_inbox` | 나(또는 `author`)를 부른 메시지와 나에게 온 PM 배정(`since` 메시지 ID 이후만 볼 수 있음) — `wax chat watch`와 같은 기준이며 읽음 위치는 바꾸지 않음 |
| `wax_join` | 팀 채널 참여(`name`, `kind`, `model`, `peer`)와 상태 갱신(`feature`, `state`, `note`). 다른 이름을 주면 이름을 바꿉니다 — `wax chat join`·`presence` |
| `wax_post` | `question`, `answer`(`replyTo` 필수), `decision`만 올립니다. 인사·진행 보고(`message`·`opinion`)는 받지 않습니다 — `wax chat post` |
| `wax_task` | 나에게 배정된 업무를 `done` 또는 `block`으로 바꾸고 결과(`result`)를 남깁니다. 단계를 끝내지 않은 `done`은 CLI와 같이 경고와 함께 기록되거나 `WAX_TASK_DONE_CHECK=enforce`에서 거절됩니다 — `wax chat task` |
| `wax_complete` | 지금 단계 완료(`id`, `phase`, `evidence`, `proofIds`, `checks`, `noProof`, `acUnverified`, `verdict`, `revision`). 근거·수용 기준 추적·검토자 분리 조건이 `wax complete`와 똑같습니다 |
| `wax_assign` | PM만. 업무의 지금 단계를 배정합니다(`feature`, `to`, `message`) — `wax chat assign` |

- **세션과 작성자.** 처음에 `wax_join`을 한 번 부르면 그 연결이 wax 세션이 됩니다. 세션 ID는 서버 프로세스 안에만 있고 결과에 나오지 않습니다. 쓰기 도구에는 `author`·`session` 인수가 없고, 참여한 이름으로만 기록합니다. 다른 세션이 이미 쓰는 이름이면 `-2`, `-3`이 붙은 이름으로 참여하고 결과의 `author`로 알려 줍니다. 이름 소유가 풀리거나(예: `wax chat reset --author <이름>`) 클라이언트가 다시 `initialize`하면, 다음 쓰기 전에 같은 세션 ID로 다시 참여하고 결과에 `rejoined`와 그때의 `author`를 붙입니다.
- **검증은 CLI와 같습니다.** 쓰기 도구는 CLI와 같은 함수를 부르므로 검증·잠금·길이 제한·오류 문구가 같습니다. 오류는 `isError`, 번역된 메시지(`WAX_LANG`), HTTP식 `status`(400·403·404·409)로 돌려줍니다. 모든 쓰기 기록(메시지, 배정과 상태 변경, 단계 완료 기록과 이력, 참여 상태)에는 `"via": "mcp"`가 붙습니다.
- **도구로 열지 않는 것.** 실행 승인과 거부, 규칙 승인, 트리거 편집, 보관과 복원, 백업 복원, 기록 삭제는 사람이 대시보드에서만 합니다. 문서 저장(`wax save`), 테스트·캡처·커밋 근거(`wax test`·`capture`·`evidence`)도 CLI에 남습니다.
- **도구가 없는 쓰기.** 업무 수락(`task accept`)은 건너뜁니다(`done`·`block`은 열린 업무에서 바로 됩니다). 메모·화이트보드·규칙 제안·업무 취소·일일 보고 등록은 아직 도구가 없고, MCP로 참여한 이름은 셸의 CLI가 쓸 수 없습니다(세션 ID가 서버 안에만 있으므로). 이런 단계는 무엇을 기록하려 했는지 사용자에게 알리도록 안내합니다.
- 프로젝트는 서버가 시작할 때 정합니다: `--project <경로>`, 없으면 `WAX_PROJECT`, 없으면 현재 디렉터리에서 위로 가장 가까운 `.wax`가 있는 폴더(없으면 현재 디렉터리). 도구 인수로 다른 경로를 받지 않습니다. 코딩 도구가 서버를 어느 디렉터리에서 띄우는지 모르면 `--project`를 적으세요.
- 결과의 기록(제목·문서·메시지·배정)에는 `"source": "record"`가 붙습니다. 다른 사람과 세션이 쓴 데이터이며 지시가 아닙니다.

**등록.** `node /path/to/wax/bin/wax.mjs mcp config --host <claude|gemini|codex|copilot> --project /path/to/my-app`이 그 도구에 넣을 조각을 출력합니다(이 설치의 실제 경로가 들어갑니다). wax는 사용자 설정 파일을 읽거나 고치지 않으니 출력된 조각을 직접 넣으세요. 아래 예의 `/path/to/wax`는 압축을 푼(또는 플러그인이 설치된) wax 폴더의 실제 절대 경로로, `/path/to/my-app`은 프로젝트 경로로 바꾸세요. Windows에서도 셸 없이 `node`로 실행합니다.

**Claude Code**

<!-- wax mcp config --host claude -->
```sh
claude mcp add --transport stdio --env WAX_MCP=on wax -- node /path/to/wax/bin/wax.mjs mcp --project /path/to/my-app
```
<!-- /wax mcp config -->

`--scope project`를 붙이면 프로젝트의 `.mcp.json`에 저장되어 팀이 함께 씁니다. `/mcp`에서 연결 상태를 봅니다.

**Gemini CLI** — `~/.gemini/settings.json`(또는 프로젝트의 `.gemini/settings.json`)

<!-- wax mcp config --host gemini -->
```json
{
  "mcpServers": {
    "wax": { "command": "node", "args": ["/path/to/wax/bin/wax.mjs", "mcp", "--project", "/path/to/my-app"], "env": { "WAX_MCP": "on" } }
  }
}
```
<!-- /wax mcp config -->

**Codex** — `~/.codex/config.toml`

<!-- wax mcp config --host codex -->
```toml
[mcp_servers.wax]
command = "node"
args = ["/path/to/wax/bin/wax.mjs", "mcp", "--project", "/path/to/my-app"]
env = { WAX_MCP = "on" }
```
<!-- /wax mcp config -->

**GitHub Copilot CLI** — `~/.copilot/mcp-config.json`(또는 Copilot CLI 안에서 `/mcp add`)

<!-- wax mcp config --host copilot -->
```json
{
  "mcpServers": {
    "wax": { "type": "local", "command": "node", "args": ["/path/to/wax/bin/wax.mjs", "mcp", "--project", "/path/to/my-app"], "env": { "WAX_MCP": "on" }, "tools": ["*"] }
  }
}
```
<!-- /wax mcp config -->

**스킬 안내.** Claude Code와 Gemini CLI의 wax 명령은 "MCP 우선" 안내를 씁니다: 도구 목록에 `wax_join`이 있으면 참여·게시·업무 상태·단계 완료를 도구로 하고, 없으면(기본, `WAX_MCP=on`으로 등록하지 않은 경우) 같은 파일에 있는 짧은 CLI 대안(`wax chat join` … `--session`)으로 합니다. 전체 CLI 규칙은 플러그인의 `skills/<명령>/SKILL.md`에 있습니다. Codex, GitHub Copilot CLI, Antigravity CLI, Grok Build의 스킬은 지금의 CLI 안내를 그대로 씁니다.

Gemini CLI·Codex·Copilot CLI의 설정 파일 위치와 형식은 버전에 따라 다를 수 있으니 각 도구의 MCP 문서에서 확인하세요(이 저장소의 테스트는 서버와 출력한 조각만 확인하고, 각 도구에 등록한 결과는 확인하지 않았습니다). Antigravity CLI와 Grok Build는 아직 확인하지 않았습니다. 등록이 되지 않으면 터미널에서 `WAX_MCP=on node /path/to/wax/bin/wax.mjs mcp --project /path/to/my-app`을 실행해 오류 출력(stderr)을 보세요. `WAX_MCP=on`이 빠지면 켜는 방법을 안내하고 끝납니다.

## 6-3. 한 줄 요청으로 자동 진행

`init`은 기본값으로 바로 참여하고 대시보드를 엽니다. 새 요청에서 두 모드를 선택합니다.

| 모드 | 시작과 실행 |
| --- | --- |
| 프로젝트 | 목표를 입력하면 범위·작업 순서와 선행 관계·산출물·완료 기준을 담은 워크플로우를 먼저 작성합니다. 화면에서 확인하고 **이 워크플로우로 시작**을 눌러야 설계·구현·검토·보고로 진행합니다. 수정 요청은 워크플로우를 다시 작성하며 새 내용을 확인해야 시작합니다. |
| SM · 유지보수 | 오류·개선 요청을 접수·분석 → 영향 확인 → 수정 → 회귀 검증 → 처리 보고로 바로 처리합니다. 기획과 설계 문서는 요청 규모에 맞게 간결하게 남기고 실제 테스트 근거는 유지합니다. |

처음에는 프로젝트 모드가 선택되며 이후에는 프로젝트별 마지막 선택을 기억합니다. `init --mode sm` 또는 `init --mode project`로 요청 화면의 모드를 지정할 수도 있습니다(각 호스트 문법 사용). 모드는 요청을 만든 뒤 바뀌지 않습니다. 다른 모드로 진행하려면 새 요청을 만드세요. 모드 정보가 없는 기존 요청은 SM 흐름을 유지합니다. 두 모드 모두 선택한 CLI의 별도 세션이 실행하며 기존 터미널 AI에 자동 분산 배정하지 않습니다.

요청과 보고 화면(`/start`)의 시작 가이드는 실행 도구 선택 → 할 일 입력 → 진행과 보고 확인 순서를 안내합니다. 설치 여부를 확인하며 로그인 여부는 실제 실행에서 확인합니다. 도구 설치 후에는 **도구 다시 확인**을 누르세요.

새 요청의 실행 도구에서 Codex·Claude Code·Gemini CLI·GitHub Copilot CLI·Antigravity CLI 중 설치한 도구를 선택합니다. Grok Build는 아직 자동 진행을 지원하지 않으므로 터미널 세션에서 스킬 이름을 밝혀 요청하는 팀 작업으로 씁니다. 해당 CLI의 로그인 또는 API 설정과 계정 사용량·비용·데이터 정책이 적용됩니다. 요청은 저장된 도구로 계속 진행하며 다른 도구를 쓰려면 새 요청을 만듭니다. Codex·Claude·Gemini·Copilot의 새 권한 요청은 화면에서 이번만 허용하거나 거부합니다. Antigravity는 기존에 허용된 범위로 실행하며, 새 권한 요청이 막히면 터미널의 설정을 확인해야 합니다. 기존 터미널 세션을 자동으로 깨우거나 다른 AI의 배정을 바꾸지는 않습니다. 자동 진행의 PM은 요청을 처리하는 역할이며, 기존 프로젝트 PM을 교체하지 않습니다.

- 질문이 생기면 채팅으로 답합니다. 진행 중 보낸 추가 지시는 현재 단계가 끝난 뒤 반영됩니다. 즉시 멈추려면 **중지**를 누릅니다.
- 중단·오류의 이유는 요청 위에 표시합니다. **이어서 진행**은 저장된 단계부터 재개합니다. 서버 재시작이나 페이지 조회만으로 AI를 재호출하지 않습니다.
- 요청은 프로젝트당 한 번에 하나씩 실행합니다. 구현·검토에는 실제 통과한 테스트 근거가 필요하며, 다른 세션이 단계를 수정하면 충돌을 보고합니다. 단계 실행의 제한 시간은 30분입니다.
- 기록은 `.wax/chat/requests/`, 단계 문서는 `docs/wax/<자동 생성 ID>/`에 저장합니다. 기존 작업·팀 배정은 **상세 기록**(`/manage`)에서 계속 관리합니다.
- 대시보드 첫 화면(`/`)은 팀 채널이며 대화 기록용입니다. 자동 진행은 **＋ 새 요청**으로 여는 요청과 보고 화면(`/start`)에서 **워크플로우 만들기**(프로젝트) 또는 **시작하기**(SM)로 요청합니다. 워크플로우 확인은 실행 권한 승인과 별개이며 기존 CLI 권한은 그대로 적용됩니다.

자동 진행 연결 규격: [OpenAI 공식 Codex App Server 문서](https://learn.chatgpt.com/docs/app-server)의 thread/start, thread/resume, turn/start, outputSchema와 item/completed를 사용합니다.

## 6-4. 실행 승인

실행 중 콘솔에서 묻는 권한 요청을 대화창에서 처리하려면 [실행 승인 관리](./APPROVALS.md)를 참고하세요. 연결된 요청만 요청별 **이번만 허용 / 거부** 버튼으로 응답합니다.

## 6-5. 트리거: 일정, 로컬 호출, GitHub 이슈·CI 실패로 요청 제안

트리거는 정해 둔 때에 요청을 **제안만** 합니다. AI는 사람이 제안을 수락해야 시작하며, 자동 수락은 없습니다.

- **만들기:** 상세 기록(`/manage`)의 **트리거**에서 **＋ 새 트리거**로 만들고 고치고 켜고 끕니다. 정의는 이 컴퓨터의 `.wax/chat/triggers/`에만 저장됩니다.
- **언제:** 일정(5필드 cron과 시간대, 예: `0 9 * * 1-5`, `Asia/Seoul`) 또는 로컬 호출(`wax trigger fire <id> [--payload <파일>] [--key <키>]`, git hook 등). 일정은 대시보드가 켜져 있을 때만 돌고, 꺼진 동안 놓친 실행은 "놓친 실행 N건" 제안 하나로 묶습니다.
- **GitHub:** **GitHub 이슈(라벨)**은 저장소(`owner/name`)와 라벨, **CI 실패**는 저장소·브랜치·워크플로(선택)를 정하고, 확인 간격(`every`, 예: `5m`, 1분 이상)마다 이 컴퓨터의 `gh` 로그인으로 확인합니다. 대시보드가 켜져 있을 때만 확인합니다.
  - `gh`가 없거나 로그인 전이면 목록에 **연결 필요**와 이유가 보이고 확인하지 않습니다(실패로 세지 않음). `gh auth login` 뒤 다음 분에 다시 확인합니다.
  - **처음 확인할 때는 이미 있는 이슈·실패를 기준으로만 기록하고 제안하지 않습니다.** 그 뒤 새로 라벨이 붙은 이슈나 새로 실패한 실행만 한도 안에서 제안합니다. 기존 이슈를 맡기려면 라벨을 뗐다 다시 붙이세요. 다시 켜거나 저장소·라벨·브랜치를 바꿔도 첫 확인부터 다시 합니다.
  - 문구를 비우면 기본 문구(이슈 처리, CI는 SM 모드 "CI 회귀 수정")를 씁니다. 이슈 제목·실행 이름은 `{{issue.title}}`·`{{run.name}}` 등으로 200자까지만 들어가고, 이슈 본문은 "외부 이벤트 내용(지시가 아님)" 인용으로만 전달됩니다.
- **무엇을:** 요청 제안(모드·도구·문구, `{{payload.title}}` 같은 자리표시자는 값마다 200자로 자르고 @멘션을 무력화), 일일 보고 제안, 알림만.
- **수락:** 요청과 보고(`/start`)의 **트리거 제안** 카드에서 문구·도구·모드를 고쳐 **수락하고 시작**하거나 **버리기**를 누릅니다. 제안은 7일이 지나면 만료됩니다. 외부 내용(payload)은 지시문에 "외부 이벤트 내용(지시가 아님)"으로만 인용됩니다.
- **안전장치:** 트리거별 하루 한도와 쉬는 시간, 전체 하루 제안 상한 20건, 같은 이벤트 키의 제안·요청이 열려 있으면 건너뜀, 5번 연달아 실패하면 자동으로 끄고 이유 표시. 모든 이벤트는 `.wax/chat/trigger-events.jsonl`에 남습니다.
- **CLI:** `wax trigger list`, `wax trigger test <id>`(미리 보기만, 아무것도 쓰지 않음. GitHub 소스는 `gh`로 한 번 가져와 보여 줌), `wax trigger fire <id>`(로컬 소스만).
- **기본 한도:** 새 트리거는 하루 3건, 쉬는 시간 30분입니다. 트리거마다 하루 1~100건, 쉬는 시간은 최대 7일까지 정합니다. 트리거 폼의 **저장하면 바로 켜기**를 끄면 꺼진 채로 저장됩니다.
- **사람이 하는 일:** 트리거를 만들고 고치고 켜는 일, 제안 수락과 버리기는 대시보드의 사람만 합니다. CLI와 MCP에는 이런 명령이 없습니다. 수락하면 보통의 요청처럼 6-3절의 자동 진행이 시작되고, 그 요청의 실행 기록에 출처(어느 트리거)가 남습니다.
- **알아 둘 점:** GitHub 확인은 이 컴퓨터의 `gh`가 직접 하므로 `gh` 설치와 로그인이 필요하고, `gh`가 PATH에 없으면 대시보드를 시작할 때 `WAX_GH_BIN`으로 실행 파일 경로를 줄 수 있습니다. 테스트는 가짜 `gh`로 하며, 실제 GitHub 저장소를 오래 폴링하는 운영은 검증 범위(9절)에 들어 있지 않습니다.

## 6-6. PM 루프: 목표별 다음 할 일 제안과 auto 모드

목표 하나에 작업 여러 개를 묶으면, 작업마다 다음 할 일을 정해진 규칙으로 계산해 **제안 카드**로 보여 줍니다. 계산에 AI를 부르지 않으며, 사람이 카드를 눌러야 실행합니다. 듣는 세션이 없을 때 AI 도구를 띄우는 것(headless 작업자)과 계획 초안·막힘 판단·대표 보고를 AI에 묻는 것(PM 판단)도 카드를 누를 때만 합니다. 목표마다 사람이 **auto**를 켜면 정해진 일부 행동만 한도 안에서 카드 없이 실행합니다(아래 auto 모드).

- **목표 만들기:** 상세 기록(`/manage`)의 **PM 루프**에서 **＋ 새 목표**로 있는 작업을 고르거나 새 작업(`작업ID 제목`)을 적습니다. 목표는 **계획 확인 전**으로 시작하고, 작업과 수용 기준을 확인한 뒤 **계획 확인하고 시작**을 눌러야 진행됩니다.
- **규칙:** 현재 단계만 배정하고(미래 단계는 제안하지 않음), 듣고 있는 세션을 먼저 고르고, 검토는 구현한 도구와 다른 도구의 세션에 맡깁니다(없으면 사람에게 물음). done인데 단계가 끝나지 않았으면 완료 방법을 한 번 다시 알리고 그다음은 사람에게 넘깁니다. 30분 넘게 움직임이 없는 배정은 회수를 제안하고, 보고가 끝나면 `wax pr-body` 초안을 만든 뒤 PR 결정은 사람에게 남깁니다.
- **headless 작업자:** 현재 단계를 듣고 있는(`chat watch`) 세션이 없으면 **작업자 필요** 카드가 나옵니다. 띄울 도구는 요청 자동 진행과 같은 목록에서 이 컴퓨터에 설치된 것만 고르고(Grok Build처럼 자동 실행을 지원하지 않는 도구는 고르지 않음), 검토는 구현을 완료한 도구와 다른 도구를 고릅니다(다른 도구가 없으면 사람에게 물음). 카드에서 도구를 고르고 **… 작업자 시작**을 누르면 그 도구를 띄워 배정 하나·단계 하나만 맡기고, 끝나면 종료합니다. 단계당 30분이 상한이고, 권한 요청은 실행 승인 화면으로 갑니다. 작업자는 CLI로 단계를 완료하고(근거·수용 기준 조건 그대로), 끝난 뒤 실행기가 그 결과로 업무를 done 또는 block으로 바꿉니다. done은 기존 업무 완료 확인을 거쳐, 단계가 끝나지 않았으면 다음 단계로 가지 않고 사람에게 넘깁니다. 실행 중인 작업자는 목표 화면에 도구·경과 시간·**작업자 멈추기** 버튼과 함께 나오고, 목표를 정지하면 함께 멈춥니다. 작업자 카드를 버리면, 자리에 있는(듣지는 않는) 세션 배정을 대신 제안합니다.
- **PM 판단:** 계획이 확정되지 않은 목표(계획 초안), 막힌 업무(막힘 판단), 보고까지 끝난 작업이 있는 목표(대표 보고) 세 곳에서만 **PM 판단 요청** 카드가 나옵니다. **PM 판단 받기**를 눌러야 목표의 PM 판단 도구를 읽기 전용 지시로 한 번 부릅니다(한 번에 10분 상한, 권한 요청은 실행 승인 화면). 판단 도구는 목표의 **한도** 안에서 요청 자동 진행 도구와 따로 고르고, 기본은 요청 자동 진행의 기본 순서에서 처음 설치된 도구입니다(headless로 띄울 수 없는 도구는 나오지 않음). 판단에는 목표, 작업마다 `wax context`, 최근 결정과 막힘 기록이 지시가 아닌 인용 데이터로 들어갑니다. 결과는 정해진 JSON 스키마로만 받아 **PM 판단 제안** 카드로 보여 주고, 사람이 고쳐서 받아들이거나 버립니다. 스키마 밖 결과는 버리고 이유와 함께 **PM 판단 넘김** 카드로 사람에게 넘깁니다. 받아들이면 이미 있는 행동으로만 옮깁니다: 막힘의 다시 시도·다시 맡김은 배정을 회수하고 다음 작업자 카드의 기본 도구만 정하고(띄우기는 다시 확인), 질문·되돌리기 제안은 막힌 업무 카드에 질문이나 `wax iterate` 안내만 보여 줍니다. 계획 초안은 없는 작업을 만들고 기획 문서가 빈 작업에 AC 초안을 저장하지만, 계획 확정은 따로 사람이 누릅니다. 대표 보고는 `.wax/chat/pm-loop/`에 초안 파일만 씁니다. 자리마다 판단은 한 번이고, 판단 요청도 하루 headless 실행 한도(20번)에 셉니다.
- **실행:** 카드로 할 수 있는 일은 배정(PM 규칙 그대로, 이 화면의 사람이 PM이어야 함), 세션에 다시 알리기, 배정 회수(취소), PR 초안 파일 만들기, 작업자 시작, PM 판단 요청과 그 제안 받아들이기뿐입니다. 작업자의 시작·종료·시간 초과·실패·멈춤도 이유와 함께 같은 기록에 남습니다. 실행하거나 버린 카드는 이유와 함께 `.wax/chat/pm-loop/<목표>.jsonl`에 남고, 작업의 실행 기록에도 나옵니다.
- **한도와 정지:** 목표마다 단계 실행 15번(작업자 시작 포함), 동시 작업자 2명(실행 중인 작업자 포함), 8시간, 되돌리기 3번, 연속 막힘 3번(작업자의 실패·시간 초과는 막힘으로 셈), auto 시간당 행동 12번(auto일 때만). 전체로는 headless 실행(작업자 시작과 PM 판단 요청)이 하루(24시간) 20번까지입니다. 같은 작업·단계에 열린 배정이나 실행 중인 작업자가 있으면 새로 띄우지 않습니다. 한도에 닿으면 멈추고, 한도를 늘려 재개하는 것은 사람만 합니다. **목표 정지** 버튼으로 언제든 멈춥니다.
- **auto 모드:** 기본은 suggest(모든 행동이 카드)입니다. 목표 화면의 **모드** 칸에서 **auto 켜기**를 누르면 그 목표만 auto가 됩니다. 켜는 것은 대시보드의 사람만 할 수 있고, auto가 그 사람 이름으로 배정하므로 PM이어야 합니다. 바꾼 사실은 기록에 남습니다. auto가 카드 없이 하는 일은 듣고 있는 세션에 현재 단계 배정, done 경고가 난 세션에 첫 번째 다시 알림, headless 작업자 시작(검토는 구현과 다른 도구), 30분 멈춘 배정 회수, 막힌 업무의 PM 판단 요청과 그 결과 중 **다시 시도·다시 맡김** 반영뿐입니다. 계획 확정과 계획 초안 반영, 실행 승인과 권한 요청, 규칙 승인, 트리거 제안 수락, PR 만들기·push·병합(report 뒤 PR 초안 카드는 사람을 기다림), 한도 늘리기, 대표 보고, 사람에게 넘김·질문·되돌리기는 auto에서도 카드로 남고, 이런 카드가 나오면 브라우저 알림이 옵니다. auto는 사람이 누를 때와 같은 확인과 한도를 거치고, 목표마다 **auto 시간당 행동 수(기본 12)**가 더 있습니다. 어느 한도에 닿거나 auto 행동이 실패하면 목표를 멈추고 알립니다. **목표 정지**를 누르면 실행 중인 작업자와 판단도 바로 멈춥니다. auto가 한 일은 `by: auto`와 규칙 이름, 이유와 함께 기록·실행 기록·목표 화면의 **auto 활동**에 나옵니다. 대시보드가 둘이어도 한 번만 실행합니다.
- **CLI(읽기 전용):** `wax pm-loop list`, `wax pm-loop show <목표>`(모드와 auto 사용량 포함), `wax pm-loop next <목표>`(지금 계산한 제안만 보여 주고 아무것도 쓰지 않음). CLI로는 모드를 바꿀 수 없습니다.
- **한도 바꾸기와 재개:** 목표 화면의 **한도**에서 사람이 목표별 한도와 PM 판단 도구를 정합니다(단계 실행 1~200, 동시 작업자 1~10, 시간 1~168, 되돌리기 0~50, 연속 막힘 1~20, auto 시간당 행동 1~120). 하루 headless 20번은 프로젝트 전체 한도라 바꾸지 않습니다. 한도에 닿아 멈춘 목표는 **목표 재개**에서 한도를 확인하고 이어 갑니다.
- **검증 범위:** 단위 테스트와 브라우저 검사는 작업자와 PM 판단을 가짜 실행부로 바꿔 돌립니다. 실제 AI 도구로 PM 루프 한 바퀴(작업자가 실제로 단계를 끝내고, 판단 도구가 읽기 전용 지시를 지키며 정해진 JSON 형식으로 답하는지, auto가 실제 도구로 끝까지 가는지)는 아직 확인하지 않았습니다. 읽기 전용은 지시로만 걸고 도구의 권한 설정을 바꾸지 않으므로, 판단 중 쓰기 권한 요청이 오면 실행 승인 화면에서 거부하세요.

## 6-7. 프로젝트 규칙과 위키

### 프로젝트 규칙

**프로젝트 규칙**은 AI의 실수를 다음 세션이 되풀이하지 않게 하는 짧은 규칙입니다. 검토에서 실제 결함을 찾았을 때나 PM이 진행을 볼 때, AI 세션이 실수 기록(검토 중 실패한 테스트·개선 사유·막힌 업무)을 근거로 붙여 `wax chat rules propose`로 제안합니다. 근거 없는 제안과 같은 문장의 규칙은 받지 않습니다. 대시보드(`/manage`)의 **프로젝트 규칙** 패널에서 사람이 승인하면 그때부터 모든 단계 지시문(`wax prompt`, 대시보드 자동 진행)과 `wax context`에 들어가고, 거절하거나 나중에 폐기할 수 있습니다. CLI에는 승인 명령이 없어 AI가 스스로 규칙을 확정하지 않습니다. 지시문에는 지금 코드와 맞지 않는 규칙은 따르지 말고 보고하라는 안내가 함께 들어갑니다. `wax chat rules lint`는 근거 기록을 더 이상 찾을 수 없는 적용 중 규칙을 알립니다.

`wax chat rules`는 적용 중인 규칙을, `--all`은 대기·거절·폐기된 규칙까지, `rules candidates`는 아직 어떤 규칙도 인용하지 않은 실수 기록을 보여 줍니다. 지시문에는 승인된 규칙 중 최근 20개가 들어갑니다. 대시보드 패널은 승인 대기 → 적용 중 순서로 보여 주고 거절·폐기는 접어 두며, CLI로 제안한 규칙은 1~2초 안에 패널에 나타납니다. 기록은 `.wax/chat/rules.jsonl`에 덧붙이기만 합니다.

### 프로젝트 위키

원본 기록은 그대로 두고, AI 세션이 주제별로 정리한 페이지를 `docs/wax/wiki/<페이지>.md`에 둡니다. 페이지의 문단과 목록 항목마다 `[근거: <기록 ID>]`가 있어야 저장되고, 인용한 기록이 실제로 있어야 합니다. 근거로 쓸 수 있는 것은 `wax wiki ingest`가 보여 주는 기록 ID(작업 `feature:`, 단계 문서 `doc:`, 결정 `note:`·`msg:`, 검토 중 실패한 테스트 `proof:`, 개선 사유 `iterate:`, 막힌 업무 `blocked:`, 프로젝트 규칙 `rule:`)와 `commit:<해시>`, `file:<경로>[#L10-L20]`입니다. wax는 AI를 부르지 않습니다. 정리는 일일 보고 뒤나 대표가 요청할 때 AI 세션이 합니다.

```sh
wax wiki ingest --batch 20          # 아직 반영하지 않은 기록 묶음(오래된 것부터)
wax wiki save auth --file auth.md   # 근거를 확인해 저장. 이미 있는 페이지는 --base <hash> 필요
wax wiki skip doc:login/plan        # 위키에 남기지 않을 기록
wax wiki lint                       # 근거 없는 문단·사라진 근거(오류), 폐기된 규칙·저장 뒤 바뀐 파일(확인)
```

이미 있는 페이지는 읽을 때의 hash(`wax wiki show`)를 `--base`로 넘겨야 고쳐지므로, 다른 세션이 고친 내용을 덮어쓰지 않습니다. 인용한 기록은 반영한 것으로 표시되어 다음 묶음에서 빠집니다. 개선 주기로 단계 문서가 바뀌어 근거가 사라지거나, 저장한 뒤 커밋으로 인용 파일이 바뀌면 `lint`가 알립니다. `wax context`는 이 작업을 인용한 페이지를, 대시보드(`/manage`)의 **프로젝트 위키** 패널은 페이지와 점검 결과를 보여 주고, `wax search`·`wax recall`도 위키 페이지를 찾습니다. 위키는 참고 자료이므로 지금 코드에서 다시 확인하세요. 실제로 실행하지 않은 테스트는 통과했다고 기록하면 안 됩니다.

## 6-8. 프로젝트 종류와 B1 디자인실

요청과 보고 화면에서 프로젝트 종류를 고르면 현재 미션·방·필수 산출물과 검증을 확인할 수 있습니다. Roblox 게임과 AI 룩북은 실제 플레이 또는 생성·저장·상품 연결에 맞는 검증을 요구합니다. **웹 서비스**는 요청 문장이나 저장소의 `package.json`(React·Next.js·Vite·Vue·Svelte·`@playwright/test` 등)으로 자동 선택되며, 워크스페이스(`workspaces`, `pnpm-workspace.yaml`)의 하위 패키지도 살펴봅니다. React Native·Expo·Electron·Tauri 앱은 웹 서비스로 고르지 않습니다. 설계에서 화면 시안 캡처, 구현에서 핵심 흐름 Playwright 테스트(`e2e-smoke`), 검토에서 수용 기준 테스트(`e2e-acceptance`)와 로딩·오류·빈 상태·모바일 화면 검토(`ui-review`)를 요구합니다. AI는 `playwright-cli`로 화면을 열어 탐색·재현·캡처하고, 근거로는 `node node_modules/@playwright/test/cli.js test`를 `wax test`로 실행한 기록만 인정합니다. wax는 셸 없이 실행하므로 `npx` 대신 이 경로를 쓰면 Windows에서도 동작합니다. Windows에서 `playwright-cli`는 `wax capture`의 `--` 뒤에서 실행되지 않으니 먼저 캡처한 뒤 `--file`만 지정하세요. 캡처는 `wax capture <작업ID> --check <검증 ID> --file <파일> [-- <캡처 명령>]`으로 `.wax/artifacts/`에 보관합니다. 필요한 도구의 설치 여부는 `wax doctor`의 `browser` 항목에서 확인합니다. B1 디자인실의 무드보드·제작물 버튼에서 등록한 시안을 확인하세요. 검토 실패 시 **수정 후 다시 검증**으로 개발 단계부터 이어갈 수 있습니다. 디자인실 제작물에서 Figma 프레임이나 Blender 컬렉션을 연결하면, 선택한 실행 도구(Codex·Claude Code)의 MCP로 실제 제작하고 대표의 수정 의견을 같은 대상의 다음 버전으로 반영한 뒤 확정한 버전을 개발에 인계합니다. 연결 상태는 그 실행 도구에서 실제로 검사합니다. 자세한 방법은 [디자인실 안내](DESIGN_STUDIO.md)를 참고하세요.

캡처 라벨(`--viewport`·`--scroll`·`--state`)과 같은 조건의 시안 비교(`wax compare`)는 4절 "화면 캡처와 시안 비교"를 보세요.

├── .wax/features/email-login.json    # 단계, 산출물, 근거, 개선 이력

### 백업과 복원

`wax backup > wax-backup.json`으로 백업하고, `wax import --file wax-backup.json`으로 미리 본 뒤 미리보기의 fingerprint를 `--apply <fingerprint>`로 넘겨 복원합니다.

`wax backup`은 작업 기록(`.wax/features`)과 함께 프로젝트 규칙·작업노트 메모·업무 배정·PM 지정·채널·화이트보드·일일보고 목록(`.wax/chat`)과 위키 상태(`.wax/wiki`)를 담습니다. 세션 참여 정보·실행 중인 요청·검색 색인·실행 승인 기록은 담지 않습니다. 위키 페이지와 보고서 문서(`docs/wax`)는 저장소 파일이라 git으로 보존하세요. `wax import`는 복원할 프로젝트에 같은 작업이나 같은 기록 파일이 있으면 덮어쓰거나 합치지 않고 건너뛰며, 미리보기의 `files`에 파일별 상태를 보여 줍니다. `--prefix`로 사본을 만들 때는 기록 파일이 원래 작업 ID를 가리키므로 작업만 복원합니다. 기록 파일은 모두 합쳐 128MB까지 담고, 넘으면 크기만 남깁니다. 이전 버전의 백업(작업 기록만)도 그대로 복원됩니다.

손상 백업 원문은 파일당 1MB, 최대 1000건, JSON에 담는 전체 원문은 64MB까지 보존합니다. 한도를 넘긴 파일은 크기와 생략 이유를 남기며 정상 작업은 계속 백업합니다.

| 변수 | 기본값 | 하는 일 |
| --- | --- | --- |

`WAX_TASK_DONE_CHECK`와 `WAX_REVIEW_SEPARATION`은 각 세션과 대시보드가 시작할 때의 값을 따르므로, 팀 전체에 적용하려면 모두 같은 값으로 시작하세요.

## 8. 문제 해결

| 증상 | 확인할 내용 |
| --- | --- |
| `/wax:` 명령이 보이지 않음 | `claude plugin list`에 `wax@wax`가 켜져 있는지(한 번 설치), 또는 `--plugin-dir` 절대 경로·Gemini 확장 연결을 확인하고 새 세션을 시작하세요. |
| Antigravity CLI에 스킬이 보이지 않음 | `install-project.mjs --project <경로> --check`로 `.agents/skills` 연결을 확인하고 새 `agy` 세션을 시작하세요. |
| Grok Build에 스킬이 보이지 않음 | `install-project.mjs --project <경로> --check`로 `.grok/skills` 연결을 확인하고(0.13.5 이전에 연결한 프로젝트는 연결 명령을 다시 실행) 새 `grok` 세션을 시작하세요. |
| Codex에 스킬이 보이지 않음 | `install-project.mjs --project <경로> --check`로 연결과 원본 폴더를 확인하고 새 세션을 시작하세요. |
| 단계가 넘어가지 않음 | 현재 단계 문서, 완료 근거, 검토 통과 여부를 확인하세요. 구현·검토는 통과한 테스트나 커밋 근거(`--proofs`)가 필요합니다. |
| 대시보드 자동 진행 도구 목록에 Grok Build가 없음 | Grok Build는 자동 진행과 PM 루프 작업자를 지원하지 않습니다. 터미널 세션에서 스킬 이름을 밝혀 요청하세요(5-4절). |
| 브라우저 알림이 오지 않음 | **알림 켜기**를 눌렀는지, 버튼이 **알림 차단됨**이면 사이트 설정에서 알림을 허용했는지, 대시보드 탭이 열려 있는지 확인하세요. 탭을 보고 있는 동안에는 알리지 않습니다. |
| 트리거가 **연결 필요**로 나옴 | 이 컴퓨터에서 `gh auth status`를 확인하고 `gh auth login` 뒤 기다리면 다음 분에 다시 확인합니다. `gh`가 PATH에 없으면 `WAX_GH_BIN`으로 경로를 주고 대시보드를 다시 시작하세요. |
| 기존 GitHub 이슈가 제안되지 않음 | 첫 확인은 이미 있는 항목을 기준으로만 기록합니다. 라벨을 뗐다 다시 붙이세요(6-5절). |
| 트리거가 저절로 꺼짐 | 5번 연달아 실패하면 꺼집니다. 목록의 이유를 확인해 고친 뒤 다시 켜세요. |
| PM 루프 목표가 멈춤 | 목표 화면의 이유(한도, 연속 막힘, auto 행동 실패)를 확인하고, 원인을 고친 뒤 **목표 재개**에서 한도를 확인하세요. |
| `wax mcp`가 시작하지 않음 | 등록한 설정의 env에 `WAX_MCP=on`이 있는지, 터미널에서 `WAX_MCP=on node /path/to/wax/bin/wax.mjs mcp --project <경로>`의 오류 출력을 확인하세요(6-2절). |
| CLI가 영어(또는 한국어)로 나옴 | `WAX_LANG=ko` 또는 `WAX_LANG=en`을 지정하세요. 없으면 `LC_ALL`·`LC_MESSAGES`·`LANG`을 따릅니다. |
| 비정상 종료 후 계속 저장 중으로 나옴 | wax는 주인 프로세스가 끝난 저장 잠금을 다음 저장 때 회수합니다. 그래도 남으면 `doctor`로 잠금 경로를 확인하고, 해당 프로젝트의 wax 작업이 모두 끝났는지 확인한 뒤 `.wax/features/<id>.lock` 디렉터리를 제거하세요. |
| (웹 서비스) AI 버튼이 비활성화됨 | 제공자·모델 ID·키를 설정하고 서버를 재시작하세요. |
| (웹 서비스) AI 요청에 401·403·404가 표시됨 | API 키, 모델 이름, 모델 접근권한을 확인하세요. |
| (웹 서비스) AI 요청에 429가 표시됨 | 제공자의 사용 한도·요금을 확인하고 잠시 후 다시 시도하세요. |
| (웹 서비스) 저장 충돌이 표시됨 | 복구 패널에서 초안을 다운로드하거나 최신 기록과 비교한 뒤 다시 가져오세요. 서버는 원본을 자동으로 덮어쓰지 않습니다. |

"(웹 서비스)" 줄은 wax 웹 서비스(wax-service)를 함께 쓸 때의 증상입니다.

기록 문제는 `node "/path/to/wax/bin/wax.mjs" doctor --project "/path/to/project"`로 한 번에 검사할 수 있습니다. 정상 기록 수와 문제 파일·잠금 경로를 JSON으로 출력합니다. 이 명령은 파일을 수정하거나 잠금을 제거하지 않으며 문제가 있으면 종료 코드 1을 반환합니다.

## 9. 업데이트와 검증 범위

호스트 세션을 종료하고 기존 플러그인을 백업한 뒤 새 ZIP을 기존과 같은 플러그인 경로에 배치합니다. 마켓플레이스로 설치했다면 각 도구의 업데이트 명령을 씁니다(INSTALL.md). 작업 프로젝트의 `.wax`와 `docs/wax`는 유지하세요. 직접 수정한 플러그인은 변경 내용을 비교·병합한 뒤 업데이트하세요.

0.13.x 이하에서 공개 저장소를 마켓플레이스로 등록했다면, 0.14.0에서 저장소 이력이 새로 시작되어 업데이트가 실패할 수 있습니다. 이때는 등록을 지우고 다시 등록합니다(1절 "0.14.0 공개 저장소 안내"). Codex는 5-1절의 전환 명령을 그대로 쓰고, 다른 도구는 그 도구의 마켓플레이스 제거 명령 뒤 처음 설치할 때와 같이 등록·설치합니다.

자동 검사 대상은 상태 저장·단계 전환·동시 수정 충돌·CLI·Codex 설치 및 스킬 실행기·읽기 전용 진단·ZIP 압축 해제 후 실행입니다. Claude 플러그인 규격과 Gemini 명령 문법도 확인합니다. Claude Code 2.1, Codex 0.162, GitHub Copilot CLI 1.0.97에서 마켓플레이스 설치와 실제 명령 실행을 확인했습니다. Windows Node.js 22.17.0에서 junction 설치·연결 실행·한글 경로·단계 전환·테스트 근거·백업을 검증했습니다. Windows에서 `npm run test:windows`로 재현할 수 있습니다. 공개 배포본은 Ubuntu·macOS·Windows와 Node 22·24에서 검사를 통과한 버전만 올라갑니다.

아직 검증하지 않은 것:

- 실제 AI 계정으로 코드 수정부터 최종 검토까지 진행하는 전체 과정, 실제 Gemini CLI·Antigravity CLI·Grok Build 세션, 유료 API 호출.
- PM 루프의 실제 도구 한 바퀴(headless 작업자, PM 판단, auto 모드). 테스트는 가짜 작업자와 가짜 판단으로 합니다(6-6절).
- MCP 서버를 각 도구에 실제로 등록한 결과. 테스트는 서버와 출력한 설정 조각만 확인합니다(6-2절).
- 실제 GitHub 저장소를 대상으로 한 트리거 폴링. 테스트는 가짜 `gh`로 합니다(6-5절).
- 자동 진행에서 각 제공자의 실제 계정으로 하는 작업. 공식 CLI 프로토콜의 모의 실행으로 승인·거부·중지·이어가기와 보고 처리를 검증했습니다(6-3절).
