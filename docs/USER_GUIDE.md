# wax 사용 매뉴얼

wax는 기능 하나를 **기획 → 설계 → 구현 → 검토 → 보고**로 나누어 진행하고, 문서와 완료 근거를 프로젝트에 남깁니다.

이 매뉴얼은 wax 0.16.0 기준입니다. 설치한 버전은 플러그인 폴더에서 `node bin/wax.mjs --version`으로 확인합니다. 이번 릴리스에서 바뀐 점은 배포본의 `RELEASE_NOTES.md`에, 버전마다 바뀐 점은 [변경 이력](https://wax.me2shop.com/changelog/)에 있습니다.

쓰는 방법은 두 가지입니다. 터미널의 AI 세션에서 단계 명령을 하나씩 실행하거나(3·4절, 다른 도구는 5절), 대시보드에서 한 줄로 요청해 선택한 도구가 끝까지 진행하게 합니다(6-3절). 어느 쪽이든 기록은 같은 `.wax/`에 남습니다.

## 1. 무엇이 필요한가요?

Node.js 22 이상과 로그인된 Claude Code, Codex, Antigravity CLI, GitHub Copilot CLI, Grok Build 또는 Gemini CLI 중 하나가 필요합니다. wax는 공개 저장소 [cafein-network/wax](https://github.com/cafein-network/wax)에서 각 도구의 마켓플레이스로 바로 설치하거나, [wax 사이트](https://wax.me2shop.com/#download)에서 ZIP으로 내려받을 수 있습니다. 배포본에는 플러그인 소스·테스트·매뉴얼이 들어 있습니다. wax 코드에는 AGPL-3.0 라이선스(무료로 쓰고 고치고 배포할 수 있으며, 배포 시 소스 제공 조건 준수, 수정본을 네트워크로 제공하면 원격 사용자에게 대응 소스 제공)가 적용되며 AI 도구와 API의 사용 요금·한도는 별도입니다.

**0.16.0 공개 저장소 안내.** 0.16.0에서 공개 저장소 `cafein-network/wax`를 새 이력으로 다시 만들었습니다. 설치 주소는 그대로입니다. 0.16.0 전에 등록한 마켓플레이스의 업데이트가 이력 불일치로 실패하면 그 도구에서 `wax` 마켓플레이스 등록을 지우고 다시 등록하세요. 공개 저장소 clone을 프로젝트에 연결했다면(Antigravity CLI·Grok Build 등) clone에서 `git pull`이 실패할 때 clone을 새로 받고 `install-project.mjs --project <프로젝트>`를 다시 실행하세요(9절, INSTALL.md의 "업데이트 및 직접 개선"). 작업 프로젝트의 `.wax`와 `docs/wax`는 그대로 둡니다. 0.16.0 전의 GitHub 릴리스 ZIP과 출처 증명은 더 이상 제공하지 않으며, 변경 내역은 [변경 이력](https://wax.me2shop.com/changelog/)에 남아 있습니다.

## 2. 코드 내려받기

ZIP을 **모두 압축 풀기**로 해제한 뒤 내부에 `package.json`과 `bin/wax.mjs`가 있는 `wax` 폴더를 찾습니다. `.claude-plugin` 숨김 폴더도 포함되어 있어야 합니다. 플러그인은 `npm install` 없이 실행됩니다.

Windows·WSL 예제와 업데이트 방법은 ZIP 안의 `INSTALL.md`를 참고하세요. 이 매뉴얼에서 `/path/to/wax`은 예시 경로입니다. 반드시 압축을 푼 실제 절대 경로로 바꾸세요.

아래 예제에서 `/path/to/my-app`은 **실제로 코딩할 프로젝트 디렉터리**로 바꾸세요. 해당 디렉터리는 먼저 존재해야 합니다. 플러그인 소스 디렉터리와 작업할 프로젝트를 구분하세요.

## 3. Claude Code에서 첫 작업 시작

작업할 프로젝트에서 wax 플러그인을 로드합니다. 이 방식은 해당 Claude 세션에 적용되므로 새 세션을 열 때 같은 옵션을 사용하세요.

```sh
cd /path/to/my-app
claude --plugin-dir "/path/to/wax"
```

다른 컴퓨터에서는 `--plugin-dir` 뒤의 경로도 실제 위치로 바꾸세요. npm 설치 없이 동작합니다.

매번 `--plugin-dir`을 붙이지 않으려면 한 번만 설치합니다: `claude plugin marketplace add "/path/to/wax"` 뒤 `claude plugin install wax@wax`. 압축을 푼 폴더가 그대로 마켓플레이스이며, Codex(`codex plugin marketplace add` → `codex plugin add wax@wax`)와 GitHub Copilot CLI(`copilot plugin marketplace add` → `copilot plugin install wax@wax`)도 같은 폴더로 한 번 설치합니다. 업데이트·제거는 설치 안내(INSTALL.md)의 "한 번 설치" 절을 보세요.

처음에는 Claude 대화창에서 시작 명령을 한 번 실행합니다.

```text
/wax:init
```

설정 질문 없이 기본 이름으로 바로 참여하고 대시보드를 엽니다. 작업은 진행 중인 것이 하나면 그 작업, 아니면 없음으로 정합니다. PM이 없는 프로젝트에서는 init한 세션이 PM이 되고(`--no-pm`이면 지정하지 않음), 이미 PM이 있으면 그대로 유지합니다. 이름·작업·PM 옵션을 명시하면 그대로 적용합니다. 끝나면 이 세션이 팀 채널에 참여해 가상 사무실에 캐릭터로 나타나고, 다른 AI 세션이 참여하는 방법(`/wax:join`)을 알려 줍니다. init과 join은 대기 상태로 참여하며, 실제 단계 작업을 시작할 때 작업 중으로 바뀝니다. 대시보드를 나중에 다시 열 때도 `/wax:init`을 실행합니다.

자동 진행은 대시보드의 요청과 보고 화면(`/start`)에서 한 줄로 요청합니다(6-3절). 터미널에서 각 단계를 직접 관리하려면 다음처럼 기능을 요청합니다.

```text
/wax:plan email-login 이메일과 비밀번호로 로그인하는 기능을 만들어줘
```

wax가 기존 코드를 확인하고 요구사항·범위·수용 기준을 정리합니다. 결정이 필요한 질문에 답한 뒤 결과를 확인하세요. 한 명령은 그 단계의 작업을 수행하며, 모든 후속 단계를 한꺼번에 실행하지 않습니다.

## 4. 단계를 차례로 진행

| 명령 | 하는 일 |
| --- | --- |
| `/wax:init` | 시작하기: 팀 채널 참여, 맡을 작업, 대시보드 열기, PM 지정을 한 번에 |
| `/wax:join` | 다른 AI 세션이 팀 채널에 참여(이름·작업만 정함) |
| `/wax:plan email-login …` | 새 기능의 문제·범위·수용 기준 정리 |
| `/wax:design email-login` | 구조·데이터·수정 파일·검증 방법 설계 |
| `/wax:implement email-login` | 호스트의 도구로 실제 코드 수정 및 관련 검사 실행 |
| `/wax:review email-login` | 설계와 실제 결과 비교, 테스트 근거와 미검증 항목 기록 |
| `/wax:report email-login` | 결과·검증·사용법·남은 과제 정리 |
| `/wax:status email-login` | 현재 단계와 완료 근거 확인 |
| `/wax:iterate email-login 만료 토큰 처리 개선` | 이전 주기를 보관하고 구현 단계로 돌아가기 |

예를 들어 첫 기획을 마친 후 다음 명령을 한 번씩 실행합니다.

```text
/wax:design email-login
/wax:implement email-login
/wax:review email-login
/wax:report email-login
```

현재 단계의 문서와 완료 근거가 있어야 다음 단계로 넘어갑니다. 구현은 실제로 통과한 테스트(`wax test`)나 커밋(`wax evidence`) 근거를, 검토는 통과한 테스트 근거와 확인된 통과 판정을 함께 연결해야 완료됩니다. 문서만 고치는 작업처럼 실행할 검증이 없으면 `--no-proof <사유>`로 사유를 남기고 넘어가며, 그 사유는 완료 기록과 다른 도구가 읽는 인수인계 문맥에 그대로 남습니다. 검토는 수용 기준 표에 더해 구조 → 기능 → 효율 → 표현 순서로 점검합니다. 역할별 흐름과 권한(화면에서 숨기는 데 그치지 않고 서버에서도 막히는지), 되돌릴 수 없는 동작의 확인·취소 경로, 수치·집계와 원본 데이터의 일치, 실제에 가까운 데이터 양에서의 찾기·속도, 로딩·오류·빈 화면을 보고, 해당하지 않으면 해당 없음과 이유를 적습니다. 발견한 문제에는 누가 왜 곤란한지를 함께 적습니다. 해결되지 않은 문제나 미검증 기준이 남으면 검토를 완료하지 않고 그 이유를 알려줍니다.

구현을 완료할 때 wax는 연결한 통과 테스트마다 고치기 전에 실패한 같은 검사(같은 명령, 같은 `--checks`, 같은 폴더, 그 사이 코드가 바뀜)를 근거에서 찾아 빨강→초록 짝으로 완료 기록(`completed.implement.redGreen`)에 남깁니다. 그래서 고치기 전에 바뀔 동작을 시험하는 검사를 `wax test`로 먼저 돌려 실패를 남기고, 고친 뒤 같은 명령으로 다시 돌리세요. 열린 결함은 `wax test <id> --checks d-1 -- …`처럼 결함 ID로 고치기 전 실패와 고친 뒤 통과를 남깁니다. 짝이 없으면 기본(`WAX_RED_GREEN=warn`)은 완료하고 경고하며, `enforce`는 거절합니다. 실패를 먼저 볼 수 없는 변경(설정 값 같은)이면 `wax complete implement … --no-red <사유>`로 사유를 남기세요. 짝이 있으면 `--no-red`는 거절됩니다. 테스트 이름을 읽을 수 있는 출력(TAP·JUnit)이면 다른 테스트가 실패했다가 통과한 경우를, 트리 지문으로는 테스트 파일만 바뀐 경우를 경고로 남깁니다. Node 24 이상의 `node --test`는 파이프에서도 TAP이 아닌 형식으로 출력하므로, 이름까지 맞춰 보려면 빨강과 초록 모두 `--test-reporter=tap`을 붙이세요(두 번 다 같은 명령이어야 짝이 됩니다). 판정 결과는 `wax status <id>`의 `redGreen`(한 줄 요약·경고·결함별 짝·사유), `wax quality-report`의 "실패를 먼저 본 근거" 절, `wax pr-body`의 "검증 근거" 절(짝 5개까지 표), 실행 기록(대시보드·`wax trace`)의 구현 방문에서 근거마다 빨강·초록 표시로 보입니다. PM 루프 목표에서 사람이 **빨강→초록 필수**를 켜면 그 목표의 작업에는 `enforce`가 적용됩니다(6-6절).

기능 ID는 영문 소문자·숫자로 시작하며 소문자·숫자·하이픈만 포함하는 1~64자입니다. `email-login`, `dashboard`, `payment-v2`처럼 정하세요.

### 개선 주기(iterate)

검토에서 문제가 발견됐다면 다음과 같이 개선합니다.

```text
/wax:iterate email-login 만료된 인증 토큰을 거부하도록 개선
/wax:implement email-login
/wax:review email-login
/wax:report email-login
```

### 수용 기준 추적

기획은 수용 기준을 한 줄에 하나씩 `- AC-1: <기준> — 검증: <방법>`처럼 줄 맨 앞에 ID를 붙여 적습니다(줄 맨 앞의 `AC-<번호>`만 ID로 읽고, 본문 중간의 언급은 선언으로 보지 않습니다). 기획에 AC ID가 있으면 검토를 완료할 때 `--checks-file` JSON 배열에 ID마다 `{"id": "ac-1", "status": "pass", "detail": "<확인 내용>", "proofIds": ["<근거 ID>"]}` 항목을 넣어야 합니다. `pass`는 현재 주기의 통과한 테스트나 커밋 근거가 연결되어야 인정되고, 빠졌거나 `unverified`이거나 근거 없는 기준이 남으면 검토가 완료되지 않습니다. 정말 검증할 수 없는 기준만 `--ac-unverified <사유>`로 남기고 넘어가며, `fail`이 하나라도 있으면 사유와 관계없이 거절하므로 `wax iterate`로 고칩니다. 추적표(AC → 상태 → 근거)는 `wax status <id>`의 `acceptanceTrace`, `wax context <id>`, 보고 단계 프롬프트에 나타납니다. AC ID가 없는 기존 기획은 이전과 똑같이 동작합니다.

### 계획 단계

기획은 수용 기준 아래에 일을 잘게 나눈 단계를 `` - S-1: <무엇> — files: <바꿀 파일> — check: `<wax test가 실행할 명령>` — done: <완료 기준> — AC: AC-1 ``처럼 줄 맨 앞에 적을 수 있습니다. 칸 구분은 ` — `나 ` -- `, 칸 이름은 `files`·`check`·`done`·`AC`(`파일`·`검사`·`완료`도 받음)이고(제목 바로 뒤의 이름 없는 칸은 제목의 설명으로 이어 읽음), 표의 `| S-1 | …` 줄도 읽습니다. `check`는 백틱 안의 명령 하나(wax는 셸 없이 실행하므로 `|`·`&`·`;`·`<`·`>`·`$`·`\`·`*` 같은 셸 문자 없이), `checks=<ID>`, 또는 시험할 수 없는 단계의 `없음(<사유>)`입니다. 기획에 AC ID가 있으면 기획을 완료할 때 wax가 단계를 검사합니다. 없는 AC를 가리키는 단계와 같은 S ID 둘은 늘 거절합니다. 단계가 없거나 `check`가 없거나 형식 밖이면 기본(`WAX_PLAN_STEPS=warn`)은 완료하고 경고하며, `enforce`는 거절합니다. 어느 단계도 가리키지 않는 AC, 파일이 8개를 넘는 단계, 빠진 번호, 모르는 칸 이름, 같은 `check`를 쓰는 단계, Windows에서 `npx`·`npm`·`yarn`·`pnpm`으로 시작하는 검사는 경고만 합니다. 요약은 완료 기록 `completed.plan.steps`에 남습니다. AC ID가 없는 기존 기획은 이전과 똑같이 동작합니다.

구현에서는 단계마다 그 `check` 명령을 그대로 `wax test <id> -- <명령>`으로 실행하세요. 명령(Windows에서는 `\`·`/`와 드라이브 글자 대소문자를 같게 봄)이 단계의 `check`와 같거나 `checks=<ID>`의 ID가 모두 `--checks`에 있으면 wax가 근거에 단계(`step: "S-1"`)를 붙입니다. 같은 `check`를 쓰는 단계가 여럿이면(예: 모두 `node --test`) 기획 순서에서 이 주기에 아직 통과 근거가 없는 첫 단계에 붙이고, 모두 통과했으면 마지막 단계에 붙입니다. 실패 근거도 같은 규칙이라 한 단계의 고치기 전 실패와 고친 뒤 통과가 같은 단계에 붙습니다. 진행을 분명히 하려면 단계마다 그 단계만 보는 명령(예: 테스트 파일 하나)을 적으세요. `wax test <id> --step S-1 -- …`로 직접 붙일 수도 있고, `--step`이 늘 먼저입니다(구현 단계에서 기획에 있는 단계만). 다른 명령에 `--step`을 붙이면 근거는 남지만 "단계 검사와 다른 명령"으로 표시되고 단계 진행으로 세지 않습니다. 단계 진행은 이 주기 구현에서 그 단계의 검사가 통과했는지이고, 같은 검사의 고치기 전 실패가 있으면 "빨강→초록"까지 적습니다. 구현을 완료할 때 `check`가 있는 단계에 통과 근거가 없으면 기본(`WAX_PLAN_STEPS=warn`)은 완료하고 경고하며, `enforce`는 거절합니다(`없음(<사유>)` 단계는 세지 않습니다). 요약은 `completed.implement.steps`에, 단계마다의 빨강→초록은 `completed.implement.redGreen.steps`에, 완료에 연결한 근거의 짝이 어느 단계인지는 짝의 `step`에 남습니다. `redGreen.steps`의 `ok`·`missing`은 `wax status`의 단계 진행과 같은 계산(이 주기에 그 단계의 통과 근거에 고치기 전 실패 짝이 있는지)이라, 단계마다 빨강→초록을 남기고 `--proofs`에 마지막 초록만 연결해도 앞 단계가 `missing`으로 남지 않습니다. `ok` 단계의 `linked`는 그 단계의 짝이 `--proofs`로 연결한 근거의 짝인지입니다. 빨강→초록 판정(`redGreen.state`·`pairs`)은 지금처럼 연결한 통과 근거만 봅니다. 진행은 `wax status <id>`의 `planSteps`("계획 단계 3/5 끝남(빨강→초록 2)"와 단계 표), `wax context`의 "계획 단계"(남은 단계 첫 3개와 검사 명령), `wax quality-report`의 "계획 단계" 절, `wax pr-body`의 "검증 근거" 절(단계 10개까지 표), 실행 기록(대시보드·`wax trace`)의 구현 방문에서 보입니다. 구현 지시문(`wax prompt implement`, PM 루프 작업자)에는 다음 단계와 남은 단계 목록이 인용 데이터로 들어갑니다. PM 루프 작업자는 단계의 `check` 명령을 그대로 실행해 자동으로 붙게 하고, 여러 단계가 같은 검사 명령을 쓰면 `--step`으로 단계를 붙입니다(목표 허용 **검사 명령**이 구현 단계의 `--step S-n`을 받습니다).
### 설계 방법 고르기

설계 단계에서는 설계를 쓰기 전에 방법 2~3개를 내고 사람이 고르게 할 수 있습니다. 작업자는 `.wax/tmp/<파일>.json`에 `[{"title":"…","summary":"…","tradeoffs":"…","cost":"S|M|L","risk":"low|medium|high"}, …]`를 쓰고 `wax approach <id> --propose --file <파일> [--author <세션 이름>]`으로 냅니다(제목 120자, 요약·장단점 1000자를 넘는 글은 잘라 남기고 숨은 문자는 지웁니다. 비용·위험은 작업자의 어림). 하나뿐이면 `wax approach <id> --propose` 대신 `--single <사유>`로 선언합니다. 사람은 `wax approach <id>`로 낸 방법과 revision을 보고 `wax approach <id> --pick <N> --author <이름> --revision <n> [--reason <이유>]`로 고릅니다. 고르기는 사람만 합니다: wax가 띄운 작업자 실행(`WAX_WORKER=1`)과 작업자·`auto`·`pm-loop` 이름은 거절되고, 기록에는 CLI에서 골랐다는 `via: cli`가 남으며, 작업자 요청이면 실행 승인 화면에 "작업자가 부를 일이 아닌 명령"으로 표시됩니다. 설계 단계인 동안은 다시 고를 수 있고(마지막 고르기가 유효, 이력에 남음), 사람이 고른 뒤에는 사람이 **다시 내 줘**를 누르지 않는 한 작업자가 새 방법을 내지 못합니다. 방법은 3번까지 낼 수 있습니다. 설계를 완료할 때 낸 방법이 있는데 사람이 고르지 않았으면 늘 거절됩니다. 아무 기록이 없으면 기본(`WAX_APPROACH=warn`)은 완료하고 경고하며, `ask`는 거절하고, `always`는 `--single`도 받지 않고 사람이 고른 방법만 받습니다. `off`는 보지 않습니다. 판정은 완료 기록 `completed.design.approach`에, 기록은 작업의 `approach`에 남습니다.

**대시보드에서 고르기:** 작업의 **실행 기록**을 열면 **설계 방법** 칸에 낸 방법(제목·요약·장단점·"비용 S · 위험 낮음(작업자 어림)")이 글자 그대로 보입니다. **이것으로**를 누르면 확인 단계가 나오고, 설계 문서를 이미 저장했으면 "설계 문서를 새 방법으로 다시 써야 합니다"를 먼저 보입니다. 이유(선택, 500자)를 적고 **이 방법으로 고르기**를 누르면 기록에 `via: dashboard`가 남습니다. 마음에 드는 방법이 없으면 **다시 내 줘**를 누르고 무엇을 바꿔 달라고 할지 메모(필수, 500자)를 보냅니다. 그러면 작업자가 새 묶음을 낼 수 있고(고른 뒤에도), 새 묶음을 내고 사람이 다시 고르기 전에는 설계를 완료할 수 없습니다. 고르기와 다시 내 줘는 대시보드의 사람만 할 수 있고(작업자·`auto`·`pm-loop` 이름은 거절), 화면을 본 뒤 방법이 바뀌었으면 거절하고 다시 읽습니다. **PM 루프:** headless 설계 작업자는 지시문대로 방법을 내고 단계를 완료하지 않은 채 끝납니다. 이 경우 완료하지 않은 done 경고·다시 알림·다시 시도는 없고, 목표에 사람 카드 **설계 방법을 골라 주세요**가 하나 나옵니다(같은 고르기·다시 내 줘, 버릴 수 없음). 시간이 지나도 스스로 고르지 않고 auto도 고르지 않습니다. 고르거나 다시 내 달라고 하면 다음 작업자 카드가 나오고, 다음 설계 작업자는 고른 방법과 이유(또는 다시 내 달라는 메모)를 인용 데이터로 받습니다. 방법 내기와 설계 쓰기는 둘 다 단계 실행 한도에 셉니다. 목표 시작 화면의 **설계 방법 고르기**에서 기본(`WAX_APPROACH`)·사람이 고름(`ask`)·늘 사람이 고름(`always`)·쓰지 않음(`off`)을 고르면 목표에 든 작업마다 작업 기록 `discipline.approach`에 남아 환경 변수보다 먼저 적용됩니다. 기본값이 `warn`이어도 설계 지시문은 방법을 먼저 내라고 하므로, PM 루프 목표의 설계 단계는 보통 이 카드에서 사람을 기다립니다. 원하지 않으면 시작 화면에서 **쓰지 않음**을 고르세요. `wax status`의 `approachSummary`, 품질 보고서와 PR 초안의 **설계 방법** 절에 고른 방법·이유·고르지 않은 방법(또는 "방법 고르기 건너뜀: <사유>")이 인용으로 들어갑니다.

### 검토자 분리

단계를 완료한 세션 이름은 `wax complete ... --author <이름>`으로 완료 기록(`completed`)과 이력(`history`)에 남습니다. 구현을 완료했거나 현재 주기의 구현 근거(`wax test`·`wax evidence --author`)를 남긴 세션이 검토까지 완료하면 기본(`WAX_REVIEW_SEPARATION=warn`)으로는 완료하되 경고를 남깁니다. 경고는 CLI 오류 출력(`wax: 경고: …`), 완료 기록의 `warning`, 대시보드 기록 타임라인의 단계 완료 항목, 자동 진행 요청 대화와 인수인계 문맥에 보입니다. `WAX_REVIEW_SEPARATION=enforce`로 실행한 세션과 대시보드는 구현한 세션의 검토 완료와 `--author` 없는 검토 완료를 거절합니다(대시보드 자동 진행은 한 세션이 모든 단계를 맡으므로 검토에서 멈춥니다). `off`는 확인하지 않습니다. 팀 전체에 적용하려면 모든 세션과 대시보드를 같은 설정으로 시작하세요. 이름은 세션이 스스로 밝히는 값이라 보안 경계가 아니라 실수를 막는 장치입니다. 이전 기록에는 완료 세션이 없으며 그대로 읽고 가져올 수 있습니다.

### 두 단계 검토

검토는 두 단계로 합니다. 1단계 **명세**는 수용 기준(`ac-N`), 계획 단계(`s-N`), 빨강→초록(`red-green`), 재검증할 결함(`d-N`)이고, 하나라도 실패면 거기서 멈추고 품질은 보지 않은 채 결함과 함께 `wax iterate`로 돌아갑니다. 2단계 **품질**은 명세가 모두 통과한 뒤에만 보며 `q-tests`(빠진 경우·약한 단언), `q-structure`, `q-security`, `q-simplicity`, 그 밖의 `q-<이름>`(20개까지)입니다. 두 단계 모두 같은 검토 세션이 합니다(그 세션이 구현 세션과 달라야 하는 것은 위 "검토자 분리"). 항목은 같은 `--checks-file`에 `{"id": "s-1", "stage": "spec", "status": "pass", "detail": "…", "proofIds": ["…"]}`, `{"id": "q-tests", "stage": "quality", "status": "pass", "detail": "…"}`처럼 넣습니다. `ac-N`·`d-N`·`s-N`·`red-green`은 `stage`를 적지 않으면 명세로 보고, 다른 단계를 적으면 거절합니다. 명세나 품질 항목의 `fail`은 늘 거절하고, 품질 `unverified`는 `detail`이 있어야 받습니다. 기획에 S-N이 있는데 `s-N` 항목이 빠졌거나, 구현 완료의 빨강→초록이 짝 확인이 아닌데(`missing`·`partial`·`waived`) `red-green` 항목이 없거나, 품질 항목이 하나도 없으면 기본(`WAX_REVIEW_STAGES=warn`)은 완료하고 경고하며 `enforce`는 거절합니다. `off`는 빠진 항목을 보지 않습니다. 검사가 없는 단계(`check: 없음(사유)`)는 근거 없는 `pass`도 통과로 세고, 그 밖의 명세 `pass`는 현재 주기 근거가 있어야 통과로 셉니다. 요약은 완료 기록 `completed.review.stages`에 남고 `wax status <id>`의 `reviewStages`("명세 통과(4) → 품질 통과(3, 미검증 1)"), 실행 기록의 검토 방문, `wax quality-report`의 "두 단계 검토" 절(품질 항목은 ISO/IEC 25010 특성에도 셈), `wax pr-body`에 보입니다. iterate할 때 `--defects-file` 결함에 `"stage": "spec"`이나 `"quality"`를 붙이면 주기마다 어느 단계에서 돌아갔는지 셉니다. `stage`가 없는 옛 checks 파일과 기록은 그대로 읽습니다(품질 항목 없음 경고만).

### 근거 신선도

`wax test`·`wax evidence`는 근거를 남길 때 작업 트리 지문(`tree`)을 함께 저장합니다. 지문은 HEAD 커밋과, HEAD와 다르거나 추적되지 않은(무시 목록 제외) 파일별 Git blob ID입니다(`.wax/`는 제외). 지문은 읽기 전용 Git 명령으로만 만들며 프로젝트 `.git`(index 포함)에 쓰지 않습니다. 이후 `wax context`는 근거마다 "이후 바뀐 파일 N개"를, 머리말에는 현재 주기의 검토 근거(없으면 구현 근거) 이후 바뀐 파일을 보여 주고, `wax status <id>`는 같은 내용을 `evidenceFreshness`로, 보고 단계 지시문(`wax prompt report`, 대시보드 자동 진행)은 "검토 근거 이후 바뀐 파일 N개: …"로 알립니다. 대시보드 근거 카드에도 "이후 바뀐 파일 N개"가 붙고 마우스를 올리면 파일 목록이 보입니다. 이 표시는 판정이 아니라 관찰이며 단계 진행을 막지 않습니다. 바뀐 파일이 근거와 관련 있으면 테스트를 다시 실행하세요. 바뀐·추적되지 않은 파일이 200개를 넘거나 합계 64MB를 넘거나 Git 명령이 5초 안에 끝나지 않으면 멈추지 않고 지문을 "미확인"으로 남깁니다. Git이 없는 프로젝트와 이 기능 이전의 근거에는 지문이 없어 "이후 변경 미확인"으로 표시되며, 그대로 읽고 백업·복원할 수 있습니다. `wax test <id> --worktree <경로> -- …`는 PM 루프가 등록한 작업자별 워크트리(`.wax/chat/worktrees.jsonl`, `<프로젝트>/.wax/worktrees/` 아래, 그 작업의 것만)에서 명령·커밋·지문을 읽고 근거는 프로젝트에 남깁니다(근거에 `worktree`가 붙습니다). 등록되지 않은 폴더는 거절합니다. 워크트리는 사람이 목표에서 격리 브랜치를 켰을 때 PM 루프가 만듭니다(6-6 "작업자마다 격리 브랜치").

### 작업 인수인계

새 세션에서 기존 작업을 이어받을 때는 먼저 다음 명령으로 인수인계 문맥을 읽으세요.

```sh
node /path/to/wax/bin/wax.mjs --project /path/to/my-app context login --budget 3000
```

`login`은 기존 작업 ID입니다. 목표, 현재 단계와 다음 행동, 화이트보드 결정과 답변·결정이 연결되지 않은 질문, 실행 근거, 개선 사유와 단계 문서 발췌를 보여 줍니다. 각 항목의 `.wax/features/<id>.json#/...` 또는 `.wax/chat/board/<id>.jsonl#<노트 ID>` 참조로 원본을 확인할 수 있습니다. 단계 스킬과 `work`에서도 작업 전에 이 명령을 읽도록 안내합니다.

`--budget`은 유니코드 문자 수이며 토큰 수가 아닙니다. 기본 3,000자, 범위 1,000~100,000자입니다. 끝의 표시/전체 개수와 `…`는 생략된 항목과 원문이 있음을 알려 줍니다. 출력은 규칙에 따른 발췌이므로 최신 `status`, 전체 단계 `prompt`와 필요한 원본도 확인하세요. 질문은 해당 작업 보드 범위이며, 답변이 연결돼도 실제 해결을 보장하지 않습니다. 손상된 보드 기록은 제외 개수를 표시하고, 안전하지 않은 저장 경로나 손상된 작업 파일은 오류로 알립니다.

조회는 읽기 전용이며 외부 AI를 호출하지 않습니다. 과거 주기의 테스트와 현재 주기의 테스트를 구분하고 실행 당시 커밋·작업 트리 상태를 표시합니다. 기록된 통과는 현재 코드의 통과를 보장하지 않으므로 변경 후에는 필요한 테스트를 다시 실행하세요.

### 단계별 소요 시간과 실행 기록

wax는 작업 이력으로 단계마다 걸린 시간을 계산합니다. 단계에 들어간 때부터 완료한 때까지의 실제 경과 시간이며, 개선 주기로 구현에 다시 들어간 구간은 같은 단계에 더합니다. 대시보드 **작업 진행**의 작업마다 단계별 시간과 합계가 나오고, 진행 중인 단계는 "12분째"처럼 표시합니다. `wax status <id>` JSON에는 `durations`로 들어갑니다. 보관한 기간과 백업·복원 사이의 공백은 세지 않고, 시각이 없거나 거꾸로 간 예전 기록은 건너뜁니다. 사용량은 PM 루프가 띄운 headless 작업자·PM 판단에서 도구가 스스로 알린 값만 `usage`로 들어갑니다(6-6절 "사용량"). 대화형 세션의 비용·토큰은 작업 단계와 맞출 기록이 없어 넣지 않습니다.

단계 방문마다 언제, 어느 세션·도구가, 어떤 근거로, 무엇을 바꾸며 지나갔는지는 `wax trace <id>`(Markdown)나 `wax trace <id> --json`, 대시보드의 실행 기록 패널에서 봅니다(6절 "대시보드에서 기록 확인하기"). 검토 방문에는 수용 기준과 함께 결함 재검증 결과가, 검토를 끝낸 iterate가 기록한 결함은 그 검토 방문에 나옵니다. 둘 다 읽기 전용이며 AI를 부르지 않습니다.

### 왜 멈췄나 진단(diagnose)

목표나 작업이 멈췄을 때 `wax diagnose <목표 ID|작업 ID>`가 wax 기록만 읽고 이유를 모아 보여 줍니다. 목표면 그 목표의 작업 모두, 작업이면 그 작업과 그 작업이 든 PM 루프 목표의 기록을 읽습니다(작업 기록, 목표 기록과 결정 기록, 실행 승인, 스냅숏, 도구 상태, 워크트리 준비, 요청). 보고서 맨 위의 한 줄 요약은 "왜 멈췄나"의 첫 발견이고, 그 아래 차원마다 발견이 나옵니다: **왜 멈췄나**(목표 상태·멈춤 이유, 마지막 사람 카드와 그 뒤 시간, 마지막 작업자의 실패), **되풀이한 실패와 시도**(작업자 실행을 넘어 같은 실패 근거 수, 되풀이 경고·멈춤, 원인 찾기 가설, 같은 업무의 다시 시도. 설계 단계에서 방법을 낸 실행은 다시 시도로 세지 않습니다), **계획과 수용 기준**(기획 AC와 검토 추적표, 기획 완료 때의 계획 단계 경고, 이 주기 구현에 통과 근거가 없는 계획 단계, 다시 정한 결정·아직 보지 않은 결정, 열린 결함), **빠진 근거**(`--no-proof`·`--no-red`·`--ac-unverified`·`--defect-unverified` 사유, 빨강→초록, 근거 뒤 커밋이 바뀜), **승인 기다린 시간**(사람이 결정한 승인의 기다린 시간 합·가장 긴 것, 아직 열린 승인), **도구별 비용과 시간**(도구가 알린 사용량만, 모르는 실행은 "알 수 없음"으로 따로), **도구가 낸 오류**(실패한 실행의 출력 끝과 JSON-RPC 오류, 도구 상태 기록), **기록 읽기**(깨진 줄, 잘림, 링크). 발견마다 `파일:줄` 인용이 붙고(들여쓴 JSON은 `#/proofs/3` 같은 JSON 포인터까지), 인용이 없는 것은 발견으로 내지 않습니다. 숫자는 기록의 시각과 값으로만 계산하고 옆에 계산 방법을 적습니다. 발견이 없는 차원은 "찾은 것 없음"과 읽은 파일 수를 보입니다.

`--json`은 같은 보고서를 JSON으로, `--since <ISO 시각>`은 그 시각 이후의 기록 줄만 봅니다. 진단은 읽기 전용입니다. 기록을 고치지 않고, AI·네트워크·git을 부르지 않으며, 링크(심볼릭 링크)인 기록은 따라가지 않습니다. 파일마다 20MB·5만 줄까지만 읽고 넘으면 "잘림"으로 알리며, 깨진 줄은 건너뛰고 "읽지 못한 줄"로 알립니다. 출력의 기록 글은 끝 기록의 출력 끝과 같은 규칙으로 비밀값·토큰·홈 폴더·프로젝트 경로·사용자 이름·이메일을 지우지만 빠뜨릴 수 있으니 남에게 보내기 전에 읽어 보세요. 종료 코드는 늘 0이고(진단은 판정이 아닙니다), 목표·작업이 없거나 기록을 읽지 못하면 1입니다. 설치·잠금 점검은 `wax doctor`입니다(8절).

버그 보고에 붙일 것은 **지운 묶음**으로 만듭니다. 두 번에 나눕니다. ① `wax diagnose <ID> --bundle <새 폴더> [--level skeleton|evidence|full] [--keep-email]`이 없는 새 폴더(프로젝트 밖도 됩니다. 프로젝트의 `.wax`·`.git` 안은 받지 않습니다)에 지운 사본을 씁니다: `report.md`·`report.json`(진단 보고서), `records/`(인용한 기록 줄, 프로젝트의 `.wax/` 자리), `README.txt`(무엇이 들었나, 수준, wax·OS·Node 버전, 기록에 나온 도구), `scrub-log.txt`(바꾼 규칙과 횟수, 값은 적지 않음), `files.txt`(파일 목록과 크기). `skeleton`(기본)은 근거 출력·보고 글·단계 문서 본문·승인 명령을 `<omitted>`로 두고, `evidence`는 인용한 줄의 본문(근거 출력, 끝 기록의 출력 끝, 승인 명령)까지, `full`은 이 대상에 든 기록 줄 전체(목표·작업·승인·요청 기록 전체, 같이 쓰는 기록은 이 대상의 줄만)를 넣습니다. 기록 사본은 줄 수와 줄 번호가 원래와 같아서(넣지 않은 줄은 빈 줄) 보고서의 `.wax/…:줄` 인용이 `records/…:줄`에 맞습니다. 비밀값·토큰·홈 폴더·프로젝트 경로·사용자 이름·이메일(`--keep-email`을 주면 남김)은 JSON 값마다 지우고, 이름이 token·key·secret으로 끝나는 칸의 40자 이상 토큰 꼴 값은 `<token>`이 되며, 이름에 secret·token·password가 든 칸은 늘 `<omitted>`입니다. wax가 직접 계산하는 SHA-256 열쇠(승인의 `repeatKey`, 가져오기 전 검사의 `checks.key`)는 비밀값이 아니라서 남깁니다(되풀이가 보이게). `.env` 내용, 스냅숏 객체, 캡처 이미지, 대화형 사용량(`.wax/usage/`)은 어느 수준에서도 넣지 않습니다. 폴더가 이미 있으면 덮어쓰지 않고 거절하고, 링크인 기록은 따라가지 않습니다. 파일은 `0o600`, 폴더는 `0o700`입니다(Windows는 폴더 ACL을 따릅니다). ② 파일을 모두 열어 본(고쳐도 됩니다) 뒤 `wax diagnose --zip <폴더> [--keep-email]`이 폴더를 다시 검사합니다. 지우기 규칙에 맞는 줄이 하나라도 있거나 링크·특수 파일이 있으면 압축하지 않고 위치(`파일:줄 규칙`, 값은 적지 않음)를 적습니다. 다시 검사는 줄 전체를 보므로 칸 이름 바로 뒤의 토큰도 잡습니다. 위 두 열쇠 칸의 64자 소문자 16진수 값만 토큰으로 세지 않습니다. 없으면 `<폴더>.zip`을 새로 씁니다(이미 있으면 거절). 지우기는 빠뜨릴 수 있으니 보내기 전에 꼭 읽어 보세요. 두 명령은 사람이 터미널에서 합니다(wax가 띄운 작업자 `WAX_WORKER=1`은 거절).

대시보드(`/manage`)의 목표 화면과 작업 화면에도 **진단** 버튼이 있습니다. 누르면 같은 보고서를 읽기 전용 칸에 화면 언어로 보이고, 인용을 누르면 그 기록(같은 규칙으로 지운 것)을 펼칩니다. 보고서가 인용한 기록만 열 수 있습니다. 화면은 파일을 쓰지 않으므로 남에게 보낼 묶음은 화면에 보이는 `--bundle` 명령(프로젝트 바로 위의 새 폴더 `../wax-diagnose-<ID>`)으로 터미널에서 만듭니다. 계획 단계는 `wax status`와 같은 판정으로 봅니다: 이 주기 구현에서 그 단계에 붙은 `wax test` 근거(`step` 칸, 그 칸이 없는 옛 근거는 `check`가 같은 단계)가 S 줄의 `check` 명령과 같은 명령(또는 `checks=<ID>`를 모두 덮는 `--checks`)으로 통과했는지입니다. `check: 없음(사유)`과 검사가 없거나 형식 밖인 단계는 세지 않고, 구현에 들어가기 전에는 보지 않습니다.

### 화면 캡처와 시안 비교

화면이 있는 작업은 캡처를 근거로 남깁니다. `wax capture <작업ID> --check <검증 ID> --file <파일> [-- <캡처 명령>]`은 캡처를 `.wax/artifacts/`에 보관하고, 캡처마다 찍은 조건을 라벨로 붙일 수 있습니다.

- `--viewport <너비>x<높이>`: 화면 크기(예: `1280x800`, 각 16384 이하)
- `--scroll top|bottom|<픽셀>`: 스크롤 위치
- `--state <이름>`: 화면 상태. 영문 소문자로 시작하는 32자 이하 이름(예: `default`, `hover`, `focus`, `open`, `loading`, `error`, `empty`)

웹 프로젝트(6-8절)의 설계·검토 안내는 360·768·1280과 시안보다 넓은 1920 폭을 상태별로 찍고, 화면 변화가 스크롤·클릭·호버·시간 중 무엇 때문인지 적게 합니다. 라벨은 PR 설명 초안, `wax trace`, 대시보드 실행 기록 패널에 함께 보입니다.

`wax compare <작업ID> [--json]`은 검토 캡처(`ui-review`)를 폭·스크롤·상태가 모두 같은 설계 캡처(`design-preview`)와 짝지어 보여 줍니다. 기준은 이 프로젝트에서 찍은 설계 캡처뿐입니다. 라벨마다 가장 최근 캡처를 쓰고, 기준은 검토한 주기 이하에서 가장 최근 설계 주기의 캡처를 고릅니다. 짝이 없는 캡처(시안 없음, 다시 캡처하지 않은 시안)와 라벨 없는 예전 캡처는 짝짓지 않고 따로 적으며, 디자인실 인계 미리보기는 라벨 없는 참고로 표시합니다. 두 PNG의 크기가 같으면 서로 다른 픽셀 비율을 보여 주지만 관찰값일 뿐 일치 판정이 아니고, 크기가 다르면 다르다고만 적습니다. 대시보드 실행 기록 패널의 마지막 검토 방문에 두 캡처가 나란히(휴대폰 폭에서는 위아래로) 나오고, PR 설명 초안에도 요약이 들어갑니다. 읽기 전용이며 AI를 부르지 않습니다. 검토 안내는 설계 캡처와 같은 라벨로 찍고 `wax compare`를 읽어 남은 차이를 숨기지 않고 적게 합니다.

### PR 설명 초안

`wax pr-body <작업ID> [--out <파일>] [--json]`은 작업 기록만으로 PR 설명 Markdown 초안을 만듭니다. 제안 PR 제목, 작업 단계와 주기, 저장된 보고 문서, 수용 기준 표, "품질 한눈에"(품질 특성별 근거 수, 결함 기록과 열린 결함, 승인한 프로젝트 매뉴얼의 검사 명령마다 이번 주기에 통과한 근거가 있는지, 전체 보고서 명령), PM 루프 작업자가 있었으면 "단계별 작업자" 표(단계마다 띄운 도구 순서, 완료한 작업자, 실패 뒤 auto 행동. 예: Codex → Claude Code, `switch-unhealthy`), 현재 주기의 테스트·커밋 근거와 화면 캡처, 시안 비교 요약, 근거 없이 완료한 단계의 사유, PM 루프 headless 실행이 있었으면 "사용량(도구가 알린 값)" 절(도구별 합과 알리지 않은 실행 수), 근거 신선도가 들어갑니다. 빠진 기록은 빠졌다고 적고 지어내지 않습니다. 기록 속 `@이름`은 코드 표기로 바꿔 GitHub 알림이 가지 않게 합니다. 표준 출력이나 `--out` 파일에만 쓰고(이미 있는 파일은 덮어쓰며, 디렉터리나 심볼릭 링크는 거절), `gh`나 네트워크를 부르지 않으며 PR을 만들지 않습니다.

**결함 기록:** 검토에서 결함을 찾으면 검토를 완료하지 말고 `wax iterate <작업ID> --reason <사유> --defects-file <파일>`로 구현에 돌아갑니다. 파일은 `[{"title":"<무엇이 잘못됐나>","detail":"<재현 방법과 영향>","ac":"AC-1"}]` 형식의 JSON 배열이며(`detail`·`ac`는 선택), 결함마다 D-1, D-2 … 번호가 붙어 작업 기록에 남습니다. 다음 주기 검토는 열린 결함마다 `--checks-file`에 `{"id":"d-1","status":"pass","proofIds":["<현재 주기 통과 테스트 근거 ID>"]}`를 넣어야 완료됩니다. 재검증은 그 주기에 통과한 테스트 근거로만 인정하고, `fail`이면 완료를 거절합니다. 재검증할 수 없는 결함이 남으면 `--defect-unverified <사유>`로 이유를 남기며, 그 결함은 열린 채로 다음 주기에 다시 확인합니다. 열린 결함은 구현·검토 지시문과 `wax context`에 나옵니다.

**결정 기록:** 작업자가 사람에게 묻지 않고 정한 것(이름, 구조, 의존성, 동작, 테스트, 범위, 수용 기준의 애매한 해석)은 `wax ruling <작업ID> --what <무엇을 정했나> --why <왜> --cost <틀렸다면 드는 비용> [--area naming|structure|dependency|behavior|test|scope|other] [--author <세션 이름>]`으로 남깁니다. 셸 특수 문자를 피하려면 같은 칸을 담은 JSON 파일(`{"what":"…","why":"…","cost":"…","area":"…"}`)을 `--file <파일>`로 줍니다. 결정은 지금 단계·주기에 R-1, R-2 … 번호로 작업 기록에 붙고 주기가 바뀌어도 남습니다. `--phase <단계>`를 주면 지금 단계일 때만 남깁니다. 한도는 작업마다 50개, `what` 200자, `why` 500자, `cost` 300자이고, 끝났거나 보관한 작업에는 남길 수 없습니다. `--area` 없이 `what`에 삭제·`delete`·`drop`·`migration`·`auth`·권한·`secret`·비밀·`skip test`·`AC-`가 있으면 **사람이 정할 일일 수 있음** 표시가 붙습니다(막지는 않음). `wax status <작업ID>`의 `rulingSummary`에 "결정 3개(확인 안 함 2)"와 줄 목록이 나오고, 보고 단계 지시문은 결정 표를 넣어 확인 안 한 결정을 숨기지 말라고 합니다. 결정 기록은 정했다고 알리는 곳이지 정해도 되는 일을 넓히지 않습니다. PM 루프 작업자 지시문은 사람 결정 자리, 보안, 되돌릴 수 없는 일, 범위(AC 빼기·계획에 없는 기능)를 혼자 정하지 말고 막힘으로 보고하라고 고정 목록으로 알립니다.

**결정 확인함·다시 정하기:** 대시보드에서 작업의 **실행 기록**을 열면 위에 **결정 기록** 칸이 나옵니다(확인 안 한 것과 **사람이 정할 일일 수 있음** 표시가 붙은 것이 위). 작업자가 쓴 글은 글자 그대로 보입니다. 결정마다 **확인함**을 누르거나, 틀렸으면 **다시 정하기**를 눌러 무엇이 틀렸고 어떻게 정해야 하는지 메모(필수, 500자 이하)를 적고 **다시 정함 확정**을 누릅니다. 확정하기 전에 결과를 먼저 보여 줍니다. 작업이 검토·보고·끝 단계면 사람의 iterate와 같이 결함(D-N, "결정 다시 정함: …") 하나와 함께 구현으로 돌아가 다음 주기 검토에서 재검증하고, 기획·설계·구현 단계면 단계는 그대로 두고 이번 주기에 결함을 열어 같은 주기 검토에서 재검증합니다(그 단계 문서를 고쳐야 하면 지금 단계에서 다시 하게 하세요). 다시 정한 결정은 더 바꾸지 않고 그 결함으로 고칩니다. 확인함·다시 정하기는 대시보드의 사람만 할 수 있고(작업자·`auto`·`pm-loop` 이름은 거절), CLI·MCP에는 길이 없습니다. 화면을 본 뒤 작업이 바뀌었으면(예: 작업자가 그 사이 완료) 거절하고 화면을 다시 읽습니다. 확인 안 한 결정은 진행을 막지 않습니다. 목표 화면은 작업마다 "결정 3개(확인 안 함 2)"와 **결정 보기** 링크를, PR 초안 카드는 확인 안 한 결정 개수를 보여 줍니다. 품질 보고서(`wax quality-report`)와 PR 초안(`wax pr-body`, 10개까지, 넘으면 개수)에는 **작업자가 정한 것** 표(ID, 단계, 무엇, 왜, 틀리면 드는 비용, 상태)가 인용으로 들어가며 @이름은 알림이 가지 않게 바꿉니다.

**비밀값 점검:** 구현과 검토를 완료할 때 wax는 이 작업에서 더해진 줄과 새 파일을 점검합니다. 기준은 작업을 만들 때의 커밋이며, 그 뒤의 커밋과 아직 커밋하지 않은 변경, 추적하지 않는 새 파일을 봅니다(`.gitignore`가 빼는 파일은 보지 않음). 작업의 워크트리(`.wax/worktrees/<목표>-<n>`) 안에서 완료하면 그 워크트리를 보고, 프로젝트 폴더에서 완료하면 프로젝트와 이 작업에 쓰는 중인 워크트리를 모두 봅니다(워크트리에서 찾은 것은 `.wax/worktrees/<id>/<파일>`로 보이고, 본 워크트리는 완료 기록 `secretScan.worktrees`에 남습니다). 찾는 것은 형식이 확실한 것뿐입니다. AWS·GitHub·Anthropic·OpenAI·Google·xAI·Slack·Stripe 라이브 키, PEM 개인 키 머리글이 있는 줄, 저장소에 들어가려는 `.env`(`.env.example` 등 예시 제외)·개인 키 파일(`.pem`, `.key`, `id_rsa` …), 커밋하거나 올려 둔 `.wax/` 기록입니다. 찾으면 완료를 거절하고 파일·줄·규칙과 값의 앞 4자만 보여 줍니다. 기록에도 값은 남지 않습니다. 이미 커밋하거나 push했다면 키를 폐기하고 새로 발급해야 합니다. 예시·테스트용 값이면 그 줄에 `wax-secrets: allow`를 적고, 파일 전체를 빼려면 `docs/wax/secrets-allow.txt`에 경로를 한 줄씩 적습니다. 둘 다 저장소에 남아 검토에서 보입니다. 미리 확인하려면 `wax secrets <작업ID> [--json]`(찾으면 종료 코드 1)을 씁니다. `WAX_SECRET_SCAN=warn`이면 완료는 하고 경고와 완료 기록(`secretScan`)에만 남기며, `off`면 점검하지 않습니다. Git 저장소가 아니면 점검하지 않습니다. 품질 보고서는 이 결과를 보안성 근거로 셉니다.

**변경 영향:** `wax impact <작업ID> [--json]`은 이 작업에서 바뀐 파일(작업을 만들 때의 커밋 뒤의 커밋, 커밋하지 않은 변경, 새 파일)과 관련된 테스트를 찾아, 현재 주기의 테스트 근거가 그 테스트를 돌렸는지 보여 줍니다. 관련 테스트는 세 가지입니다. 바뀐 테스트 파일 자체, 바뀐 파일을 상대 경로로 `import`·`require`하는 테스트, 이름이 같은 테스트(`pay.mjs` ↔ `pay.test.mjs`)입니다. 근거 명령에 그 테스트 경로가 있거나, 테스트 파일을 하나도 집지 않은 전체 실행(`npm test`, `node --test`, `pytest`, `go test` 등)이면 돌린 것으로 봅니다. 돌리지 않은 관련 테스트, 마지막 실행이 실패한 관련 테스트, 관련 테스트를 찾지 못한 바뀐 소스는 검토 단계 지시문(`wax prompt review`, 대시보드 요청, PM 루프 작업자)과 품질 보고서에 관찰값으로 들어갑니다. 완료를 막지는 않습니다. 이름과 import만 보는 단순한 규칙이라 빠지거나 더 나오는 테스트가 있을 수 있으니, 관련 없으면 검토 문서에 이유를 적습니다.

**의존성 점검:** `wax deps <작업ID> [--json]`은 이 작업에서 바뀐 의존성 선언(`package.json`, `requirements*.txt`)의 더해진·바뀐·빠진 패키지와 바뀐 잠금 파일(`package-lock.json`, `pnpm-lock.yaml`, `poetry.lock`, `go.sum`, `Cargo.lock` 등)을 보여 줍니다. npm 패키지는 설치된 `node_modules`에서 라이선스를 읽고, GPL·AGPL·LGPL·MPL처럼 배포 조건이 붙는 라이선스는 따로 표시합니다. 취약점은 wax가 조회하지 않습니다(네트워크를 쓰지 않음). 대신 의존성이 바뀐 작업의 검토 지시문이 감사 명령을 `wax test <작업ID> --checks sec-deps -- npm audit --omit=dev`처럼 돌려 근거를 남기라고 안내하고, 품질 보고서는 그 근거를 보안성으로 셉니다. 네트워크나 도구가 없으면 미검증으로 보고합니다. 완료를 막지는 않습니다.

`wax quality-report <작업ID> [--out <파일>] [--json]`은 작업 기록만으로 품질 보고서 Markdown을 만듭니다. ISO/IEC 25010 품질 특성(기능 적합성, 성능 효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성)별 근거, 필수 검증, 수용 기준, 결함 기록, 주기별 테스트 근거, 시안 비교, 미검증·근거 없이 완료한 사유, 근거 신선도가 들어갑니다. 수용 기준과 runtime·integration 필수 검증은 기능 적합성, visual·preview 필수 검증은 사용성으로 셉니다. 다른 특성은 `wax test --checks`의 ID가 `func-`·`perf-`·`compat-`·`ux-`·`a11y-`·`rel-`·`sec-`·`maint-`·`port-`로 시작할 때만 셉니다(예: `--checks perf-checkout`). 근거가 없는 특성은 "근거 없음"으로 둡니다. 자체 보고서이며 공인 시험성적서가 아닙니다. 읽기만 하고 AI나 네트워크를 부르지 않습니다.

보고 단계 안내는 보고를 완료한 뒤 이 초안을 만들지 제안하고, `gh pr create --draft --body-file <파일>`은 사용자가 승인할 때만 실행하게 합니다. PR 만들기·push·병합은 늘 사람이 정합니다. PM 루프(6-6절)도 보고가 끝난 작업에 초안 파일 카드만 내고 PR 결정은 사람에게 남깁니다.

**인증 안내(2026-10-20 확인):** 2026-06-18부터 개인 Google 로그인에 포함되던 Gemini CLI 이용이 종료됐으며 무료·Google AI Pro·Ultra 모두 해당합니다. 계속 이용하려면 지원되는 API 인증 또는 기존 Gemini Code Assist Standard·Enterprise 라이선스가 필요합니다. Google 전환 공지는 유료 API 키 이용을 명시하고 개인 사용자에게 Antigravity CLI 이전을 안내합니다. Standard·Enterprise 신규 구독 판매도 2026-10-09 중단됐고 기존 구독은 계약과 별도 종료 일정에 따릅니다. wax 설치는 AI 이용 권한을 제공하지 않습니다. [개인 계정 종료 안내](https://developers.google.com/gemini-code-assist/docs/deprecations/code-assist-individuals) · [API·Antigravity 전환 안내](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/) · [기업 구독 일정](https://docs.cloud.google.com/gemini/docs/codeassist/sunset)

## 5-1. Codex에서 사용

터미널에서 공개 마켓플레이스를 한 번 등록하고 설치합니다. Codex용 목록은 `.agents/plugins/marketplace.json`에 있으며 ZIP에도 포함됩니다.

```sh
codex plugin marketplace add cafein-network/wax
codex plugin add wax@wax
```

`already added from a different source`가 나오면 먼저 `codex plugin marketplace list`로 이전 ZIP 경로나 Git 주소를 확인합니다. 공개 저장소로 전환하려면 아래 명령을 한 줄씩 실행하고, 앞 명령이 성공했을 때만 다음으로 넘어갑니다. 마켓플레이스 등록 제거는 작업 프로젝트의 소스나 `.wax` 기록을 삭제하지 않습니다.

```sh
codex plugin marketplace remove wax
codex plugin marketplace add cafein-network/wax
codex plugin add wax@wax
```

등록 출처가 이미 공개 GitHub 저장소인데 `plugin wax was not found in marketplace wax`가 나오면 `codex plugin marketplace upgrade wax`로 갱신한 뒤 `codex plugin list --marketplace wax --available --json`에서 `wax@wax`를 확인하고 다시 설치합니다. ZIP 출처라면 새 ZIP을 같은 경로에 풉니다. 여전히 목록에 없으면 `codex --version`, 마켓플레이스 목록과 플러그인 목록 결과를 함께 확인하세요. 설치 뒤에는 새 Codex 세션을 시작합니다. 자세한 내용은 [설치 안내](../INSTALL.md)의 오류 해결 절을 참고하세요.

특정 프로젝트에만 연결하려면 다음 프로젝트 연결기를 사용합니다. Antigravity CLI(5-2절)·Grok Build(5-4절)도 같은 연결기를 씁니다. 압축을 푼 원본은 계속 같은 위치에 두세요.

```sh
node "/path/to/wax/scripts/install-project.mjs" --project "/path/to/my-app"
node "/path/to/wax/scripts/install-project.mjs" --project "/path/to/my-app" --check
cd /path/to/my-app
codex
```

Codex의 `/skills`에서 13개 스킬을 확인하고 대화창에서 사용합니다. `$`는 스킬 호출, `@`는 파일 첨부입니다. 배정받은 일은 `$wax:work <업무ID>`로 실행하며, wax 팀 채널의 `@이름` 알림과 구분하세요. 다음 예시는 셸 터미널 명령이 아닙니다.

```text
$wax:init
$wax:plan email-login 이메일 로그인 구현
$wax:design email-login
$wax:implement email-login
$wax:review email-login
$wax:report email-login
$wax:status email-login
$wax:iterate email-login 만료 토큰 처리 개선
```

연결기는 프로젝트의 `.agents/skills/wax-*`(Codex·Antigravity CLI·GitHub Copilot CLI)와 `.grok/skills/wax-*`(Grok Build)에 같은 원본 스킬을 연결합니다. 한 위치라도 같은 이름의 다른 스킬이 있으면 어디에도 쓰지 않고 멈춥니다. 기존 다른 스킬이나 도구 설정을 덮어쓰지 않으며 같은 연결을 반복해도 됩니다. Windows는 디렉터리 junction, Linux·WSL은 심볼릭 링크를 사용합니다. 원본 경로가 바뀌면 설치 확인이 실패하므로 기존 링크를 확인한 뒤 다시 연결하세요. 새 스킬이 보이지 않으면 Codex를 재시작합니다.

현재 단계의 문서·완료 근거와 `.wax/features` 기록은 다른 호스트와 공유합니다. Codex 자체의 로그인·도구 권한을 사용합니다.

## 5-2. Antigravity CLI에서 사용

Antigravity CLI(`agy`)는 프로젝트의 `.agents/skills`에서 스킬을 읽으므로 5-1절의 프로젝트 연결기를 그대로 사용합니다. Codex용으로 이미 연결했다면 추가 설치가 필요 없습니다. 개인 Google 계정으로 쓰던 Gemini CLI 사용자도 이 방법으로 옮겨 오면 됩니다.

```sh
node "/path/to/wax/scripts/install-project.mjs" --project "/path/to/my-app" --check
cd /path/to/my-app
agy
```

새 세션의 `/skills`에서 13개 스킬을 확인합니다. Antigravity CLI는 스킬을 슬래시 명령으로 바꾸므로 `/plan email-login 이메일 로그인 구현`, `/design email-login`처럼 스킬 이름으로 호출합니다. 실제 표시 이름은 `/skills` 목록을 따르며, 이름이 겹치면 "wax plan 단계를 실행해줘"처럼 요청할 수 있습니다. 시작 명령 `/init`이 Antigravity CLI 자체 명령과 겹치면 "wax init 스킬로 시작해줘"처럼 요청하세요.

`agy plugin install`이나 `agy plugin import gemini`는 파일을 다른 위치로 복사·변환하므로 스킬이 함께 제공되는 CLI를 찾지 못할 수 있습니다. 프로젝트 연결 방식을 사용하세요. 실제 Antigravity CLI 세션 실행은 아직 검증하지 않았습니다.

## 5-3. GitHub Copilot CLI에서 사용

GitHub Copilot CLI(`copilot`)에는 한 번만 설치합니다. Microsoft Copilot이 아니라 GitHub Copilot 구독으로 쓰는 터미널 도구입니다. 압축을 푼 wax 폴더를 로컬 마켓플레이스로 등록하면 모든 프로젝트에서 wax 스킬을 씁니다.

```sh
copilot plugin marketplace add "/path/to/wax"
copilot plugin install wax@wax
```

로컬 마켓플레이스는 폴더를 복사하지 않고 바로 읽습니다. 새 버전은 같은 경로의 폴더 내용을 바꾸면 다음 세션부터 적용됩니다. 처음에는 "wax init 스킬로 시작해줘"로 시작합니다. 스킬은 "wax plan 스킬로 email-login 이메일 로그인 기획해줘", "wax design 스킬로 email-login 설계해줘"처럼 이름을 밝혀 요청합니다(`/status` 같은 GitHub Copilot CLI 자체 명령과 이름이 겹치기 때문). 팀 채널에서 세션 종류는 `copilot`, 기본 이름은 `copilot-<폴더 이름>`입니다.

프로젝트에 `.agents/skills`(5-1절)를 연결해 둔 경우에도 충돌하지 않습니다. 같은 이름의 스킬은 프로젝트 쪽이 우선하고 한 벌만 보입니다.

## 5-4. Grok Build에서 사용

Grok Build(`grok`)는 xAI의 터미널 코딩 도구로, 공식 프로젝트 스킬 위치인 `.grok/skills`를 읽습니다. 5-1절의 프로젝트 연결기가 이 위치에도 연결하므로 같은 명령을 실행한 뒤 시작합니다.

```sh
node "/path/to/wax/scripts/install-project.mjs" --project "/path/to/my-app" --check
cd /path/to/my-app
grok
```

새 세션의 `/skills`에서 13개 스킬을 확인합니다. Grok Build에는 `/plan`(플랜 모드)·`/code-review` 같은 자체 명령이 있으므로 GitHub Copilot CLI처럼 "wax init 스킬로 시작해줘", "wax plan 스킬로 email-login 이메일 로그인 기획해줘"처럼 스킬 이름을 밝혀 요청합니다. 팀 채널에서 세션 종류는 `grok`, 기본 이름은 `grok-<폴더 이름>`입니다. Grok Build는 Claude Code 플러그인도 읽으므로 Claude Code에 wax를 설치했다면 연결 없이 보일 수 있으며, 같은 이름의 스킬은 우선순위가 높은 위치 하나만 쓰입니다. 대시보드 첫 화면의 자동 진행 도구에는 아직 Grok Build가 없습니다. 실제 Grok Build 세션 실행은 아직 검증하지 않았습니다.

## 6. 팀 대시보드: AI 세션 협업과 일일 업무보고

대시보드는 어느 코딩 도구의 세션이든 한 화면에서 같은 방식으로 보여 줍니다. 팀 패널의 각 세션에는 **다음 명령**이 그 도구의 문법으로 나옵니다. 배정된 업무가 있으면 work, 없으면 맡은 작업의 현재 단계, 맡은 작업이 끝났으면 status이며, 복사 버튼으로 그 세션에 그대로 붙여 넣을 수 있습니다. 업무 배정 폼에서 담당 세션을 고르면 그 세션이 실행할 명령을 미리 보여 주고, 가상 사무실에서 캐릭터를 눌러도 같은 다음 명령이 나옵니다. 도움말(`/help`)의 "도구별로 부르는 방법" 표에 모든 명령이 정리되어 있습니다.

세션은 참여할 때 `wax chat join --model <모델>`로 자기 모델을 밝힐 수 있습니다(같은 도구에서도 모델을 바꿀 수 있기 때문). 대시보드와 인사기록 카드에 "도구 · 모델"로 표시되며, 세션이 스스로 밝힌 값입니다.

여러 코딩 도구 세션(Claude Code·Codex·Antigravity CLI·GitHub Copilot CLI·Grok Build·Gemini CLI)이 같은 프로젝트에서 일할 때, 각 세션의 AI가 **팀원**으로 참여합니다. 대화·업무 배정·일일 보고는 프로젝트의 `.wax/chat/`에 저장되고, 로컬 대시보드에서 실시간으로 확인합니다. 상세 기록과 팀 채널은 기록을 보여 줍니다. 요청과 보고 화면(`/start`)에서 사용자가 요청을 보내면 선택한 CLI의 별도 세션이 작업합니다. 가상 사무실의 안내 NPC(진행 소식을 전하는 제이크, 도움말·사무실을 안내하는 써니, 디자인실 제작 순서를 안내하는 제니)는 프로젝트 기록과 현재 시각으로 말합니다. 리나의 도구 소식은 서버가 공식 공개 릴리스를 소스마다 1시간 간격으로 확인합니다. 프로젝트·설치 버전·세션 정보는 보내지 않으며, 조회 실패 시 마지막 자료를 유지하고 실패한 소스만 5분부터 최대 1시간까지 간격을 늘려 다시 시도합니다. 호출 한도 응답의 대기 시간을 따르고 수동 새로고침은 1분에 한 번으로 제한합니다. `WAX_TOOL_NEWS=off`로 외부 조회를 끌 수 있습니다. NPC 안내와 캐릭터 잡담은 화면 연출이라 기록되지 않습니다. 자세한 내용은 대시보드의 **도움말**(`/help`)을 보세요.

### 대시보드 열기

```sh
node "/path/to/wax/bin/wax.mjs" --project "/path/to/my-app" dashboard
```

`http://127.0.0.1:4330/`을 엽니다(`--port`나 `WAX_DASHBOARD_PORT`로 변경). AI 세션에서는 `/wax:init`(Codex `$wax:init`, Antigravity `/init`)이 대시보드를 바로 열어 줍니다. 첫 화면은 팀 채널이고, **＋ 새 요청**을 누르면 요청과 보고 화면(`/start`)의 시작 가이드가 열립니다. 0.13.5까지의 `/?mode=…`·`/?request=…` 주소는 `/start`로 이어집니다. 따로 대시보드 명령은 없고, 나중에 다시 열 때도 init을 실행합니다. 이미 켜져 있으면 주소만 알려 주고, 꺼져 있으면 세션이 백그라운드로 실행하거나 따로 실행할 명령을 안내합니다. `dashboard --status`로 실행 여부만 확인할 수 있습니다. 화면 사용법은 대시보드 상단의 **도움말**(`/help`)에 정리되어 있습니다. 서버는 이 컴퓨터(127.0.0.1)에서만 열립니다. 웹에서 쓰는 사람 이름은 `WAX_CHAT_USER`로 정합니다(기본 "대표"). 화면 언어는 오른쪽 위의 언어 선택(한국어·English)으로 바꾸며 이 브라우저에 기억됩니다. 처음에는 브라우저 언어가 한국어면 한국어, 아니면 영어로 열리고 주소에 `?lang=ko`·`?lang=en`을 붙여 정할 수도 있습니다. 화면 문구만 바뀌고 메시지·문서·보고서처럼 사람과 AI가 쓴 내용은 쓴 그대로 보여 줍니다.

### 브라우저 알림

팀 채널·요청과 보고·상세 기록 화면 위쪽의 **알림 켜기**를 누르면 브라우저가 알림 권한을 묻습니다(페이지를 열 때는 묻지 않음). 그 뒤 탭을 보고 있지 않을 때 다음 일을 브라우저 알림으로 받습니다.

- AI 세션의 질문
- 새 실행 승인 요청
- 작업 단계 완료
- 새 트리거 제안과 알림만 하는 트리거(6-5절)
- 사람이 결정할 PM 루프 카드와 PM 루프 정지(6-6절). auto가 카드 없이 처리하는 행동은 알리지 않습니다.

알림을 누르면 그 탭으로 돌아와 해당 메시지·승인·작업을 엽니다. 탭을 보고 있는 동안, 내가 쓴 글, 화면을 열거나 다시 연결하기 전부터 있던 기록은 알리지 않고, 같은 일은 한 번만 알립니다. 가려진 동안 쌓인 수는 탭 제목 앞에 `(2)`처럼 붙고 탭을 다시 보면 사라집니다. 켜고 끈 선택은 이 브라우저에만 저장되며, 브라우저가 알림을 막았거나 지원하지 않으면 버튼에 **알림 차단됨**·**알림 미지원**으로 표시됩니다. 막혔다면 주소창의 사이트 설정에서 알림을 허용한 뒤 새로고침하세요. 대시보드 탭이 열려 있어야 알림이 옵니다.

### 화면 구성

| 화면 | 내용 |
| --- | --- |
| `/`·`/chat` 팀 채널 | 작업별 채널과 전체 채널(general)의 대화, 받는 사람 지정, 작업 탭. 대표도 글을 쓸 수 있습니다 |
| `/start` 요청과 보고 | 시작 가이드, 한 줄 요청과 기획부터 결과 보고까지 자동 진행(6-3절), 질문 답변, 중지·재개, 트리거 제안 카드(6-5절) |
| `/manage` 상세 기록 | 오늘의 숫자, 실행 기록, PM 루프(6-6절), 가상 사무실 패널, 타임라인(단계·근거·대화·업무·보고), 먼저 확인할 일, 팀 상태와 "지금 하는 일", 업무 배정, 작업 진행과 단계별 소요 시간, 최근 결정, 프로젝트 규칙·위키(6-7절), 미해결 질문, 일일 업무보고, 트리거(6-5절) |
| `/office` 가상 사무실 | 캐릭터를 누르면 인사기록 카드가 열립니다. 정면 얼굴과 부서 팀장·팀원(직급 없이 프로젝트 이름이 부서명, PM이 팀장), 레벨, 기획·설계·구현·검토·테스트·소통·보고 여섯 능력치 육각형, 버그 발생률(내 작업 중 실패한 테스트 비율)·버그 발견(검토 중 실패한 테스트)·커밋·작업 시간(업무 수락→완료), 달성 배지를 보여 줍니다. 모두 기록으로 계산하며(테스트·커밋은 `wax test`·`wax evidence`에 붙인 `--author` 이름에, 이름이 없으면 그 시각 같은 작업·단계의 업무를 수락한 담당자에게 돌림), 기록이 없으면 보통(50)에서 시작합니다. AI 세션의 직급은 기록으로 쌓은 레벨에 따라 사원 → 주임 → 대리 → 과장 → 차장 → 부장으로 오르고, 사람은 AI 팀에 일을 맡기는 쪽이라 레벨과 상관없이 대표로 표시합니다. 이 프로젝트의 PM은 직급과 별도로 직책 팀장(PM)이 함께 붙습니다. 위쪽의 **스킬 지도**는 사원 × 분야(단계·검증 종류·코드 영역) 격자로 누가 어떤 일을 실제로 해 봤는지, 아무도 기록이 없는 빈 분야와 한 명만 해 본 분야가 어디인지 보여 줍니다. 칸의 숫자는 완료한 업무·통과한 검증·연결한 커밋 수이고(실패한 검증은 ✕로 따로 표시), 코드 영역은 커밋이 고친 파일 경로로 나눕니다. 휴대폰에서는 화면 전체로 열리고 표만 가로로 밀어 보며 사원 이름 열은 고정됩니다. CLI는 `wax chat skills`이고, PM은 배정 전에 이 지도를 봅니다. 인사기록 카드의 **작업노트** 탭은 그 사원이 최근 7일 동안 날마다 한 일(배정·시작·완료·막힌 업무, 통과·실패 테스트, 커밋과 고친 영역, 메시지·화이트보드 노트, 보고서, 메모)을 기록에서 그대로 모아 날짜별로 접어 보여 주고, 지금 맡은 업무와 마지막 메모를 위에 둡니다. ### 대시보드에서 기록 확인하기

상단 통계 카드를 누르면 관련 작업·업무·타임라인으로 이동합니다. **먼저 확인할 일**은 현재 막힌 업무, 선택한 날짜의 실패한 테스트 근거, 오래된 미해결 질문 순으로 표시합니다. 같은 작업·단계의 이후 통과 기록이 있으면 이전 실패는 이 목록에서 빠지고 타임라인에는 남습니다. 실패 기록만으로 현재 작업 전체가 실패했다고 판단하지 마세요.

**원문 보기**는 요약에서 생략된 질문·결정의 전체 본문을, **실행 근거 보기**는 저장된 실제 명령·종료 코드·출력을 기존 문서 창에서 보여 줍니다. 버튼을 눌러도 명령을 다시 실행하지 않습니다. 최근 결정과 테스트 근거는 선택한 날짜 기준이며, 업무와 미해결 질문은 현재 전체 기록 기준입니다.

**실행 기록.** **작업 진행**의 각 작업 옆 **실행 기록**을 누르거나 `/manage?feature=<작업ID>`로 열면, 작업이 단계를 지나간 과정을 단계 방문마다 세로 타임라인으로 보여 줍니다. 방문마다 시작·끝·걸린 시간(단계별 소요 시간과 같은 계산), 결과(단계 완료·구현으로 되돌림과 그 이유·진행 중, 요청이 연결되어 있으면 질문·막힘), 완료한 세션과 실행 도구, 그때의 커밋, 완료 근거와 사유, 연결한 테스트·커밋 근거와 기록 이후 바뀐 파일, 검토의 수용 기준 결과, 앞 방문 끝 커밋과 이번 방문 끝 커밋 사이에 바뀐 파일(커밋 기준)이 펼쳐집니다. 되돌린 반복은 같은 단계를 다시 방문한 줄로 보입니다. **Markdown 내려받기**는 같은 내용을 PR 설명 초안과 같은 규칙(@이름·HTML 무력화)으로 내려받고, CLI에서는 `wax trace <id>`(Markdown)나 `wax trace <id> --json`으로 봅니다. 읽기 전용이며 AI를 부르지 않습니다. 단계를 완료하거나 되돌릴 때 이력에 그때의 커밋(`head`), 커밋 안 된 변경 여부(`dirty`, `.wax/` 제외), 아는 경우 실행 도구(`tool`, 대시보드 자동 진행)가 함께 남으며, Git이 없거나 이 기능 이전의 기록은 해당 칸을 비워 둡니다. PM 루프 headless 작업자가 일한 방문에는 **사용량(도구가 알린 값)**이 도구별로 나오고, 사용량을 알리지 않은 실행 수도 함께 나옵니다. 작업자 실행마다 **이 실행이 바꾼 파일(커밋 안 된 변경 포함)**과 diff, 사람만 하는 **이 실행 전으로 되돌리기**도 나옵니다(6-6절 "실행별 파일 스냅숏과 되돌리기"). 대화형 세션의 토큰·비용은 Claude Code 사용량 기록과 단계 방문을 맞출 세션 기록이 없어 보여 주지 않습니다.

날짜를 빠르게 바꿔도 마지막으로 선택한 날짜의 응답만 적용됩니다. 갱신 실패 시 마지막 성공 기록과 재시도 버튼을 유지합니다. 재연결 시 세션 정보를 다시 읽으며, 입력 중인 배정 내용과 새 작업 정보는 배경 갱신으로 지우지 않습니다.

### 세션끼리 대화하기

처음 한 세션은 `/wax:init`으로 시작하고, 다른 AI 세션은 `/wax:join`(Codex `$wax:join`, Antigravity `/join`, GitHub Copilot CLI·Grok Build "wax join 스킬로 참여해줘")으로 참여합니다. init이나 join을 건너뛰어도 세션에서 처음 실행한 wax 명령이 자동으로 참여시킵니다. 같은 이름이 이미 활동 중이면(같은 폴더에서 같은 도구 세션을 둘 이상 띄운 경우) `claude-my-app-2`처럼 번호를 붙여 참여하고 그 이름을 알려 줍니다. init을 여러 번 해서 지난 세션이 이름을 잡고 있으면 `/wax:init --reset`(join도 같음)으로 지난 세션을 정리한 뒤 기본 이름으로 참여합니다. 듣는 중이거나 작업 중인 세션은 남기며, PM·업무는 이름에 남아 그 이름으로 참여한 새 세션이 이어받습니다. 참여한 세션은 wax 단계 명령을 실행할 때 단계를 시작하면 상태를 "작업 중"으로 바꾸고 그 작업 채널의 최근 메시지를 읽습니다. 단계를 마치면 맡은 업무의 상태(완료·막힘)에 결과를 기록합니다. 참여자 이름은 기본적으로 `도구-폴더이름`(예: `my-app` 폴더의 Claude 세션은 `claude-my-app`)입니다. 폴더 이름에서 영문·한글 등 글자·숫자·공백·`_`·`.`·`-`가 아닌 문자는 `-`로 바꾸고 40자 안으로 줄입니다. 같은 도구의 세션을 여러 개 쓰거나 이름을 바꾸려면 아무 wax 명령에나 `--name <이름>`을 붙입니다(예: `/wax:join --name claude-front`). 그 세션은 이후 명령에서도 그 이름을 쓰고, 바로 채널에 참여합니다. 이전 이름으로 참여한 적이 있으면 그 이름은 "자리 비움"으로 바뀝니다. 이름은 세션 대화 안에서만 기억하므로 새 세션에서는 다시 지정합니다.

맡을 작업도 함께 정할 수 있습니다. `/wax:join --name claude-front --feature chatbot`(`--project=chatbot`도 같음)처럼 실행하면 그 세션이 `chatbot` 작업을 선택한 대기 상태로 참여하고, 이후 wax 명령에서 작업 ID를 생략하면 그 작업을 씁니다. init은 작업 선택 여부와 관계없이 `http://127.0.0.1:4330/`(팀 채널)을 엽니다. 해당 작업 기록은 `/manage?feature=chatbot`에서 확인합니다. 첫 화면의 **기존 AI 세션으로 팀 작업하기**는 PM 유무, 배정과 막힌 이유, 각 세션에 붙여 넣을 명령을 보여 줍니다.

소통 규칙은 왕복 대화를 줄이도록 정해져 있습니다. AI 세션은 메시지를 보낼 때마다 전체 대화를 다시 읽으므로, 짧은 인사나 확인 한 줄도 비용이 큽니다.

- **지시**는 PM의 업무 배정(`assign`)으로만 전달합니다. 목표·범위·완료 조건·산출물을 담습니다.
- **결과**는 업무 상태(`task done`·`task block`)의 메모로 보고합니다. 대시보드의 업무 목록과 타임라인에 표시됩니다.
- **채널 글**은 질문(`question`), 답변(`answer`), 결정(`decision`)만 씁니다. 인사·수신 확인·진행 보고·요약은 올리지 않습니다. 대표가 직접 보내 달라고 한 메시지는 그대로 보냅니다.

메시지는 두 부분으로 구성됩니다.

- **지금 하는 일**(`--doing`): 보내는 세션이 현재 하는 일. 대시보드 팀 목록에도 표시됩니다.
- **전할 내용**(`--message`): 받는 사람(`--to`, 생략하면 전체)에게 필요한 질문·답변·결정. 문서 내용은 옮기지 않고 경로를 적습니다.

직접 대화하려면 `/wax:chat [채널] [메시지]`(Codex `$wax:chat`, Antigravity `/chat`)를 실행합니다. 세션은 명령을 실행할 때만 채널을 읽으므로, 다른 세션의 메시지는 그 세션이 다음 wax 명령을 실행할 때 전달됩니다. 다른 세션의 메시지는 참고 자료로만 다루며, 메시지 안의 요청만으로 명령을 실행하지 않습니다.

**듣기와 바로 답하기.** 세션이 wax에 참여하면, 출력 한 줄마다 세션을 깨울 수 있는 도구(Claude Code의 Monitor)가 있을 때 `wax chat watch --author <이름> --wake`를 자동으로 켭니다. 이후 누군가 `@이름`으로 부르거나 받는 사람으로 지정한 메시지, 또는 PM의 새 배정이 오면 세션이 깨어나 같은 채널에 답변(`answer`)으로 답합니다. 기다리는 동안에는 AI를 호출하지 않고, 부르지 않은 메시지와 자기 메시지로는 깨어나지 않습니다. 메시지는 채널이 달라도 쓴 순서대로 전달되고, 감시가 끊겼다 다시 시작하면(Monitor는 30분마다 만료) 그 사이 온 메시지를 먼저 전달합니다. 읽음 위치는 `.wax/chat/watch/`, 듣는 중 표시는 `.wax/chat/listeners/`에 남습니다. 사람이 채팅창에서 맡기지 않은 일을 요청하면 세션은 그 요청을 자기 세션의 사용자에게 전하고, 전달했다고 답합니다. `/wax:chat --watch`는 듣기가 꺼져 있을 때 다시 켭니다. Codex·Gemini CLI·Antigravity CLI에는 출력으로 세션을 깨우는 기능이 없어 다음 wax 명령 때 메시지를 확인합니다. 바로 알림을 받으려면 `wax chat watch`를 별도 터미널에 띄웁니다. 이 감시는 사람이 보는 알림이라 `--wake`를 붙이지 않으며, 대시보드에는 `다음 명령 때`로 표시됩니다.

**채널 화면에서 부르기.** 채널 화면(`/chat`) 입력창 위에 참여한 AI 세션이 **받는 사람** 버튼으로 나옵니다. 버튼에는 `바로 답함`(듣는 중), `다음 명령 때`, `자리 비움`이 표시됩니다. 받는 사람을 고르거나 `@이름`으로 부르고 보내면, 누가 곧 답하고 누가 나중에 확인하는지 안내가 나옵니다. 받는 사람이 없으면 기록만 남고 AI 세션은 깨어나지 않습니다. 메시지마다 있는 **답장**을 누르면 그 메시지에 이어서 답하고, 질문이면 유형이 답변으로 바뀝니다.

**입력창 자동완성.** 입력창에서 `@`를 치면 참여한 세션, `/`를 치면 wax 명령, `#`을 치면 작업이 목록으로 나옵니다. 화살표로 고르고 Enter나 Tab으로 넣으며, Esc로 닫습니다. `@이름`을 고르면 그 세션이 받는 사람으로도 선택됩니다. `/명령`은 받는 사람이 한 명이면 그 도구의 문법(Claude Code `/wax:review`, Codex `$wax:review` 등)으로, 아니면 `wax review`로 넣고, 작업 스레드나 작업 채널에서는 작업 ID도 채웁니다.

**작업 탭.** 채널 왼쪽의 **작업** 탭은 요청·업무 배정·이어진 대화·실행 승인을 **답변 필요 · 진행 중 · 완료**로 나눠 오늘·어제·지난 7일·지난 30일·이전으로 묶어 보여 줍니다. 위의 **작업 찾기**는 모든 상태에서 제목·내용·담당·ID를 찾습니다. 별 버튼으로 고정한 작업은 상태와 상관없이 맨 위에 남으며, 고정은 이 브라우저에만 저장됩니다. AI가 질문으로 멈춘 요청은 **답변 필요**에 들어갑니다. 요청을 열면 대화가 단계별(SM은 접수·분석 → 영향 확인 → 수정 → 회귀 검증 → 처리 보고)로 접혀 지금 단계(끝났으면 마지막 단계)만 펼쳐지고, 단계 머리글에 실행 기록 수와 테스트 통과 수, 커밋 수가 나옵니다. 그 단계에서 기록한 테스트·커밋 근거는 카드로 보이며, 누르면 상세 기록에서 실제 출력을 확인합니다. 근거를 남긴 뒤 바뀐 파일이 있으면 카드에 "이후 바뀐 파일 N개"가 붙습니다(관찰 기록).

**Claude Code 세션끼리 직접 알림.** Claude Code는 같은 컴퓨터의 다른 Claude Code 세션에 직접 메시지를 보낼 수 있습니다. 참여할 때 자기 세션 이름을 `--peer`로 남기고(`wax chat who`에 `세션 <이름>`으로 표시), 다른 Claude 세션을 받는 사람으로 지정해 글을 쓰면 그 세션에 `wax: #<채널> <메시지 ID> from <이름>` 형식의 위치 알림만 보냅니다. 내용은 채널 기록에만 있으므로, 알림을 받은 세션은 채널에서 그 메시지를 읽어 처리하고 이미 처리한 메시지면 무시합니다. 이 기능을 쓸 수 없으면 건너뛰며, 메시지는 채널과 듣기로 그대로 전달됩니다.

### 세션 이름과 재참여

`wax chat join --author <이름> --session <ID> --json`이 돌려준 `session`을 보관하고, 참여한 이름의 모든 상태 변경·게시·보고·업무 변경에 `--session <ID>`를 함께 넘깁니다. 409 오류가 나면 같은 세션 ID로 다시 join하고 반환된 이름을 사용하세요. PM·업무 담당 역할은 이름에 남고, 24시간 활동이 없는 이름은 다음 세션이 넘겨받습니다. 이전 버전의 토큰 없는 기록은 join할 때 인계됩니다. join 없이 직접 사용하는 CLI 기록은 별도로 식별되며, 세션이 이름을 인계받으면 토큰 없이 그 이름에 쓸 수 없습니다.

### 세션 상태 자동 표시

Claude Code 세션은 플러그인 훅이 차례 상태를 알아서 남깁니다. 세션이 `chat presence`로 알리지 않아도 대시보드가 다음을 압니다.

| 자동 상태 | 뜻 |
|---|---|
| 작업 중 | 프롬프트를 받았거나 도구를 쓰는 중 |
| 사람 기다림 | 실행 승인이나 질문의 답을 기다림 |
| 끝남(안 봄) | 차례를 끝냈고 아직 아무도 보지 않음 |
| 쉬는 중 | 끝난 차례를 사람이 봤거나 새 세션 |
| 소식 없음 | 작업 중·사람 기다림인데 20분 넘게 훅이 없음 |

- **이어지는 방법:** 훅이 세션을 시작할 때 `WAX_HOST_SESSION`을 그 세션의 명령 환경에 넣고, `wax chat join`이 이 값으로 참여 기록과 잇습니다. 이 환경을 쓸 수 없는 Claude Code에서는 세션 문맥에 알려 준 ID를 `--host-session <ID>`로 넘깁니다. 이어지면 `join`이 "세션 상태 훅과 이어졌습니다"라고 알려 줍니다.
- **보는 곳:** 팀 채널 맨 위의 **나를 기다리는 세션**(사람 기다림 먼저, 끝남(안 봄) 다음), 사무실 이름표의 표시(사람 기다림은 `?`, 끝남은 점), 브라우저 알림(같은 보고는 한 번), `wax chat who`의 자동 상태 칸. 목록에서 **열어 보기**를 누르거나 사무실 캐릭터를 열거나 그 세션에게 메시지를 보내면 끝난 차례를 본 것으로 남깁니다.
- **동료 기다리기:** `wax chat wait <이름> [--until done|blocked|idle] [--timeout <초>]`는 이 명령 뒤에 그 세션이 끝나거나 사람을 기다리거나 쉬게 될 때까지 기다립니다. 이미 끝나 있던 차례는 세지 않습니다. 기본은 `done`, 600초이고, 그동안 못 보면 종료 코드 1입니다.
- **이어진 세션의 자리 비움:** 10분 무응답 규칙 대신, 세션이 끝났거나(`SessionEnd`) 2시간 넘게 훅이 없을 때 자리 비움으로 봅니다.
- **남기는 것:** `.wax/chat/host/<세션 해시>.json`에 상태·훅 이름·알림 종류·승인 요청의 도구 이름과 시각만 남깁니다. 프롬프트, 메시지, 도구 입력은 남기지 않습니다. 기록은 `.wax`가 있는 프로젝트에만 쓰고, 하루 넘게 소식 없는 기록과 200개를 넘는 오래된 기록은 지웁니다.
- **범위:** Claude Code 대화형 세션만입니다. Codex는 훅을 켜려면 사용자 설정을 고쳐야 해서 넣지 않았고, 다른 도구는 플러그인으로 붙일 수 있는 상태 훅을 확인하지 못했습니다. 이런 세션은 `who`에 "자동 상태 없음"으로 나옵니다. 대시보드가 띄운 headless 실행(요청 자동 진행, PM 루프 작업자)은 기록하지 않고, 요청·PM 루프 화면에서 상태를 봅니다.
- **끄기:** `WAX_HOST_STATE=off`로 Claude Code를 시작하면 훅이 아무것도 하지 않습니다.

### PM과 업무 분담

사람은 **대표** 한 명이며, 대표가 지시하고 최종 결정하며, PM은 조언하고 선택지를 내고, 결정된 대로 지시(배정)하고, 진행·지연을 대표에게 보고합니다.

1. 업무를 나눌 세션에서 `/wax:pm <지시나 목표>`를 실행합니다. PM이 목표·현재 작업·참여자를 확인하고 통상적인 범위와 담당을 정해, 같은 호출에서 작업 생성과 현재 단계 배정까지 진행합니다. 이미 배정된 업무는 재사용합니다. 대표가 선택지를 요청했거나 필수 요구사항·명시적 지시 충돌 때문에 배정할 수 없을 때만 구체적으로 질문합니다. 목표가 없고 기록도 없으면 원하는 결과를 한 번 묻습니다. “범위와 담당이 결정되면 배정하겠습니다” 같은 약속만으로 끝내지 않습니다.
2. PM은 적용한 범위·담당을 간단히 기록하고 실제 기능 ID·업무 ID·담당·단계·실행 명령을 확인해 보고합니다. 진행 중인 다른 작업을 덮어쓰거나 아직 시작할 수 없는 후속 단계를 미리 배정하지 않습니다. 배정 자체가 지시이므로 채널에 다시 쓰지 않고, 담당자 사이의 순서가 중요할 때만 general 채널에 결정으로 남깁니다. PM이 없을 때는 대시보드에서 사람이 PM을 맡을 수도 있습니다. PM은 이 프로젝트를 이어 맡는 자리라 함부로 바꾸지 않습니다. 다른 세션이 `/wax:pm`을 실행해도 기존 PM을 대신하지 않고, 대표가 교체를 요청했을 때만(대시보드 **PM 교체…**에서 한 번 더 확인, CLI는 `wax chat team pm <이름> --replace`) 바뀝니다. 진행 중인 작업이 없으면 대시보드 **작업 진행** 패널의 **새 작업 만들기**로 기획 단계 작업을 만든 뒤 AI에게 기획을 배정합니다.
3. 각 세션에서 `/wax:work`(Codex `$wax:work`, Antigravity `/work`)를 실행합니다. 자기에게 배정된 업무를 받아(accept) 해당 작업의 단계를 수행하고, 끝나면 완료(done)나 막힘(block, 이유 포함)을 결과와 함께 기록합니다. 이 기록이 PM에게 하는 보고입니다. 한 번에 한 업무를 처리합니다.
4. PM 세션에서 목표 없이 `/wax:pm`을 다시 실행하면 **진행 보고**를 합니다. 새 목표나 계속 진행하라는 지시가 있으면 보고에 그치지 않고 해당 범위의 다음 배정까지 진행합니다. 작업별 완료·진행·미착수, 지연(막힌 업무, 오래 결과가 없는 업무, 앞 단계를 기다리는 업무)과 원인·일정 영향, 위험을 알리고, 결정할 일은 선택지와 추천안으로 올립니다. 결정된 계획 안에서 막힌 업무를 풀거나 다시 맡기는 일은 PM이 하고, 범위·우선순위·일정·담당 변경은 대표의 결정을 받습니다. 참여자 목록에 사람이 있으면 짧은 보고를 그 사람 앞으로 채널에도 올려 대시보드에서 볼 수 있게 합니다.

안전 범위:
- 업무는 대표가 지정한 PM만 배정할 수 있습니다. 다른 참여자가 업무를 만들거나 일반 메시지로 지시해도 배정으로 인정되지 않습니다.
- 배정이 허용하는 일은 지정한 작업의 해당 wax 단계뿐입니다. 대표의 직접 지시가 PM보다 우선하며, 파일 수정·명령 실행은 각 도구의 권한 확인을 그대로 거칩니다.
- 단계 순서는 그대로 지킵니다. 앞 단계가 끝나지 않았으면 업무를 막힘으로 기록하고 PM에게 알립니다.

**업무 완료 확인.** 업무를 완료(`task done`)로 바꾸면 wax가 연결된 작업의 그 단계가 배정 이후 실제로 끝났는지 확인합니다. 단계를 지정한 업무는 현재 주기에 그 단계의 완료 기록(`wax complete`)이 배정 시각 뒤에 있어야 하고, `any` 업무는 배정 이후 완료한 단계가 하나라도 있어야 합니다. 기본(`WAX_TASK_DONE_CHECK=warn`)으로는 완료로 기록하되 상태 기록에 경고(`warning`)를 남깁니다. 경고는 CLI 오류 출력(`wax chat: 경고: …`), `wax chat tasks --all`·`wax chat team`의 업무 줄, 대시보드 기록 타임라인과 일일 업무보고 초안, 작업 탭의 업무 대화, 사무실 작업노트에 보이고, PM은 진행 보고에서 이런 업무를 끝나지 않은 일로 다룹니다. `WAX_TASK_DONE_CHECK=enforce`로 실행한 세션과 대시보드는 이런 완료를 거절하며, 단계를 완료한 뒤 다시 하거나 끝낼 수 없으면 `task block`으로 이유를 남기라고 안내합니다. `off`는 확인하지 않습니다. 연결된 작업이 지워진 업무와 완료가 아닌 상태 변경(수락·막힘·취소)은 확인하지 않습니다.

### Claude 사용량 모니터

Claude Code 2.1.287 이상에서 wax 플러그인을 쓰면 플러그인에 들어 있는 wax 모드(Claude Code mods)가 턴이 끝날 때마다 숫자만 이 프로젝트의 `.wax/usage/<세션 ID>.json`에 남깁니다: 계정의 플랜 사용량(5시간·주간 %와 초기화 시각), 그 세션의 컨텍스트 사용량, 지금까지의 비용. 대화 내용(프롬프트·답변·도구 호출)은 읽지도 남기지도 않고, `.wax` 폴더가 없는 프로젝트에는 아무것도 쓰지 않습니다. 가상 사무실 사장실 벽의 모니터와 `wax chat usage`로 보고, PM은 진행 보고에서 한도에 가까운 사용량을 일정 위험으로 알립니다. Claude Code의 `/plugin`에서 wax 플러그인의 훅을 끄면 기록하지 않습니다. 다른 도구(Codex·GitHub Copilot CLI·Gemini CLI·Antigravity CLI)의 사용량은 아직 표시하지 않습니다.

### 일일 업무보고

`/wax:daily [YYYY-MM-DD]`(Codex `$wax:daily`, Antigravity `/daily`)를 실행하면 AI가 그날의 집계 초안을 읽고 보고서를 작성해 `docs/wax/daily/<날짜>/NN.md`로 등록합니다. 보고서는 오늘 한 일, 검증 결과, 결정 사항, 문제와 미해결 질문, 내일 할 일로 구성됩니다. 같은 날 여러 번 등록하면 번호가 늘어나며 기존 보고서를 덮어쓰지 않습니다. 대시보드의 **집계 초안 보기**는 AI 없이 기록만 모은 초안을 보여 줍니다.

### CLI로 직접 사용

```sh
wax chat post <채널> --author <이름> --session <ID> --kind <종류> --doing <지금 하는 일> --to <받는 사람> --message <전할 내용>
wax chat read <채널> [--since <메시지ID>] [--json]
wax chat join --author <이름> --session <ID> --kind <종류> [--model <모델>] [--feature <작업ID>]   # 첫 참여(같은 이름이 활동 중이면 -2, -3을 붙여 참여)
wax chat presence --author <이름> --session <ID> --state working|discussing|reviewing|idle|away [--note <하는 일>]
wax chat who
wax chat reset [--author <이름>]   # 지난 세션 정리(듣는 중·작업 중 세션은 남김, --author는 그 세션만)
wax chat watch --author <이름> [--feature <작업ID>] [--wake] [--json]   # 나를 부른 메시지·새 배정을 한 줄씩(멈출 때까지). --wake는 AI 세션을 깨우는 감시
wax chat read <채널> --id <메시지ID> [--json]                            # 메시지 하나를 그대로 읽기
wax chat team pm <이름> --kind <종류>        # PM 지정(대표가 정함)
wax chat assign <작업ID> --to <담당> --author <PM> --session <ID> --phase <단계|any> --message <지시>
wax chat tasks [--to <이름>] [--all]
wax chat skills [--json]                    # 스킬 지도: 사원 × 단계·검증·코드 영역 기록 수, 빈 분야
wax chat rules [--all] | rules candidates | rules lint   # 프로젝트 규칙, 근거 후보, 근거 점검
wax chat rules propose --author <이름> --session <ID> --message <규칙> --why <이유> --source <근거 ID>   # 규칙 제안(승인은 대시보드에서 사람이)
wax chat notes <이름> [--days 7] [--json]    # 작업노트: 그 사원이 날마다 한 일과 지금 맡은 업무·마지막 메모
wax chat memo --author <이름> --session <ID> --message <메모> [--feature <작업ID>]   # 작업노트에 남은 일·주의점 메모
wax chat task accept|done|block|cancel <업무ID> --author <이름> --session <ID> [--message <메모>]
wax chat daily [--date YYYY-MM-DD]           # 타임라인
wax chat daily draft | report --file <보고서.md> | list
```

**보낸 뒤 받는 사람 상태.** `wax chat post`는 메시지 ID 다음 줄에 받는 사람(`--to`와 본문의 `@이름`)마다 지금 듣는 중인지(대시보드 받는 사람 고르기와 같은 판정), 세션 상태 훅으로 이어졌으면 그 상태(작업 중·사람 기다림·끝남(안 봄)·쉬는 중·소식 없음·세션 끝남), 참여한 적 없는 이름인지를 한 줄로 보여 줍니다. 아무도 듣고 있지 않으면 "저장만 됨: 받는 세션이 지금 듣고 있지 않아 깨우지 않습니다. 사람에게 알리거나 `wax chat wait`를 쓰세요"가 붙습니다. `--json`에는 `recipients`(`name`·`member`·`listening`·`host`)와 `storedOnly`가 들어가고, MCP `wax_post` 결과도 같습니다. 받는 사람이 없으면 지금처럼 ID만 나옵니다. 메시지는 늘 그대로 저장되고, 이 확인은 어떤 세션도 깨우거나 띄우지 않습니다.

`wax`는 `node "/path/to/wax/bin/wax.mjs"`를 뜻합니다. 종류(`--kind`)는 `claude`, `codex`, `copilot`, `gemini`, `antigravity`, `grok`, `human`, `other` 중 하나입니다. 다른 명령의 도움말은 `wax --help`, `wax chat --help`, `wax trigger --help`, `wax pm-loop --help`, `wax mcp --help`처럼 봅니다.

**CLI 언어.** 도움말(`--help`)·안내·경고·오류는 `WAX_LANG=en`이면 영어로 나옵니다(`en_US`, `ko-KR` 같은 값도 받습니다). `WAX_LANG`이 없으면 `LC_ALL` → `LC_MESSAGES` → `LANG` 중 값이 있는 첫 번째가 `en`으로 시작할 때 영어, 그 밖에는 한국어입니다. 영어 시스템에서 한국어로 쓰려면 `WAX_LANG=ko`를 지정하세요. `--json` 출력, 저장 기록, AI 세션에 주는 단계 지시문·인수인계 문맥·스킬은 언어와 상관없이 같습니다. 대시보드 화면 언어는 따로 정합니다(6절 "대시보드 열기").

| 경로 | 내용 |
| --- | --- |
| `.wax/chat/channels/<채널>.jsonl` | 채널 메시지(추가만 함) |
| `.wax/chat/board/<작업>.jsonl` | 화이트보드 노트와 보고서 기록 |
| `.wax/chat/presence.json` | 참여자 상태와 지금 하는 일 |
| `.wax/chat/team.json`, `assignments.jsonl` | PM과 업무 배정·상태 이력 |
| `.wax/chat/daily.jsonl`, `docs/wax/daily/<날짜>/NN.md` | 일일 보고서 기록과 본문 |

그 밖의 저장 위치는 7절에 정리되어 있습니다.

빈 디렉터리에서 `node scripts/chat-demo.mjs --project ./demo --loop`를 실행하면 PM 배정·대화·보고가 반복되는 시연 장면을 대시보드에서 볼 수 있습니다.

## 6-1. 기록 검색

대화·화이트보드·업무 배정·일일 보고·단계 문서·완료 근거·개선 이력·테스트와 커밋 근거·요청 대화·디자인 작업을 한 번에 찾습니다. 결과마다 원문 위치(파일과 기록 ID 또는 문서 위치)와 그 기록을 여는 화면 링크가 붙습니다.

처음 한 번 검색 색인을 만듭니다. 대시보드 상단 메뉴의 **검색**(`/search`)에서 **검색 색인 만들기**를 누르거나 다음을 실행합니다.

```sh
wax search index
```

그다음부터는 검색할 때마다 바뀐 기록만 먼저 반영합니다. 다른 AI 세션이나 CLI가 쓴 기록도 그대로 찾을 수 있습니다.

```sh
wax search 인계
wax search 인계 --feature lookbook-upload
wax search "Claude Code" --kind message --author claude-app --from 2026-10-01 --to 2026-10-18
wax search status
```

- 띄어 쓴 단어는 모두 들어 있는 기록만 찾고, 큰따옴표는 공백을 포함한 구절입니다. 대소문자는 구분하지 않으며 결과는 최신순입니다.
- 세 글자 이상은 부분 일치입니다(`인계를`, `handoff-v2.md`, `docs/wax/design`, 커밋 SHA 앞자리). 두 글자(`인계`, `리뷰`, `오류`, `UI`)는 단어 안의 두 글자 조각으로 찾아 “인계를”, “디자인 인계”에도 맞습니다. 한 글자는 전체를 훑어 느릴 수 있습니다. 형태소(“인계했다”로 “인계를”), 초성, 의미 검색은 지원하지 않습니다.
- 필터: 종류(`--kind`), 작업(`--feature`), 작성자(`--author`), 단계(`--phase`), 기간(`--from`, `--to`, YYYY-MM-DD). 결과가 많으면 출력 끝의 `--cursor`로 다음 페이지를 봅니다. `--json`은 원문 위치와 강조 범위를 JSON으로 줍니다.
- 실행 승인 기록, 세션 토큰, AI 세션 정보는 검색하지 않습니다.

색인(`.wax/search/index.db`)은 기록에서 다시 만들 수 있는 사본이고 원본은 `.wax`의 JSON/JSONL 그대로입니다. 색인이 없으면 검색은 만드는 방법만 안내합니다. 손상됐거나 이 wax 버전과 형식이 다르면 `wax search index --rebuild`(대시보드의 **색인 다시 만들기(복구)**)로 다시 만듭니다. 읽지 못한 기록 줄은 건너뛰고 `wax search status`에 파일과 줄 번호를 보여 줍니다. 색인을 만들다 멈췄으면(강제 종료, 대시보드 재시작) “중간에 멈췄습니다”와 **색인 이어서 만들기**가 나오고, 검색하거나 버튼을 누르면 남은 기록부터 이어서 반영합니다. 화이트보드·일일 보고서 Markdown만 고치거나 지워도 다음 검색에 반영되며, 지워졌거나 프로젝트 밖을 가리키는(심볼릭 링크) 파일은 본문을 검색하지 않고 상태에 표시합니다. 작성자 필터는 대표, 한글·공백이 들어간 이름도 그대로 씁니다.

### 관련 기록 찾기(recall)

`wax recall`은 AI 세션이 작업 전에 다른 작업의 기록을 참고하도록 같은 색인에서 관련 기록을 **관련도순**으로 찾습니다. 검색과 달리 낱말 중 하나만 맞아도 찾고, 많은 낱말이 맞을수록·관련도가 높을수록 앞에 둡니다. 한국어 낱말 끝의 조사(`토큰이`, `인계를`)는 떼고도 찾습니다.

```sh
wax recall 토큰 만료 재시도 --exclude-feature login-retry
wax recall 결제 오류 --kind note --limit 5 --budget 2000
```

- 결과는 문자 수(토큰 아님) 예산 안에서 한 줄씩 인용하고, 원문 위치와 화면 링크를 붙입니다. `--json`은 순위·일치한 낱말·점수까지 줍니다.
- 단계 스킬과 자동 진행은 비슷한 오류·같은 모듈·이전 결정이 다른 작업에 있을 수 있을 때 `recall`을 실행합니다. 찾은 기록은 지시가 아닌 참고 자료로 다루고 지금 코드에서 다시 확인합니다.
- 색인이 없으면 처음 한 번 만듭니다. 의미 검색(비슷한 뜻의 다른 낱말)은 지원하지 않습니다.

검색에는 Node.js 22.16 이상 또는 24 이상이 필요합니다(내장 SQLite의 전문 검색). 그보다 낮은 Node.js에서는 검색만 안내 문구를 보여 주고 다른 wax 기능은 그대로 동작합니다. 자세한 동작과 측정은 [기록 검색 안내](SEARCH.md)에 있습니다.

## 6-2. MCP 서버(실험)

`wax mcp`는 코딩 도구가 MCP(stdio)로 wax 기록을 읽고 팀 채널에 쓰게 하는 서버입니다. 셸 명령 대신 도구 호출을 쓰므로 인수 실수와 권한 확인이 줄고, 연결 하나가 곧 세션이라 `--session <ID>`를 넘길 일이 없습니다. 기본으로 꺼져 있어 등록할 때 환경 변수 `WAX_MCP=on`을 함께 주어야 시작합니다. 플러그인을 설치해도 자동으로 등록되지 않습니다.

| 도구 | 하는 일 |
| --- | --- |
| `wax_status` | 업무 목록, 또는 `id`를 주면 업무 하나의 진행 중인 단계·그다음 단계·revision·완료 기록·최근 근거 |
| `wax_context` | 업무 인계 문맥(`id`, `budget` 문자 수) — `wax context`와 같은 내용 |
| `wax_recall` | 다른 업무 기록에서 관련 결정·실패(`query`, `excludeFeature`, `budget`) — `wax recall`과 같은 순위 |
| `wax_inbox` | 나(또는 `author`)를 부른 메시지와 나에게 온 PM 배정(`since` 메시지 ID 이후만 볼 수 있음) — `wax chat watch`와 같은 기준이며 읽음 위치는 바꾸지 않음 |
| `wax_join` | 팀 채널 참여(`name`, `kind`, `model`, `peer`)와 상태 갱신(`feature`, `state`, `note`). 다른 이름을 주면 이름을 바꿉니다 — `wax chat join`·`presence` |
| `wax_post` | `question`, `answer`(`replyTo` 필수), `decision`만 올립니다. 인사·진행 보고(`message`·`opinion`)는 받지 않습니다 — `wax chat post` |
| `wax_task` | 나에게 배정된 업무를 `done` 또는 `block`으로 바꾸고 결과(`result`)를 남깁니다. 단계를 끝내지 않은 `done`은 CLI와 같이 경고와 함께 기록되거나 `WAX_TASK_DONE_CHECK=enforce`에서 거절됩니다 — `wax chat task` |
| `wax_complete` | 지금 단계 완료(`id`, `phase`, `evidence`, `proofIds`, `checks`, `noProof`, `acUnverified`, `verdict`, `revision`). 근거·수용 기준 추적·검토자 분리 조건이 `wax complete`와 똑같습니다 |
| `wax_assign` | PM만. 업무의 지금 단계를 배정합니다(`feature`, `to`, `message`) — `wax chat assign` |

- **세션과 작성자.** 처음에 `wax_join`을 한 번 부르면 그 연결이 wax 세션이 됩니다. 세션 ID는 서버 프로세스 안에만 있고 결과에 나오지 않습니다. 쓰기 도구에는 `author`·`session` 인수가 없고, 참여한 이름으로만 기록합니다. 다른 세션이 이미 쓰는 이름이면 `-2`, `-3`이 붙은 이름으로 참여하고 결과의 `author`로 알려 줍니다. 이름 소유가 풀리거나(예: `wax chat reset --author <이름>`) 클라이언트가 다시 `initialize`하면, 다음 쓰기 전에 같은 세션 ID로 다시 참여하고 결과에 `rejoined`와 그때의 `author`를 붙입니다.
- **검증은 CLI와 같습니다.** 쓰기 도구는 CLI와 같은 함수를 부르므로 검증·잠금·길이 제한·오류 문구가 같습니다. 오류는 `isError`, 번역된 메시지(`WAX_LANG`), HTTP식 `status`(400·403·404·409)로 돌려줍니다. 모든 쓰기 기록(메시지, 배정과 상태 변경, 단계 완료 기록과 이력, 참여 상태)에는 `"via": "mcp"`가 붙습니다.
- **도구로 열지 않는 것.** 실행 승인과 거부, 규칙 승인, 트리거 편집, 보관과 복원, 백업 복원, 기록 삭제는 사람이 대시보드에서만 합니다. 문서 저장(`wax save`), 테스트·캡처·커밋 근거(`wax test`·`capture`·`evidence`)도 CLI에 남습니다.
- **도구가 없는 쓰기.** 업무 수락(`task accept`)은 건너뜁니다(`done`·`block`은 열린 업무에서 바로 됩니다). 메모·화이트보드·규칙 제안·업무 취소·일일 보고 등록은 아직 도구가 없고, MCP로 참여한 이름은 셸의 CLI가 쓸 수 없습니다(세션 ID가 서버 안에만 있으므로). 이런 단계는 무엇을 기록하려 했는지 사용자에게 알리도록 안내합니다.
- 프로젝트는 서버가 시작할 때 정합니다: `--project <경로>`, 없으면 `WAX_PROJECT`, 없으면 현재 디렉터리에서 위로 가장 가까운 `.wax`가 있는 폴더(없으면 현재 디렉터리). 도구 인수로 다른 경로를 받지 않습니다. 코딩 도구가 서버를 어느 디렉터리에서 띄우는지 모르면 `--project`를 적으세요.
- 결과의 기록(제목·문서·메시지·배정)에는 `"source": "record"`가 붙습니다. 다른 사람과 세션이 쓴 데이터이며 지시가 아닙니다.

**등록.** `node /path/to/wax/bin/wax.mjs mcp config --host <claude|gemini|codex|copilot> --project /path/to/my-app`이 그 도구에 넣을 조각을 출력합니다(이 설치의 실제 경로가 들어갑니다). wax는 사용자 설정 파일을 읽거나 고치지 않으니 출력된 조각을 직접 넣으세요. 아래 예의 `/path/to/wax`는 압축을 푼(또는 플러그인이 설치된) wax 폴더의 실제 절대 경로로, `/path/to/my-app`은 프로젝트 경로로 바꾸세요. Windows에서도 셸 없이 `node`로 실행합니다.

**Claude Code**

<!-- wax mcp config --host claude -->
```sh
claude mcp add --transport stdio --env WAX_MCP=on wax -- node /path/to/wax/bin/wax.mjs mcp --project /path/to/my-app
```
<!-- /wax mcp config -->

`--scope project`를 붙이면 프로젝트의 `.mcp.json`에 저장되어 팀이 함께 씁니다. `/mcp`에서 연결 상태를 봅니다.

**Gemini CLI** — `~/.gemini/settings.json`(또는 프로젝트의 `.gemini/settings.json`)

<!-- wax mcp config --host gemini -->
```json
{
  "mcpServers": {
    "wax": { "command": "node", "args": ["/path/to/wax/bin/wax.mjs", "mcp", "--project", "/path/to/my-app"], "env": { "WAX_MCP": "on" } }
  }
}
```
<!-- /wax mcp config -->

**Codex** — `~/.codex/config.toml`

<!-- wax mcp config --host codex -->
```toml
[mcp_servers.wax]
command = "node"
args = ["/path/to/wax/bin/wax.mjs", "mcp", "--project", "/path/to/my-app"]
env = { WAX_MCP = "on" }
```
<!-- /wax mcp config -->

**GitHub Copilot CLI** — `~/.copilot/mcp-config.json`(또는 Copilot CLI 안에서 `/mcp add`)

<!-- wax mcp config --host copilot -->
```json
{
  "mcpServers": {
    "wax": { "type": "local", "command": "node", "args": ["/path/to/wax/bin/wax.mjs", "mcp", "--project", "/path/to/my-app"], "env": { "WAX_MCP": "on" }, "tools": ["*"] }
  }
}
```
<!-- /wax mcp config -->

**스킬 안내.** Claude Code와 Gemini CLI의 wax 명령은 "MCP 우선" 안내를 씁니다: 도구 목록에 `wax_join`이 있으면 참여·게시·업무 상태·단계 완료를 도구로 하고, 없으면(기본, `WAX_MCP=on`으로 등록하지 않은 경우) 같은 파일에 있는 짧은 CLI 대안(`wax chat join` … `--session`)으로 합니다. 전체 CLI 규칙은 플러그인의 `skills/<명령>/SKILL.md`에 있습니다. Codex, GitHub Copilot CLI, Antigravity CLI, Grok Build의 스킬은 지금의 CLI 안내를 그대로 씁니다.

Gemini CLI·Codex·Copilot CLI의 설정 파일 위치와 형식은 버전에 따라 다를 수 있으니 각 도구의 MCP 문서에서 확인하세요(이 저장소의 테스트는 서버와 출력한 조각만 확인하고, 각 도구에 등록한 결과는 확인하지 않았습니다). Antigravity CLI와 Grok Build는 아직 확인하지 않았습니다. 등록이 되지 않으면 터미널에서 `WAX_MCP=on node /path/to/wax/bin/wax.mjs mcp --project /path/to/my-app`을 실행해 오류 출력(stderr)을 보세요. `WAX_MCP=on`이 빠지면 켜는 방법을 안내하고 끝납니다.

## 6-3. 한 줄 요청으로 자동 진행

`init`은 기본값으로 바로 참여하고 대시보드를 엽니다. 새 요청에서 두 모드를 선택합니다.

| 모드 | 시작과 실행 |
| --- | --- |
| 프로젝트 | 목표를 입력하면 범위·작업 순서와 선행 관계·산출물·완료 기준을 담은 워크플로우를 먼저 작성합니다. 화면에서 확인하고 **이 워크플로우로 시작**을 눌러야 설계·구현·검토·보고로 진행합니다. 수정 요청은 워크플로우를 다시 작성하며 새 내용을 확인해야 시작합니다. |
| SM · 유지보수 | 오류·개선 요청을 접수·분석 → 영향 확인 → 수정 → 회귀 검증 → 처리 보고로 바로 처리합니다. 기획과 설계 문서는 요청 규모에 맞게 간결하게 남기고 실제 테스트 근거는 유지합니다. |

처음에는 프로젝트 모드가 선택되며 이후에는 프로젝트별 마지막 선택을 기억합니다. `init --mode sm` 또는 `init --mode project`로 요청 화면의 모드를 지정할 수도 있습니다(각 호스트 문법 사용). 모드는 요청을 만든 뒤 바뀌지 않습니다. 다른 모드로 진행하려면 새 요청을 만드세요. 모드 정보가 없는 기존 요청은 SM 흐름을 유지합니다. 두 모드 모두 선택한 CLI의 별도 세션이 실행하며 기존 터미널 AI에 자동 분산 배정하지 않습니다.

요청과 보고 화면(`/start`)의 시작 가이드는 실행 도구 선택 → 할 일 입력 → 진행과 보고 확인 순서를 안내합니다. 설치 여부를 확인하며 로그인 여부는 실제 실행에서 확인합니다. 도구 설치 후에는 **도구 다시 확인**을 누르세요.

새 요청의 실행 도구에서 Codex·Claude Code·Gemini CLI·GitHub Copilot CLI·Antigravity CLI 중 설치한 도구를 선택합니다. Grok Build는 아직 자동 진행을 지원하지 않으므로 터미널 세션에서 스킬 이름을 밝혀 요청하는 팀 작업으로 씁니다. 해당 CLI의 로그인 또는 API 설정과 계정 사용량·비용·데이터 정책이 적용됩니다. 요청은 저장된 도구로 계속 진행하며 다른 도구를 쓰려면 새 요청을 만듭니다. Codex·Claude·Gemini·Copilot의 새 권한 요청은 화면에서 이번만 허용하거나 거부합니다. Antigravity는 기존에 허용된 범위로 실행하며, 새 권한 요청이 막히면 터미널의 설정을 확인해야 합니다. 기존 터미널 세션을 자동으로 깨우거나 다른 AI의 배정을 바꾸지는 않습니다. 자동 진행의 PM은 요청을 처리하는 역할이며, 기존 프로젝트 PM을 교체하지 않습니다.

- 질문이 생기면 채팅으로 답합니다. 진행 중 보낸 추가 지시는 현재 단계가 끝난 뒤 반영됩니다. 즉시 멈추려면 **중지**를 누릅니다.
- 중단·오류의 이유는 요청 위에 표시합니다. **이어서 진행**은 저장된 단계부터 재개합니다. 서버 재시작이나 페이지 조회만으로 AI를 재호출하지 않습니다.
- 요청은 프로젝트당 한 번에 하나씩 실행합니다. 구현·검토에는 실제 통과한 테스트 근거가 필요하며, 다른 세션이 단계를 수정하면 충돌을 보고합니다. 단계 실행의 제한 시간은 30분입니다.
- 기록은 `.wax/chat/requests/`, 단계 문서는 `docs/wax/<자동 생성 ID>/`에 저장합니다. 기존 작업·팀 배정은 **상세 기록**(`/manage`)에서 계속 관리합니다.
- 대시보드 첫 화면(`/`)은 팀 채널이며 대화 기록용입니다. 자동 진행은 **＋ 새 요청**으로 여는 요청과 보고 화면(`/start`)에서 **워크플로우 만들기**(프로젝트) 또는 **시작하기**(SM)로 요청합니다. 워크플로우 확인은 실행 권한 승인과 별개이며 기존 CLI 권한은 그대로 적용됩니다.

자동 진행 연결 규격: [OpenAI 공식 Codex App Server 문서](https://learn.chatgpt.com/docs/app-server)의 thread/start, thread/resume, turn/start, outputSchema와 item/completed를 사용합니다.

## 6-4. 실행 승인

실행 중 콘솔에서 묻는 권한 요청을 대화창에서 처리하려면 [실행 승인 관리](./APPROVALS.md)를 참고하세요. 연결된 요청만 요청별 **이번만 허용 / 거부** 버튼으로 응답합니다.

파일 쓰기 요청(Claude Code의 `Write`·`Edit`·`MultiEdit`, Codex의 파일 변경)의 카드에는 **변경 미리보기**가 접힌 채로 붙습니다. 요약 줄에 파일 수와 더한·뺀 줄 수(`+3 −1`)가 보이고, 펼치면 바뀌는 줄과 앞뒤 3줄이 나옵니다. 미리보기는 요청에 적힌 경로·내용과 지금 프로젝트 파일로 대시보드가 계산하며 AI를 부르지 않습니다. 계산 시각이 함께 적히고, 파일이 바뀌면 다시 계산합니다. Codex 요청은 도구가 보낸 diff를 그대로 보여 줍니다.

- `Edit`의 바꿀 글을 지금 파일에서 못 찾거나 여러 곳에서 찾으면 짐작하지 않고 그 사실만 적습니다.
- 프로젝트 밖 경로, 링크를 따라가면 밖인 경로, `.git/`·`.wax/chat/`·`.env*`, 이진 파일, 256KB·5000줄이 넘는 파일, `NotebookEdit`은 "미리보기 없음: 이유"로 표시합니다. 긴 diff는 400줄에서 자릅니다.
- 미리보기는 보기만 위한 것입니다. 허용·거부와 목표 허용 판정은 바뀌지 않고, 승인 기록에도 저장하지 않습니다. 허용한 뒤의 실제 결과는 그 사이 파일이 바뀌면 다를 수 있습니다.

**거부 이유.** **거부** 버튼 아래 접힌 **거부 이유 남기기(선택)** 칸에 이유를 적고 거부하면, 그 글이 승인 기록에 남고 결정된 카드에 보입니다(500자까지, 제어 문자는 지움). Claude Code에는 거부 응답과 함께 인용으로 전달되어, 다음에 무엇을 다르게 할지 알려 줄 수 있습니다. Codex·Gemini CLI·GitHub Copilot CLI는 거부 응답에 글을 실을 수 없어 **이유는 기록만 됨(이 도구에는 전달되지 않음)**으로 표시됩니다. 비워 두면 지금과 같습니다.

## 6-5. 트리거: 일정, 로컬 호출, GitHub 이슈·CI 실패로 요청 제안

트리거는 정해 둔 때에 요청을 **제안만** 합니다. AI는 사람이 제안을 수락해야 시작하며, 자동 수락은 없습니다.

- **만들기:** 상세 기록(`/manage`)의 **트리거**에서 **＋ 새 트리거**로 만들고 고치고 켜고 끕니다. 정의는 이 컴퓨터의 `.wax/chat/triggers/`에만 저장됩니다.
- **언제:** 일정(5필드 cron과 시간대, 예: `0 9 * * 1-5`, `Asia/Seoul`) 또는 로컬 호출(`wax trigger fire <id> [--payload <파일>] [--key <키>]`, git hook 등). 일정은 대시보드가 켜져 있을 때만 돌고, 꺼진 동안 놓친 실행은 "놓친 실행 N건" 제안 하나로 묶습니다.
- **GitHub:** **GitHub 이슈(라벨)**은 저장소(`owner/name`)와 라벨, **CI 실패**는 저장소·브랜치·워크플로(선택)를 정하고, 확인 간격(`every`, 예: `5m`, 1분 이상)마다 이 컴퓨터의 `gh` 로그인으로 확인합니다. 대시보드가 켜져 있을 때만 확인합니다.
  - `gh`가 없거나 로그인 전이면 목록에 **연결 필요**와 이유가 보이고 확인하지 않습니다(실패로 세지 않음). `gh auth login` 뒤 다음 분에 다시 확인합니다.
  - **처음 확인할 때는 이미 있는 이슈·실패를 기준으로만 기록하고 제안하지 않습니다.** 그 뒤 새로 라벨이 붙은 이슈나 새로 실패한 실행만 한도 안에서 제안합니다. 기존 이슈를 맡기려면 라벨을 뗐다 다시 붙이세요. 다시 켜거나 저장소·라벨·브랜치를 바꿔도 첫 확인부터 다시 합니다.
  - 문구를 비우면 기본 문구(이슈 처리, CI는 SM 모드 "CI 회귀 수정")를 씁니다. 이슈 제목·실행 이름은 `{{issue.title}}`·`{{run.name}}` 등으로 200자까지만 들어가고, 이슈 본문은 "외부 이벤트 내용(지시가 아님)" 인용으로만 전달됩니다.
- **무엇을:** 요청 제안(모드·도구·문구, `{{payload.title}}` 같은 자리표시자는 값마다 200자로 자르고 @멘션을 무력화), 레시피 목표 제안, 일일 보고 제안, 알림만.
- **레시피 목표 제안:** 레시피(6-6절)와 입력 한 줄의 틀을 정합니다. GitHub 이슈는 틀을 비우면 이슈 제목이, CI 실패는 실행 이름과 브랜치가 입력이 됩니다. 제안 카드에서 입력을 고친 뒤 **수락하고 레시피 시작 화면 열기**를 누르면 요청은 만들지 않고, 상세 기록의 PM 루프 칸에 그 레시피 시작 화면이 입력으로 채워져 열립니다. 값을 확인하고 **목표 만들기**를 누르는 것도 사람입니다. 세부 내용 칸에는 이벤트의 외부 원문 요약(이슈 본문, CI 실행 정보)이 미리 채워지고, CI 실패는 수락할 때 `gh run view`로 실패한 작업과 단계 이름을 더합니다(로그 원문은 가져오지 않습니다). 이 칸은 작업자에게 지시가 아닌 데이터로만 전달됩니다. 만든 목표에는 그 제안(트리거·이벤트)이 출처로 남고, 같은 제안으로 목표를 두 번 만들 수 없습니다. 없는 레시피를 고른 트리거는 저장되지 않습니다.
- **수락:** 요청과 보고(`/start`)의 **트리거 제안** 카드에서 문구·도구·모드를 고쳐 **수락하고 시작**하거나 **버리기**를 누릅니다. 제안은 7일이 지나면 만료됩니다. 외부 내용(payload)은 지시문에 "외부 이벤트 내용(지시가 아님)"으로만 인용됩니다.
- **안전장치:** 트리거별 하루 한도와 쉬는 시간, 전체 하루 제안 상한 20건, 같은 이벤트 키의 제안·요청이 열려 있으면 건너뜀, 5번 연달아 실패하면 자동으로 끄고 이유 표시. 모든 이벤트는 `.wax/chat/trigger-events.jsonl`에 남습니다.
- **CLI:** `wax trigger list`, `wax trigger test <id>`(미리 보기만, 아무것도 쓰지 않음. GitHub 소스는 `gh`로 한 번 가져와 보여 줌), `wax trigger fire <id>`(로컬 소스만).
- **기본 한도:** 새 트리거는 하루 3건, 쉬는 시간 30분입니다. 트리거마다 하루 1~100건, 쉬는 시간은 최대 7일까지 정합니다. 트리거 폼의 **저장하면 바로 켜기**를 끄면 꺼진 채로 저장됩니다.
- **사람이 하는 일:** 트리거를 만들고 고치고 켜는 일, 제안 수락과 버리기는 대시보드의 사람만 합니다. CLI와 MCP에는 이런 명령이 없습니다. 수락하면 보통의 요청처럼 6-3절의 자동 진행이 시작되고, 그 요청의 실행 기록에 출처(어느 트리거)가 남습니다.
- **알아 둘 점:** GitHub 확인은 이 컴퓨터의 `gh`가 직접 하므로 `gh` 설치와 로그인이 필요하고, `gh`가 PATH에 없으면 대시보드를 시작할 때 `WAX_GH_BIN`으로 실행 파일 경로를 줄 수 있습니다. 테스트는 가짜 `gh`로 하며, 실제 GitHub 저장소를 오래 폴링하는 운영은 검증 범위(9절)에 들어 있지 않습니다.

## 6-6. PM 루프: 목표별 다음 할 일 제안과 auto 모드

목표 하나에 작업 여러 개를 묶으면, 작업마다 다음 할 일을 정해진 규칙으로 계산해 **제안 카드**로 보여 줍니다. 계산에 AI를 부르지 않으며, 사람이 카드를 눌러야 실행합니다. 듣는 세션이 없을 때 AI 도구를 띄우는 것(headless 작업자)과 계획 초안·막힘 판단·대표 보고를 AI에 묻는 것(PM 판단)도 카드를 누를 때만 합니다. 목표마다 사람이 **auto**를 켜면 정해진 일부 행동만 한도 안에서 카드 없이 실행합니다(아래 auto 모드).

- **목표 만들기:** 상세 기록(`/manage`)의 **PM 루프**에서 **＋ 새 목표**로 있는 작업을 고르거나 새 작업(`작업ID 제목`)을 적습니다. 목표는 **계획 확인 전**으로 시작하고, 작업과 수용 기준을 확인한 뒤 **계획 확인하고 시작**을 눌러야 진행됩니다. 자주 하는 일은 레시피로 한 번에 시작할 수 있습니다(아래 "레시피로 시작").
- **규칙:** 현재 단계만 배정하고(미래 단계는 제안하지 않음), 듣고 있는 세션을 먼저 고르고, 검토는 구현한 도구와 다른 도구의 세션에 맡깁니다(없으면 사람에게 물음). done인데 단계가 끝나지 않았으면 완료 방법을 한 번 다시 알리고 그다음은 사람에게 넘깁니다. 30분 넘게 움직임이 없는 배정은 회수를 제안하고, 보고가 끝나면 `wax pr-body` 초안을 만든 뒤 PR 결정은 사람에게 남깁니다.
- **headless 작업자:** 현재 단계를 듣고 있는(`chat watch`) 세션이 없으면 **작업자 필요** 카드가 나옵니다. 띄울 도구는 요청 자동 진행과 같은 목록에서 이 컴퓨터에 설치된 것만 고르고(Grok Build처럼 자동 실행을 지원하지 않는 도구는 고르지 않음), 검토는 구현을 완료한 도구와 다른 도구를 고릅니다(다른 도구가 없으면 아래 **직접 검토**). GitHub Copilot CLI는 실행 파일만이 아니라 버전 출력까지 확인해, VS Code가 PATH에 둔 연결용 `copilot`만 있으면 설치되지 않은 것으로 봅니다. 카드에서 도구를 고르고 **… 작업자 시작**을 누르면 그 도구를 띄워 배정 하나·단계 하나만 맡기고, 끝나면 종료합니다. 단계당 30분이 상한이고, 그 전이라도 작업자가 10분 동안 아무 출력이 없으면 멈추고 업무를 block합니다(**무응답 멈춤**, 실행 승인을 기다린 시간은 세지 않음). 권한 요청은 실행 승인 화면으로 갑니다. 작업자는 CLI로 단계를 완료하고(근거·수용 기준 조건 그대로), 끝난 뒤 실행기가 그 결과로 업무를 done 또는 block으로 바꿉니다. done은 기존 업무 완료 확인을 거쳐, 단계가 끝나지 않았으면 다음 단계로 가지 않고 사람에게 넘깁니다. 실행 중인 작업자는 목표 화면에 도구·경과 시간·**작업자 멈추기** 버튼과 함께 나오고, 목표를 정지하면 함께 멈춥니다. 작업자 카드를 버리면, 자리에 있는(듣지는 않는) 세션 배정을 대신 제안합니다. 작업자는 CLI로 단계를 완료해 완료 이력에 도구가 없으므로, 실행 기록의 **실행 도구**는 그 작업자를 띄운 시작 기록의 도구로 보여 줍니다(검토자 분리도 같은 기록을 봅니다).
- **Antigravity CLI 작업자:** Antigravity CLI는 headless로 띄우면 실행 권한을 물을 수 없어, 사용자 Antigravity 설정 `settings.json`(예: `~/.gemini/antigravity-cli/settings.json`)의 `permissions.allow`에 없는 명령을 바로 거부합니다. 구현·검토는 검사와 `wax test`를 실행해야 끝나므로, 이 단계의 작업자 카드에서 Antigravity CLI를 고르면 이 설정 이름과 함께 경고가 나옵니다(그래도 고를 수는 있습니다). 허용 목록은 명령 하나하나의 패턴이라 이 단계의 명령이 허용되는지 미리 알 수 없어서, wax는 이 설정을 읽어 경고를 끄지 않고 늘 알리며, 설정을 바꾸지도 않습니다. auto는 이 단계를 설치된 다른 headless 도구로 맡기고, 다른 도구가 없으면 띄우지 않고 카드로 남겨 사람에게 알립니다.
- **도구 상태 기억:** 작업자나 PM 판단이 도구 상태 때문에 실패하면(정해진 세 모양만: **모델·인증 거부** 예: Codex의 `model_not_found`, **사용 한도** 예: Codex의 "You've hit your usage limit … try again at …", **headless 권한 거부** 예: Antigravity CLI의 명령 실행 거부) 이 컴퓨터의 `.wax/chat/tool-health.jsonl`에 한 줄 남깁니다. 모양은 플러그인의 `tool-failures/<도구>.json`에 실제 출력 예시와 함께 정해져 있고, 테스트 실패·시간 초과·무응답 멈춤 같은 일의 실패는 남기지 않습니다. 남은 실패가 있는 도구는 작업자 카드의 기본 순서 맨 뒤로 가고(레시피 도구도) "최근 실패: Codex 모델·인증 거부(…)" 경고가 붙으며, 막힘·보고 판단에는 쓸 수 없는 도구(`unavailableTools`)로 들어갑니다. 판단이 그런 도구나 설치되지 않은 도구를 고르면 제안 카드에 경고가 붙고, 도구 고르기에는 설치된 도구만(상태가 괜찮은 도구가 위) 나옵니다. 사람은 경고를 보고 그 도구를 그대로 고를 수 있지만, auto는 띄우지 않고 카드로 남깁니다. 풀리는 때: 같은 도구가 한 번 성공하거나(권한 거부는 그 단계에서 성공해야) PM 루프 위 **도구 상태**의 **다시 시도**를 누르면 풀리고, 그 밖에는 사용 한도는 메시지의 시각이 지나면, 시각이 없으면 24시간 뒤입니다. `wax doctor`의 `toolHealth`에 도구별 한 줄이 나옵니다.
- **실패한 실행의 도구 출력:** 작업자나 PM 판단이 실패·시간 초과·되풀이 멈춤으로 끝나면, 목표 기록(`.wax/chat/pm-loop/<목표 ID>.jsonl`)의 끝 기록에 도구 출력의 끝 2000자(`output.tail`, stderr가 비면 결과 줄이나 오류 문장)와 Gemini CLI·GitHub Copilot CLI가 보낸 연결 오류의 번호·문장(`output.rpcError`)이 남습니다. 남기기 전에 API 키 같은 비밀값, 토큰, 홈 폴더, 프로젝트 경로, 사용자 이름, 이메일을 `<secret:…>`·`<token>`·`~`·`<project>`·`<user>`·`<email>`로 바꿉니다. 지우기는 빠뜨릴 수 있으니 기록을 남에게 보내기 전에 열어 보세요. 정상 끝과 사람이 멈춘 실행에는 남기지 않고, 이 출력은 작업자 지시문과 PM 판단에 넣지 않습니다.
- **쓰지 않기:** 구독을 멈춘 도구처럼 한동안 쓰지 않을 도구는 **도구 상태** 칸에서 도구마다 **쓰지 않기**를 체크합니다. 이 컴퓨터의 이 프로젝트에서, 사람이 체크를 풀 때까지 최근 실패한 도구와 같게 다룹니다: 작업자 카드의 기본 순서 맨 뒤(레시피 도구와 판단이 고른 도구도), 판단 도구 기본 순서에서 건너뜀, 막힘·보고 판단의 `unavailableTools`(`shape: disabled`), auto는 띄우지 않음, 검토자로 세지 않음(아래 직접 검토). 성공·**다시 시도**·24시간으로는 풀리지 않습니다. 사람은 카드에서 경고를 보고 그 도구를 직접 고를 수 있습니다. 켜고 끈 사람과 시각은 `.wax/chat/tool-disabled.jsonl`에 남고 `wax doctor`의 `toolHealth`에도 나옵니다. 바꾸는 곳은 대시보드뿐이고 CLI 명령은 없습니다. 사용자의 도구 설정은 바꾸지 않습니다.
- **직접 검토:** 검토를 맡길 headless 도구(구현 도구와 다르고, 설치되어 있고, 상태가 괜찮고, 쓰지 않기가 아니고, headless에서 명령 실행 권한을 물을 수 없다는 경고가 없는 도구)가 없으면 검토 카드의 기본은 처음부터 **직접 검토**입니다. 예를 들어 Claude Code가 구현했고 다른 도구가 Antigravity CLI뿐이면, 한 번 실패하기 전에도 직접 검토 카드가 나옵니다. 카드에 그 작업의 수용 기준과 할 명령이 작업 ID까지 채워져 복사 버튼과 함께 나옵니다: `wax status <id>`, `wax test <id> -- <검사 명령>`, `wax save review <id> --file .wax/tmp/review-<id>.md`, `wax complete review <id> --verdict pass --evidence "<확인한 내용>" --proofs <proof ID>`(AC가 있으면 `--checks-file`, 대시보드 사람 이름으로 `--author`). 시작 화면에 검사 명령을 적었으면(허용을 체크하지 않았어도) `wax test` 줄에 그 명령이 채워지고, AC가 있으면 AC 확인 파일의 JSON 모양(AC마다 `id`·`status`·`detail`·`proofIds`)이 예시로 나옵니다. 검사 명령은 허용처럼 대시보드 메모리에만 있어 대시보드를 다시 시작하면 자리 표시로 돌아갑니다. 검토 완료는 대시보드에서 하지 않고 지금처럼 CLI에서 근거와 함께 합니다. 상태가 나쁜 도구가 있으면 경고를 보고 골라 작업자로 띄울 수도 있습니다. 버그 수정 레시피의 검토 메모는 "고치기 전 코드에서 재현 테스트가 실패하는지 확인(예: `git stash`로 고친 부분을 잠시 치우고 테스트)"입니다.
- **이 목표 동안 같은 요청 허용:** 목표 시작 화면(**＋ 새 목표**와 레시피 시작 화면)의 이 칸에서 고정된 네 종류만 체크해 켭니다. 늘 꺼진 채 시작하고, 레시피가 제안한 종류에는 **레시피 제안** 표시만 붙습니다. 내장 레시피 셋(버그 수정·기능 추가·동작 유지 정리)은 **wax 명령**·**검사 명령**·**.wax/tmp 쓰기**를 제안합니다. **wax 명령**은 작업자 자신의 작업 ID·단계의 `wax status`·`save`·`complete`(셸 특수 문자 없음, `--file`·`--checks-file`은 `.wax/tmp/` 안, 근거 면제 옵션 없음, `--author`는 작업자 이름, `--project`는 바로 이 프로젝트일 때만)와 결정 기록 `wax ruling <작업 ID> --phase <그 단계> --author <작업자 이름> --file .wax/tmp/<파일>`(이 모양 하나뿐, `--what` 같은 글 옵션·`--area`·`--revision`은 맞지 않음), 설계 단계의 방법 내기 `wax approach <작업 ID> --propose --file .wax/tmp/<파일> [--author <작업자 이름>]`(이 모양 하나뿐, 방법 고르기 `--pick`·`--single`·`--revision`·`--reason`이나 다른 옵션이 섞이면 맞지 않음)이고 `wax test`는 들지 않습니다. 작업자 지시문은 CLI를 늘 `--project <프로젝트>`로 부르게 합니다. **검사 명령**은 시작 화면에 적은 명령(예: `node --test`)을 감싼 `wax test <작업 ID> -- <그 명령>`(`--revision`·작업자 자신의 `--author`·이 프로젝트의 `--project`, PM 루프가 이 목표·작업에 등록한 워크트리의 `--worktree`, 구현 단계에서 계획 단계 ID `--step S-n`은 붙여도 됨)뿐입니다. 검사 명령만 따로 실행하는 요청은 근거가 남지 않아(되풀이 감지와 완료 근거가 보지 못함) 실행 승인 화면으로 오고, 작업자 지시문도 고치는 중의 검사까지 늘 `wax test`로 돌리라고 알립니다. 명령을 비우면 켤 수 없고, 명령에 셸 특수 문자(`&&`, `|`, `;`, `>`, `$`, 따옴표 안의 이런 문자, 역슬래시 등)가 있으면 감싼 꼴도 맞지 않으므로 켜려 할 때 이유와 함께 거절합니다(목표를 만들지 않음). `npm test`처럼 특수 문자 없는 명령으로 바꾸세요. **.wax/tmp 쓰기**는 프로젝트 안 `.wax/tmp/` 아래 파일(심볼릭 링크를 풀어 본 실제 위치도 그 안), **프로젝트 파일 읽기**는 `.git/`·`.wax/chat/`·`.env*`를 뺀 프로젝트 안 파일입니다. 켠 종류는 그 목표가 띄운 headless 작업자(Claude Code, Codex)의 실행 승인에만 걸리고, 다른 세션·대화형 세션(`WAX_APPROVALS` 훅)·다른 목표에는 걸리지 않습니다. 사람 없이 허용한 요청도 실행 승인 기록에 `goal-allow:<목표 ID>`와 종류로 남고, 실행 승인 화면·목표 화면·실행 기록에 **목표 허용으로 허용됨 n번**이 나옵니다. 실행 승인 화면에서 켜지 않은 종류에 맞는 작업자 요청에는 **허용하고 이 목표 동안 같은 요청 허용** 버튼이 나와, 그 요청을 허용하고 그 종류를 이 목표에 켭니다. 목표 화면의 **허용 끄기**로 언제든 끄고, 목표가 완료되거나 멈추면 같이 끝납니다(재개해도 돌아오지 않음). 허용은 대시보드 프로세스 메모리에만 있어 대시보드를 다시 시작하면 꺼지고, 작업자가 파일이나 CLI로 켤 수 없습니다. 다시 시작해 꺼진 허용은 목표 화면에 **대시보드를 다시 시작해 꺼졌습니다**와 켜져 있던 종류로 나오고, 사람이 **같은 종류로 다시 켜기**를 눌러야 다시 켜집니다.
- **작업자마다 격리 브랜치:** 목표 시작 화면(**＋ 새 목표**와 레시피 시작 화면)과 목표 화면의 **작업자마다 격리 브랜치(git 브랜치와 워크트리를 만듭니다)** 칸을 체크하면 켜집니다. 늘 꺼진 채 시작하고(레시피도 켜지 못함), 켜지 않은 목표는 지금처럼 프로젝트 폴더에서 돕니다. 프로젝트가 커밋이 있는 Git 저장소의 맨 위 폴더여야 하고, 켤 때의 HEAD가 기준 커밋이 됩니다. 켜고 끄는 것은 그 목표가 작업자를 띄우기 전까지만입니다.
  - **워크트리:** 작업자를 띄울 때 작업마다 `.wax/worktrees/<목표>-<n>` 워크트리와 `wax/<목표>/<작업>-<n>` 브랜치를 만들고(기준은 목표를 켤 때의 HEAD, 같은 작업의 앞 워크트리 브랜치가 있으면 그 끝) 작업자를 그 안에서 띄웁니다. 같은 작업의 다음 단계는 같은 워크트리를 이어 쓰고, 다른 작업은 다른 워크트리를 써서 동시 작업자가 서로 덮지 않습니다. 작업자는 CLI를 `--project <프로젝트>`로, 검사 근거는 `wax test --worktree`로 남기고, 실행 기록·스냅숏·되돌리기도 그 워크트리 기준입니다.
  - **프로젝트 `.git`:** wax가 프로젝트 `.git`에 쓰는 곳은 이 `git worktree add` 하나입니다. 새 워크트리마다 브랜치 하나(와 그 reflog)와 워크트리 항목 하나(`.git/worktrees/<목표>-<n>/`)가 생기고, 다른 파일은 바뀌지 않습니다. 저장소의 훅은 돌지 않습니다. 워크트리와 브랜치는 목표가 끝나도 지우지 않습니다(아래 **로컬로 가져오기**·**워크트리 정리**는 사람이 누를 때만). `.gitignore`와 `.git/info/exclude`는 고치지 않으므로, `.gitignore`에 `.wax/`가 없으면 프로젝트의 `git status`에 `.wax/`가 추적 안 된 폴더로 보이고, 프로젝트 맨 위에서 파일을 모두 찾는 도구(예: 프로젝트 폴더에서 돌린 `node --test`)는 워크트리의 시험 파일도 찾습니다.
  - **Windows의 긴 경로:** 워크트리는 `.wax\worktrees\<목표>-<n>\` 아래에 만들어져 경로가 약 30자 길어집니다. Git for Windows의 기본 한도(260자)를 넘으면 워크트리 만들기가 실패하고 작업자를 띄우지 않으며, 오류에 해결 방법이 나옵니다. 깊은 경로가 있는 프로젝트는 `git config core.longpaths true`를 켜 두세요.
  - **.env 복사:** 목표 화면의 **새 워크트리에 복사할 .env**에서 고른 이름만(후보는 프로젝트 맨 위의 `.env`, `.env.local`과 준비 스크립트가 적은 이름) 새 워크트리에 복사합니다. 일반 파일만(링크는 따라가지 않음), 워크트리에 이미 있으면 덮어쓰지 않고, 권한은 macOS·Linux에서 0600입니다(Windows는 권한을 바꾸지 않아 원본 `.env`처럼 폴더의 접근 권한을 따릅니다). 기록에는 이름만 남고 내용은 남지 않습니다. 작업자가 읽으려면 지금처럼 사람의 승인이 필요합니다.
  - **준비 스크립트:** 저장소의 `docs/wax/worktree.json`에 `{ "setup": ["npm", "ci"], "env": [".env"], "portEnv": "PORT" }`처럼 적으면 새 워크트리마다 그 인수를 셸 없이 워크트리에서 실행합니다(5분 상한, 출력 끝 4000자만 `.wax/chat/worktree-setup.jsonl`에 남김). 저장소 코드이므로 이 컴퓨터의 사람이 목표 화면의 **준비 스크립트 확인**에서 파일·인수·인수가 가리키는 저장소 파일·해시를 보고 **이 해시 승인**을 눌러야 돕니다. 해시는 worktree.json과 인수가 가리키는 파일(예: `scripts/setup.sh`)을 함께 묶고, 첫 인수가 `npm`·`pnpm`·`yarn`·`bun`·`npx`면 프로젝트 맨 위의 `package.json`과 있는 잠금 파일(`package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lockb`, `bun.lock`)도 묶습니다. 승인 화면에 해시에 드는 파일이 모두 나오고, 하나라도 바뀌면 다시 승인해야 합니다. 이 배포 전에 승인한 패키지 관리자 준비 스크립트는 해시가 바뀌어 **승인 뒤 바뀜**으로 보이므로 한 번 다시 승인하세요. 워크트리는 커밋에서 만들어지므로 커밋한 파일이어야 합니다. 승인하지 않았으면 준비를 건너뛰고 다른 것으로 대신하지 않습니다. 실패하거나 5분을 넘기면 작업자를 띄우지 않고 막힘 카드로 남깁니다. 준비가 도는 동안 작업자나 목표를 멈추면 준비 프로세스와 그것이 띄운 프로세스를 모두 끝내고(Windows는 `taskkill /T`) 작업자를 띄우지 않습니다. 워크트리 목록에는 **준비 중 멈춤(다음 시작 때 다시 돎)**으로 나오고, 다음에 작업자를 띄우면 준비가 다시 돕니다. 해시는 이 파일들만 묶으므로, 명령이 다른 저장소 파일(스크립트가 부르는 파일 등)이나 내려받는 패키지를 실행하면 그것도 믿을 수 있을 때만 승인하세요.
  - **복사할 폴더·가져오기 전 검사(`copy`·`checks`):** worktree.json에 `"copy": ["node_modules"]`(프로젝트의 무시된 폴더, 슬래시로 나눈 상대 경로 20개까지, 글롭 없음)와 `"checks": [["node", "--test"]]`(셸 없이 돌릴 인수 배열 5개까지)를 적을 수 있습니다. 둘 다 worktree.json에 들어 있어 같은 해시로 묶이고, `checks` 인수가 가리키는 저장소 파일과 첫 인수가 패키지 관리자일 때의 `package.json`·잠금 파일도 해시에 듭니다. `copy`나 `checks`가 있으면 `setup`은 없어도 됩니다(그때 새 워크트리에서 돌 준비는 없습니다). 승인 화면에 복사할 폴더마다 지금 프로젝트에서의 상태(있음·무시됨, 없음, 무시되지 않음, 추적되는 파일이 있음, 막힌 이름 `.git`·`.wax`·`.env*`·다른 VCS 폴더, 링크)와 검사 명령이 나오고, `setup`이 `npm ci`인데 `node_modules`를 복사하려 하면 알립니다(`npm ci`는 시작할 때 `node_modules`를 지우므로 `npm install --prefer-offline`처럼 있는 폴더를 쓰는 명령이 맞습니다). 검사는 사람이 시작할 때만 그 워크트리에서 셸 없이 차례로 돌고(앞 명령이 실패해도 다음 명령을 돌립니다, 명령마다 10분·전체 30분), 결과는 작업 근거와 따로 `.wax/chat/preimport/<워크트리>.jsonl`에 남습니다. **로컬로 가져오기** 미리보기의 **가져오기 전 검사** 칸에서 **검사 실행**을 누르면 돌고, 명령마다 상태·걸린 시간·출력 끝 40줄이 보입니다(실행 중에는 3초마다 새로 읽고 **멈추기**로 멈춥니다). 목표 화면의 워크트리 줄에도 마지막 결과가 보입니다. 검사가 있으면(승인된 `checks`나 시작 화면의 검사 명령) 마지막 결과가 지금 워크트리·프로젝트 HEAD에서 통과일 때만 가져옵니다. 검사 뒤 워크트리나 HEAD가 바뀌면 "검사 뒤 바뀜, 다시 검사하세요"가 나오고 확인 버튼이 꺼지며, 서버도 다시 계산해 거절합니다. 실패를 넘기는 버튼은 없습니다: 버리거나, 워크트리를 고친 뒤 **다시 검사**하거나, 같은 작업의 작업자를 다시 띄워 고치게 합니다(정말 빼야 하면 worktree.json에서 그 검사를 빼고 다시 승인합니다). `checks`가 승인 뒤 바뀌었거나 시작 화면 명령에 셸 특수 문자가 있어 검사를 돌릴 수 없을 때도 가져오지 않습니다. 검사는 워크트리에서 돌므로, 워크트리 기준 뒤로 main이 움직였으면 몇 커밋인지 알립니다. 검사가 없으면 지금처럼 가져옵니다. 가져오기 기록에는 그때 쓴 검사 실행이 남습니다. 검사가 워크트리 파일을 바꾸면(예: 무시되지 않은 커버리지 폴더) 실패로 칩니다. 칸을 더하면 worktree.json이 바뀌므로 한 번 다시 승인합니다.
  - **빌드 폴더 빠른 복사(`copy`):** 승인한 해시의 `copy` 줄을 새 워크트리마다 한 번, `.env` 복사 뒤·준비 스크립트 앞에 프로젝트에서 워크트리로 복사합니다(방향은 늘 프로젝트 → 워크트리, 이어 쓰는 워크트리에서는 다시 하지 않음). 승인 전·바뀜이면 복사하지 않습니다. 줄마다 프로젝트에서 무시되고 추적 파일이 없으며 링크를 거치지 않는지, 새 워크트리에서도(기준 커밋의 `.gitignore`로) 무시되는지 보고, 워크트리에 이미 있으면 덮어쓰지 않습니다. 원본이 없으면 건너뛰고 실패로 치지 않습니다. 안의 링크는 워크트리 안을 가리키는 상대 링크만 글자 그대로 만들고, 절대 링크·밖으로 나가는 링크·`.git`·`.wax`·`.env*`를 가리키는 링크가 하나라도 있으면 그 줄을 복사하지 않습니다. 소켓·FIFO 같은 특수 파일은 건너뛰고, 파일의 수정 시각은 원본 그대로 둡니다. macOS는 원본과 워크트리가 같은 APFS 볼륨이면 `/bin/cp -c`(clonefile, 디스크를 거의 쓰지 않음)로 4개까지 함께 복사한 뒤 사본을 다시 걸어 링크를 검사하고, Linux는 파일마다 copy-on-write(btrfs·XFS)를 쓰고, 둘 다 안 되는 볼륨(ext4 등)은 합계 1GB까지, 남은 공간이 복사할 바이트의 두 배 이상일 때만 보통 복사합니다. 한 워크트리에 파일 30만 개, 3분까지입니다. 한도를 넘거나 입출력 오류가 나면 그 줄의 부분 사본을 지우고 준비 스크립트가 처음부터 설치합니다(작업자는 그대로 뜹니다). 사람이 복사 중에 작업자나 목표를 멈추면 부분 사본을 지우고 작업자를 띄우지 않으며 다음 시작 때 다시 복사합니다. Windows에서는 빠른 복사를 하지 않습니다(보안 검사와 긴 경로 때문에 설치보다 느릴 수 있어, 실제 PC에서 잰 뒤 켭니다). 결과는 목표 화면 워크트리 줄과 워크트리 현황의 준비 칸에 "복사 N개"로 나오고, 목록(`.wax/chat/worktrees.jsonl`)에는 줄마다 경로·결과·파일 수만 남깁니다(파일 이름은 남기지 않음). 복사한 폴더 아래 경로는 작업자가 `.gitignore`를 고쳐 무시가 풀렸거나 그 안을 커밋했어도 가져오지 않고, 미리보기의 **복사한 빌드 폴더** 줄에 개수로 보이며, 워크트리 현황의 줄 수·판정에서도 뺍니다.
  - **포트:** 워크트리마다 41000~41999에서 프로젝트의 다른 워크트리와 겹치지 않고 이 컴퓨터에서 다른 프로그램이 쓰지 않는 포트(127.0.0.1·::1에 잠깐 열고 이어 보아 확인)를 정해 작업자 환경의 `WAX_PORT`와(준비 스크립트가 승인됐으면) `portEnv` 이름(PORT로 끝나는 이름만)에 넣습니다. 확인할 수 없는 환경이면 프로젝트 안에서만 겹치지 않게 고릅니다. 확인과 실제 사용 사이에 다른 프로그램이 가져갈 수는 있습니다. 목표 화면의 워크트리 목록에 브랜치·작업·포트·복사한 .env·준비 결과가 나옵니다.
  - **로컬로 가져오기:** 목표 화면의 워크트리 목록에서 쓰는 중인 워크트리마다 상태·브랜치·바뀐 파일 요약과 **로컬로 가져오기**가 나옵니다. 누르면 먼저 읽기만 하는 미리보기를 보여 줍니다: 브랜치의 커밋과 워크트리의 커밋 안 된 변경을 함께 프로젝트 HEAD와 `git merge-tree --write-tree`로 합쳐 보고(Git 2.38 이상), 가져올 파일(새 파일·고친 파일·지운 파일, 줄 수)과 가져오지 않는 파일(`.git/`·`.wax/`·`.env*`, 링크, 하위 모듈)을 보여 줍니다. 충돌이 있으면 충돌 파일 목록만 보이고 가져오지 않습니다. 프로젝트 작업 폴더에 커밋 안 된 변경이 있거나(`.wax/` 제외) 이 목표의 작업자(또는 격리 브랜치를 켜지 않은 목표의 작업자)가 돌고 있으면 확인 버튼이 꺼지고 서버도 409로 거절합니다. **이대로 가져오기**를 누르면 서버가 미리보기를 다시 계산해 그사이 바뀌었으면 409로 거절하고, 같으면 가져오기 전 스냅숏을 남긴 뒤 파일만 프로젝트 작업 폴더에 씁니다(`git merge --squash --no-commit`의 결과와 같은 파일, 바이트 그대로, 실행 비트 포함). 커밋하지 않은 변경으로 남으므로 커밋과 push는 직접 하세요. 프로젝트 `.git`(index·HEAD·브랜치·MERGE_MSG·SQUASH_MSG·객체)은 건드리지 않습니다. 합쳐 보는 데 쓰는 객체는 운영체제 임시 폴더에만 만들고 지웁니다. 되돌리려면 그 작업의 실행 기록에서 **로컬로 가져오기** 실행의 **이 가져오기 되돌리기**를 누릅니다(실행별 되돌리기와 같은 흐름). 되돌리면 그 워크트리는 다시 쓰는 중이 됩니다. 한 번에 200개·64MB까지 가져옵니다(되돌리기 스냅숏 한도). 워크트리의 추적 안 된 파일도 가져옵니다. 다만 준비 스크립트가 `.gitignore` 밖에 만든 파일(`node_modules/` 등)은 준비가 끝난 직후 기록해 두고, 그 뒤로 내용이 그대로이면 가져오지 않습니다. 미리보기에 **준비 스크립트가 만든 뒤 그대로인 파일 N개는 가져오지 않습니다**와 폴더별 개수가 나옵니다. 작업자가 고친 준비 파일은 가져옵니다. 그 기록이 없거나 바뀌었거나 너무 커서(10만 개 넘음) 남기지 못했으면 무엇이 준비 출력인지 가를 수 없어 가져오지 않고, 직접 병합할 명령을 보여 줍니다. 준비 출력은 `.gitignore`에 넣어 두는 것이 가장 좋습니다. 가져온 워크트리는 더 쓰지 않으므로, 작업이 끝나기 전에 가져오면 다음 단계 작업자는 브랜치 끝(커밋된 변경만)에서 새 워크트리를 만듭니다. Git이 2.38보다 낮으면 버튼이 꺼지고 대신 할 명령(워크트리에서 `git add -A`·`git commit`, 프로젝트에서 `git merge --squash --no-commit <브랜치>`)이 나옵니다.
  - **가져오지 않고 버리기·워크트리 정리:** 쓰지 않을 워크트리는 **가져오지 않고 버리기**로 버림 상태로 둡니다. 목표 화면의 **워크트리 정리**는 가져왔거나 버린 워크트리만 `git worktree remove --force`로 지웁니다(훅은 돌지 않음). 그 폴더 안의 커밋 안 된 변경도 지워지고, 프로젝트 `.git`에서는 `.git/worktrees/<목표>-<n>/` 항목만 지워집니다. 브랜치는 지우지 않으므로 필요 없으면 `git branch -D`로 직접 지우세요. 쓰는 중인 워크트리는 건드리지 않습니다.
  - **워크트리 현황(대시보드·CLI, 정리 제안 말고는 읽기 전용):** 상세 기록 화면의 PM 루프 위 **워크트리 현황** 표가 프로젝트의 모든 워크트리를, 목표 화면의 격리 브랜치 칸이 그 목표의 워크트리를 같은 표로 보여 줍니다. CLI는 `wax worktree list [--goal <목표>] [--all] [--fast] [--json]`입니다. 둘 다 프로젝트의 워크트리를 목록에서 최근에 바뀐 것부터 보여 줍니다. 줄마다 상태, 활동(**작업자 실행 중**: 끝 기록이 없는 작업자 실행 / **사람 기다림**: 이 목표의 대기 실행 승인이나 끝났지만 완료가 아닌 마지막 실행 / **쉬는 중**), 목표·작업·브랜치, 커밋 안 된 파일 수(`.wax/`와 준비 출력 기준선 제외), 기준보다 앞선 커밋 수, 그 뒤 프로젝트 브랜치가 움직인 커밋 수, 만든 때와 마지막 커밋(제목), 마지막 실행, 그 워크트리에서 남긴 마지막 테스트 근거(그 뒤 바뀐 파일 수), 준비 결과, 포트와 개발 서버 주소(`http://127.0.0.1:<포트>`, 새 창으로 열림, 127.0.0.1·::1에 50ms 이어 보아 켜짐·꺼짐. 꺼져 있어도 링크는 보임)가 나옵니다. 이어서 줄 수(`+N −M`, 커밋한 것·커밋 안 된 것·추적 안 된 것, 바이너리는 개수)와 **이미 main에 있음(정리해도 됨)** 판정이 나옵니다("main"은 프로젝트 폴더가 지금 있는 브랜치 이름). 판정은 싼 것부터 봅니다: 같은 커밋 → 프로젝트 브랜치의 조상 → 바뀐 것 없음 → 파일이 모두 같음 → 합쳐도 더할 것 없음(`merge-tree`, Git 2.38 이상) → 프로젝트 브랜치의 커밋 하나와 같은 변경(`patch-id`, 갈라진 뒤 500 커밋까지). 커밋 안 된 변경은 가져오기와 같은 방법(준비 출력 기준선 제외)으로 묶어 봅니다. 가져와서 한 커밋으로 묶은 뒤 프로젝트 브랜치가 같은 줄을 더 고쳐도 잡지만, 커밋을 하나씩 골라 옮긴 경우는 잡지 못합니다. 판정할 수 없으면 **판정 모름**과 이유(시간 초과, 너무 오래돼 확인 못 함 등)입니다. 표에는 기록 칸이 먼저 보이고 줄 수와 판정은 줄마다 뒤에 채워집니다. 표는 처음 볼 때와 **새로 고침**을 누를 때 읽고, 저절로는 30초보다 자주 다시 읽지 않습니다. 판정이 **이미 main에 있음**(바뀐 것 없음 포함)이고 작업자가 돌지 않는 쓰는 중 워크트리에는 **정리** 버튼이 생깁니다. 누르면 지울 폴더, 판정, "무시된 파일(node_modules/ 등)과 이 폴더의 다른 파일이 지워집니다. 브랜치는 남습니다"가 나오고, **폴더 지우기**를 눌러야 지웁니다. 이때 서버가 캐시 없이 status·임시 커밋·판정을 다시 계산해, 화면이 본 지문(워크트리·브랜치 끝·프로젝트 HEAD·임시 커밋·판정 이유)과 같고 여전히 이미 main에 있을 때만 워크트리 정리와 같은 명령(`git worktree remove --force`, 훅 없음)으로 지우고 목록을 지움(`reason: integrated`)으로 내립니다. 본 뒤 워크트리나 프로젝트가 바뀌었거나 이 목표의 작업자가 돌고 있으면 지우지 않고 이유를 보입니다. 브랜치는 지우지 않고 `git branch -D <브랜치>` 명령을 복사할 수 있게 보여 줍니다. 사람 이름으로만 할 수 있고(엔진·auto·작업자 이름은 거절), CLI에는 이 길이 없습니다. 폴더가 사라졌거나 다른 브랜치로 옮긴 워크트리는 **폴더 없음**·**등록된 브랜치가 아님**으로 보입니다. git 칸은 목록에서 내린 것을 뺀 최근 50줄만 채우고(표에서는 **더 보기**로 50줄씩 더), 목록에서 내린 워크트리는 `--all`(표에서는 **지운 것도 보기**)일 때만 기록 칸으로 보입니다. `--fast`는 줄 수와 판정을 뺍니다. 커밋 안 된 파일이 2000개를 넘으면 줄 수와 판정을 건너뜁니다. git은 읽기 전용 명령만, 한 프로젝트에 동시에 4개까지, 명령마다 5초(`status`는 10초)·줄마다 15초·표 전체 60초 안에서 돌리고 넘은 칸만 **시간 초과**로 둡니다. 프로젝트 `.git`과 워크트리 index에 쓰지 않습니다(선택 잠금 끔). 판정과 줄 수에 새 객체가 필요하면(임시 커밋, `merge-tree`, 추적 안 된 파일의 `add -N`) OS 임시 폴더의 객체 저장소와 index 사본에만 쓰고 바로 지웁니다. 두 커밋 ID에만 달린 결과는 대시보드 메모리에만 기억합니다(파일에 남기지 않음, 최근 500개). 가져오기·버리기·워크트리 정리는 지금처럼 대시보드 목표 화면에서 사람만 합니다.
  - **PR 검토 워크트리:** 목표에 검토 단계 작업이 있으면 목표 화면의 격리 브랜치 칸에 **PR 검토 워크트리**가 나옵니다(격리 브랜치를 켜지 않은 목표도). 작업과 PR 번호를 고르고 **PR 정보 읽기**를 누르면 프로젝트 폴더에서 `gh pr view`로 제목·작성자·머리 커밋·포크인지, 바뀐 파일 가운데 실행에 걸리는 것(`docs/wax/worktree.json`, 준비·검사 해시에 드는 파일, `package.json`·잠금 파일, `.github/`, 스크립트)과 받을 원격을 보여 줍니다(PR 본문은 읽지 않고, PR 글은 글자로만 보입니다). **받기**를 누르면 프로젝트 `.git`에 쓰는 것(받은 객체, 숨은 ref `refs/wax/review/pr-<N>`, 워크트리 항목)을 보이고, **받기 확인** 뒤에야 받습니다. 받는 곳은 PR 저장소와 같은 주소의 원격(보통 `origin`)뿐이고, 없으면 받지 않습니다(원격을 더하지 않음). 얕은 클론에서도 받지 않습니다. 받은 커밋이 화면에서 본 머리와 다르면(그사이 새 push) ref를 지우고 다시 읽으라고 합니다. 워크트리는 브랜치 없이 PR 머리 커밋에 떼어 낸 HEAD(`git worktree add --detach`)로 `.wax/worktrees/<목표>-<n>/`에 만들고, 그 작업의 검토 작업자가 거기서 뜹니다. `.env`·빌드 폴더를 복사하지 않고 준비 스크립트도 돌리지 않습니다. 검토 작업자의 명령 실행은 지금처럼 사람의 실행 승인으로 가고, 목표 허용의 검사(test) 종류는 사람이 워크트리 줄의 **이 PR 코드 실행 허용**을 확인한 뒤에만 그 워크트리에서 맞습니다. 허용은 머리 커밋과 지금 프로젝트 worktree.json 해시에 묶여 `.wax/chat/review-runs.jsonl`에 남고, 새 push를 받거나 worktree.json이 바뀌면 다시 해야 합니다. 같은 저장소의 PR도 같은 허용을 거치고, 포크 PR은 크게 표시합니다. PR이 worktree.json을 바꿨으면 그렇다고 알리고 PR의 것은 쓰지 않습니다. 검토 워크트리는 가져오지 않습니다(가져오기·가져오기 전 검사·정리 제안 없음, 검토 작업자가 바꾼 파일은 버려짐). PR에 새 커밋이 있으면 **PR 정보 읽기**가 알려 주고 **새 머리로 다시 받기**는 앞 검토 워크트리를 버림으로 둡니다. 버렸거나 그 작업이 검토 단계를 지난 검토 워크트리는 **워크트리 정리**로 지우고, 이때 wax가 만든 `refs/wax/review/pr-<N>`도 지웁니다(그 ref가 아직 머리 커밋을 가리킬 때만, 같은 PR을 보는 다른 검토 워크트리가 없을 때만). 받은 객체는 `git gc`가 지울 때까지 남습니다.
  - 켜기, 준비 스크립트 승인, 가져오기, 버리기, 정리, PR 정보 읽기·받기·코드 실행 허용은 대시보드의 사람만 합니다. 작업자·auto·CLI·MCP로는 할 수 없습니다.
- **빨강→초록 필수:** 목표 시작 화면(**＋ 새 목표**와 레시피 시작 화면)과 목표 화면의 **빨강→초록 필수** 칸을 체크하면 목표에 든 작업마다 작업 기록에 `discipline.redGreen: "enforce"`가 남고, 그 작업의 구현 완료는 `WAX_RED_GREEN=enforce`처럼 빨강→초록 짝이나 `--no-red` 사유가 있어야 합니다(4절). 늘 꺼진 채 시작하고(레시피도 켜지 못함), 계획 초안으로 목표에 더해진 작업에도 같이 남습니다. 끄면 작업 기록에서 지워지고 `WAX_RED_GREEN`을 따릅니다. 끝난 목표는 끌 수만 있습니다. 켜고 끄기는 대시보드의 사람만 하며 목표 기록에 남습니다. `WAX_RED_GREEN=off`면 이 설정과 상관없이 계산하지 않습니다.

- **PM 판단:** 계획이 확정되지 않은 목표(계획 초안), 막힌 업무(막힘 판단), 보고까지 끝난 작업이 있는 목표(대표 보고) 세 곳에서만 **PM 판단 요청** 카드가 나옵니다. **PM 판단 받기**를 눌러야 목표의 PM 판단 도구를 읽기 전용 지시로 한 번 부릅니다(한 번에 10분 상한, 권한 요청은 실행 승인 화면). 판단 도구는 목표의 **한도** 안에서 요청 자동 진행 도구와 따로 고르고, 기본은 요청 자동 진행의 기본 순서에서 처음 설치된 도구입니다(headless로 띄울 수 없는 도구는 나오지 않음). 판단에는 목표, 작업마다 `wax context`, 최근 결정과 막힘 기록이 지시가 아닌 인용 데이터로 들어갑니다. 결과는 정해진 JSON 스키마로만 받아 **PM 판단 제안** 카드로 보여 주고, 사람이 고쳐서 받아들이거나 버립니다. 스키마 밖 결과는 버리고 이유와 함께 **PM 판단 넘김** 카드로 사람에게 넘깁니다. 받아들이면 이미 있는 행동으로만 옮깁니다: 막힘의 다시 시도·다시 맡김은 배정을 회수하고, 받아들인 도구를 그 작업의 **선호 작업자 도구**로 정해 남은 단계의 작업자 카드에서도 기본 도구로 씁니다(띄우기는 다시 확인). 검토자 분리가 먼저라, 선호 도구가 구현했으면 검토는 다른 도구(막혔던 도구는 되도록 피함)로 고르고 다른 도구가 없으면 사람에게 묻습니다. 사람이 작업자 카드에서 다른 도구를 고르거나 작업이 끝나면 선호를 지우고, 지운 사실을 기록과 실행 기록에 남깁니다. 질문·되돌리기 제안은 막힌 업무 카드에 질문이나 `wax iterate` 안내만 보여 줍니다. 계획 초안은 없는 작업을 만들고 기획 문서가 빈 작업에 AC 초안을 저장하지만, 계획 확정은 따로 사람이 누릅니다. 대표 보고는 `.wax/chat/pm-loop/`에 초안 파일만 씁니다. 자리마다 판단은 한 번이고, 판단 요청도 하루 headless 실행 한도(20번)에 셉니다.
- **실행:** 카드로 할 수 있는 일은 배정(PM 규칙 그대로, 이 화면의 사람이 PM이어야 함), 세션에 다시 알리기, 배정 회수(취소), PR 초안 파일 만들기, 작업자 시작, PM 판단 요청과 그 제안 받아들이기뿐입니다. 작업자의 시작·종료·시간 초과·실패·멈춤도 이유와 함께 같은 기록에 남습니다. 실행하거나 버린 카드는 이유와 함께 `.wax/chat/pm-loop/<목표>.jsonl`에 남고, 작업의 실행 기록에도 나옵니다.

- **실행별 파일 스냅숏과 되돌리기:** headless 작업자를 띄우기 직전과 끝난 직후에 작업 트리 상태를 남깁니다. 남기는 범위는 근거 신선도와 같습니다: 그때의 커밋과, 그 커밋과 다른 파일·`.gitignore` 밖의 추적 안 된 파일(`.wax/` 제외). 그 파일들의 바이트는 프로젝트 `.git`이 아니라 wax 전용 저장소 `.wax/chat/snapshots/objects.git`에 줄 끝 변환 없이 넣고, 커밋에 있는 내용은 복사하지 않고 되돌릴 때 프로젝트 저장소에서 읽기만 합니다. 바뀐 파일 200개·합계 64MB·git 명령 5초를 넘거나 Git 저장소가 아니면 **미확인**으로 남기고, 작업자는 그대로 띄웁니다.
  - **실행 기록:** 작업자가 일한 방문에 **이 실행이 바꾼 파일(커밋 안 된 변경 포함)**이 실행마다 나옵니다(새 파일·고친 파일·지운 파일과 더하고 뺀 줄 수, 크거나 이진 파일은 "+? −?"). 파일을 누르면 그 파일의 diff가 펼쳐집니다. 같은 폴더에서 다른 작업자가 함께 돌았으면 그 수를, 실행 중 커밋이 생겼으면 커밋 수를 적습니다. 커밋 사이 차이(**바뀐 파일**)는 그대로 그 위에 있습니다.
  - **이 실행 전으로 되돌리기(사람만):** 실행 기록에서 **이 실행 전으로 되돌리기**를 누르면 미리보기가 나옵니다. 그 실행이 바꾼 파일 가운데 지금 내용이 실행이 끝났을 때와 같은 파일만 **되돌림**(실행 전 내용으로 쓰기, 실행 전에 없던 파일은 지우기)이고, 실행 뒤 사람이나 다른 작업자가 고친 파일, 링크, 프로젝트 밖, `.git/`·`.wax/`·`.env*`는 이유와 함께 **건드리지 않음**입니다. **되돌리기 확인**을 누르면 서버가 미리보기를 다시 계산해 그사이 바뀌었으면 거절하고, 쓰기 직전 상태를 먼저 스냅숏으로 남긴 뒤(그래서 **이 되돌리기를 되돌리기**로 되돌릴 수 있음) 파일을 씁니다(임시 파일에 쓰고 이름 바꾸기). 파일 내용만 되돌리고 커밋·브랜치는 건드리지 않습니다. 실행 중 커밋이 있었으면 미리보기가 알려 주고, 커밋을 없애는 것은 사람이 git으로 합니다. `.gitignore`에 맞는 파일(`node_modules/`, `.env` 등)은 스냅숏에 없어 되돌리지 않습니다. 프로젝트에 실행 중인 작업자가 있으면 되돌리기를 받지 않습니다(먼저 멈추세요). 되돌리기는 `.wax/chat/snapshots/restores.jsonl`과 목표 결정 기록(**되돌리기 · 되돌림**)에 남습니다.
  - **CLI(읽기 전용):** `wax snapshot list [--goal <목표>]`, `wax snapshot show <실행>`(바뀐 파일과 diff). 되돌리기는 대시보드에만 있습니다(작업자도 CLI를 쓰므로).
  - **보존:** 목표가 완료·정지되고 30일이 지났거나 스냅숏 저장소가 1GB를 넘으면 끝난 목표의 오래된 실행부터 지우고 wax 전용 저장소만 정리(`git gc`)합니다. 진행 중인 목표의 스냅숏은 지우지 않습니다. 스냅숏에는 커밋 안 된 파일 내용이 들어 있으니 `.wax/`를 공개 저장소에 올리지 마세요. 요청 자동 진행과 디자인실 실행에는 아직 스냅숏을 남기지 않습니다.
- **한도와 정지:** 목표마다 단계 실행 15번(작업자 시작 포함), 동시 작업자 2명(실행 중인 작업자 포함), 8시간, 되돌리기 3번, 연속 막힘 3번(작업자의 실패·시간 초과는 막힘으로 셈), auto 시간당 행동 12번(auto일 때만), 작업자 무응답 멈춤 10분, 되풀이 기준 3번, 원인 찾기 시도 2번. 전체로는 headless 실행(작업자 시작과 PM 판단 요청)이 하루(24시간) 20번까지입니다. 같은 작업·단계에 열린 배정이나 실행 중인 작업자가 있으면 새로 띄우지 않습니다. 한도에 닿으면 멈추고, 한도를 늘려 재개하는 것은 사람만 합니다. **목표 정지** 버튼으로 언제든 멈춥니다.
- **auto 모드:** 기본은 suggest(모든 행동이 카드)입니다. 목표 화면의 **모드** 칸에서 **auto 켜기**를 누르면 그 목표만 auto가 됩니다. 켜는 것은 대시보드의 사람만 할 수 있고, auto가 그 사람 이름으로 배정하므로 PM이어야 합니다. 바꾼 사실은 기록에 남습니다. auto가 카드 없이 하는 일은 듣고 있는 세션에 현재 단계 배정, done 경고가 난 세션에 첫 번째 다시 알림, headless 작업자 시작(검토는 구현과 다른 도구, 받아들인 다시 맡김의 도구는 남은 단계에도, 구현·검토의 기본 도구가 Antigravity CLI면 설치된 다른 도구로, 다른 도구가 없으면 카드로 남김), 30분 멈춘 배정 회수, 막힌 업무의 PM 판단 요청과 그 결과 중 **다시 시도·다시 맡김** 반영뿐입니다. 계획 확정과 계획 초안 반영, 실행 승인과 권한 요청, 규칙 승인, 트리거 제안 수락, PR 만들기·push·병합(report 뒤 PR 초안 카드는 사람을 기다림), 한도 늘리기, 대표 보고, 사람에게 넘김·질문·되돌리기는 auto에서도 카드로 남고, 이런 카드가 나오면 브라우저 알림이 옵니다. auto는 사람이 누를 때와 같은 확인과 한도를 거치고, 목표마다 **auto 시간당 행동 수(기본 12)**가 더 있습니다. 어느 한도에 닿거나 auto 행동이 실패하면 목표를 멈추고 알립니다. **목표 정지**를 누르면 실행 중인 작업자와 판단도 바로 멈춥니다. auto가 한 일은 `by: auto`와 규칙 이름, 이유와 함께 기록·실행 기록·목표 화면의 **auto 활동**에 나옵니다. 대시보드가 둘이어도 한 번만 실행합니다.
- **실패 뒤 다시 시도(auto 규칙):** 대시보드를 `WAX_STUCK_CHECK=stop`으로 시작했고, 실패한 작업자 실행의 앞뒤 스냅숏이 모두 남았을 때(Git 저장소 프로젝트)만 판단 없이 한 번 다시 시도하는 **다시 시도(규칙)** 카드가 나옵니다. 토큰 한도를 정한 목표에서는 사용량을 알리는 도구로, 비용 한도를 정한 목표에서는 비용을 알리는 도구로 띄울 때만입니다. auto 목표는 이 카드를 바로 실행하고, suggest 목표는 사람이 누릅니다. 도구 상태 실패(사용 한도·설정·headless 권한)는 그 단계를 상태가 괜찮은 다른 도구로 다시 맡깁니다(`switch-unhealthy`, 검토는 구현 도구가 아닌 도구, 고를 도구가 없으면 지금처럼 사람 카드). 일시 실패(`transient`)는 2분 뒤 같은 도구로 다시 띄웁니다(`retry-transient`, 일시 실패를 알아보는 규칙은 실제 출력 예시가 생기면 더합니다). headless 작업자가 단계를 완료하지 않고 done을 보고한 첫 번째는 같은 도구로 다시 띄우고, 지시문 맨 앞에 그 사실을 적습니다(`retry-unfinished`, 두 번째는 지금처럼 사람에게 넘김). 막힘 판단이 스키마 밖·실패·시간 초과면 상태가 괜찮은 다른 판단 도구로 한 번 다시 묻습니다(`retry-judge`). 모두 단계(판단은 자리)마다 한 번이고, 다른 auto 행동과 같은 한도를 셉니다. 조건이 맞지 않으면 지금처럼 막힌 업무 카드와 막힘 판단이 나오고, auto 목표의 카드에는 규칙을 쓰지 않은 이유가 붙습니다. 기본값 `warn`에서는 이 규칙이 동작하지 않습니다.
- **CLI(읽기 전용):** `wax pm-loop list`, `wax pm-loop show <목표>`(모드와 auto 사용량 포함), `wax pm-loop next <목표>`(지금 계산한 제안만 보여 주고 아무것도 쓰지 않음). CLI로는 모드를 바꿀 수 없습니다.
- **사용량:** headless 작업자와 PM 판단이 끝나면 도구가 스스로 알린 사용량을 그 실행의 기록에 남깁니다. Claude Code는 입력·출력·캐시 읽기·캐시 쓰기·추론 토큰과 비용·차례 수를, Antigravity CLI는 입력·출력·추론·캐시 읽기·합계 토큰과 차례 수를 알립니다. Codex, Gemini CLI, GitHub Copilot CLI는 알리지 않음으로 남습니다. wax는 가격을 계산하지 않고, 캐시 토큰을 입력에 더하지 않으며, 도구마다 토큰의 뜻이 달라 도구별로 따로 더합니다. 목표 화면의 한도 칸, `wax pm-loop show`, 실행 기록, `wax status`, PR 설명 초안에 나오고, 보고 단계 지시에는 이 합계가 인용 데이터로 들어가 보고서가 숫자를 지어내지 않고 이 값을 인용합니다. 이 기능 전의 기록은 "사용량 기록 없음"으로 셉니다.
- **토큰 한도(선택):** 목표를 만들 때나 재개할 때 **토큰 한도**(1,000~10,000,000,000, 비우면 없음)를 정할 수 있습니다. 도구가 알린 토큰(합계를 알리면 그 값, 아니면 입력·출력·캐시 토큰의 합) 합이 한도에 닿으면 다른 한도처럼 목표가 멈추고, 실행 중인 작업자는 끝까지 둡니다. 사용량을 알리는 도구(Claude Code, Antigravity CLI)에만 걸리므로, 한도를 정한 목표에서 auto는 사용량을 알리지 않는 도구를 띄우지 않고 사람 카드로 남깁니다(카드에 경고가 붙고, 사람은 고를 수 있습니다). 늘리는 것은 재개하는 사람만 합니다.
- **비용 한도(USD, 선택):** 목표를 만들 때나 재개할 때, 레시피의 한도에서 **비용 한도(USD, 선택)**(0.01~10000달러, 소수 둘째 자리까지, 비우면 없음)를 정할 수 있습니다. 소수점은 `.`으로 적습니다(`1,5`처럼 쉼표를 쓰면 거절하고 안내합니다). 도구가 알린 비용(지금은 Claude Code만 알립니다)의 합이 한도에 닿거나 넘으면 그 실행이 끝난 뒤 목표가 멈추고, 실행 중인 작업자는 끝까지 둡니다. wax는 가격을 계산하지 않습니다. 구독 로그인에서는 실제 청구액이 아니라 도구가 API 가격으로 친 값일 수 있어, 화면에 늘 "도구가 알린 비용(실제 청구와 다를 수 있음)"이 붙습니다. 비용을 알리지 않는 실행(Codex·Gemini CLI·GitHub Copilot CLI, 토큰만 알리는 Antigravity CLI, 옛 기록)은 0으로 더하지 않고 "알 수 없음 N번"으로 따로 세며, 그것 때문에 멈추지 않습니다. 한도를 정한 목표에서 auto는 비용을 알리지 않는 도구를 띄우지 않고(다시 시도 규칙도 쓰지 않습니다) 사람 카드로 남깁니다(카드에 "이 도구는 비용을 알리지 않습니다" 경고가 붙고, 사람은 고를 수 있습니다). 목표 화면에는 `$1.23 / $5.00 · 알 수 없음 2번`처럼, PR 초안과 실행 기록의 사용량에는 "도구가 알린 비용 $1.23(2번은 알 수 없음, …)"으로 보입니다. 늘리는 것은 재개하는 사람만 합니다.
- **한도 바꾸기와 재개:** 목표 화면의 **한도**에서 사람이 목표별 한도와 PM 판단 도구를 정합니다(단계 실행 1~200, 동시 작업자 1~10, 시간 1~168, 되돌리기 0~50, 연속 막힘 1~20, auto 시간당 행동 1~120, 무응답 멈춤 0~30분, 0이면 끔. 출력 없이 오래 도는 검사가 있으면 늘리세요. 되풀이 기준 2~10, 오래 걸리는 검사를 같은 결과로 다시 돌리는 것이 정상인 프로젝트는 늘리세요. 원인 찾기 시도 1~5. 토큰 한도와 비용 한도는 선택이며 비우면 없앱니다). 하루 headless 20번은 프로젝트 전체 한도라 바꾸지 않습니다. 한도에 닿아 멈춘 목표는 **목표 재개**에서 한도를 확인하고 이어 갑니다.
- **검증 범위:** 단위 테스트와 브라우저 검사는 작업자와 PM 판단을 가짜 실행부로 바꿔 돌립니다. 2026-10-31에 macOS에서 실제 도구로 한 바퀴를 돌렸습니다(설계 문서 `docs/design/PM_LOOP.md`의 "실제 도구 한 바퀴"). Claude Code 작업자는 plan·design·implement·report를 실제로 끝내고 정해진 JSON으로 결과를 돌려줬고, Claude Code PM 판단(막힘·대표 보고)은 읽기 전용 지시를 지키며 스키마를 통과했습니다. 검토자 분리는 구현한 도구를 검토 도구 목록에서 뺐고, auto는 Codex 실패 → 막힘 판단 → 다른 도구로 다시 맡김을 카드 없이 이어 가다 하루 한도에서 멈췄습니다. 이 컴퓨터의 Codex는 계정 문제로 실행되지 않아 Codex 작업자의 성공은 확인하지 못했고, Antigravity CLI 작업자는 비대화형 모드에서 명령 실행 권한을 물을 수 없어 검토를 끝내지 못했습니다(Antigravity CLI 설정 `permissions.allow`에 필요한 실행을 허용해야 함). 이때 드러난 세 가지(받아들인 "다시 맡김"이 그 단계에만 적용되어 auto가 단계마다 실패한 도구를 다시 띄움, Antigravity CLI의 명령 권한을 카드가 미리 알리지 않음, 실행 기록의 실행 도구가 `-`로 나옴)는 위처럼 고쳤고 가짜 도구로 검사했습니다. 고친 뒤 실제 도구로 다시 돌리지는 않았습니다. 읽기 전용은 지시로만 걸고 도구의 권한 설정을 바꾸지 않으므로, 판단 중 쓰기 권한 요청이 오면 실행 승인 화면에서 거부하세요.

### 레시피로 시작

자주 하는 일(버그 하나 고치기 등)은 **레시피**로 목표를 한 번에 시작합니다. 레시피는 목표의 시작 값(작업과 수용 기준 초안, 단계별 기본 작업자 도구, PM 판단 도구, 한도, 단계 메모)을 저장해 둔 틀일 뿐이고, 레시피로 만든 목표도 보통 목표와 똑같이 흐릅니다.

- **시작:** PM 루프의 **레시피로 시작**을 누르고 레시피를 고른 뒤 **이 레시피로 시작** → 입력 한 줄(예: 버그 수정은 "무엇이 고장 났나요?")을 적고 **채우기**를 누릅니다. 레시피가 설명칸을 두면(내장 레시피는 모두, 예: 버그 수정의 "재현 방법과 기대 동작") 그 아래 여러 줄 칸(2000자, 선택)에 자세한 내용을 적습니다. 목표 제목, 작업 ID(입력으로 만든 조각 `{slug}`, 영문이 없으면 짧은 해시이고 고칠 수 있음), 작업 제목과 AC, 단계별 기본 작업자 도구, PM 판단 도구, 한도가 미리 채워지고 모두 고칠 수 있습니다. **목표 만들기**를 누르면 서버가 고친 값을 레시피와 같은 검사로 다시 확인합니다(형식 밖이면 거절, 작업이 이미 다른 진행 중 목표에 있으면 지금처럼 거절). 설명칸의 글은 이때 작업 설명 틀(`{details}`)에 채워져 새 작업의 설명이 되고, 작업자 지시문에는 지시가 아닌 인용 데이터로만 들어갑니다. 설명칸을 비우면 설명 없이 만듭니다.
- **계획 확인은 그대로 사람이:** 기획 문서가 빈 작업에 AC 초안(`- AC-n:`)을 바로 저장하므로 계획 초안 판단(AI 한 번)은 나오지 않습니다. 목표는 계획 확인 전으로 시작하고, **계획 확인하고 시작**을 눌러야 진행됩니다. 목표는 늘 suggest로 만들어지고, 레시피의 auto는 **auto 권장** 표시일 뿐입니다(켜는 것은 목표 화면에서 PM).
- **단계별 기본 도구:** 작업자 카드의 기본 도구만 바꿉니다. 이 컴퓨터에 설치된 도구일 때만 쓰고, 검토는 구현 도구와 같으면 무시하고 기존 순서로 고르며, 막힘 판단으로 정해진 선호 도구가 있으면 그것이 먼저입니다. 이 도구로 고른 카드와 기록의 이유에는 "레시피 기본 도구"라고 나옵니다. 구현·검토에 Antigravity CLI를 정해도 명령 권한 경고와 auto의 다른 도구 고르기는 그대로입니다. 띄우기는 매번 사람이 확인합니다.
- **단계 메모:** 그 단계 작업자 지시문에 지시가 아닌 인용 데이터(`@이름` 무력화)로만 들어갑니다. push·PR 금지, 근거 면제 금지, 프로젝트 밖 쓰기 금지 같은 고정 문장이 앞섭니다.
- **내장과 개인:** 내장 레시피는 **버그 수정**(`bugfix`, 단계 실행 8번·2시간), **기능 추가**(`feature`, 기본 한도), **동작 유지 정리**(`refactor`, 단계 실행 8번·4시간) 세 개이고 특정 도구를 정하지 않습니다. 개인 레시피는 이 컴퓨터의 `.wax/recipes/<id>.json`(Git에 올라가지 않음)이고, 같은 id면 개인 → 공유 → 내장 순으로 먼저 쓰입니다. 레시피 칸의 **＋ 새 레시피**, **고치기**(내장은 **개인 레시피로 고치기**), **지우기**로 대시보드에서 사람만 관리합니다(JSON 편집, 저장할 때 같은 검사). 파일을 직접 고쳐도 되지만, 검사에 걸린 레시피는 목록에 이유와 함께 **쓸 수 없음**으로 나옵니다. 저장·지우기 기록은 `.wax/chat/recipes.jsonl`에 남습니다.
- **공유 레시피:** 저장소의 `docs/wax/recipes/<id>.json`에 둔 레시피는 팀이 함께 씁니다. 다른 사람이 올린 레시피가 이 컴퓨터의 도구 선택이나 작업자 지시를 몰래 바꾸지 않도록, 이 컴퓨터에서 사람이 **검토**를 눌러 정리된 내용 전체(작업·AC·설명 틀·도구·판단 도구·한도·메모·허용 제안)와 직전에 승인한 내용과의 차이를 보고 **이 내용 승인**을 눌러야 시작할 수 있습니다. 승인은 파일 내용(sha256)에 묶여, 파일이 한 글자라도 바뀌면 **승인 뒤 바뀜(승인 필요)**으로 돌아갑니다. 승인 전이거나 바뀌었거나 검사에 걸린 공유 레시피는 시작 버튼이 없고, 같은 id의 내장 레시피로 대신 시작하지도 않습니다. **거절**과 **폐기**(승인 거두기)도 있고, 승인·거절·폐기는 이 컴퓨터의 `.wax/chat/recipes.jsonl`에만 남습니다(파일은 바꾸지 않음).
- **프로젝트 매뉴얼:** 저장소의 `docs/wax/manual.md`에 팀이 함께 지킬 작업 규칙과 확인 기준(예: "화면을 바꾸면 390px 캡처를 남김")을 적어 두면, 레시피 칸 맨 위 **프로젝트 매뉴얼**의 **검토**에서 본문 전체·검사 명령 제안·직전 승인본과의 차이를 보고 **이 내용 승인**을 누른 뒤부터 PM 루프 작업자 지시문, `wax prompt <단계> <작업ID>`, 대시보드 요청의 단계 지시문에 인용 데이터로 들어갑니다. `wax context`에는 본문 대신 승인 상태와 해시가 나옵니다. 지시가 아닌 데이터로 들어가고 wax의 고정 지시가 앞서며, PM 판단에는 넣지 않습니다. 16KB·400줄을 넘거나 숨은 문자가 있으면 잘라 쓰지 않고 쓸 수 없음으로 둡니다. 승인은 공유 레시피처럼 파일 내용(sha256)에 묶여, 작업자를 포함해 누가 파일을 고치면 다시 승인할 때까지 빠집니다(예전 승인본으로 대신 쓰지 않음). 맨 앞에 `---` / `checks: ["npm test"]` / `---` 블록을 두면 목표 시작 화면의 검사 명령 칸 아래에 제안으로만 나오고, 눌러야 칸에 채워집니다. `wax quality-report`는 이 검사 명령마다 현재 주기에 통과한 테스트 근거가 있는지 관찰값으로 보여 줄 뿐, 명령을 실행하거나 완료 조건으로 강제하지 않습니다. 매뉴얼은 허용·도구·한도·모드를 바꾸지 못합니다. 결정은 이 컴퓨터의 `.wax/chat/manual.jsonl`에만 남고, 작업자 시작·끝 기록과 실행 기록에 넣은 매뉴얼의 해시 앞 12자가 남습니다.
- **공유로 내보내기:** 개인 레시피의 **공유로 내보내기**는 그 레시피를 `docs/wax/recipes/<id>.json`에 쓰고(같은 이름이 있으면 덮어씀) 이 컴퓨터에서는 승인한 것으로 기록합니다. 대시보드가 공유 파일을 쓰는 것은 이때뿐입니다. 저장소에 올리는 commit·push는 직접 하고, 다른 컴퓨터에서는 그 사람이 승인해야 쓰입니다.
- **목표를 레시피로 저장:** 끝났거나 멈춘 목표 화면의 **레시피로 저장**은 그 목표로 개인 레시피 초안을 만들어 편집기에 엽니다. 작업 제목과 AC는 목표의 작업 그대로(작업 ID는 `<앞부분>-{slug}`), 단계별 도구는 그 단계를 실제로 끝낸 작업자의 도구(실패한 도구는 빠짐), PM 판단 도구는 목표의 값, 한도는 쓴 값의 1.5배(올림, 범위 안), 메모는 비어 있습니다. 목표 제목 틀(`goal`)에 입력 자리 `{input}`을 넣어야 저장됩니다(예: `"{input} 고치기"`). 저장 기록에는 어느 목표에서 왔는지(`from`)가 남습니다.
- **형식:** `schema: 1`, id는 영문 소문자·숫자·-(64자), 정해진 속성만, 숨은 문자 없음, 이름 200자·설명 500자·입력 안내 200자·단계 메모 1000자, 설명칸 안내 200자·예시 500자, 작업 1~20개(제목 200자, 설명 틀 1000자, AC 작업마다 1~10개·300자), 자리 표시는 `{input}`과 `{slug}`(작업 설명 틀은 `{input}`과 `{details}`, 메모는 셋 다)뿐, 도구는 headless로 띄울 수 있는 도구만, 한도는 목표 한도와 같은 범위(빠진 한도는 기본값), mode는 `suggest` 또는 `auto`, 허용 제안 `allow`는 `wax`·`test`·`write`·`read` 중에서만(제안일 뿐 켜지 않음). 파일 하나 64KB, 위치(개인·공유·내장)마다 레시피 50개까지 읽습니다. 단계를 건너뛰는 설정은 없습니다.
- **기록:** 목표와 `goal created` 기록에 레시피 id·위치·파일 해시와 시작 화면에서 고친 칸이 남고, 목표 화면과 실행 기록에 **레시피: <이름>**이 나옵니다.
- **CLI(읽기 전용):** `wax recipe list`, `wax recipe show <id>`, `wax recipe check [<파일>]`(파일 하나 또는 모든 레시피를 같은 검사로 확인, 쓸 수 없는 것이 있으면 종료 코드 1). 공유 레시피는 이 컴퓨터의 승인 상태와 함께 나오고, 승인 전인 것은 종료 코드를 바꾸지 않습니다. CLI로는 레시피를 만들거나 승인하거나 목표를 시작하지 않습니다.

## 6-7. 프로젝트 규칙과 위키

### 프로젝트 규칙

**프로젝트 규칙**은 AI의 실수를 다음 세션이 되풀이하지 않게 하는 짧은 규칙입니다. 검토에서 실제 결함을 찾았을 때나 PM이 진행을 볼 때, AI 세션이 실수 기록(검토 중 실패한 테스트·개선 사유·막힌 업무·검토에서 찾은 결함 `defect:<작업>/D-N`)을 근거로 붙여 `wax chat rules propose`로 제안합니다. 근거 없는 제안과 같은 문장의 규칙은 받지 않습니다. 대시보드(`/manage`)의 **프로젝트 규칙** 패널에서 사람이 승인하면 그때부터 모든 단계 지시문(`wax prompt`, 대시보드 자동 진행)과 `wax context`에 들어가고, 거절하거나 나중에 폐기할 수 있습니다. CLI에는 승인 명령이 없어 AI가 스스로 규칙을 확정하지 않습니다. 지시문에는 지금 코드와 맞지 않는 규칙은 따르지 말고 보고하라는 안내가 함께 들어갑니다. `wax chat rules lint`는 근거 기록을 더 이상 찾을 수 없는 적용 중 규칙을 알립니다.

`wax chat rules`는 적용 중인 규칙을, `--all`은 대기·거절·폐기된 규칙까지, `rules candidates`는 아직 어떤 규칙도 인용하지 않은 실수 기록을 보여 줍니다. 제목(대소문자·공백·문장부호 무시)이 같은 결함이 여러 작업에서 나왔으면 "반복된 결함"으로 맨 앞에 둡니다. 같은 실수를 막는 규칙의 근거로 가장 쓸모 있기 때문입니다. 매뉴얼(`docs/wax/manual.md`)은 wax가 고치지 않으므로, 팀이 함께 지킬 기준이 되면 사람이 규칙을 매뉴얼로 옮깁니다. 지시문에는 승인된 규칙 중 최근 20개가 들어갑니다. 대시보드 패널은 승인 대기 → 적용 중 순서로 보여 주고 거절·폐기는 접어 두며, CLI로 제안한 규칙은 1~2초 안에 패널에 나타납니다. 기록은 `.wax/chat/rules.jsonl`에 덧붙이기만 합니다.

### 프로젝트 위키

원본 기록은 그대로 두고, AI 세션이 주제별로 정리한 페이지를 `docs/wax/wiki/<페이지>.md`에 둡니다. 페이지의 문단과 목록 항목마다 `[근거: <기록 ID>]`가 있어야 저장되고, 인용한 기록이 실제로 있어야 합니다. 근거로 쓸 수 있는 것은 `wax wiki ingest`가 보여 주는 기록 ID(작업 `feature:`, 단계 문서 `doc:`, 결정 `note:`·`msg:`, 검토 중 실패한 테스트 `proof:`, 개선 사유 `iterate:`, 막힌 업무 `blocked:`, 검토에서 찾은 결함 `defect:`, 프로젝트 규칙 `rule:`)와 `commit:<해시>`, `file:<경로>[#L10-L20]`입니다. wax는 AI를 부르지 않습니다. 정리는 일일 보고 뒤나 대표가 요청할 때 AI 세션이 합니다.

```sh
wax wiki ingest --batch 20          # 아직 반영하지 않은 기록 묶음(오래된 것부터)
wax wiki save auth --file auth.md   # 근거를 확인해 저장. 이미 있는 페이지는 --base <hash> 필요
wax wiki skip doc:login/plan        # 위키에 남기지 않을 기록
wax wiki lint                       # 근거 없는 문단·사라진 근거(오류), 폐기된 규칙·저장 뒤 바뀐 파일(확인)
```

이미 있는 페이지는 읽을 때의 hash(`wax wiki show`)를 `--base`로 넘겨야 고쳐지므로, 다른 세션이 고친 내용을 덮어쓰지 않습니다. 인용한 기록은 반영한 것으로 표시되어 다음 묶음에서 빠집니다. 개선 주기로 단계 문서가 바뀌어 근거가 사라지거나, 저장한 뒤 커밋으로 인용 파일이 바뀌면 `lint`가 알립니다. `wax context`는 이 작업을 인용한 페이지를, 대시보드(`/manage`)의 **프로젝트 위키** 패널은 페이지와 점검 결과를 보여 주고, `wax search`·`wax recall`도 위키 페이지를 찾습니다. 위키는 참고 자료이므로 지금 코드에서 다시 확인하세요. 실제로 실행하지 않은 테스트는 통과했다고 기록하면 안 됩니다.

## 6-8. 프로젝트 종류와 B1 디자인실

요청과 보고 화면에서 프로젝트 종류를 고르면 현재 미션·방·필수 산출물과 검증을 확인할 수 있습니다. Roblox 게임과 AI 룩북은 실제 플레이 또는 생성·저장·상품 연결에 맞는 검증을 요구합니다. **웹 서비스**는 요청 문장이나 저장소의 `package.json`(React·Next.js·Vite·Vue·Svelte·`@playwright/test` 등)으로 자동 선택되며, 워크스페이스(`workspaces`, `pnpm-workspace.yaml`)의 하위 패키지도 살펴봅니다. React Native·Expo·Electron·Tauri 앱은 웹 서비스로 고르지 않습니다. 설계에서 화면 시안 캡처, 구현에서 핵심 흐름 Playwright 테스트(`e2e-smoke`), 검토에서 수용 기준 테스트(`e2e-acceptance`)와 로딩·오류·빈 상태·모바일 화면 검토(`ui-review`)를 요구합니다. AI는 `playwright-cli`로 화면을 열어 탐색·재현·캡처하고, 근거로는 `node node_modules/@playwright/test/cli.js test`를 `wax test`로 실행한 기록만 인정합니다. wax는 셸 없이 실행하므로 `npx` 대신 이 경로를 쓰면 Windows에서도 동작합니다. Windows에서 `playwright-cli`는 `wax capture`의 `--` 뒤에서 실행되지 않으니 먼저 캡처한 뒤 `--file`만 지정하세요. 캡처는 `wax capture <작업ID> --check <검증 ID> --file <파일> [-- <캡처 명령>]`으로 `.wax/artifacts/`에 보관합니다. 필요한 도구의 설치 여부는 `wax doctor`의 `browser` 항목에서 확인합니다. B1 디자인실의 무드보드·제작물 버튼에서 등록한 시안을 확인하세요. 검토 실패 시 **수정 후 다시 검증**으로 개발 단계부터 이어갈 수 있습니다. 디자인실 제작물에서 Figma 프레임이나 Blender 컬렉션을 연결하면, 선택한 실행 도구(Codex·Claude Code)의 MCP로 실제 제작하고 대표의 수정 의견을 같은 대상의 다음 버전으로 반영한 뒤 확정한 버전을 개발에 인계합니다. 연결 상태는 그 실행 도구에서 실제로 검사합니다. 자세한 방법은 [디자인실 안내](DESIGN_STUDIO.md)를 참고하세요.

캡처 라벨(`--viewport`·`--scroll`·`--state`)과 같은 조건의 시안 비교(`wax compare`)는 4절 "화면 캡처와 시안 비교"를 보세요.

| `.git`에서 지움 | 워크트리 항목 `.git/worktrees/<목표>-<n>/` | 프로젝트 `.git` | `git worktree remove` 때만 |

wax는 이 밖에 프로젝트 `.git`에 쓰지 않습니다. index, HEAD, 기존 브랜치, config, `FETCH_HEAD`, `.gitignore`, `.git/info/exclude`를 바꾸지 않고, 커밋·push·브랜치 지우기·`git worktree prune`·`git gc`를 하지 않으며, 저장소의 git 훅이 돌지 않게 합니다. 합쳐 보기에 필요한 객체는 운영체제 임시 폴더에만 만듭니다. 작업자로 띄운 AI 도구가 스스로 부르는 git 명령(커밋 등)과, 준비 스크립트·검사 명령이 하는 일은 그 도구와 명령의 몫이며 실행 승인으로 다스립니다.

### 백업과 복원

`wax backup > wax-backup.json`으로 백업하고, `wax import --file wax-backup.json`으로 미리 본 뒤 미리보기의 fingerprint를 `--apply <fingerprint>`로 넘겨 복원합니다.

`wax backup`은 작업 기록(`.wax/features`)과 함께 프로젝트 규칙·작업노트 메모·업무 배정·PM 지정·채널·화이트보드·일일보고 목록(`.wax/chat`)과 위키 상태(`.wax/wiki`)를 담습니다. 세션 참여 정보·실행 중인 요청·검색 색인·실행 승인 기록은 담지 않습니다. 위키 페이지와 보고서 문서(`docs/wax`)는 저장소 파일이라 git으로 보존하세요. `wax import`는 복원할 프로젝트에 같은 작업이나 같은 기록 파일이 있으면 덮어쓰거나 합치지 않고 건너뛰며, 미리보기의 `files`에 파일별 상태를 보여 줍니다. `--prefix`로 사본을 만들 때는 기록 파일이 원래 작업 ID를 가리키므로 작업만 복원합니다. 기록 파일은 모두 합쳐 128MB까지 담고, 넘으면 크기만 남깁니다. 이전 버전의 백업(작업 기록만)도 그대로 복원됩니다.

손상 백업 원문은 파일당 1MB, 최대 1000건, JSON에 담는 전체 원문은 64MB까지 보존합니다. 한도를 넘긴 파일은 크기와 생략 이유를 남기며 정상 작업은 계속 백업합니다.

## 8. 문제 해결

| 증상 | 확인할 내용 |
| --- | --- |
| `/wax:` 명령이 보이지 않음 | `claude plugin list`에 `wax@wax`가 켜져 있는지(한 번 설치), 또는 `--plugin-dir` 절대 경로·Gemini 확장 연결을 확인하고 새 세션을 시작하세요. |
| Antigravity CLI에 스킬이 보이지 않음 | `install-project.mjs --project <경로> --check`로 `.agents/skills` 연결을 확인하고 새 `agy` 세션을 시작하세요. |
| Grok Build에 스킬이 보이지 않음 | `install-project.mjs --project <경로> --check`로 `.grok/skills` 연결을 확인하고(0.13.5 이전에 연결한 프로젝트는 연결 명령을 다시 실행) 새 `grok` 세션을 시작하세요. |
| Codex에 스킬이 보이지 않음 | `install-project.mjs --project <경로> --check`로 연결과 원본 폴더를 확인하고 새 세션을 시작하세요. |
| 단계가 넘어가지 않음 | 현재 단계 문서, 완료 근거, 검토 통과 여부를 확인하세요. 구현·검토는 통과한 테스트나 커밋 근거(`--proofs`)가 필요합니다. |
| 대시보드 자동 진행 도구 목록에 Grok Build가 없음 | Grok Build는 자동 진행과 PM 루프 작업자를 지원하지 않습니다. 터미널 세션에서 스킬 이름을 밝혀 요청하세요(5-4절). |
| 브라우저 알림이 오지 않음 | **알림 켜기**를 눌렀는지, 버튼이 **알림 차단됨**이면 사이트 설정에서 알림을 허용했는지, 대시보드 탭이 열려 있는지 확인하세요. 탭을 보고 있는 동안에는 알리지 않습니다. |
| 트리거가 **연결 필요**로 나옴 | 이 컴퓨터에서 `gh auth status`를 확인하고 `gh auth login` 뒤 기다리면 다음 분에 다시 확인합니다. `gh`가 PATH에 없으면 `WAX_GH_BIN`으로 경로를 주고 대시보드를 다시 시작하세요. |
| 기존 GitHub 이슈가 제안되지 않음 | 첫 확인은 이미 있는 항목을 기준으로만 기록합니다. 라벨을 뗐다 다시 붙이세요(6-5절). |
| 트리거가 저절로 꺼짐 | 5번 연달아 실패하면 꺼집니다. 목록의 이유를 확인해 고친 뒤 다시 켜세요. |
| PM 루프 목표가 멈춤 | 목표 화면의 이유(한도, 연속 막힘, auto 행동 실패)를 확인하고, 원인을 고친 뒤 **목표 재개**에서 한도를 확인하세요. |
| `wax mcp`가 시작하지 않음 | 등록한 설정의 env에 `WAX_MCP=on`이 있는지, 터미널에서 `WAX_MCP=on node /path/to/wax/bin/wax.mjs mcp --project <경로>`의 오류 출력을 확인하세요(6-2절). |
| CLI가 영어(또는 한국어)로 나옴 | `WAX_LANG=ko` 또는 `WAX_LANG=en`을 지정하세요. 없으면 `LC_ALL`·`LC_MESSAGES`·`LANG`을 따릅니다. |
| 비정상 종료 후 계속 저장 중으로 나옴 | wax는 주인 프로세스가 끝난 저장 잠금을 다음 저장 때 회수합니다. 그래도 남으면 `doctor`로 잠금 경로를 확인하고, 해당 프로젝트의 wax 작업이 모두 끝났는지 확인한 뒤 `.wax/features/<id>.lock` 디렉터리를 제거하세요. |
| (웹 서비스) AI 버튼이 비활성화됨 | 제공자·모델 ID·키를 설정하고 서버를 재시작하세요. |
| (웹 서비스) AI 요청에 401·403·404가 표시됨 | API 키, 모델 이름, 모델 접근권한을 확인하세요. |
| (웹 서비스) AI 요청에 429가 표시됨 | 제공자의 사용 한도·요금을 확인하고 잠시 후 다시 시도하세요. |
| (웹 서비스) 저장 충돌이 표시됨 | 복구 패널에서 초안을 다운로드하거나 최신 기록과 비교한 뒤 다시 가져오세요. 서버는 원본을 자동으로 덮어쓰지 않습니다. |

"(웹 서비스)" 줄은 wax 웹 서비스(wax-service)를 함께 쓸 때의 증상입니다.

기록 문제는 `node "/path/to/wax/bin/wax.mjs" doctor --project "/path/to/project"`로 한 번에 검사할 수 있습니다. 정상 기록 수와 문제 파일·잠금 경로를 JSON으로 출력합니다. 이 명령은 파일을 수정하거나 잠금을 제거하지 않으며 문제가 있으면 종료 코드 1을 반환합니다.

## 9. 업데이트와 검증 범위

호스트 세션을 종료하고 기존 플러그인을 백업한 뒤 새 ZIP을 기존과 같은 플러그인 경로에 배치합니다. 마켓플레이스로 설치했다면 `node "/path/to/wax/bin/wax.mjs" update`가 설치된 도구를 모두 확인하고 각 도구의 업데이트 명령을 차례로 실행합니다(`--check`는 확인만, `--yes`는 Gemini CLI 확장 동의까지, 도구별 명령은 INSTALL.md). Antigravity CLI·Grok Build는 프로젝트 연결이라 명령을 실행한 폴더(또는 `--project <경로>`)의 연결을 봅니다. 실행 파일(`agy`·`grok`)은 있는데 그 프로젝트에 연결이 없으면 "설치됨, 이 프로젝트에 wax 연결 없음"과 연결 명령을 보여 줍니다. 작업 프로젝트의 `.wax`와 `docs/wax`는 유지하세요. 직접 수정한 플러그인은 변경 내용을 비교·병합한 뒤 업데이트하세요.

0.16.0 전에 공개 저장소를 마켓플레이스로 등록했다면, 0.16.0에서 저장소 이력이 새로 시작되어 업데이트가 실패할 수 있습니다. 이때는 등록을 지우고 다시 등록합니다(1절 "0.16.0 공개 저장소 안내"). Codex는 5-1절의 전환 명령을 그대로 쓰고, 다른 도구는 그 도구의 마켓플레이스 제거 명령 뒤 처음 설치할 때와 같이 등록·설치합니다. `wax update`는 이 실패를 알아보고 다시 등록하는 명령을 보여 주지만 직접 실행하지는 않습니다. 프로젝트 연결(Antigravity CLI·Grok Build 등)은 연결한 공개 저장소 clone에서 `git pull`이 실패하면 clone을 새로 받고 `install-project.mjs --project <프로젝트>`를 다시 실행합니다.

자동 검사 대상은 상태 저장·단계 전환·동시 수정 충돌·CLI·Codex 설치 및 스킬 실행기·읽기 전용 진단·ZIP 압축 해제 후 실행입니다. Claude 플러그인 규격과 Gemini 명령 문법도 확인합니다. Claude Code 2.1, Codex 0.162, GitHub Copilot CLI 1.0.97에서 마켓플레이스 설치와 실제 명령 실행을 확인했습니다. Windows Node.js 22.17.0에서 junction 설치·연결 실행·한글 경로·단계 전환·테스트 근거·백업을 검증했습니다. Windows에서 `npm run test:windows`로 재현할 수 있습니다. 공개 배포본은 Ubuntu·macOS·Windows와 Node 22·24에서 검사를 통과한 버전만 올라갑니다.

아직 검증하지 않은 것:

- 실제 AI 계정으로 코드 수정부터 최종 검토까지 진행하는 전체 과정, 실제 Gemini CLI·Antigravity CLI·Grok Build 세션, 유료 API 호출.
- PM 루프의 실제 도구 한 바퀴 가운데 Codex 작업자의 성공, Gemini CLI 작업자, Antigravity CLI 작업자의 구현·검토(사용자 설정 `permissions.allow`에 명령 허용이 필요하고 카드가 경고함), 한 바퀴 뒤 고친 것(남은 단계의 선호 작업자 도구, Antigravity CLI 경고, 실행 기록의 실행 도구)을 실제 도구로 다시 돈 결과, Windows의 auto 모드와 목표 허용. macOS에서 Claude Code 작업자·PM 판단·auto로 돈 결과는 6-6절에 있습니다. Windows에서는 2026-11-02에 Claude Code·GitHub Copilot CLI 작업자와 Claude Code PM 판단으로 한 바퀴를 돌았고, 그때 찾은 문제(Codex 종료 확인, Copilot CLI ACP 순서, Windows 경로의 목표 허용, 재시작으로 꺼진 허용, Gemini CLI 0.64 경로)는 고쳐서 가짜 도구로 검사했습니다(`docs/design/PM_LOOP.md`의 "Windows 실제 도구 한 바퀴").
- MCP 서버를 각 도구에 실제로 등록한 결과. 테스트는 서버와 출력한 설정 조각만 확인합니다(6-2절).
- 실제 GitHub 저장소를 대상으로 한 트리거 폴링. 테스트는 가짜 `gh`로 합니다(6-5절).
- 자동 진행에서 각 제공자의 실제 계정으로 하는 작업. 공식 CLI 프로토콜의 모의 실행으로 승인·거부·중지·이어가기와 보고 처리를 검증했습니다(6-3절).
