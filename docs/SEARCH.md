# wax 기록 검색

대화·화이트보드·업무·단계 문서·완료 근거·테스트·커밋·요청·디자인 작업을 한 번에 찾고, 결과마다 원문 위치로 이동합니다.

## 구조

- **원본은 그대로**: `.wax`의 JSON/JSONL 파일이 유일한 원본입니다. 검색은 이 파일들에서 다시 만들 수 있는 SQLite 색인(`.wax/search/index.db`)만 씁니다. 색인을 지워도 기록은 사라지지 않습니다.
- **표**: `docs`(문서 하나 = 원문 기록 하나 또는 문서의 한 부분)에 종류·작업·채널·작성자·유형·단계·상태·시각·순번·원문 위치·화면 링크를 별도 열로 두고, `(at, id)`, `(kind, at)`, `(feature, at)`, `source` 색인으로 필터와 최신순 정렬을 처리합니다. `sources`는 원본 파일마다 크기·수정 시각·inode·읽은 위치·확인용 해시·읽지 못한 줄을 기록합니다.
- **전문 검색**: FTS5 두 개를 씁니다. `docs_tri`(trigram, 제목·본문)는 세 글자 이상의 부분 일치, `docs_bi`(unicode61, 내용 없이 색인만)는 단어 안의 두 글자 조각을 토큰으로 둡니다.
- **동기화**: JSONL은 마지막으로 읽은 바이트 위치부터 새로 끝난 줄만 읽습니다(쓰는 중인 마지막 줄은 다음 동기화에서). 파일이 줄었거나, 교체됐거나(inode), 크기가 같은데 수정 시각이 바뀌었거나, 읽은 범위의 처음 4KB·마지막 64바이트 해시가 달라지면 그 파일만 다시 읽습니다. JSON(작업·요청·디자인 작업)은 크기·수정 시각·inode가 바뀌면 그 파일의 문서만 바꿉니다. 지워진 파일의 문서는 지웁니다. 화이트보드·일일 보고서처럼 기록이 가리키는 Markdown은 `refs` 표에 (파일, 문서)마다 상태·크기·수정 시각·inode를 남기고, 동기화할 때마다 파일별로 한 번 확인해 그 파일만 고쳐지거나 교체·삭제돼도 그 파일을 한 번만 읽어 가리키는 문서를 모두 다시 씁니다(직접 쓰거나 가져온 기록 여러 개가 같은 파일을 가리키는 경우 포함). 읽기 전용 `status`도 이렇게 바뀐 파일을 미반영 변경으로 세어 `stale`로 표시합니다. 없거나 읽을 수 없는 파일은 본문을 비우고 상태(`file-missing` 등)를 남겨 예전 본문을 최신처럼 보여 주지 않습니다.
- **트랜잭션**: 원본 파일 하나의 반영은 `BEGIN IMMEDIATE` 짧은 트랜잭션 하나입니다. 파일을 읽고 파싱하는 일은 트랜잭션 밖에서 하고, 트랜잭션 안에서 계획했던 상태(크기·inode·위치)가 그대로인지 다시 확인해 다른 프로세스가 먼저 반영했으면 다시 계획합니다. 같은 기록 ID는 한 번만 들어갑니다(`ref` UNIQUE). WAL, `busy_timeout` 3초, 실패하면 “다른 wax 프로세스가 검색 색인을 쓰고 있습니다” 오류를 냅니다. 긴 AI 작업이나 원본 쓰기를 색인 트랜잭션에 묶지 않습니다.

## 검색 범위

| 종류 | 원본 | 원문 위치 예 | 화면 |
| --- | --- | --- | --- |
| 채널 메시지 | `.wax/chat/channels/<채널>.jsonl` | `…/general.jsonl#m-000012-ab12cd` | `/chat?channel=…#m-…`(해당 메시지로 이동·강조, 최근 200개 밖이면 따로 불러옴) |
| 화이트보드 노트·보고서 | `.wax/chat/board/<작업>.jsonl`, `docs/wax/<작업>/board-reports/NNN.md` | `…#n-…`, 보고서 경로 | `/manage?feature=…` |
| 업무 배정·상태 | `.wax/chat/assignments.jsonl` | `…#t-…`, `…#s-…` | `/manage?feature=…` |
| 일일 업무보고 | `.wax/chat/daily.jsonl` + `docs/wax/daily/<날짜>/NN.md` | 보고서 경로 | `/manage?date=…` |
| 작업, 단계 문서, 완료 근거, 개선 이력, 테스트·커밋 근거 | `.wax/features/<id>.json` | `#/title`, `#/artifacts/<단계>`, `#/completed/<단계>`, `#/history/<n>`, `#/proofs/<n>` | `/manage?feature=…` |
| 요청 대화·워크플로우 | `.wax/chat/requests/<id>.json` | `#/messages/<n>`, `#/workflow/document` | `/?request=…` |
| 디자인 작업 | `.wax/design/jobs/<id>.json` | `#/brief`, `#/feedback/<n>`, `#/versions/<n>`, `#/handoff` | `/office?studio=1` |

테스트 근거는 명령·커밋·검증 항목 ID와 출력 앞 4,000자, 커밋 근거는 SHA·메시지·파일 목록을 검색합니다. 실행 승인 기록(`.wax/approvals`), 승인 시크릿, 세션 토큰, 요청·디자인 작업의 소유 프로세스·AI 스레드 ID, presence는 색인하지 않습니다. 심볼릭 링크인 기록 파일은 건너뜁니다. 기록이 가리키는 Markdown은 `docs/wax/` 아래 상대 경로만 받고, 프로젝트 루트부터 모든 경로 구간이 실제 디렉터리이고 마지막이 일반 파일이어야 읽습니다. 중간이든 마지막이든 심볼릭 링크가 있으면 읽지 않고 `refused`로 표시하며(POSIX에서는 `O_NOFOLLOW`로 열고 inode를 다시 확인), 색인 파일(`index.db`, `-wal`, `-shm`)이 일반 파일이 아니면 손상으로 보고 재구축 때 링크만 지웁니다. 작성자는 기록 ID와 별개로 `chat/validate.mjs`의 이름 규칙(대표, 한글, 공백, `_ . -` 포함 40자)대로 보존합니다. 구조화된 리뷰 판정(P1/P2, 미해결 지적)은 아직 기록 모델이 없어 별도 종류로 보여 주지 않습니다. 리뷰 내용은 검토 단계 문서·완료 근거·노트·메시지로 검색됩니다.

## 검색어의 의미

| 검색어 | 방식 | 예 |
| --- | --- | --- |
| 세 글자 이상 | trigram 부분 일치(대소문자 무시) | `인계를`, `handoff-v2.md`, `docs/wax/design`, `a1b2c3d`, `"Claude Code"` |
| 글자·숫자 두 글자 | 단어 안 두 글자 조각 토큰 | `인계`(“인계를”, “디자인 인계”에 일치), `리뷰`, `오류`, `UI` |
| 한 글자, 기호가 섞인 두 글자 | 제목·본문 LIKE 훑기(필터가 있으면 그 범위) | `계`, `1%` |

- 띄어 쓴 단어는 모두 들어 있어야 합니다(AND). 큰따옴표는 공백을 포함한 구절입니다. 최대 8개 단어.
- 기본 unicode61만으로는 `인계`가 “인계를”에 잡히지 않고, trigram만으로는 두 글자가 0건입니다. 그래서 두 색인을 단어 길이에 따라 나눠 씁니다.
- 결과는 최신순(시각, 같은 시각이면 색인 순서)이며 `(시각, id)` 커서로 페이지를 넘깁니다. 넘기는 사이 새 기록이 와도 다음 페이지가 밀리지 않습니다. 전체 수는 1,000까지 세고 넘으면 `1000+`로 표시합니다.
- SQL은 모두 바인딩하고, FTS 질의는 항상 따옴표 구절로 만들어 `"`, `-`, `*`, `NEAR`, `OR` 같은 입력도 글자로 찾습니다. LIKE의 `%`, `_`, `\`는 이스케이프합니다. 화면은 원문을 텍스트 노드로만 넣고 강조는 위치 범위(`marks`)로 받습니다.
- 초성 검색, 형태소 분석(“인계했다”로 “인계를” 찾기), 동의어·의미 검색, 관련도 순위는 이번 범위가 아닙니다.

## 사용

```sh
wax search index                 # 처음 한 번 색인 만들기(이후 검색할 때마다 바뀐 기록만 반영)
wax search 인계 --feature lookbook-upload
wax search "Claude Code" --kind message --from 2026-10-01 --to 2026-10-18 --author claude-app
wax search status                # 상태·미반영 변경·읽지 못한 기록(파일과 줄 번호)
wax search index --rebuild       # 손상·형식 변경 시 재구축(원본은 그대로)
```

`--json`은 결과·원문 위치·강조 범위를 JSON으로 출력합니다. `--no-sync`는 반영 없이 지금 색인만 찾고, 결과에 그 사실을 표시합니다. 색인 만들기가 중간에 멈춘 상태라면 `--no-sync` 결과도 `complete:false`와 이어서 만들기 안내를 함께 냅니다. 대시보드는 상단 메뉴의 **검색**(`/search`)에서 같은 검색·필터·페이지 이동과 색인 만들기·재구축을 제공합니다. 색인 만들기는 대시보드 프로세스를 막지 않도록 별도 `wax search index` 프로세스로 실행합니다.

색인이 없으면 만들 때까지 검색은 안내만 하고(조회만으로 색인을 만들지 않음), 손상(열 수 없음)·형식 변경이면 재구축 안내와 함께 거절합니다. 색인을 만드는 동안에는 `building` 표시에 그 프로세스 ID를 남기고 `rebuild.lock`을 쥡니다. 그 프로세스가 살아서 잠금을 쥐고 있을 때만 “만드는 중”(결과가 일부일 수 있음, 검색은 동기화하지 않음)이고, 강제 종료·실패·대시보드 재시작으로 끝났으면 “중간에 멈춤(`interrupted`)”입니다. 이때 검색이나 **색인 이어서 만들기**(`wax search index`)는 남은 원본부터 이어서 반영하고 표시를 지웁니다. 시간이 지났다는 이유만으로 살아 있는 작업을 회수하지 않습니다. 읽지 못한 JSONL 줄은 건너뛰고 파일·줄 번호를 상태에 남기며 원본은 바꾸지 않습니다. 원본 기록을 쓰는 wax 명령은 색인이 없거나 망가져도 그대로 동작합니다.

## 측정

`node scripts/bench-search.mjs 10000,100000`로 다시 잴 수 있습니다. 합성 채널 메시지(20개 파일)이며 실제 프로젝트 데이터가 아닙니다. Node 26.0.0, macOS arm64, 따뜻한 파일 캐시, 앞 2회를 뺀 중앙값입니다. 모든 질의는 JSONL 전체 읽기(`readRecords` + 대소문자 무시 부분 문자열)와 **같은 기록 ID 집합**을 돌려주는지 모든 페이지를 넘겨 확인했습니다. 이 수치는 이 조건의 측정값이며 다른 환경의 응답 속도를 보장하지 않습니다.

| 항목 | 1만 건 | 10만 건 |
| --- | --- | --- |
| JSONL 크기 → 색인 크기 | 2.7MB → 10.8MB | 27.6MB → 107.9MB |
| 전체 색인(`wax search index`, 프로세스 시작 포함) | 0.87초 | 9.2초(최대 메모리 약 196MB) |
| 변경 없는 동기화 / 100건 추가 후 동기화 | 0.8ms / 7.9ms | 1.0ms / 6.2ms |
| CLI 검색 `wax search 인계 --json`(프로세스 시작 포함) | 96ms | 99ms(최대 메모리 약 94MB) |
| 대시보드 API `GET /api/search?q=인계`(동기화 포함, 응답 JSON까지) | 4.8ms | 4.4ms |

첫 페이지(20건) 조회, JSONL 전체 읽기 대비:

일치가 많은 흔한 단어는 일치 집합 전체를 최신순으로 정렬하고 1,000까지 세므로 10만 건에서 수십 ms가 걸립니다. 드문 단어·필터 조합은 1ms 아래입니다. 브라우저에서 입력을 멈춘 뒤 결과가 그려지기까지는 입력 대기 350ms를 포함해 약 0.8초(픽스처 32건, Playwright 타이핑 포함)였습니다. 색인 크기는 원문(본문 사본) + trigram 색인이 대부분이며 두 글자 색인은 내용 없이 저장합니다.

## 2차: 원본 저장소 전환(이번 변경에 포함하지 않음)

최종 목표는 `.wax/wax.db`에 상태·이력을 저장하고 JSON은 내보내기·백업으로 쓰는 것입니다. 이번 검색 색인은 그 전 단계이며 원본을 바꾸지 않습니다.

- **경계**: 원본을 읽고 쓰는 곳은 `workflow.mjs`(작업), `chat/store.mjs`(JSONL 추가·잠금), `chat/requests.mjs`·`chat/design.mjs`(JSON 원자적 쓰기), `approvals.mjs`, `backup.mjs`, `chat/watcher.mjs`(변경 감지)입니다. 전환은 이 경계에 저장 어댑터(`readFeature/updateFeature`, `appendRecord/readRecords`, `readJob/writeJob`)를 두고 JSON 어댑터와 SQLite 어댑터를 같은 계약 테스트로 검증하는 순서가 안전합니다.
- **스키마 버전**: 색인은 `meta.schema`(현재 3: 2에서 참조 Markdown 추적, 3에서 같은 파일을 가리키는 문서를 모두 추적)가 다르면 거절하고 재구축합니다. 원본 DB는 이와 별개의 `schema_version`과 단계별 마이그레이션을 두고, 이전 버전 wax가 같은 프로젝트를 쓰면 쓰기를 거부하도록 버전 잠금을 둡니다.
- **전환 명령**: `wax storage migrate --dry-run`(건수·해시 비교 보고) → 백업 생성 → 파일별 트랜잭션 복사와 진행 위치 기록(중단 후 재개) → JSON 원본과 DB를 모든 레코드 해시로 대조 → 명시적 확인 뒤에만 전환 표시. `init`이나 일반 조회는 절대 자동 전환·삭제하지 않고, `wax storage rollback`으로 JSON 원본으로 돌아갈 수 있어야 합니다.
- **전환 전 정리할 계약**: 작업 revision·충돌 감지, 대화·보드 ID(`m-`/`n-` 순번+난수), 단계 문서·근거의 파일 원문 참조(`#/artifacts/…`), 백업·복원·doctor 형식, 여러 CLI 프로세스의 동시 쓰기(현재 파일 잠금 → DB 트랜잭션), 워처의 증분 읽기(파일 크기·mtime → DB 변경 순번), 이전 버전 CLI와의 동시 실행.
- **후속 검증**: 전환 dry-run과 재개·롤백, 혼합 버전 동시 실행 거부, 대용량 백업 왕복, Windows 파일 잠금과 WAL, 디자인 산출물(이미지·Blender 파일)은 계속 파일로 두고 경로·메타데이터만 DB에 둡니다.
