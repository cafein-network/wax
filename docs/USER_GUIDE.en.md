# wax User Guide

wax splits each feature into **plan → design → implement → review → report** and keeps the documents and completion evidence in your project.

This guide describes wax 0.16.0. Check the installed version with `node bin/wax.mjs --version` in the plugin folder. What changed in this release is in `RELEASE_NOTES.md` in the distribution, and what changed in each version is on the [changelog](https://wax.me2shop.com/changelog/) page (in Korean).

There are two ways to work. Run the stage commands one by one in an AI session in your terminal (sections 3 and 4; other tools in section 5), or send a one-line request from the dashboard and let the chosen tool carry it through (section 6-3). Either way the records go to the same `.wax/`.

## 1. What do I need?

Node.js 22 or later and one signed-in Claude Code, Codex, Antigravity CLI, GitHub Copilot CLI, Grok Build or Gemini CLI. Install wax from the public repository [cafein-network/wax](https://github.com/cafein-network/wax) through each tool's marketplace, or download the ZIP from the [wax site](https://wax.me2shop.com/#download). The release includes the plugin source, tests and this guide. The wax code is licensed under AGPL-3.0 (free to use, change and share; distributions must offer the source, and if you provide a modified version over a network, remote users must be able to get its corresponding source). Usage fees and limits of AI tools and APIs are separate.

**0.16.0 public repository note.** In 0.16.0 the public repository `cafein-network/wax` was recreated with a fresh history. The install address is the same. If updating a marketplace registered before 0.16.0 fails because the history does not match, remove the `wax` marketplace registration in that tool and register it again. If you linked a clone of the public repository into a project (Antigravity CLI, Grok Build and others) and `git pull` fails in that clone, clone it again and re-run `install-project.mjs --project <project>` (section 9, and "Updating and improving it yourself" in INSTALL.md). Leave `.wax` and `docs/wax` in your projects as they are. GitHub release ZIPs and provenance attestations from before 0.16.0 are no longer offered; the change history remains on the [changelog](https://wax.me2shop.com/changelog/) page.

## 2. Getting the code

Unzip the archive with **Extract all**, then find the `wax` folder that contains `package.json` and `bin/wax.mjs`. It must also contain the hidden `.claude-plugin` folder. The plugin runs without `npm install`.

See `INSTALL.md` in the ZIP for Windows and WSL examples and updating. In this guide `/path/to/wax` is an example path; always replace it with the real absolute path where you extracted the plugin.

In the examples below, replace `/path/to/my-app` with **the project directory you actually code in**. That directory must already exist. Keep the plugin source directory and your project apart.

## 3. Starting your first task in Claude Code

Load the wax plugin in your project. This applies to that Claude session, so use the same option whenever you open a new session.

```sh
cd /path/to/my-app
claude --plugin-dir "/path/to/wax"
```

On another computer, change the path after `--plugin-dir` to its real location too. No npm install is needed.

To avoid adding `--plugin-dir` every time, install once: `claude plugin marketplace add "/path/to/wax"`, then `claude plugin install wax@wax`. The extracted folder is itself the marketplace, and Codex (`codex plugin marketplace add` → `codex plugin add wax@wax`) and GitHub Copilot CLI (`copilot plugin marketplace add` → `copilot plugin install wax@wax`) install once from the same folder. For updating and removing, see "Install once" in INSTALL.md.

At first, run the start command once in the Claude chat.

```text
/wax:init
```

It joins with a default name and opens the dashboard without setup questions. If exactly one task is in progress it picks that task, otherwise none. If the project has no PM, the init session becomes the PM (skip with `--no-pm`); an existing PM is kept. Name, task and PM options you pass are applied as given. When it finishes, the session has joined the team channel, appears as a character in the virtual office, and shows how other AI sessions join (`/wax:join`). init and join join in the idle state and switch to working when real stage work starts. Run `/wax:init` again later to reopen the dashboard.

Automatic runs are requested in one line on the dashboard's Requests & reports screen (`/start`, section 6-3). To manage each stage yourself from the terminal, request a feature like this:

```text
/wax:plan email-login Build sign-in with email and password
```

wax reads the existing code and sets out requirements, scope and acceptance criteria. Answer the questions that need a decision, then check the result. One command performs that stage only; it does not run every following stage at once.

## 4. Moving through the stages

| Command | What it does |
| --- | --- |
| `/wax:init` | Get started: join the team channel, choose a task, open the dashboard and set the PM in one step |
| `/wax:join` | Join another AI session to the team channel (sets only its name and task) |
| `/wax:plan email-login …` | Set out the problem, scope and acceptance criteria for a new feature |
| `/wax:design email-login` | Design the structure, data, files to change and how to verify |
| `/wax:implement email-login` | Change the real code with the host's tools and run the related checks |
| `/wax:review email-login` | Compare the design with the actual result and record test evidence and unverified items |
| `/wax:report email-login` | Summarize results, verification, usage and remaining work |
| `/wax:status email-login` | Check the current stage and completion evidence |
| `/wax:iterate email-login Handle expired tokens` | Archive the previous cycle and go back to implementation |

For example, after the first plan, run each of these once:

```text
/wax:design email-login
/wax:implement email-login
/wax:review email-login
/wax:report email-login
```

The next stage opens only when the current stage has its document and completion evidence. Implement must link a passing test (`wax test`) or commit (`wax evidence`) proof, and review must link a passing test proof together with a confirmed pass. When there is no runnable check, such as a documentation-only change, complete with `--no-proof <reason>`; the reason stays in the completion record and in the handoff context other tools read. Besides the acceptance-criteria table, review checks in the order structure → function → efficiency → presentation: role flows and permissions (blocked on the server, not just hidden on screen), confirm, cancel or edit paths for actions that cannot be undone, numbers and totals against the source data, search and speed with a realistic amount of data, and loading, error and empty screens, marking anything that does not apply as not applicable with a reason. Each finding also says who is affected and why. If problems or unverified criteria remain, review does not complete and tells you why.

When implement completes, wax looks in the proofs, for each linked passing test, for a failing run of the same check before the fix (same command, same `--checks`, same folder, with the code changed in between) and keeps it as a red→green pair in the completion record (`completed.implement.redGreen`). So run a check that tests the behavior you will change with `wax test` first to record the failure, then run the same command again after the fix. For open defects, record the failure before the fix and the pass after it under the defect ID, as in `wax test <id> --checks d-1 -- …`. Without a pair the default (`WAX_RED_GREEN=warn`) completes with a warning and `enforce` refuses. If the change cannot show a failure first (such as a setting value), give the reason with `wax complete implement … --no-red <reason>`; `--no-red` is refused when a pair exists. When the output names its tests (TAP or JUnit), a different test failing first is recorded as a warning, and the tree fingerprints flag a change to test files only. `node --test` on Node 24 and later prints a non-TAP format even through a pipe, so to match test names add `--test-reporter=tap` to both the red and the green run (both must be the same command to pair). The result shows in `wax status <id>` as `redGreen` (one-line summary, warnings, per-defect pairs, reason), in the "Failure seen first" section of `wax quality-report`, in the "Verification" section of `wax pr-body` (a table of up to 5 pairs), and in the run trace (dashboard and `wax trace`) as red and green marks on the implement visit's proofs. When a person turns on **Require red→green** for a PM loop goal, `enforce` applies to that goal's tasks (6-6).

A feature ID starts with a lowercase letter or digit and contains only lowercase letters, digits and hyphens, 1–64 characters. Use names like `email-login`, `dashboard` or `payment-v2`.

### Improvement cycles (iterate)

If review finds problems, improve it like this:

```text
/wax:iterate email-login Reject expired auth tokens
/wax:implement email-login
/wax:review email-login
/wax:report email-login
```

### Acceptance-criteria trace

The plan writes one acceptance criterion per line with its ID at the start of the line, such as `- AC-1: <criterion> — check: <method>` (only `AC-<number>` at the start of a line counts as an ID; mentions in the middle of a sentence are not declarations). When the plan declares AC IDs, completing review needs one `{"id": "ac-1", "status": "pass", "detail": "<what was checked>", "proofIds": ["<proof ID>"]}` item per ID in the `--checks-file` JSON array. A `pass` counts only with a passing test or commit proof from the current iteration; if any criterion is missing, `unverified` or without proof, review does not complete. Only for a criterion that truly cannot be verified, complete with `--ac-unverified <reason>`; any `fail` is refused regardless of a reason, so fix it with `wax iterate`. The trace (AC → status → proofs) appears in `acceptanceTrace` of `wax status <id>`, in `wax context <id>` and in the report-stage prompt. Plans without AC IDs work exactly as before.

### Plan steps

Below the acceptance criteria, the plan can split the work into small steps written at the start of a line, such as `` - S-1: <what> — files: <files to change> — check: `<command wax test will run>` — done: <done when> — AC: AC-1 ``. Fields are separated by ` — ` or ` -- ` and named `files`, `check`, `done` and `AC` (the Korean names `파일`, `검사` and `완료` work too; an unnamed field right after the title is read as part of the title), and table rows like `| S-1 | …` are read as well. `check` is one command in backticks (wax runs it without a shell, so no shell characters such as `|`, `&`, `;`, `<`, `>`, `$`, `\` or `*`), `checks=<ID>`, or `none(<reason>)` for a step that cannot be tested. When the plan declares AC IDs, wax checks the steps as the plan completes. A step pointing to an AC the plan does not declare and two steps with the same S ID are always refused. With no steps, or a step whose `check` is missing or out of format, the default (`WAX_PLAN_STEPS=warn`) completes with a warning and `enforce` refuses. An AC no step points to, a step with more than 8 files, a missing number, an unknown field name, steps sharing the same `check`, and on Windows a check starting with `npx`, `npm`, `yarn` or `pnpm` only warn. A summary is kept in the completion record as `completed.plan.steps`. Plans without AC IDs work exactly as before.

During implement, run each step's `check` command as it is with `wax test <id> -- <command>`. When the command matches the step's `check` (on Windows `\` and `/` and the drive letter case count as the same) or every ID of `checks=<ID>` is in `--checks`, wax tags the proof with the step (`step: "S-1"`). When several steps share the same `check` (for example all `node --test`), wax tags the first of them in plan order that has no passing proof in this iteration yet, and the last one once all have passed. Failing runs follow the same rule, so a step's failing run before the fix and its passing run after land on the same step. To keep progress clear, give each step a command that checks only that step (for example one test file). You can also tag it yourself with `wax test <id> --step S-1 -- …`, and `--step` always wins (implement stage only, and only a step the plan has). `--step` on another command keeps the proof but marks it "different command from the step check", and it does not count as step progress. A step is done when its check passed in this iteration's implement; when a failing run of the same check came before the fix, it also says "red→green". When implement completes and a step with a `check` has no passing proof, the default (`WAX_PLAN_STEPS=warn`) completes with a warning and `enforce` refuses (`none(<reason>)` steps do not count). The summary is kept as `completed.implement.steps`, each step's red→green as `completed.implement.redGreen.steps`, and the step of each pair from the proofs linked to completion as the pair's `step`. `ok` and `missing` in `redGreen.steps` use the same computation as the step progress in `wax status` (whether a passing proof of that step in this iteration has a failing run before the fix as its pair), so when you leave a red→green for every step and link only the last green with `--proofs`, the earlier steps are not left `missing`. `linked` on an `ok` step says whether that step's pair belongs to a proof linked with `--proofs`. The red→green verdict (`redGreen.state` and `pairs`) still looks only at the linked passing proofs. Progress shows in `wax status <id>` as `planSteps` ("Plan steps 3/5 done (2 red→green)" and a step table), in `wax context` under "계획 단계" (the first three remaining steps and their checks), in the "Plan steps" section of `wax quality-report`, in the "Verification" section of `wax pr-body` (a table of up to 10 steps), and in the implement visit of the run trace (dashboard and `wax trace`). The implement prompt (`wax prompt implement`, PM loop workers) quotes the next step and the remaining steps as data. PM loop workers run the step's `check` command as it is so the step is added automatically, and when several steps share the same check command they add `--step` (the goal allowance's **Test command** accepts `--step S-n` in the implement stage).
### Design approach

In the design stage, a worker can propose 2-3 approaches before writing the design and let a person pick. The worker writes `[{"title":"…","summary":"…","tradeoffs":"…","cost":"S|M|L","risk":"low|medium|high"}, …]` to `.wax/tmp/<file>.json` and runs `wax approach <id> --propose --file <file> [--author <session name>]` (text over 120 characters for the title or 1000 for the summary and tradeoffs is clipped, hidden characters are removed, and cost and risk are the worker's estimate). If there is only one, it declares `--single <reason>` instead of `--propose`. A person sees the approaches and the revision with `wax approach <id>` and picks with `wax approach <id> --pick <N> --author <name> --revision <n> [--reason <reason>]`. Only a person picks: worker runs wax started (`WAX_WORKER=1`) and worker, `auto` and `pm-loop` names are refused, the record keeps `via: cli` for a pick made in the CLI, and a worker's request to pick is marked on the execution approvals screen as "Not a command a worker should run". While the task is in design the pick can be changed (the last pick counts and the history keeps them all), and after a person picks, workers can no longer propose new approaches unless the person clicks **Propose again**. Approaches can be proposed at most 3 times. Completing design is always refused when approaches were proposed and no person picked. With no record at all, the default (`WAX_APPROACH=warn`) completes with a warning, `ask` refuses, and `always` refuses `--single` too and accepts only an approach a person picked. `off` checks nothing. The result is kept in the completion record as `completed.design.approach`, and the record in the task's `approach`.

**Picking on the dashboard:** open a task's **run trace** and the **Design approach** section shows the proposed approaches (title, summary, trade-offs and "Cost S · Risk Low (worker’s estimate)") as written. **Use this** opens a confirm step; if a design document is already saved it first says "The design document must be rewritten for the new approach". Add an optional reason (500 characters) and click **Pick this approach**; the record keeps `via: dashboard`. If none fits, click **Propose again** and send a note saying what to change (required, 500 characters). A worker can then propose a new round (even after a pick), and design cannot be completed until a new round is proposed and a person picks again. Only a person on the dashboard can pick or ask again (worker, `auto` and `pm-loop` names are refused), and if the approaches changed after you looked, it is refused and reloaded. **PM loop:** a headless design worker proposes as its instructions say and ends without completing the stage. Then there is no unfinished-done warning, renotify or retry; the goal shows one person card, **Pick a design approach** (the same pick and propose again; it cannot be dismissed). It never picks on its own when time passes, and auto does not pick. After you pick or ask again, the next worker card appears, and the next design worker gets the chosen approach and reason (or your note) as quoted data. Proposing and writing both count toward the phase-run limit. The **Design approach picking** field on the goal start screen sets Default (`WAX_APPROACH`), A person picks (`ask`), A person always picks (`always`) or Off (`off`); the choice is kept on every task of the goal as `discipline.approach` and wins over the environment variable. Even with the `warn` default the design instructions ask for approaches first, so a PM loop goal usually waits for a person at this card in design. If you do not want that, choose **Off** on the start screen. `wax status` shows `approachSummary`, and the quality report and PR draft get a **Design approach** section with the chosen approach, reason and the ones not chosen (or "Approach pick skipped: <reason>"), quoted.

### Reviewer separation

`wax complete ... --author <name>` records the session that completed a stage in the completion record (`completed`) and history. When the session that completed implement, or recorded this cycle's implement proofs (`wax test`/`wax evidence --author`), also completes review, the default (`WAX_REVIEW_SEPARATION=warn`) completes it with a warning. The warning appears in the CLI error output (`wax: 경고: …`, or `wax: warning: …` in English), the completion record's `warning`, the stage-completed entry on the dashboard timeline, the auto-run request conversation and the handoff context. Sessions and dashboards started with `WAX_REVIEW_SEPARATION=enforce` reject a review completed by the implementing session or without `--author` (dashboard auto-run uses one session for every stage, so it stops at review). `off` skips the check. To apply it to the whole team, start every session and the dashboard with the same setting. Names are self-reported by sessions, so this guards against mistakes rather than acting as a security boundary. Older records have no completing session and still load and import as before.

### Two-stage review

Review runs in two stages. Stage one, **spec**, covers the acceptance criteria (`ac-N`), the plan steps (`s-N`), red→green (`red-green`) and the defects due for re-verification (`d-N`); if any of them fails, review stops there without the quality pass and goes back with `wax iterate` and the defects. Stage two, **quality**, is checked only after the whole spec passed: `q-tests` (missing cases, weak assertions), `q-structure`, `q-security`, `q-simplicity` and any other `q-<name>` (up to 20). The same reviewing session does both stages (that this session must differ from the implementing one is "Reviewer separation" above). Put the items in the same `--checks-file`, such as `{"id": "s-1", "stage": "spec", "status": "pass", "detail": "…", "proofIds": ["…"]}` and `{"id": "q-tests", "stage": "quality", "status": "pass", "detail": "…"}`. `ac-N`, `d-N`, `s-N` and `red-green` count as spec when `stage` is left out, and another stage is refused. A failed spec or quality item is always refused, and an `unverified` quality item needs a `detail`. When the plan has S-N steps but an `s-N` item is missing, when implement completed without confirmed red→green pairs (`missing`, `partial` or `waived`) and there is no `red-green` item, or when there is no quality item at all, the default (`WAX_REVIEW_STAGES=warn`) completes with a warning and `enforce` refuses. `off` does not look for missing items. A step without a check (`check: none(<reason>)`) counts a `pass` without proof as passed; any other spec `pass` needs a proof from the current iteration. The summary is kept in the completion record `completed.review.stages` and shows in `reviewStages` of `wax status <id>` ("Spec passed (4) → Quality passed (3, 1 unverified)"), the review visit of the run trace, the "Two-stage review" section of `wax quality-report` (quality items also count toward the ISO/IEC 25010 characteristics) and `wax pr-body`. When review iterates, add `"stage": "spec"` or `"quality"` to the `--defects-file` defects to count at which stage each iteration was sent back. Older checks files and records without `stage` are read as they are (only the no-quality-items warning).

### Evidence freshness

`wax test` and `wax evidence` store a working-tree fingerprint (`tree`) with each proof: the HEAD commit plus the Git blob ID of every file that differs from HEAD or is untracked and not ignored (`.wax/` is left out). It is built with read-only Git commands and never writes to the project `.git` (including the index). Afterwards `wax context` marks each proof with "N files changed since" and puts the files changed since the current cycle's review proof (or implement proof when there is none) in its header; `wax status <id>` reports the same as `evidenceFreshness`, and the report-phase prompt (`wax prompt report` and dashboard auto-run) says "N files changed since the review proof: …". Dashboard evidence cards show "N files changed since" with the file list on hover. This is an observation, not a verdict, and never blocks a phase; rerun the tests when the changed files matter to the proof. When more than 200 files are changed or untracked, they total more than 64 MB, or a Git command takes longer than 5 seconds, the fingerprint is recorded as unknown instead of stalling. Projects without Git and proofs from before this feature have no fingerprint and show "unknown"; they still load, back up and restore as before. `wax test <id> --worktree <path> -- …` reads the command, commit and fingerprint from a per-worker worktree the PM loop registered (`.wax/chat/worktrees.jsonl`, under `<project>/.wax/worktrees/`, for that task only) and keeps the proof in the project (the proof gets a `worktree` field). Unregistered folders are refused. The PM loop creates worktrees when a person turns on isolated branches for a goal (6-6, "Isolated branch per worker").

### Handing over a task

When a new session picks up an existing task, first read the handover context with:

```sh
node /path/to/wax/bin/wax.mjs --project /path/to/my-app context login --budget 3000
```

`login` is the existing task ID. The output shows the goal, the current stage and next action, whiteboard decisions and questions without an answer or decision, execution evidence, improvement reasons and excerpts from stage documents. Each item carries a `.wax/features/<id>.json#/...` or `.wax/chat/board/<id>.jsonl#<note ID>` reference so you can open the source. Stage skills and `work` also tell the AI to read this before starting.

`--budget` counts Unicode characters, not tokens. The default is 3,000 and the range is 1,000–100,000. The shown/total counts and `…` at the end mark omitted items and longer originals. The output is a rule-based excerpt, so also check the latest `status`, the full stage `prompt` and any source you need. Questions are limited to that task's board, and a linked answer does not guarantee the problem is solved. Damaged board records are counted as excluded, and unsafe storage paths or damaged task files are reported as errors.

Reading this is read-only and never calls an external AI. Tests from earlier cycles are kept apart from tests in the current cycle, and each shows the commit and working-tree state at the time it ran. A recorded pass does not guarantee the current code passes, so run the tests again after changes.

### Time per stage and the run trace

wax computes the time each stage took from the task history: the real elapsed time from entering a stage until completing it, with the time spent on a revisit after an improvement cycle added to the same stage. Each task under **Task progress** on the dashboard shows the time per stage and the total, and the stage in progress shows as "12 min so far". `wax status <id>` JSON includes it as `durations`. Time while archived and the gap between a backup and its restore are not counted, and older records with missing or backward timestamps are skipped. Usage is included as `usage` only for what the tools themselves reported on headless workers and PM judgments launched by the PM loop (section 6-6, "Usage"). Cost and tokens of interactive sessions are left out because no record ties them to a task stage.

For each stage visit, see when it happened, which session and tool did it, on what evidence and what changed with `wax trace <id>` (Markdown) or `wax trace <id> --json`, or in the run trace panel on the dashboard (section 6, "Checking records on the dashboard"). A review visit shows defect re-verification next to the acceptance criteria, and defects logged by the iterate that ended a review appear on that review visit. Both are read-only and call no AI.

### Diagnosing why it stopped (diagnose)

When a goal or task stops, `wax diagnose <goal ID|task ID>` reads only wax records and gathers the reasons. For a goal it reads all of its tasks; for a task, that task and the records of the PM loop goals it belongs to (task records, goal and decision records, execution approvals, snapshots, tool health, worktree setup and requests). The one-line summary at the top is the first finding under "Why it stopped", followed by findings per dimension: **Why it stopped** (goal state and stop reason, the last human card and the time after it, the last worker's failure), **Repeated failures** (proofs of the same failure across worker runs, repeat warnings and stops, root-cause hypotheses, retries of the same assignment; a design run that proposed approaches is not counted as a retry), **Plan and AC adherence** (plan ACs against the review trace, plan step warnings from when the plan was completed, plan steps without a passing proof in this cycle's implement, overridden and not-yet-seen decisions, open defects), **Missing evidence** (`--no-proof`, `--no-red`, `--ac-unverified` and `--defect-unverified` reasons, red→green, the commit changing after a proof), **Approval wait** (total and longest wait of approvals a person decided, approvals still open), **Cost and time per tool** (only usage the tool reported; unknown runs are counted separately as "unknown"), **Tool errors** (the output tail and JSON-RPC error of failed runs, tool health records) and **Reading records** (unreadable lines, truncation, links). Every finding cites `file:line` (for indented JSON also a JSON pointer such as `#/proofs/3`), and nothing without a cite is reported as a finding. Numbers come only from the times and values in the records, with how they were computed next to them. A dimension with no findings shows "Nothing found" and the number of files read.

`--json` prints the same report as JSON, and `--since <ISO time>` looks only at record lines from that time on. Diagnosis is read-only: it never changes records, calls no AI, network or git, and does not follow records that are links (symbolic links). It reads each file up to 20 MB and 50,000 lines and reports "truncated" past that, and skips unreadable lines and reports them. Record text in the output is scrubbed of secrets, tokens, the home folder, project paths, the user name and emails with the same rules as the output tail of end records, but scrubbing can miss things, so read it before sending it to anyone. The exit code is always 0 (a diagnosis is not a verdict), and 1 when the goal or task is missing or its records cannot be read. Install and lock checks are `wax doctor` (section 8).

For a bug report, make a **scrubbed bundle** in two steps. (1) `wax diagnose <ID> --bundle <new folder> [--level skeleton|evidence|full] [--keep-email]` writes scrubbed copies into a new folder that must not exist (outside the project is fine; inside the project's `.wax` or `.git` is refused): `report.md` and `report.json` (the diagnosis report), `records/` (the cited record lines, standing for the project's `.wax/`), `README.txt` (what is inside, the level, wax, OS and Node versions, the tools in the records), `scrub-log.txt` (the rules and counts of what was replaced, no values) and `files.txt` (the file list and sizes). `skeleton` (the default) leaves proof output, reports, stage document bodies and approval commands as `<omitted>`; `evidence` keeps the bodies of the cited lines (proof output, the output tail of end records, approval commands); `full` holds every record line of the target (whole goal, task, approval and request records, and only this target's lines of shared logs). Record copies keep the original line count and line numbers (lines not included are blank), so a `.wax/…:line` cite in the report matches `records/…:line`. Secrets, tokens, the home folder, project paths, the user name and emails (kept with `--keep-email`) are scrubbed per JSON value, a value of 40 or more token characters under a field whose name ends in token, key or secret becomes `<token>`, and fields whose name contains secret, token or password are always `<omitted>`. The SHA-256 keys wax computes itself (an approval's `repeatKey`, a pre-import check's `checks.key`) are not secrets and stay, so repeats remain visible. `.env` contents, snapshot objects, capture images and interactive usage (`.wax/usage/`) are never included at any level. An existing folder is refused rather than overwritten, and records that are links are not followed. Files are `0o600` and folders `0o700` (on Windows the folder ACL applies). (2) After opening every file (editing is fine), `wax diagnose --zip <folder> [--keep-email]` checks the folder again. If any line still matches a scrubbing rule, or there are links or special files, nothing is zipped and the locations are listed (`file:line rule`, no values). The check sees whole lines, so a token right after a field name is caught too; only a 64-character lowercase hex value in the two key fields above is not counted as a token. Otherwise it writes a new `<folder>.zip` (refused if it exists). Scrubbing can miss things, so always read it before sending. Both commands are for a person in a terminal (a worker wax started, `WAX_WORKER=1`, is refused).

The goal and task screens of the dashboard (`/manage`) also have a **Diagnose** button. It shows the same report in a read-only box in the screen language, and selecting a cite opens that record (scrubbed with the same rules). Only records the report cites can be opened. The screen writes no files, so make a bundle to send in a terminal with the `--bundle` command shown on the screen (a new folder `../wax-diagnose-<ID>` next to the project). Plan steps are judged the same way as `wax status`: a step counts as green when a `wax test` proof tagged to it in this cycle's implement (its `step` field; older proofs without one count for each step with the same `check`) passed with the same command as the S line's `check` (or with `--checks` covering all of its `checks=<ID>`). Steps with `check: none(reason)` and steps without a usable check are not counted, and nothing is judged before implement starts.

### Screen captures and design comparison

Work with a screen keeps captures as evidence. `wax capture <task-id> --check <check-id> --file <file> [-- <capture command>]` stores the capture in `.wax/artifacts/`, and each capture can carry labels for the conditions it was taken under.

- `--viewport <width>x<height>`: screen size (e.g. `1280x800`, each 16384 or less)
- `--scroll top|bottom|<pixels>`: scroll position
- `--state <name>`: screen state, a name of up to 32 characters starting with a lowercase letter (e.g. `default`, `hover`, `focus`, `open`, `loading`, `error`, `empty`)

For web projects (section 6-8) the design and review guidance captures each state at 360, 768 and 1280 and at 1920, wider than the design, and asks what caused each change: scrolling, a click, hover or time. The labels also show in the PR description draft, `wax trace` and the dashboard's run trace panel.

`wax compare <task-id> [--json]` pairs each review capture (`ui-review`) with the design capture (`design-preview`) that has the same width, scroll and state. The baseline is only design captures taken in this project. The latest capture per label is used, and the baseline comes from the latest design iteration at or before the reviewed one. Captures without a partner (no baseline, baseline not re-captured) and older unlabeled captures are listed separately instead of paired, and design-studio handoff previews show as unlabeled references. When the two PNGs have the same size, the share of differing pixels is shown as an observation, not a match verdict; when the sizes differ, it only says so. The last review visit in the dashboard's run trace panel shows the two captures side by side (stacked at phone width), and the PR description draft carries a summary. It is read-only and calls no AI. The review guidance captures with the same labels as the design captures, reads `wax compare` and writes down the remaining differences instead of hiding them.

### PR description draft

`wax pr-body <task-id> [--out <file>] [--json]` builds a Markdown PR description draft from the task records alone: a suggested PR title, the task stage and iteration, the saved report document, the acceptance-criteria table, "Quality at a glance" (evidence per quality characteristic, recorded and open defects, whether each test command of the approved project manual has a passing proof in this cycle, and the full report command), a "Workers by phase" table when PM loop workers ran (the tools launched in order, who completed the phase, and auto actions after a failure, for example Codex → Claude Code with `switch-unhealthy`), the current iteration's test and commit proofs and screen captures, the design comparison summary, the reasons for stages completed without proof, a "Usage (as reported by the tools)" section when the PM loop ran headless workers (per-tool sums and the number of runs that did not report), and evidence freshness. Missing records are reported as missing, never made up. `@name` in the records is turned into code so GitHub sends no notification. It writes only to standard output or the `--out` file (an existing file is overwritten; directories and symbolic links are refused), calls neither `gh` nor the network, and never creates a PR.

**Defect log:** when review finds defects, do not complete review; go back to implement with `wax iterate <task-id> --reason <reason> --defects-file <file>`. The file is a JSON array such as `[{"title":"<what is wrong>","detail":"<how to reproduce and the impact>","ac":"AC-1"}]` (`detail` and `ac` are optional); each defect is numbered D-1, D-2 … and kept in the task record. The next review completes only when each open defect has `{"id":"d-1","status":"pass","proofIds":["<passing test proof ID from this iteration>"]}` in `--checks-file`. Re-verification accepts only tests that passed in that iteration, and `fail` refuses completion. If a defect cannot be re-verified, give the reason with `--defect-unverified <reason>`; the defect stays open and is checked again next iteration. Open defects appear in the implement and review instructions and in `wax context`.

**Rulings:** what a worker decided without asking a person (names, structure, dependencies, behavior, tests, scope, how to read an unclear acceptance criterion) is recorded with `wax ruling <task-id> --what <what you decided> --why <why> --cost <cost if wrong> [--area naming|structure|dependency|behavior|test|scope|other] [--author <session name>]`. To avoid shell special characters, pass a JSON file with the same fields (`{"what":"…","why":"…","cost":"…","area":"…"}`) with `--file <file>`. Each ruling is numbered R-1, R-2 … for the current phase and iteration and stays in the task record across iterations. With `--phase <stage>` it is recorded only while that is the current stage. The limits are 50 per task, 200 characters for `what`, 500 for `why` and 300 for `cost`; finished and archived tasks refuse rulings. Without `--area`, a `what` containing 삭제, `delete`, `drop`, `migration`, `auth`, 권한, `secret`, 비밀, `skip test` or `AC-` gets a **May need a person** mark (it does not block). `rulingSummary` in `wax status <task-id>` shows the totals (`total`, `unacknowledged`, `flagged`) and one line per ruling, unacknowledged first, and the report instructions include the ruling table and say not to hide unacknowledged ones. A ruling announces a decision; it does not widen what a worker may decide. The PM loop worker instructions carry a fixed list (person decision points, security, irreversible actions, scope such as dropping an AC or adding unplanned features) that a worker must report as blocked instead of deciding.

**Acknowledging a ruling or deciding it again:** open a task's **Run trace** on the dashboard and a **Rulings** section appears at the top (unacknowledged ones and those marked **May need a person** first). Text the worker wrote is shown as plain text. For each ruling press **Acknowledge**, or, if it is wrong, press **Decide again**, write a note on what is wrong and how it should be decided (required, up to 500 characters) and press **Confirm deciding again**. The result is shown before you confirm. If the task is in review, report or done, it goes back to implement with one defect (D-N, "Ruling decided again: …") like a person's iterate and is rechecked in the next cycle's review; in plan, design or implement the stage stays and the defect opens in this cycle and is rechecked in this cycle's review (if that stage's document must change, have it redone in the current stage). A ruling decided again is not changed further; fix it through that defect. Only a person on the dashboard can acknowledge or decide again (worker, `auto` and `pm-loop` names are refused), and there is no CLI or MCP path. If the task changed after the screen read it (for example a worker completed in the meantime), the mark is refused and the screen reloads. Unacknowledged rulings do not block progress. The goal screen shows "3 rulings, 2 unacknowledged" and a **View rulings** link per task, and the PR draft card shows how many are unacknowledged. The quality report (`wax quality-report`) and the PR draft (`wax pr-body`, up to 10, then a count) quote a **What the worker decided** table (ID, stage, what, why, cost if wrong, status), with @names changed so nobody is notified.

**Secret scan:** when implement and review complete, wax scans the lines and files added by the task. The base is the commit at task creation; later commits, uncommitted changes and new untracked files are read (files `.gitignore` excludes are not). Completing inside the task's worktree (`.wax/worktrees/<goal>-<n>`) scans that worktree; completing from the project folder scans the project and every worktree in use for the task (a finding there shows as `.wax/worktrees/<id>/<file>`, and the scanned worktrees are kept in `secretScan.worktrees` of the completion record). It looks only for unambiguous formats: AWS, GitHub, Anthropic, OpenAI, Google, xAI, Slack and Stripe live keys, PEM private key headers, `.env` files (except examples such as `.env.example`) and private key files (`.pem`, `.key`, `id_rsa` …) entering the repository, and committed or staged `.wax/` records. A finding refuses completion and shows only the file, line, rule and the first 4 characters of the value; the value is never kept in the records either. If it was already committed or pushed, revoke the key and issue a new one. For an example or test value put `wax-secrets: allow` on that line; to leave out a whole file list its path in `docs/wax/secrets-allow.txt`, one per line. Both stay in the repository and show up in review. To check beforehand run `wax secrets <task-id> [--json]` (exit code 1 when something is found). With `WAX_SECRET_SCAN=warn` the stage completes and the finding is kept only as a warning and in the completion record (`secretScan`); `off` skips the scan. Projects outside Git are not scanned. The quality report counts the result as security evidence.

**Change impact:** `wax impact <task-id> [--json]` finds the tests related to the files this task changed (commits after the task-creation commit, uncommitted changes and new files) and shows whether this iteration's test proofs ran them. Related tests are the changed test files themselves, tests that `import` or `require` a changed file by relative path, and tests with the same name (`pay.mjs` ↔ `pay.test.mjs`). A test counts as run when a proof command names its path, or when a whole-suite run picks no test file (`npm test`, `node --test`, `pytest`, `go test` and the like). Related tests not run, related tests whose last run failed and changed sources with no related test go into the review stage prompt (`wax prompt review`, dashboard requests, PM loop workers) and the quality report as observations. They never block completion. The rule only looks at names and imports, so it can miss or add tests; when one is unrelated, say why in the review document.

**Dependency check:** `wax deps <task-id> [--json]` lists the packages added, changed or removed in the dependency manifests this task changed (`package.json`, `requirements*.txt`) and the changed lockfiles (`package-lock.json`, `pnpm-lock.yaml`, `poetry.lock`, `go.sum`, `Cargo.lock` and the like). npm package licenses are read from the installed `node_modules`, and licenses with distribution terms such as GPL, AGPL, LGPL and MPL are marked. wax does not look up vulnerabilities itself (it uses no network). Instead, the review prompt of a task whose dependencies changed asks for an audit run recorded as `wax test <task-id> --checks sec-deps -- npm audit --omit=dev`, and the quality report counts that proof as security evidence. Without a network or the tool, report it as unverified. It never blocks completion.

`wax quality-report <task-id> [--out <file>] [--json]` builds a Markdown quality report from the task records alone: evidence by ISO/IEC 25010 quality characteristic (functional suitability, performance efficiency, compatibility, usability, reliability, security, maintainability, portability), required checks, acceptance criteria, the defect log, test proofs per iteration, the design comparison, reasons for unverified items and completions without proof, and evidence freshness. Acceptance criteria and runtime or integration required checks count as functional suitability; visual and preview required checks count as usability. Other characteristics count only when a `wax test --checks` ID starts with `func-`, `perf-`, `compat-`, `ux-`, `a11y-`, `rel-`, `sec-`, `maint-` or `port-` (for example `--checks perf-checkout`). A characteristic without evidence is shown as "No evidence". It is a self-assessment, not a test certificate. It only reads, and calls neither AI nor the network.

After report completes, the report guidance offers to make this draft and runs `gh pr create --draft --body-file <file>` only when the user approves. Creating, pushing and merging a PR is always a person's call. The PM loop (section 6-6) likewise only offers a draft file card for tasks that finished report and leaves the PR decision to a person.

Reports, conversations and whiteboard posts travel as a line of notes that streams from the sender's seat along the corridors and the elevator shaft to the recipient (or, without one, the latest conversation partner in the same channel) or to the whiteboard, while speech bubbles still appear above heads. The room follows each session's current state, not the task stage. The dashboard panel shows the same view |
| `/search` Search · `/help` Help | Record search and index management (section 6-1), how to use each screen and how to call commands in each tool |

Changing the date shows that day's records.

### Checking records on the dashboard

Selecting a stat card at the top jumps to the related tasks, assignments or timeline. **Check first** lists blocked assignments, failed test evidence on the selected date, and old open questions, in that order. If a later pass exists for the same task and stage, the earlier failure leaves this list but stays in the timeline. Don't conclude that a whole task failed from a failure record alone.

**View original** shows the full text of questions and decisions shortened in summaries, and **View evidence** shows the saved command, exit code and output in the existing document window. The buttons never rerun the command. Recent decisions and test evidence follow the selected date; assignments and open questions follow all current records.

**Run trace.** Select **Run trace** next to a task in **Task progress**, or open `/manage?feature=<task ID>`, to see how the task went through its phases as a vertical timeline of phase visits. Each visit expands to its start, end and time taken (computed like the time per stage), outcome (phase completed, sent back to implement with the reason, in progress, and questions or blocks when a request is linked), the completing session and tool, the commits at the time, completion evidence and reasons, linked test and commit proofs with files changed since they were recorded, review acceptance-criteria results, and files changed between the commit at the end of the previous visit and the end of this one (committed changes). Iterations show as revisits of the same phase. **Download Markdown** saves the same content with the PR-description rules (`@name` and HTML neutralized); on the command line use `wax trace <id>` (Markdown) or `wax trace <id> --json`. It is read-only and calls no AI. Completing or sending back a phase now also records the commit (`head`), whether there were uncommitted changes (`dirty`, `.wax/` excluded) and, when known, the tool (`tool`, dashboard auto-run) in the history; projects without Git and older records leave those cells empty. A visit where a PM loop headless worker ran shows **Usage (as reported by the tools)** per tool, together with the number of runs that did not report usage. Each worker run also shows **Files this run changed (including uncommitted)** with its diff, and **Restore to before this run**, which only a person can do (section 6-6, "File snapshots per run and restore"). Tokens and cost of interactive sessions are not shown because no record ties a Claude Code usage session to a phase visit.

Even if you switch dates quickly, only the response for the last selected date is applied. If a refresh fails, the last successful records and a retry button stay. Reconnecting rereads session information, and background refreshes never clear an assignment or new task you are typing.

### Sessions talking to each other

Start the first session with `/wax:init` and join other AI sessions with `/wax:join` (Codex `$wax:join`, Antigravity `/join`, GitHub Copilot CLI and Grok Build "join with the wax join skill"). Even if you skip init or join, the first wax command a session runs joins it automatically. If the same name is already active (two or more sessions of the same tool in the same folder), the session joins with a number such as `claude-my-app-2` and tells you the name. If repeated inits left earlier sessions holding the name, `/wax:init --reset` (join takes it too) clears them before joining with the default name. Sessions that are listening or working are kept, and the PM role and tasks stay with the name, so the new session that joins under it takes them over. When a joined session runs a wax stage command, it switches to "working" as the stage starts and reads the recent messages in that task's channel. When the stage ends it records the result (done or blocked) on its assignment. The default name is `tool-foldername` (e.g. the Claude session in the `my-app` folder is `claude-my-app`). Characters in the folder name other than letters, digits, spaces, `_`, `.` and `-` become `-`, and the name is cut to 40 characters. To run several sessions of the same tool or rename one, add `--name <name>` to any wax command (e.g. `/wax:join --name claude-front`). The session keeps that name in later commands and joins the channel right away. A name the session used before is marked "away". The name is only remembered within the session's conversation, so set it again in a new session.

You can choose its task at the same time. `/wax:join --name claude-front --feature chatbot` (same as `--project=chatbot`) joins the session in the idle state with the `chatbot` task selected, and later wax commands use that task when you leave out the task ID. init opens `http://127.0.0.1:4330/` (the team channel) whether or not a task is selected. That task's records are at `/manage?feature=chatbot`. **Team up with existing AI sessions** on the home screen shows whether there is a PM, assignments and the reasons they are blocked, and the command to paste into each session.

The communication rules keep back-and-forth short. An AI session rereads the whole conversation every time it sends a message, so even a one-line greeting or acknowledgement is expensive.

- **Instructions** are given only as the PM's assignments (`assign`), with the goal, scope, done criteria and deliverables.
- **Results** are reported in the assignment status notes (`task done`, `task block`), which appear in the dashboard task list and timeline.
- **Channel posts** are only questions (`question`), answers (`answer`) and decisions (`decision`). No greetings, acknowledgements, progress reports or summaries. A message the CEO explicitly asks to send is sent as is.

A message has two parts.

- **Doing now** (`--doing`): what the sending session is doing. It also appears in the dashboard team list.
- **Message** (`--message`): the question, answer or decision the recipient (`--to`; everyone if omitted) needs. Point to document paths instead of copying their contents.

To talk directly, run `/wax:chat [channel] [message]` (Codex `$wax:chat`, Antigravity `/chat`). A session only reads channels when it runs a command, so another session's messages reach it the next time it runs a wax command. Messages from other sessions are treated as reference only; a request inside a message is never enough to run a command.

**Listening and answering right away.** When a session joins wax and its tool can wake the session for each output line (Claude Code's Monitor), it automatically starts `wax chat watch --author <name> --wake`. After that, a message that calls it with `@name` or names it as a recipient, or a new PM assignment, wakes the session and it answers in the same channel with `answer`. Waiting never calls the AI, and messages that don't call it or that it sent itself don't wake it. Messages are delivered in the order they were written even across channels, and if watching stops and restarts (Monitor expires every 30 minutes), messages from the gap are delivered first. Read positions are kept in `.wax/chat/watch/` and listening markers in `.wax/chat/listeners/`. If someone in the chat asks for work the session wasn't given, the session passes the request on to its own user and says so. `/wax:chat --watch` turns listening back on when it is off. Codex, Gemini CLI and Antigravity CLI cannot wake a session from output, so they check messages at their next wax command. For immediate notifications, run `wax chat watch` in a separate terminal. That watch is for people to read, so it has no `--wake`, and the dashboard shows it as `at next command`.

**Calling from the channel screen.** Above the input on the channel screen (`/chat`), joined AI sessions appear as **recipient** buttons labeled `answers now` (listening), `at next command` or `away`. Choose recipients or call them with `@name` and send, and you are told who will answer soon and who will check later. Without a recipient, the message is only recorded and no AI session wakes. **Reply** on each message continues from that message, and replying to a question makes it an answer.

**Input suggestions.** Type `@` in the input for joined sessions, `/` for wax commands and `#` for tasks. Pick with the arrow keys, insert with Enter or Tab, and close with Esc. Choosing `@name` also selects that session as a recipient. A `/command` is written in the recipient tool's syntax when there is one recipient (Claude Code `/wax:review`, Codex `$wax:review` and so on), otherwise as `wax review`, and the task ID is filled in inside a work thread or a task channel.

**Work tab.** The **Work** tab on the left of the channel lists requests, assignments, continued conversations and execution approvals as **Answer needed · In progress · Done**, grouped into today, yesterday, the last 7 days, the last 30 days and earlier. **Find work** above searches titles, content, owners and IDs in every state. Work pinned with the star button stays on top whatever its state; pins are kept in this browser only. A request stopped by an AI question is listed under **Answer needed**. Opening a request folds its conversation by stage (in SM: intake and analysis → impact check → fix → regression check → resolution report), with only the current stage (or the last one once finished) open, and each stage header shows its progress updates, passing tests and commits. Test and commit evidence recorded in a stage appears as cards that open the detail records with the actual output. A card shows "N files changed since" when files changed after the proof was recorded (an observation).

**Direct notifications between Claude Code sessions.** Claude Code can message other Claude Code sessions on the same computer directly. A session records its own session name with `--peer` when joining (shown as `session <name>` in `wax chat who`). When you post with another Claude session as a recipient, that session only receives a pointer like `wax: #<channel> <message ID> from <name>`. The content stays in the channel record, so the notified session reads the message from the channel and ignores ones it already handled. When this isn't available it is skipped, and the message still arrives through the channel and listening.

### Session names and rejoining

Keep the `session` returned by `wax chat join --author <name> --session <ID> --json`, and pass `--session <ID>` with every status change, post, report and assignment change for that name. On a 409 error, join again with the same session ID and use the name it returns. PM and assignment roles stay with the name, and a name inactive for 24 hours is taken over by the next session. Records without tokens from earlier versions are handed over on join. CLI records written without join are identified separately, and once a session takes over a name, it cannot be written without the token.

### Automatic session state

For Claude Code sessions, a plugin hook records the state of each turn. The dashboard knows the following even when a session never runs `chat presence`.

| Auto state | Meaning |
|---|---|
| working | received a prompt or is using tools |
| waiting for you | waiting for an execution approval or an answer |
| done (unseen) | finished its turn and nobody has looked yet |
| idle | a person saw the finished turn, or a new session |
| no news | working or waiting for you, but no hook for over 20 minutes |

- **How it links:** when a session starts, the hook puts `WAX_HOST_SESSION` into that session's command environment, and `wax chat join` uses it to link the join record. On Claude Code versions without that environment, pass the ID given in the session context with `--host-session <ID>`. Once linked, `join` says "Linked to the session state hook".
- **Where you see it:** **Sessions waiting for you** at the top of the team channel (waiting for you first, then done (unseen)), a mark on the office name tag (`?` for waiting for you, a dot for done), browser notifications (once per report) and the auto state column of `wax chat who`. Clicking **Open** in the list, opening the office character or sending that session a message marks the finished turn as seen.
- **Waiting for a teammate:** `wax chat wait <name> [--until done|blocked|idle] [--timeout <seconds>]` waits until that session finishes, waits for a person or goes idle after the command starts. A turn that had already ended does not count. The default is `done` with 600 seconds; if it is not seen in time the exit code is 1.
- **Away for linked sessions:** instead of the 10-minute rule, a linked session is away when it ended (`SessionEnd`) or had no hook for over 2 hours.
- **What is stored:** `.wax/chat/host/<session hash>.json` holds only the state, hook name, notification type, the tool name of an approval request, and the time. Prompts, messages and tool input are never stored. Records are written only in projects that have `.wax`; records silent for over a day, and the oldest beyond 200, are removed.
- **Scope:** interactive Claude Code sessions only. Codex is left out because enabling its hooks needs a user config change, and no plugin-attachable state hook was confirmed for the other tools. Their sessions show "No auto state" in `who`. Headless runs started by the dashboard (request auto-run, PM loop workers) are not recorded; their state is on the request and PM loop screens.
- **Turning it off:** start Claude Code with `WAX_HOST_STATE=off` and the hook does nothing.

### The PM and sharing work

There is one person, the **CEO**. The CEO gives direction and makes final decisions; the PM advises, offers options, turns decisions into assignments and reports progress and delays to the CEO.

1. In the session that splits the work, run `/wax:pm <instruction or goal>`. The PM checks the goal, current tasks and participants, picks the usual scope and owners, and in the same call creates the task and assigns its current stage. Existing assignments are reused. It only asks a specific question when the CEO asked for options or when it cannot assign because of missing requirements or conflicting explicit instructions. With no goal and no records, it asks once for the outcome you want. It never stops at a promise such as "I'll assign once scope and owners are decided."
2. The PM briefly records the scope and owners it applied, then reports the real feature ID, task ID, owner, stage and command. It does not overwrite other tasks in progress or assign later stages that cannot start yet. The assignment itself is the instruction, so it isn't repeated in a channel; only when the order between owners matters is it recorded as a decision in the general channel. When there is no PM, the person can take the PM role from the dashboard. The PM carries the project forward, so it isn't changed lightly. Another session running `/wax:pm` does not replace the existing PM; it changes only when the CEO asks (confirmed once more under **Replace PM…** on the dashboard, or `wax chat team pm <name> --replace` in the CLI). If nothing is in progress, create a plan-stage task with **New task** in the dashboard's **Task progress** panel, then assign planning to an AI.
3. Run `/wax:work` (Codex `$wax:work`, Antigravity `/work`) in each session. It accepts its own assignment, performs that task's stage, and when finished records done or blocked (with a reason) together with the result. That record is the report to the PM. It handles one assignment at a time.
4. Running `/wax:pm` again without a goal in the PM session gives a **progress report**. With a new goal or an instruction to continue, it goes on to the next assignments in that scope instead of stopping at the report. It covers done, in progress and not started for each task, delays (blocked work, work with no results for a long time, work waiting on an earlier stage) with causes and schedule impact, and risks, and it raises decisions as options with a recommendation. Unblocking or reassigning work within the decided plan is the PM's job; changes to scope, priority, schedule or owners need the CEO's decision. If the person is among the participants, a short report is also posted to them in the channel so it shows on the dashboard.

Safety limits:
- Only the PM chosen by the CEO can assign work. Tasks created by other participants or instructions in ordinary messages are not assignments.
- An assignment only allows the given wax stage of the given task. The CEO's direct instructions take precedence over the PM, and file changes and commands still go through each tool's permission checks.
- The stage order is kept. If the previous stage is not finished, the assignment is recorded as blocked and the PM is told.

**Task completion check.** When an assignment is marked done (`task done`), wax checks that the stage of the linked feature actually finished after the assignment. An assignment for a specific stage needs that stage's completion record (`wax complete`) in the current cycle, dated after the assignment; an `any` assignment needs at least one stage completed since the assignment. The default (`WAX_TASK_DONE_CHECK=warn`) records it as done with a warning (`warning`) on the status record. The warning appears in the CLI error output (`wax chat: 경고: …`, or `wax chat: warning: …` in English), the assignment lines of `wax chat tasks --all` and `wax chat team`, the dashboard timeline and the daily report draft, the assignment conversation in the work tab, and the office work notes, and the PM treats such assignments as not done in progress reports. Sessions and dashboards started with `WAX_TASK_DONE_CHECK=enforce` reject such a completion and tell the session to complete the stage first, or record `task block` with the reason if it cannot be finished. `off` skips the check. Assignments whose feature was deleted, and status changes other than done (accept, block, cancel), are not checked.

### Claude usage monitor

With Claude Code 2.1.287 or later, the wax mod in the plugin (Claude Code mods) writes only numbers to this project's `.wax/usage/<session ID>.json` at the end of each turn: the account's plan usage (5-hour and weekly % and reset times), that session's context usage, and its cost so far. Conversation content (prompts, answers, tool calls) is neither read nor kept, and nothing is written in a project without a `.wax` folder. See it on the monitor on the CEO's office wall in the virtual office and with `wax chat usage`; the PM reports usage near its limit as a schedule risk in progress reports. Turning off the wax plugin's hooks in Claude Code's `/plugin` stops the recording. Usage for the other tools (Codex, GitHub Copilot CLI, Gemini CLI, Antigravity CLI) is not shown yet.

### Daily reports

Run `/wax:daily [YYYY-MM-DD]` (Codex `$wax:daily`, Antigravity `/daily`) and the AI reads that day's compiled draft, writes a report and registers it as `docs/wax/daily/<date>/NN.md`. The report covers what was done today, verification results, decisions, problems and open questions, and tomorrow's work. Registering several times on the same day increases the number and never overwrites an earlier report. **View draft** on the dashboard shows a draft compiled from the records without AI.

### Using the CLI directly

```sh
wax chat post <channel> --author <name> --session <ID> --kind <kind> --doing <doing now> --to <recipient> --message <message>
wax chat read <channel> [--since <message ID>] [--json]
wax chat join --author <name> --session <ID> --kind <kind> [--model <model>] [--feature <task ID>]   # first join (adds -2, -3 if the name is active)
wax chat presence --author <name> --session <ID> --state working|discussing|reviewing|idle|away [--note <doing>]
wax chat who
wax chat reset [--author <name>]   # clear earlier sessions (keeps listening or working ones; --author clears only that one)
wax chat watch --author <name> [--feature <task ID>] [--wake] [--json]   # messages calling me and new assignments, one line each, until stopped. --wake wakes an AI session
wax chat read <channel> --id <message ID> [--json]                       # read one message as is
wax chat team pm <name> --kind <kind>        # set the PM (decided by the CEO)
wax chat assign <task ID> --to <owner> --author <PM> --session <ID> --phase <stage|any> --message <instruction>
wax chat tasks [--to <name>] [--all]
wax chat skills [--json]                    # skill map: records per member by stage, check and code area, and empty areas
wax chat rules [--all] | rules candidates | rules lint   # project rules, evidence candidates, evidence check
wax chat rules propose --author <name> --session <ID> --message <rule> --why <why> --source <evidence IDs>   # propose a rule (a person approves it in the dashboard)
wax chat notes <name> [--days 7] [--json]    # work notes: what a member did each day, current assignments and latest memo
wax chat memo --author <name> --session <ID> --message <memo> [--feature <task ID>]   # leave what remains and what to watch
wax chat task accept|done|block|cancel <assignment ID> --author <name> --session <ID> [--message <note>]
wax chat daily [--date YYYY-MM-DD]           # timeline
wax chat daily draft | report --file <report.md> | list
```

**Recipient state after posting.** After the message ID, `wax chat post` prints one line with each recipient (`--to` and `@name` in the body): whether it is listening now (the same rule as the dashboard's recipient picker), its state from the session-state hooks when linked (working, waiting for you, done (unseen), idle, no news, session ended), and whether the name never joined. When nobody is listening, a "Stored only: no recipient session is listening now, so none was woken. Tell a person or use `wax chat wait`." line follows. `--json` carries `recipients` (`name`, `member`, `listening`, `host`) and `storedOnly`, and so does the MCP `wax_post` result. Without recipients only the ID is printed, as before. The message is always stored as before, and this check never wakes or starts a session.

`wax` means `node "/path/to/wax/bin/wax.mjs"`. The kind (`--kind`) is one of `claude`, `codex`, `copilot`, `gemini`, `antigravity`, `grok`, `human` or `other`. For other commands see `wax --help`, `wax chat --help`, `wax trigger --help`, `wax pm-loop --help`, `wax mcp --help` and so on.

**CLI language.** Help (`--help`), messages, warnings and errors are in English with `WAX_LANG=en` (values such as `en_US` and `ko-KR` are accepted too). Without `WAX_LANG`, the CLI uses English when the first of `LC_ALL` → `LC_MESSAGES` → `LANG` that is set starts with `en`, and Korean otherwise; `WAX_LANG=ko` keeps Korean on an English system. `--json` output, saved records, and the stage prompts, handoff context and skills given to AI sessions stay the same in either language. The dashboard's screen language is set separately (section 6, "Opening the dashboard").

| Path | Contents |
| --- | --- |
| `.wax/chat/channels/<channel>.jsonl` | Channel messages (append only) |
| `.wax/chat/board/<task>.jsonl` | Whiteboard notes and report records |

## 6-1. Searching records

Search conversations, whiteboard notes, assignments, daily reports, stage documents, completion evidence, improvement history, test and commit evidence, request conversations and design jobs in one place. Every result shows where the original is (file plus record ID or document location) and links to the screen that opens it.

Build the search index once. Press **검색 색인 만들기** (Build search index) under **검색** (Search, `/search`) in the dashboard menu, or run:

```sh
wax search index
```

After that, each search first brings in only the records that changed, including records written by other AI sessions and CLIs.

```sh
wax search handoff
wax search 인계 --feature lookbook-upload
wax search "Claude Code" --kind message --author claude-app --from 2026-10-01 --to 2026-10-18
wax search status
```

- Every word separated by spaces must appear; double quotes search a phrase with spaces. Matching ignores case, and results are newest first.
- Three or more characters match anywhere in the text (`handoff-v2.md`, `docs/wax/design`, the start of a commit SHA, or Korean such as `인계를`). Two letters or digits (`UI`, or Korean such as `인계`) match two-character pieces inside words, so `인계` also finds “인계를”. A single character scans everything and can be slow. Stemming, Korean initial-consonant search and semantic search are not supported.
- Filters: kind (`--kind`), task (`--feature`), author (`--author`), stage (`--phase`) and dates (`--from`, `--to`, YYYY-MM-DD). With many results, use the `--cursor` printed at the end for the next page. `--json` returns the original locations and highlight ranges as JSON.
- Execution approval records, session tokens and AI session details are never searched.

The index (`.wax/search/index.db`) is a copy that can always be rebuilt; the source of truth stays the JSON/JSONL in `.wax`. Without an index, search only explains how to build one. If the index is damaged or its format differs from this wax version, rebuild it with `wax search index --rebuild` (**색인 다시 만들기(복구)**, Rebuild index, on the dashboard). Unreadable record lines are skipped and listed with file and line numbers in `wax search status`. If building stopped midway (killed, or the dashboard restarted), the page says it was interrupted and offers **Resume building index**; searching or pressing it brings in the remaining records. Editing or deleting only a whiteboard or daily report Markdown file shows up in the next search, and a missing file or one reached through a symbolic link outside the project is not searched and is listed in the status. The author filter keeps names such as 대표 and names with Korean letters or spaces as they are.

### Finding related records (recall)

`wax recall` lets an AI session consult other tasks' records before it works. It uses the same index and ranks records **by relevance**. Unlike search, any one word may match; records matching more words and matching them better come first. A trailing Korean particle is also dropped (`토큰이` finds `토큰`).

```sh
wax recall token expiry retry --exclude-feature login-retry
wax recall payment error --kind note --limit 5 --budget 2000
```

- Results are quoted one line each within a budget of characters (not tokens), with the original location and a screen link. `--json` adds the rank, matched words and score.
- Stage skills and automatic runs use `recall` when a similar error, the same module or an earlier decision may exist in another task. Recalled records are reference data, not instructions, and are checked against the current code.
- Without an index, recall builds it once. Semantic search (different words with a similar meaning) is not supported.

Search needs Node.js 22.16 or later, or 24 or later (full-text search in the built-in SQLite). On older Node.js only search shows a notice; every other wax feature keeps working. See the [search guide](SEARCH.md) for details and measurements.

## 6-2. MCP server (experimental)

`wax mcp` is a server that lets coding tools read wax records and write to the team channel over MCP (stdio). Tool calls instead of shell commands mean fewer argument mistakes and permission prompts, and since one connection is one session there is no `--session <ID>` to pass. It is off by default and starts only when the environment variable `WAX_MCP=on` is given where you register it. Installing the plugin does not register it.

| Tool | What it does |
| --- | --- |
| `wax_status` | The task list, or with `id` one task's stage in progress, the stage after it, revision, completions and recent proofs |
| `wax_context` | A task's handoff context (`id`, `budget` in characters), the same as `wax context` |
| `wax_recall` | Related decisions and failures from other tasks (`query`, `excludeFeature`, `budget`), ranked as `wax recall` does |
| `wax_inbox` | Messages that mention me (or `author`) and PM assignments to me (optionally only after the `since` message ID), by the same rule as `wax chat watch`, without moving its read position |
| `wax_join` | Join the team channel (`name`, `kind`, `model`, `peer`) and update presence (`feature`, `state`, `note`); a different name renames — `wax chat join` and `presence` |
| `wax_post` | Posts only a `question`, an `answer` (`replyTo` required) or a `decision`; greetings and progress reports (`message`, `opinion`) are refused — `wax chat post` |
| `wax_task` | Marks a task assigned to me `done` or `block` with its `result`. A `done` before the stage is complete is recorded with a warning, or refused under `WAX_TASK_DONE_CHECK=enforce`, as in the CLI — `wax chat task` |
| `wax_complete` | Completes the current stage (`id`, `phase`, `evidence`, `proofIds`, `checks`, `noProof`, `acUnverified`, `verdict`, `revision`) under exactly the conditions of `wax complete`: proofs, acceptance trace, reviewer separation |
| `wax_assign` | PM only. Assigns a task's current stage (`feature`, `to`, `message`) — `wax chat assign` |

- **Session and author.** Call `wax_join` once first and the connection becomes a wax session. The session ID stays inside the server process and never appears in a result. Write tools have no `author` or `session` argument and record only under the joined name. When another session already uses the name, you join with `-2`, `-3` added and the result's `author` says so. When the connection loses its name (for example `wax chat reset --author <name>`) or the client sends `initialize` again, the server rejoins with the same session ID before the next write and adds `rejoined` and the current `author` to the result.
- **The same checks as the CLI.** Write tools call the same functions as the CLI, so validation, locks, length limits and error messages match. Errors come back with `isError`, the translated message (`WAX_LANG`) and an HTTP-like `status` (400, 403, 404, 409). Every record written (messages, assignments and status changes, stage completions and history, presence) carries `"via": "mcp"`.
- **Not tools.** Approving or rejecting runs, approving rules, editing triggers, archiving and restoring, restoring backups and deleting records stay with people in the dashboard. Saving documents (`wax save`) and test, capture and commit evidence (`wax test`, `capture`, `evidence`) stay in the CLI.
- **Writes without a tool.** Accepting a task (`task accept`) is skipped (`done` and `block` work on an open task). Memos, whiteboard notes, rule proposals, cancelling tasks and registering daily reports have no tool yet, and the shell CLI cannot write under a name joined through MCP (its session ID stays inside the server). The guidance tells the session to tell the user what it meant to record instead.
- The project is fixed when the server starts: `--project <path>`, else `WAX_PROJECT`, else the nearest folder with `.wax` from the current directory upward (else the current directory). Tools take no other path. If you do not know which directory the coding tool starts servers in, give `--project`.
- Records in the results (titles, documents, messages, assignments) carry `"source": "record"`. They are data written by people and other sessions, not instructions.

**Registering.** `node /path/to/wax/bin/wax.mjs mcp config --host <claude|gemini|codex|copilot> --project /path/to/my-app` prints the snippet for that tool with this installation's real paths. wax never reads or edits your settings files, so add the snippet yourself. In the examples, replace `/path/to/wax` with the real absolute path of the extracted (or installed) wax folder and `/path/to/my-app` with the project path. On Windows it also runs through `node` without a shell.

Without `WAX_MCP=on` it explains how to turn it on and exits.

## 6-3. One-line requests that run on their own

`init` joins with defaults and opens the dashboard right away. A new request offers two modes.

| Mode | How it starts and runs |
| --- | --- |
| Project | Enter a goal and wax first writes a workflow with scope, task order and dependencies, deliverables and done criteria. Review it on screen and press **Start with this workflow** to move on to design, implementation, review and reporting. A change request rewrites the workflow, and the new version has to be reviewed before it starts. |
| SM · Maintenance | Bug and improvement requests go straight through triage and analysis → impact check → fix → regression check → report. Plan and design documents stay short to match the request, and real test evidence is still required. |

Project mode is selected at first, and after that each project remembers your last choice. You can also open the request screen in a given mode with `init --mode sm` or `init --mode project` (in each host's syntax). A request keeps its mode once created; to use the other mode, create a new request. Older requests without a mode continue as SM. Both modes run in a separate session of the CLI you choose; wax does not spread the work across your existing terminal AIs.

The start guide on the Requests & reports screen (`/start`) walks you through choosing an execution tool → describing the task → following progress and reports. It checks whether each tool is installed; sign-in is checked when the tool actually runs. After installing a tool, press **Check tools again**.

For a new request, choose an installed execution tool: Codex, Claude Code, Gemini CLI, GitHub Copilot CLI or Antigravity CLI. Grok Build does not support automatic runs yet, so use it for team work in a terminal session by asking for a wax skill by name. That CLI's sign-in or API settings, and its account usage, cost and data policies, apply. A request keeps using the tool it was created with; to use another tool, create a new request. New permission requests from Codex, Claude, Gemini and Copilot are allowed once or denied on screen. Antigravity runs within the permissions it already has, and if a new permission request is blocked you need to check its terminal settings. wax never wakes up an existing terminal session or changes another AI's assignment by itself. The PM for automatic runs handles the request and does not replace your project's PM.

- Answer questions in the chat. Extra instructions sent during a run are applied after the current stage finishes. Press **Stop** to halt right away.
- The reason for a stop or error is shown above the request. **Continue** resumes from the saved stage. Restarting the server or viewing a page never calls the AI again.
- Requests run one at a time per project. Implementation and review need real passing test evidence, and a stage changed by another session is reported as a conflict. Each stage may run for up to 30 minutes.
- Records are saved in `.wax/chat/requests/` and stage documents in `docs/wax/<generated ID>/`. Existing tasks and team assignments are still managed in **Detailed records** (`/manage`).
- The dashboard's first screen (`/`) is the team channel, for conversation records. To run work automatically, open **＋ New request** and use **Create workflow** (Project) or **Start** (SM) on the Requests & reports screen (`/start`). Workflow review is separate from execution approvals; your existing CLI permissions still apply.

Automatic runs connect using thread/start, thread/resume, turn/start, outputSchema and item/completed from the [official OpenAI Codex App Server documentation](https://learn.chatgpt.com/docs/app-server).

## 6-4. Execution approvals

To answer the permission requests a tool asks in its console from the chat window instead, see [Managing execution approvals](./APPROVALS.md). Only connected requests can be answered, each with its own **Allow this time only / Deny** buttons.

Cards for file-write requests (Claude Code `Write`, `Edit` and `MultiEdit`, and Codex file changes) carry a collapsed **Change preview**. Its summary line shows the number of files and the added and removed line counts (`+3 −1`); expand it to see the changed lines with three lines of context. The dashboard computes the preview from the path and content in the request and the current project file; no AI is called. The time it was computed is shown, and it is recomputed when the file changes. For Codex requests the diff the tool sent is shown as is.

- When the text an `Edit` replaces is not in the current file, or appears in several places, nothing is guessed; the card says so.
- Paths outside the project, links that lead outside it, `.git/`, `.wax/chat/` and `.env*`, binary files, files over 256 KB or 5,000 lines, and `NotebookEdit` show "No preview: <reason>". Long diffs are cut at 400 lines.
- The preview is for reading only. Allow and deny, and goal allowance matching, do not change, and the preview is not stored in the approval record. If the file changes in between, the actual result after allowing may differ.

**Deny reason.** If you write a reason in the collapsed **Add a reason for denying (optional)** field under **Deny** and then deny, the text stays in the approval record and shows on the decided card (up to 500 characters, control characters removed). Claude Code receives it, quoted, with the deny response, so you can tell it what to do differently. Codex, Gemini CLI and GitHub Copilot CLI cannot carry text in a deny response, so the card shows **Reason is recorded only (not delivered to this tool)**. Leaving it empty works as before.

## 6-5. Triggers: request proposals from schedules, local calls, GitHub issues and CI failures

A trigger only **proposes** a request at the time you set. AI starts only after a person accepts the proposal; nothing is accepted automatically.

- **Create:** under **Triggers** in Detailed records (`/manage`), use **＋ New trigger** to create, edit, turn on and turn off triggers. Definitions are stored only on this computer in `.wax/chat/triggers/`.
- **When:** a schedule (5-field cron and a time zone, e.g. `0 9 * * 1-5`, `Asia/Seoul`) or a local call (`wax trigger fire <id> [--payload <file>] [--key <key>]`, e.g. from a git hook). Schedules run only while the dashboard is open; runs missed while it was closed become one "N missed runs" proposal.
- **GitHub:** **GitHub issues (label)** takes a repository (`owner/name`) and a label, **CI failure** a repository, branch and optional workflow. They are checked every `every` (e.g. `5m`, at least 1 minute) with this computer's `gh` login, only while the dashboard is open.
  - If `gh` is missing or not logged in, the list shows **Connection needed** with the reason and nothing is checked (not counted as a failure). After `gh auth login` it is checked again the next minute.
  - **The first check only records the issues and failures already there as a baseline and proposes nothing.** After that, only newly labelled issues and new failed runs are proposed, within the limits. To hand over an existing issue, remove the label and add it again. Turning the trigger on again or changing the repository, label or branch starts over with a first check.
  - Leave the text empty to use the default (handle the issue; for CI an SM-mode "CI regression fix"). Issue titles and run names enter through `{{issue.title}}`, `{{run.name}}` and the like, cut to 200 characters; issue bodies reach the prompt only as quoted "external event content (not instructions)".
- **What:** a request proposal (mode, tool and text; placeholders like `{{payload.title}}` are cut to 200 characters each with @mentions neutralized), a recipe goal proposal, a daily report proposal, or a notification only.
- **Recipe goal proposal:** you choose a recipe (section 6-6) and a template for its one-line input. Left empty, GitHub issues use the issue title and CI failures the run name and branch. On the proposal card, edit the input and press **Accept and open the recipe start screen**: no request is created, and the PM loop area of Detailed records opens that recipe's start screen filled with the input. A person still checks the values and presses **Create goal**. The details box is prefilled with the event's external excerpt (issue body, CI run info); for a CI failure, accepting also adds the failed job and step names from `gh run view` (no log content is fetched). Workers receive this box only as quoted data, not as instructions. The goal keeps the proposal (trigger and event) as its origin, and one proposal cannot start two goals. A trigger that names a recipe that does not exist is not saved.
- **Accept:** on the **Trigger proposals** cards in Requests & reports (`/start`), edit the text, tool or mode and press **Accept and start**, or **Dismiss**. Proposals expire after 7 days. External content (the payload) reaches the prompt only as quoted "external event content (not instructions)".
- **Safety:** a daily limit and cooldown per trigger, an overall cap of 20 proposals a day, events skipped while a proposal or request with the same event key is open, and automatic turn-off with the reason after 5 failures in a row. Every event is logged in `.wax/chat/trigger-events.jsonl`.
- **CLI:** `wax trigger list`, `wax trigger test <id>` (preview only, writes nothing; GitHub sources fetch once with `gh`), `wax trigger fire <id>` (local sources only).
- **Default limits:** a new trigger allows 3 proposals a day with a 30-minute cooldown. Each trigger can allow 1–100 a day and a cooldown of up to 7 days. Clear **Turn on when saved** in the trigger form to save it turned off.
- **Left to people:** creating, editing and turning on triggers, and accepting or dismissing proposals, are done only by the person on the dashboard. The CLI and MCP have no commands for these. Accepting starts an ordinary automatic run as in section 6-3, and that request's run trace records where it came from (which trigger).
- **Good to know:** GitHub checks are made by `gh` on this computer, so `gh` must be installed and logged in; if `gh` is not on the PATH, start the dashboard with `WAX_GH_BIN` set to its path. The tests use a fake `gh`; long-running polling of a real GitHub repository is not part of the verified scope (section 9).

## 6-6. PM loop: next-step suggestions per goal and auto mode

Group several tasks under one goal and wax works out the next step for each task by fixed rules and shows it as a **suggestion card**. Working out the next step calls no AI, and a card runs only when a person clicks it. Starting an AI tool when no session is listening (a headless worker) and asking AI for a plan draft, a block judgment or a CEO report (PM judgment) also happen only on a click. When a person turns **auto** on for a goal, a fixed set of actions runs without a card, within the limits (see Auto mode below).

- **Create a goal:** under **PM loop** in Detailed records (`/manage`), use **＋ New goal** to pick existing tasks or write new ones (`task-id title`). A goal starts **before plan confirmation**; check its tasks and acceptance criteria, then press **Confirm the plan and start**. Work you do often can start in one go from a recipe ("Start from a recipe" below).
- **Rules:** only the current phase is assigned (never a future one), listening sessions come first, and review goes to a session of a different tool than the implementer (otherwise a person is asked). When an assignment is done but its phase is not complete, the session is reminded once and then a person takes over. An assignment with no activity for 30 minutes is suggested for reclaim, and after report a `wax pr-body` draft is made and the PR decision stays with a person.
- **Headless worker:** when no session is listening (`chat watch`) for the current phase, a **Worker needed** card appears. The tool comes from the same list as request auto-run, limited to tools installed on this computer (tools that cannot run unattended, such as Grok Build, are never picked), and review picks a tool other than the one that completed implement (if there is none, see **Review it yourself** below). GitHub Copilot CLI must also print a version, so the connector `copilot` that VS Code puts on PATH alone does not count as installed. Pick the tool on the card and press **Start … worker**: wax starts that tool for this one assignment and one phase, and it exits when done. Each phase is capped at 30 minutes, and a worker that produces no output for 10 minutes is stopped earlier and its assignment blocked (**idle stop**; time spent waiting for run approval does not count). Permission requests go to the execution approvals screen. The worker completes the phase through the CLI (the evidence and acceptance-criteria conditions still apply); after it exits, the runner marks the assignment done or blocked from its result. Done goes through the existing assignment done check, so a phase that is not complete does not advance and goes to a person. Running workers show on the goal with their tool, elapsed time and a **Stop worker** button, and stopping the goal stops them too. If you dismiss a worker card, assigning a present (not listening) session is suggested instead. A worker completes its phase through the CLI, so the completion history has no tool; the run trace's **tool** comes from the record that started that worker (reviewer separation reads the same record).
- **Antigravity CLI workers:** started headless, Antigravity CLI can't ask for permission, so it refuses any command not already in `permissions.allow` in your Antigravity `settings.json` (for example `~/.gemini/antigravity-cli/settings.json`). Implement and review need to run checks and `wax test` to finish, so picking Antigravity CLI on a worker card for those phases shows a warning that names this setting (you can still pick it). The allow list holds one pattern per command, so wax can't tell in advance whether this phase's commands are allowed: it never reads the setting to hide the warning, always warns, and never changes the setting. Auto runs those phases with another installed headless tool; if there is none, it starts nothing and leaves the card for a person, with a notification.
- **Tool health:** when a worker or PM judgment fails because of the tool itself (three fixed shapes only: **model or sign-in refused**, e.g. Codex `model_not_found`; **usage limit**, e.g. Codex "You've hit your usage limit … try again at …"; **headless permission denied**, e.g. Antigravity CLI refusing to run a command), wax writes one line to `.wax/chat/tool-health.jsonl` on this computer. The shapes live in the plugin's `tool-failures/<tool>.json` with real-output examples; failures of the work itself, such as failing tests, timeouts and idle stops, are not recorded. A tool with a remaining failure goes to the end of the worker card's default order (recipe tools too) with a "Recent failure: Codex model or sign-in refused (…)" warning, and block and report judgments receive it as an unavailable tool (`unavailableTools`). If a judgment picks such a tool or one that is not installed, the proposal card warns, and its tool list shows installed tools only (healthy ones first). You can still pick a warned tool; auto never starts one and leaves the card instead. It clears after one success of the same tool (in that phase for a permission denial) or when you press **Retry** under **Tool health** above the PM loop; otherwise a usage limit clears when the time in its message passes, and anything without a time after 24 hours. `wax doctor` shows one line per tool under `toolHealth`.
- **Tool output of a failed run:** when a worker or PM judgment ends as failed, timed out or stopped for repeating, its end record in the goal log (`.wax/chat/pm-loop/<goal ID>.jsonl`) keeps the last 2000 characters of the tool output (`output.tail`: stderr, or the result line or error message when stderr is empty) and the connection error number and message sent by Gemini CLI or GitHub Copilot CLI (`output.rpcError`). Before it is kept, secrets such as API keys, tokens, the home folder, the project path, the user name and e-mail addresses are replaced with `<secret:…>`, `<token>`, `~`, `<project>`, `<user>` and `<email>`. Scrubbing can miss things, so open the log before sending it to anyone. Normal ends and runs a person stopped keep nothing, and this output is never given to worker prompts or PM judgments.
- **Don’t use:** for a tool you will not use for a while (for example a paused subscription), check **Don’t use** for that tool under **Tool health**. On this computer, for this project, until a person unchecks it, the tool is treated like one with a recent failure: last in the worker card's default order (even as the recipe tool or a judgment's pick), skipped by the default judgment tool order, listed in block and report judgments' `unavailableTools` (`shape: disabled`), never started by auto, and not counted as a reviewer (see Review it yourself). A success, **Retry** or 24 hours never clears it. You can still pick it on a card after reading the warning. Who turned it on or off and when is kept in `.wax/chat/tool-disabled.jsonl` and shown in `wax doctor` under `toolHealth`. Only the dashboard changes it; there is no CLI command. Your tool settings are never changed.
- **Review it yourself:** when no headless tool can take the review (one other than the implementing tool, installed, healthy, not set to Don’t use, and without the warning that it cannot ask for command permission when headless), the review card defaults to **Review it yourself** from the start. For example, if Claude Code implemented the task and the only other tool is Antigravity CLI, the self-review card appears before any failure. It shows the task's acceptance criteria and the commands to run, filled in with the task ID and with copy buttons: `wax status <id>`, `wax test <id> -- <test command>`, `wax save review <id> --file .wax/tmp/review-<id>.md`, `wax complete review <id> --verdict pass --evidence "<what you checked>" --proofs <proof ID>` (plus `--checks-file` when there are ACs and `--author` with the dashboard name). If you entered a test command on the start screen (even without checking an allowance), the `wax test` line uses it, and when there are ACs the card shows the checks file's JSON shape (`id`, `status`, `detail`, `proofIds` per AC). Like allowances, the test command lives only in the dashboard's memory, so after a dashboard restart the line shows the placeholder again. The review is not completed from the dashboard; you complete it from the CLI with evidence, as before. If a warned tool is available you can still pick it and start it as the worker. The bug fix recipe's review note says to check that the reproduction test fails on the code before the fix (for example, set the fix aside with `git stash` and run the test).
- **Allow the same requests during this goal:** on a goal's start screen (**＋ New goal** and the recipe start screen) you check which of four fixed kinds to turn on. They always start unchecked; kinds a recipe suggests only get a **Recipe suggests** mark. The three builtin recipes (Bug fix, Add a feature, Behavior-preserving refactor) suggest **wax commands**, **Test command** and **Writes under .wax/tmp**. **wax commands** are `wax status`, `save` and `complete` for the worker's own task ID and phase (no shell metacharacters, `--file` and `--checks-file` only inside `.wax/tmp/`, no evidence waivers, `--author` is the worker's name, `--project` only when it is this very project) and the ruling `wax ruling <task ID> --phase <that phase> --author <worker name> --file .wax/tmp/<file>` (only this shape; text options such as `--what`, `--area` and `--revision` do not match), and proposing approaches in the design stage, `wax approach <task ID> --propose --file .wax/tmp/<file> [--author <worker name>]` (only this shape; picking an approach with `--pick`, `--single`, `--revision`, `--reason` or any other option does not match); `wax test` is not included. The worker prompt tells workers to always call the CLI with `--project <project>`. **Test command** is only `wax test <task ID> -- <that command>` wrapping the command typed on the start screen (for example `node --test`), optionally with `--revision`, the worker's own `--author`, `--project` for this project, `--worktree` for a worktree the PM loop registered to this goal and task, and in the implement stage a plan step ID with `--step S-n`. A request to run the test command on its own leaves no proof (so the repeat check and completion evidence can't see it) and comes to the execution approvals screen, and the worker prompt tells workers to run every test through `wax test`, including while they iterate. With no command it can't be turned on, and if the command contains shell metacharacters (`&&`, `|`, `;`, `>`, `$`, such characters inside quotes, backslashes and so on) the wrapped form can never match, so turning it on is refused with the reason (no goal is created). Use a command without them, such as `npm test`. **Writes under .wax/tmp** covers files under the project's `.wax/tmp/` (the real location after resolving symbolic links too), and **Reading project files** covers files inside the project except `.git/`, `.wax/chat/` and `.env*`. The kinds apply only to execution approvals from headless workers (Claude Code, Codex) that this goal starts, never to other sessions, interactive sessions (the `WAX_APPROVALS` hook) or other goals. Requests allowed without a person are still recorded with `goal-allow:<goal ID>` and the kind, and the execution approvals screen, the goal screen and the run trace show **Allowed by the goal allowance n times**. On the execution approvals screen, a worker request that matches a kind not turned on gets an **Allow and allow the same requests during this goal** button, which allows that request and turns that kind on for this goal. **Turn off the allowance** on the goal screen turns it off at any time, and it ends when the goal is done or stopped (resuming does not bring it back). The allowance lives only in the dashboard process's memory, so restarting the dashboard turns it off and a worker cannot turn it on through files or the CLI. An allowance turned off by a restart shows on the goal screen as **Turned off because the dashboard restarted** with the kinds that were on, and it comes back only when a person presses **Turn the same kinds on again**.
- **Isolated branch per worker:** check **Isolated branch per worker (creates a git branch and worktree)** on a goal's start screen (**＋ New goal** and the recipe start screen) or on the goal screen. It always starts unchecked (a recipe cannot turn it on), and a goal without it runs workers in the project folder as before. The project must be the top folder of a Git repository with at least one commit, and the HEAD at the moment you turn it on becomes the base commit. It can only be turned on or off before the goal starts its first worker.
  - **Worktrees:** when a worker starts, each task gets a worktree at `.wax/worktrees/<goal>-<n>` on branch `wax/<goal>/<task>-<n>` (based on the HEAD from when you turned it on, or on the tip of the same task's previous worktree branch), and the worker runs inside it. Later phases of the same task reuse its worktree, and different tasks get different worktrees, so concurrent workers do not overwrite each other. Workers call the CLI with `--project <project>` and leave test proofs with `wax test --worktree`; the run trace, snapshots and restores use that worktree too.
  - **Project `.git`:** this `git worktree add` is the only place wax writes to the project `.git`. Each new worktree adds one branch (and its reflog) and one worktree entry (`.git/worktrees/<goal>-<n>/`); nothing else changes, and repository hooks do not run. Worktrees and branches stay when the goal ends (**Import locally** and **Clean up worktrees** below run only when a person presses them). wax does not edit `.gitignore` or `.git/info/exclude`, so without `.wax/` in `.gitignore` the project's `git status` shows `.wax/` as an untracked folder, and tools that search the whole project from its top (for example `node --test` run in the project folder) also find the worktrees' test files.
  - **Long paths on Windows:** worktrees live under `.wax\worktrees\<goal>-<n>\`, which makes paths about 30 characters longer. If that goes over Git for Windows’ default limit (260 characters), creating the worktree fails, no worker starts, and the error says how to fix it. For projects with deep paths, turn on `git config core.longpaths true`.
  - **.env copy:** only the names you check under **.env files to copy into new worktrees** on the goal screen (candidates: `.env` and `.env.local` at the project top, plus names the setup script lists) are copied into new worktrees. Regular files only (links are not followed), never over a file already in the worktree, with mode 0600 on macOS and Linux (Windows leaves the mode alone, so the copy follows the folder’s access rights like the original `.env`). Records keep the names, not the contents. A worker still needs a person's approval to read them.
  - **Setup script:** write `{ "setup": ["npm", "ci"], "env": [".env"], "portEnv": "PORT" }` in the repository's `docs/wax/worktree.json` and those arguments run without a shell in each new worktree (5-minute cap, only the last 4000 characters of output are kept in `.wax/chat/worktree-setup.jsonl`). It is repository code, so it runs only after the person on this computer opens **Review setup script** on the goal screen, checks the file, the arguments, the repository files the arguments name and the hash, and presses **Approve this hash**. The hash covers worktree.json together with the files the arguments name (for example `scripts/setup.sh`) and, when the first argument is `npm`, `pnpm`, `yarn`, `bun` or `npx`, the project's top-level `package.json` and any lock files present (`package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lockb`, `bun.lock`). The approval screen lists every file in the hash, and any change needs approval again. A package manager setup script approved before this release shows **Changed since approval (approve again)** because its hash changed, so approve it once more. Worktrees are created from a commit, so the files must be committed. Without approval the setup is skipped and nothing runs in its place. If it fails or passes 5 minutes, the worker is not started and a blocked card is left for a person. Stopping the worker or the goal while the setup runs ends the setup process and every process it started (`taskkill /T` on Windows), and the worker is not started. The worktree list shows **setup stopped (runs again on the next start)**, and the setup runs again the next time a worker starts. The hash covers only these files, so if the command runs other repository files (such as files the scripts call) or downloaded packages, approve only when you trust those too.
  - **Folders to copy and pre-import checks (`copy`, `checks`):** worktree.json can hold `"copy": ["node_modules"]` (ignored folders of the project, up to 20 relative paths split by slashes, no globs) and `"checks": [["node", "--test"]]` (up to 5 argument arrays run without a shell). Both are part of worktree.json and so are bound by the same hash, and the repository files the `checks` arguments name and, when a check starts with a package manager, `package.json` and the lock files are in the hash too. With `copy` or `checks`, `setup` may be left out (then nothing runs to set up a new worktree). Checks run only when you start them, in that worktree, without a shell and one after another (a failing command does not stop the next ones; 10 minutes per command, 30 in total). The results are kept apart from task evidence in `.wax/chat/preimport/<worktree>.jsonl`, and the worktree line on the goal screen shows the last result. Start them with **Run checks** in the **Pre-import checks** block of the **Import locally** preview, which shows each command's status, time and the last 40 lines of output (it refreshes every 3 seconds while running, and **Stop** stops it). When there are checks (approved `checks` or the check command on the start screen), an import goes ahead only if the last run passed for the current worktree and project HEAD. If the worktree or HEAD changed after the run, the preview says "Changed since the checks ran. Run them again.", the confirm button is off and the server refuses as well. There is no button to skip a failure: discard the worktree, fix it and **Run again**, or start the task worker again to fix it (to drop a check for good, remove it from worktree.json and approve again). Imports are also refused when the checks cannot run because `checks` changed after approval or the start-screen command has shell characters. Checks run on the worktree, so when main has moved past the worktree base the preview says by how many commits. Without checks, imports work as before. The import record keeps the check run it used. A check that changes worktree files (for example a coverage folder that is not ignored) counts as a failure. Adding the fields changes worktree.json, so approve it once more.
  - **Fast copy of build folders (`copy`):** the `copy` lines of the approved hash are copied from the project into each new worktree once, after the `.env` copy and before the setup script (always project → worktree; a reused worktree is not copied again). Nothing is copied while the file is pending or changed. Each line must be ignored in the project with no tracked files and no links on the way, and ignored in the new worktree too (by the `.gitignore` of the base commit); a folder already in the worktree is never overwritten. A missing source is skipped and does not count as a failure. Links inside are made as is only when they are relative and point inside the worktree; a single absolute link, a link going outside, or one pointing at `.git`, `.wax` or `.env*` keeps the whole line from being copied. Special files such as sockets and FIFOs are skipped, and files keep the source modification time. On macOS, when the project and the worktree are on the same APFS volume, `/bin/cp -c` (clonefile, uses almost no disk) copies up to 4 parts at once and the copy is walked again to check its links; on Linux each file is cloned (copy-on-write on btrfs or XFS); on volumes that can do neither (ext4 and others) a plain copy is made only up to 1 GB in total and only when the free space is at least twice the bytes to copy. A worktree takes at most 300,000 files and 3 minutes. Over a limit or on an I/O error the partial copy of that line is removed and the setup script installs from scratch (the worker still starts). Stopping the worker or the goal during the copy removes the partial copy, does not start the worker and copies again on the next start. Windows does not use fast copy (security scanning and long paths can make it slower than installing; it will be turned on after measuring on a real PC). The result shows as "N copied" on the goal screen's worktree row and in the setup cell of the worktree overview, and the list (`.wax/chat/worktrees.jsonl`) keeps only the path, result and file count per line (no file names). Paths under a copied folder are never imported, even when the worker edited `.gitignore` so they are no longer ignored or committed them; the preview counts them in a **Copied build folder** line, and the worktree overview leaves them out of line counts and the check.

A worktree whose folder is gone or that moved to another branch shows **Folder missing** or **Not on its branch**. Git cells are filled for the latest 50 rows that are not removed (**Show more** in the table adds 50 more); removed worktrees appear, with record cells only, only with `--all` (**Show removed** in the table). `--fast` leaves out line counts and the check. With more than 2000 uncommitted files, line counts and the check are skipped. Git runs read-only commands only, at most 4 at once per project, within 5 s per command (10 s for `status`), 15 s per row and 60 s for the whole table; only cells over a limit say **Timed out**. The project `.git` and the worktree index are never written (optional locks are off). - **Repeat check:** wax watches whether a worker keeps doing the same thing within one run. The threshold is the goal limit **Repeat threshold** (3 by default).
  - **Same failing test:** among the `wax test` proofs that worker left after its run started, the same failure on the same code is counted: the same command, exit code, working tree right before the run (the contents of changed and untracked files) and output tail (2000 characters). A failure after a code change is a different failure even with the same message. Durations, timestamps, process IDs, local ports, stack positions in files inside the project or temporary folders, and the project and temporary folder paths are ignored in the comparison; other numbers such as assertion values are compared as they are. Passing runs, checks run by a person or another worker, and proofs whose working tree could not be recorded (a project that is not a Git repository, or a large tree with more than 200 changed files) are not counted. By default (`WAX_STUCK_CHECK=warn`) nothing stops: the running worker row gets a **Same failure 3 times** warning with the command, and the decision log records **Repeat check · Warned**. A dashboard started with `WAX_STUCK_CHECK=stop` stops the worker there and blocks its assignment (reason "The same test failed 3 times with the same output, so the worker was stopped: <command>", record **Worker · Stopped as stuck**). Requests allowed by the goal allowance count too. It only shows; nothing is stopped. Denying makes the worker look for another way.

  - **Root-cause mode:** when an assignment that stopped on the same failure (`stop`), that was warned (`warn`) and did not complete its phase, or whose last two worker runs each ended without completing the phase on the same failure (same command, exit code, work tree and output, the comparison `wax diagnose` uses for the same failure across runs) is handed out again (the worker card after a person reclaims it, a retry from the block judgment, or the retry of a done that did not complete the phase), the next worker prompt starts with a fixed procedure: rerun the failing command exactly through `wax test` to reproduce it, read the whole error, do not repeat an earlier hypothesis, pick one hypothesis and make only the smallest change that tests it, and if it is not fixed, undo the change and end as blocked. After the procedure, data wax computed from the records goes in only as a quoted block (the failing command, exit code, the last 2000 characters of the last failing proof's output, earlier attempts' hypotheses and results, and up to 30 files that changed between the earlier attempt's first and last failure). The output and command are scrubbed first, like the tool output of an end record (secrets, tokens, the home folder, the project path, the user name, e-mail addresses). The worker card and the running worker row show **Root-cause mode (attempt 2)**; the hypothesis the worker reports is kept in the end record (`rootCause`) and shown in the decision log as **Hypothesis: … · not fixed** (**No hypothesis reported** when there was none), and it goes into the block judgment input. When as many root-cause attempts as the goal limit **Root-cause attempts** (default 2) end without a fix, the assignment becomes one person card, **The approach may be wrong**: the list of hypotheses and the repeated command, **Try once more** (raises the limit by 1 until the goal is resumed), **Stop goal**, and a pointer back to plan or design (`wax iterate` after review, or a new task). This card cannot be dismissed, and auto uses no block judgment or retry rule on that assignment. Assignments blocked in a root-cause attempt are counted by this limit, not as blocks in a row. A run that ended in a tool failure (usage limit, configuration, permission) is not counted as an attempt, and is skipped when counting the same failure across runs. Resuming the goal counts from attempt 1 again. With `WAX_STUCK_CHECK=off` there is no root-cause mode either.

- **Usage:** when a headless worker or PM judgment ends, the usage its tool reported itself is kept on that run's record. Claude Code reports input, output, cache read, cache write and reasoning tokens plus cost and turns; Antigravity CLI reports input, output, reasoning, cache read and total tokens plus turns. Codex, Gemini CLI and GitHub Copilot CLI are recorded as not reporting. wax does not compute prices, does not fold cache tokens into input, and adds tokens per tool because a token means something different in each tool. It shows in the goal's limits area, `wax pm-loop show`, the run trace, `wax status` and the PR description draft, and the report phase instructions get the sum as quoted data so the report quotes these numbers instead of inventing them. Records written before this feature count as "no usage record".
- **Token limit (optional):** when creating or resuming a goal you can set a **Token limit** (1,000–10,000,000,000, empty for none). When the tokens the tools reported (the total a tool reports, or else its input, output and cache tokens) reach it, the goal stops like any other limit and running workers are left to finish. It applies only to tools that report usage (Claude Code, Antigravity CLI), so in a goal with this limit auto does not launch a tool that does not report usage and leaves it as a card for a person (the card carries a warning, and a person can still choose it). Only a person resuming raises it.
- **Cost limit (USD, optional):** when creating or resuming a goal, or in a recipe's limits, you can set a **Cost limit (USD, optional)** ($0.01–$10,000, up to two decimals, empty for none). Use `.` as the decimal point (a comma such as `1,5` is refused with a hint). When the cost the tools reported (only Claude Code reports it for now) reaches or passes the limit, the goal stops after that run and running workers are left to finish. wax does not compute prices. With a subscription login the value may be what the tool priced at API rates rather than your actual bill, so the screen always says "Cost reported by the tool, may differ from your bill". Runs that do not report cost (Codex, Gemini CLI, GitHub Copilot CLI, Antigravity CLI which reports only tokens, and older records) are not added as zero; they are counted separately as "unknown for N runs" and never stop the goal. In a goal with this limit auto does not launch a tool that does not report cost (nor use a retry rule with it) and leaves it as a card for a person (the card warns "This tool does not report cost", and a person can still choose it). The goal screen shows `$1.23 / $5.00 · unknown for 2 runs`, and the usage in the PR draft and run trace shows "Cost reported by the tools $1.23 (unknown for 2 runs, …)". Only a person resuming raises it.
- **Changing limits and resuming:** under the goal's **Limits**, a person sets the per-goal limits and the PM judgment tool (phase runs 1–200, concurrent workers 1–10, hours 1–168, iterations 0–50, blocks in a row 1–20, auto actions per hour 1–120, idle stop 0–30 minutes where 0 turns it off; raise it if a check runs a long time without output; repeat threshold 2–10, raise it if rerunning a long check with the same result is normal in the project; root-cause attempts 1–5; the token and cost limits are optional and emptying one removes it). The 20 headless runs a day are a project-wide limit and cannot be changed. A goal stopped at a limit continues after a person checks the limits under **Resume goal**.
- **Verified scope:** unit tests and browser checks replace the worker and PM judgment runners with fakes. On 2026-10-31 one round trip ran with real tools on macOS ("Real-tool round trip" in the design document `docs/design/PM_LOOP.md`). Claude Code workers actually finished plan, design, implement and report and returned the fixed JSON, and Claude Code PM judgments (block and CEO report) kept to the read-only instructions and passed the schema. Reviewer separation removed the implementing tool from the review tool list, and auto carried on through Codex failure → block judgment → reassign to another tool without cards until it hit the daily limit. Codex on that computer couldn't run because of an account problem, so a successful Codex worker wasn't confirmed, and the Antigravity CLI worker couldn't finish review because it can't ask for command permission in non-interactive mode (the commands have to be allowed in Antigravity CLI's `permissions.allow`). The three issues found there (an accepted "reassign" applying only to that phase, so auto restarted the failing tool every phase; the card not warning about Antigravity CLI's command permission; the run trace showing `-` as the tool) are fixed as described above and checked with fake tools. They haven't been rerun with real tools since. Read-only is enforced only by the instructions, not by changing the tool's permission settings, so deny any write permission request that arrives during a judgment on the execution approvals screen.

### Start from a recipe

Work you do often (fixing one bug, say) can start a goal in one go from a **recipe**. A recipe only stores a goal's starting values (tasks and acceptance criteria drafts, a default worker tool per phase, the PM judgment tool, limits and phase notes); a goal made from a recipe runs like any other goal.

- **Start:** click **Start from a recipe** in the PM loop, pick a recipe and click **Start with this recipe**, type the one input line (for Bug fix, "What is broken?") and click **Fill**. If the recipe has a details box (every built-in recipe does, for example "Steps to reproduce and expected behavior" for Bug fix), write more below it (several lines, 2000 characters, optional). The goal title, the task IDs (from the input part `{slug}`, a short hash when the input has no Latin letters, and editable), task titles and AC, the default worker tool per phase, the PM judgment tool and the limits are prefilled, and you can edit all of them. On **Create goal** the server checks the edited values again with the same check as recipes (anything out of format is refused, and a task already in another active goal is refused as before). The details text then fills the task description template (`{details}`) and becomes the new tasks' description, and it reaches worker prompts only as quoted data, never as instructions. Leave it empty for no description.
- **A person still confirms the plan:** the AC drafts (`- AC-n:`) are saved right away to tasks whose plan document is empty, so no plan-draft judgment (one AI run) is offered. The goal starts before plan confirmation and moves only after **Confirm the plan and start**. Goals are always created in suggest mode; a recipe's auto is only an **auto recommended** badge (the PM turns auto on from the goal screen).
- **Default tool per phase:** it only changes the default tool on worker cards. It is used only when installed on this computer, a review tool equal to the implementing tool is ignored in favor of the usual order, and a preferred tool set by a block judgment comes first. Cards and records that use it say "Recipe default tool". Naming Antigravity CLI for implement or review keeps the command-permission warning and auto still picks another tool. A person confirms every start.
- **Phase notes:** added to that phase's worker prompt only as quoted data (`@name` neutralized), never as instructions. Fixed rules such as no push or PR, no proof waivers and no writes outside the project come first.
- **Built-in and personal:** there are three built-in recipes, **Bug fix** (`bugfix`, 8 phase runs, 2 hours), **Add a feature** (`feature`, default limits) and **Behavior-preserving refactor** (`refactor`, 8 phase runs, 4 hours), and they name no tool. Personal recipes live on this computer in `.wax/recipes/<id>.json` (not committed), and for the same id a personal recipe comes first, then a shared one, then a built-in one. Only a person manages them in the dashboard, with **＋ New recipe**, **Edit** (**Edit as a personal recipe** for a built-in one) and **Delete** in the recipe panel (JSON editing, the same check on save). You can edit the files directly too, but a recipe that fails the check shows as **Unusable** with the reason. Saves and deletes are recorded in `.wax/chat/recipes.jsonl`.
- **Shared recipes:** recipes in `docs/wax/recipes/<id>.json` in the repository are shared with the team. So that a recipe someone else committed cannot quietly change tool choices or worker instructions on this computer, a person here clicks **Review**, reads the whole normalized recipe (tasks, AC, description templates, tools, judgment tool, limits, notes, allowance suggestion) and the changes since the last approved version, and clicks **Approve this content** before it can start goals. The approval is bound to the file content (sha256): if the file changes by even one character it goes back to **Changed since approval (needs approval)**. A shared recipe that is not approved, has changed or fails the check has no start button, and the built-in recipe with the same id is not used instead. You can also **Reject** it or **Retire** an approval; approvals, rejections and retirements stay only in `.wax/chat/recipes.jsonl` on this computer (the file is not changed).
- **Project manual:** write the working rules and checks your team shares (for example "capture a 390px screenshot when the screen changes") in `docs/wax/manual.md` in the repository. Under **Project manual** at the top of the recipes section, **Review** shows the whole body, the suggested test commands and the changes since the last approved version; after **Approve this content** it goes into PM loop worker prompts, `wax prompt <stage> <task-id>` and dashboard request stage prompts as quoted data. `wax context` shows its approval state and hash instead of the body. It is data, not instructions, wax's fixed instructions come first, and it is never given to PM judgments. A manual over 16 KB or 400 lines or with hidden characters is not truncated but marked unusable. Like shared recipes the approval is bound to the file content (sha256), so if anyone, workers included, edits the file it is left out until approved again (an older approved version is never used instead). A leading `---` / `checks: ["npm test"]` / `---` block only shows suggestions under the test command field of the goal start screen, which fill the field when clicked. `wax quality-report` shows, as an observation only, whether each of these commands has a passing test proof in the current iteration; it neither runs them nor makes them a completion condition. The manual cannot change allowances, tools, limits or the mode. Decisions stay only in `.wax/chat/manual.jsonl` on this computer, and worker start and end records and the run trace keep the first 12 characters of the manual hash that was given.
- **Export as shared:** **Export as shared** on a personal recipe writes it to `docs/wax/recipes/<id>.json` (an existing file with that name is replaced) and records it as approved on this computer. This is the only time the dashboard writes a shared file. Commit and push it yourself; other computers must approve it before use.
- **Save a goal as a recipe:** **Save as a recipe** on a finished or stopped goal opens a personal recipe draft made from that goal in the editor. Task titles and AC come from the goal's tasks (task IDs become `<prefix>-{slug}`), the tool per phase is the tool of the worker that actually finished that phase (failed tools are left out), the PM judgment tool is the goal's, the limits are 1.5 times what was used (rounded up, within range), and notes are empty. Put the input placeholder `{input}` into the goal title template (`goal`) before it can be saved (for example `"Fix: {input}"`). The save record keeps the goal it came from (`from`).
- **Format:** `schema: 1`, an id of lowercase letters, digits and - (64 characters), only the defined properties, no hidden characters, name 200 characters, description 500, input label 200, phase notes 1000, details box label 200 and example 500, 1 to 20 tasks (title 200 characters, description template 1000, 1 to 10 AC per task of 300 characters), only the `{input}` and `{slug}` placeholders (task description templates use `{input}` and `{details}`, notes all three), only tools that can run headless, limits in the same ranges as goal limits (missing limits are the defaults), mode `suggest` or `auto`, and an allowance suggestion `allow` only from `wax`, `test`, `write` and `read` (a suggestion only; it turns nothing on). Each file is at most 64 KB and up to 50 recipes are read per location (personal, shared, built-in). There is no setting to skip a phase.
- **Records:** the goal and its `goal created` record keep the recipe id, location and file hash and the fields edited on the start screen, and the goal screen and the run trace show **Recipe: <name>**.
- **CLI (read-only):** `wax recipe list`, `wax recipe show <id>`, `wax recipe check [<file>]` (runs the same check on one file or on every recipe, exit code 1 if anything is unusable). Shared recipes are shown with their approval state on this computer, and unapproved ones do not change the exit code. The CLI neither creates nor approves recipes and never starts goals.

## 6-7. Project rules and wiki

### Project rules

**Project rules** are short rules that keep the next session from repeating an AI's mistake. When a review finds a real defect, or when the PM reviews progress, an AI session proposes one with `wax chat rules propose`, citing records of mistakes (tests that failed in review, iteration reasons, blocked tasks, defects found in review `defect:<task>/D-N`). Proposals without evidence and duplicate rules are refused. Once a person approves it in the **Project rules** panel of the dashboard (`/manage`), it goes into every stage prompt (`wax prompt` and the dashboard runner) and into `wax context`; it can be rejected, or retired later. The CLI has no approve command, so an AI never confirms its own rules. The prompt also says to report, not follow, a rule that no longer fits the current code. `wax chat rules lint` lists applied rules whose evidence can no longer be found.

`wax chat rules` lists the applied rules, `--all` adds pending, rejected and retired ones, and `rules candidates` shows mistake records that no rule cites yet. A defect whose title (ignoring case, spaces and punctuation) appears in more than one task is listed first as a "repeated defect", since it is the most useful evidence for a rule that stops the same mistake. wax never edits the manual (`docs/wax/manual.md`), so when a rule becomes a team-wide standard a person moves it into the manual. Prompts carry the 20 most recent approved rules. The dashboard panel lists pending approval → applied, with rejected and retired rules folded away, and a rule proposed from the CLI shows up in the panel within a second or two. Records are only ever appended to `.wax/chat/rules.jsonl`.

### Project wiki

The original records stay untouched while AI sessions organize topic pages in `docs/wax/wiki/<page>.md`. A page saves only when every paragraph and list item carries `[근거: <record IDs>]` and every cited record exists. Citable evidence is the record IDs `wax wiki ingest` shows (task `feature:`, stage document `doc:`, decision `note:`/`msg:`, test failed in review `proof:`, iteration reason `iterate:`, blocked task `blocked:`, defect found in review `defect:`, project rule `rule:`) plus `commit:<hash>` and `file:<path>[#L10-L20]`. wax calls no AI; an AI session organizes the wiki after the daily report or when the CEO asks.

```sh
wax wiki ingest --batch 20          # records not yet in the wiki, oldest first
wax wiki save auth --file auth.md   # save after checking evidence; an existing page needs --base <hash>
wax wiki skip doc:login/plan        # records not worth keeping
wax wiki lint                       # uncited paragraphs and missing evidence (errors), retired rules and files changed since saving (to check)
```

An existing page changes only with the hash read by `wax wiki show` as `--base`, so one session never overwrites another's edit. Cited records count as included and leave the next batch. `lint` reports evidence that disappeared when an iteration replaced a stage document, and cited files changed by a commit after the page was saved. `wax context` lists pages that cite the task, the **Project wiki** panel of the dashboard (`/manage`) shows pages with their check results, and `wax search` and `wax recall` find wiki pages too. The wiki is reference material, so check it against the current code. A test that was not actually run must never be recorded as passed.

### Backup and restore

Back up with `wax backup > wax-backup.json`, preview the restore with `wax import --file wax-backup.json`, then restore by passing the preview's fingerprint as `--apply <fingerprint>`.

`wax backup` carries the task records (`.wax/features`) together with project rules, work-note memos, assignments, the PM, channels, whiteboards, the daily report list (`.wax/chat`) and the wiki state (`.wax/wiki`). Session presence, running requests, the search index and run approvals are not included. Wiki pages and report documents (`docs/wax`) are repository files, so keep them with git. `wax import` skips a task or record file that already exists in the target project instead of overwriting or merging it, and the preview lists each file's status under `files`. With `--prefix`, only tasks are restored, because record files point to the original task IDs. Record files are kept up to 128 MB in total; beyond that only their size is kept. Backups from earlier versions (task records only) still restore.

Damaged backup originals are kept up to 1 MB per file, 1,000 files and 64 MB of original text in the JSON. Files over the limit keep their size and the reason they were left out, and healthy work keeps being backed up.

| `WAX_PLAN_STEPS` | `warn` | Plan completed without plan steps (S-N) or with steps lacking a check, when the plan has AC, and implement completed while a step's check has not passed: `warn`, `enforce` or `off` (section 4, "Plan steps") |
| `WAX_APPROACH` | `warn` | Design completed without an approach record (`approach --propose` or `--single`): `warn`, `ask`, `always` (only an approach a person picked) or `off` (section 4, "Design approach") |
| `WAX_REVIEW_STAGES` | `warn` | Missing `s-N`, `red-green` or quality items in the two-stage review (spec → quality): `warn`, `enforce` or `off` (section 4, "Two-stage review"). A failed spec or quality item is always refused |
| `WAX_MCP` | off | `on` starts the `wax mcp` server (section 6-2) |
| `WAX_HOST_STATE` | on | With `off` at Claude Code start, the session state hook (automatic working, waiting for you and done) does nothing |
| `WAX_APPROVALS` | off | Sends permission requests from a Claude Code session started with `on` to the dashboard ([Managing execution approvals](./APPROVALS.md)) |
| `WAX_TOOL_NEWS` | on | `off` stops Rina's tool news from checking external releases |
| `WAX_GH_BIN` | `gh` | The `gh` executable GitHub triggers call (section 6-5) |

`WAX_TASK_DONE_CHECK`, `WAX_REVIEW_SEPARATION`, `WAX_RED_GREEN`, `WAX_PLAN_STEPS`, `WAX_APPROACH` and `WAX_REVIEW_STAGES` follow the value each session and dashboard was started with, so start them all with the same value to apply it to the whole team.

## 8. Troubleshooting

| Symptom | What to check |
| --- | --- |
| `/wax:` commands don't appear | Check that `wax@wax` is enabled in `claude plugin list` (install once), or check the absolute `--plugin-dir` path or the Gemini extension link, then start a new session. |
| Skills don't appear in Antigravity CLI | Check the `.agents/skills` link with `install-project.mjs --project <path> --check`, then start a new `agy` session. |
| Skills don't appear in Grok Build | Check the `.grok/skills` link with `install-project.mjs --project <path> --check` (rerun the link command for projects linked before 0.13.5), then start a new `grok` session. |
| Skills don't appear in Codex | Check the link and the original folder with `install-project.mjs --project <path> --check`, then start a new session. |
| A stage won't move on | Check the current stage document, completion evidence and whether review passed. Implement and review need a linked passing test or commit proof (`--proofs`). |
| Grok Build is missing from the dashboard's execution tools | Grok Build does not support automatic runs or PM loop workers. Ask for skills by name in a terminal session (section 5-4). |
| Browser notifications don't arrive | Check that you pressed **Turn on notifications**, that you allowed notifications in the site settings if the button says **Notifications blocked**, and that a dashboard tab is open. Nothing is notified while you are looking at the tab. |
| A trigger shows **Connection needed** | Check `gh auth status` on this computer; after `gh auth login` it is checked again the next minute. If `gh` is not on the PATH, give its path with `WAX_GH_BIN` and restart the dashboard. |
| Existing GitHub issues are not proposed | The first check only records what is already there as a baseline. Remove the label and add it again (section 6-5). |
| A trigger turned itself off | It turns off after 5 failures in a row. Fix the reason shown in the list, then turn it on again. |
| A PM loop goal stopped | Check the reason on the goal (a limit, blocks in a row, a failed auto action), fix the cause, then check the limits under **Resume goal**. |
| `wax mcp` doesn't start | Check that the registered settings' env has `WAX_MCP=on`, and read the error output of `WAX_MCP=on node /path/to/wax/bin/wax.mjs mcp --project <path>` in a terminal (section 6-2). |
| The CLI speaks English (or Korean) | Set `WAX_LANG=ko` or `WAX_LANG=en`. Without it the CLI follows `LC_ALL`, `LC_MESSAGES` and `LANG`. |
| It still says saving after a crash | wax reclaims a save lock whose owner process has ended at the next save. If one remains, find the lock path with `doctor`, make sure all wax work in that project has finished, then remove the `.wax/features/<id>.lock` directory. |
| (Web service) AI buttons are disabled | Set the provider, model ID and key, then restart the server. |
| (Web service) An AI request shows 401, 403 or 404 | Check the API key, the model name and access to the model. |
| (Web service) An AI request shows 429 | Check the provider's usage limits and billing, then try again later. |
| (Web service) A save conflict appears | Download the draft from the recovery panel or compare it with the latest record, then bring it in again. The server never overwrites the original by itself. |

Rows marked "(Web service)" apply when you also use the wax web service (wax-service).

Check records in one go with `node "/path/to/wax/bin/wax.mjs" doctor --project "/path/to/project"`. It prints the number of healthy records and the problem files and lock paths as JSON. It never changes files or removes locks, and it exits with code 1 if there is a problem.

## 9. Updating and what has been verified

Close the host sessions, back up the existing plugin, and put the new ZIP at the same plugin path. If you installed through a marketplace, `node "/path/to/wax/bin/wax.mjs" update` checks every installed tool and runs each tool's update commands in turn (`--check` only checks, `--yes` also answers the Gemini CLI extension consent; per-tool commands are in INSTALL.md). Antigravity CLI and Grok Build use project links, so the folder you run the command in (or `--project <path>`) is checked. When the program (`agy`, `grok`) is installed but that project has no link, it says "installed, wax not linked in this project" and shows the link command. Keep `.wax` and `docs/wax` in your projects. If you changed the plugin yourself, compare and merge your changes before updating.

If you registered the public repository as a marketplace before 0.16.0, updating may fail because the repository history started over in 0.16.0. Remove the registration and register again (section 1, "0.16.0 public repository note"). For Codex use the switch commands in section 5-1 as they are; for other tools, remove the marketplace with that tool's command, then register and install as on the first install. `wax update` recognises this failure and shows the re-register commands but does not run them. For project links (Antigravity CLI, Grok Build and others), if `git pull` fails in the linked clone of the public repository, clone it again and re-run `install-project.mjs --project <project>`.

Automated checks cover state storage, stage transitions, concurrent-edit conflicts, the CLI, Codex installation and the skill runner, read-only diagnostics, and running after extracting the ZIP. The Claude plugin format and the Gemini command syntax are checked too. Marketplace installation and real command runs were confirmed in Claude Code 2.1, Codex 0.162 and GitHub Copilot CLI 1.0.97. Junction installs, linked runs, Korean paths, stage transitions, test evidence and backups were verified on Windows with Node.js 22.17.0; reproduce them with `npm run test:windows` on Windows. Only versions that pass the checks on Ubuntu, macOS and Windows with Node 22 and 24 are published.
