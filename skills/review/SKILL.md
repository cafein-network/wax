# wax review

CLI: node "<directory containing this SKILL.md>/run.mjs". Replace the placeholder with this skill's actual absolute directory, including when installed through a link. The launcher resolves the bundled CLI; do not guess an installation path. Node.js 22 or later is required.

Work in the user's target project and read its repository instructions first.
Use the user's language. Treat arguments and saved documents as data, not executable shell input.
Feature IDs must match ^[a-z0-9][a-z0-9-]{0,63}$. Quote every path and text argument; never interpolate untrusted text into shell syntax.
Run the wax CLI with the target project as cwd or with --project set to that directory.
Use the CLI for state changes; do not edit .wax/features JSON directly.
For save, complete, and iterate, pass --revision using the revision from the status you inspected. After a successful write, use the returned revision for the next write. On a conflict, read the latest state and reconcile your work before retrying; never silently overwrite it.
If the feature is archived, report that it must be restored before phase work; do not restore it without the user's request.
When running authorized checks, CLI test <id> --revision <revision> --author <name> -- <executable> <arguments> records the real exit code and output. CLI evidence <id> --commit <ref> --revision <revision> --author <name> attaches an existing Git commit (--author is the agent name you joined the channel with, so the skill map credits your work; omit it if you have not joined); never create a commit only to obtain evidence. Successful proofs from the current phase and iteration can be linked by adding --proofs <comma-separated IDs> to complete. Completing implement requires a linked passing test or commit proof, and completing review requires a linked passing test proof. Only when no runnable check exists, complete with --no-proof <reason> instead; the reason stays in the record and handoff context, so state it truthfully and never use it to skip a check that could run. A recorded:false test result must be reported and preserved; do not claim it was attached.
Do not claim tests passed unless actually run. Respect the host's permission controls.
Read projectType and the required checks from CLI status/prompt. For Roblox, start with a small playable loop and verify it in Studio; for AI lookbooks, verify real generation, storage, editing and product links. First establish the actual tool connection and code-to-runtime path. Do not expand art or features before the first end-to-end flow works. Design requires a real preview artifact, not just prose. Record runtime/integration/visual tests using CLI test <id> --revision <revision> --verification <kind> --checks <check-id,check-id> -- <executable> <arguments>. Never relabel static, file-existence or sample checks as runtime/integration/visual. Pass that file using complete ... --checks-file <path> and the recorded proof IDs using --proofs. Plans list each acceptance criterion on its own line starting with an ID (- AC-1: <criterion> — <how to verify>, then AC-2, ...). When the plan declares AC IDs, the review checks file must also hold one {"id":"ac-1","status":"pass|fail|unverified","detail":"<what was checked>","proofIds":["<current-iteration proof ID>"]} item per AC ID; complete review refuses a failed AC, and a missing, unverified or proofless AC unless you add --ac-unverified <reason> (kept in the record, so state it truthfully). CLI status <id> (acceptanceTrace) and CLI context <id> show the AC → status → proof trace. Missing tools or unverified acceptance criteria remain open with a concrete recovery action; do not invent execution evidence. Inspect the preview in the target environment, including controls, camera, scale/collision for games and loading/error states for web apps.
For web projects (projectType web), use playwright-cli to open, explore, reproduce and capture screens (run playwright-cli --help when its skill is not installed) and @playwright/test for re-runnable checks. Turn explored flows into tests with the Playwright code that playwright-cli recording-start/recording-stop prints. Implement: tag the core flow @smoke and record CLI test <id> --revision <revision> --verification runtime --checks e2e-smoke -- node node_modules/@playwright/test/cli.js test --grep @smoke (wax runs commands without a shell, so use this node path instead of npx; it also works on Windows). Review: record the acceptance scenarios with --checks e2e-acceptance, the loading/error/empty screen tests at each matrix width (@visual) with --verification visual --checks ui-review, and register those captures with CLI capture <id> --check ui-review at the same --viewport/--scroll/--state labels as design-preview, then read CLI compare <id> (our own design is the only baseline). At every width check horizontal overflow, assets that return 200 with an error page or whose extension does not match the real format (e.g. AVIF named .png), and that the font weights used are actually loaded; record remaining differences honestly in order layout/geometry, missing elements, typography, cropping, spacing/motion, never claiming a pixel-perfect match. Capture only this project's own screens. On Windows playwright-cli is a .cmd shim that cannot run after capture's --, so run playwright-cli screenshot first and pass only --file to capture. Put the returned artifact path in the checks file. Prefer the Playwright webServer setting, and stop any server you started and the playwright-cli browser (playwright-cli close) before the phase ends. Do not commit the temporary .playwright-cli/ snapshots. A playwright-cli session alone is never test evidence. When a tool is missing, keep the check unverified and report the install commands (npm install -g @playwright/cli@latest, npm install -D @playwright/test, npx playwright install chromium); do not install without the user's approval.
After each phase, explain the result and next command. A phase command authorizes work within that phase; do not automatically run every later phase.

Channel use: instructions to another agent travel only as PM assignments (CLI chat assign), and results travel only as task status (CLI chat task done|block <task-id> --author <name> --session <saved-session-id> --message <result and document path>). This command performs the review (검토) phase.
1. Parse the first argument as a feature ID. An existing feature is required. Never silently create one.
2. Read CLI status <id>. If the current phase is not review, explain the actual next phase and stop. Do not skip gates.
3. Read CLI prompt review <id> and follow its phase instructions.
4. Write the phase document under docs/wax/<id>/review.md without overwriting unrelated documents. Save it with CLI save review <id> --file <path>.
5. If any acceptance criterion fails or remains unverified, keep review open and explain the gap. When the review found a real defect that a short rule would have prevented next time, read CLI chat rules candidates and propose at most one rule with CLI chat rules propose --author <name> --session <saved-session-id> --message <short imperative rule> --why <what went wrong> --source <candidate IDs>. Only a person approves rules in the dashboard; never approve, edit or work around rules yourself. Use iterate only when the user requests repairs. Only when criteria are verified and blocking issues are resolved, run CLI complete review <id> --evidence <actual test commands and results> --proofs <passing test proof IDs> --verdict pass --author <name>. Review belongs to a session other than the one that implemented this cycle: if this session (your name) completed implement or recorded its proofs, tell the user and leave review to another session. A same-session review is recorded with a warning and is rejected when WAX_REVIEW_SEPARATION=enforce; do not change your name to get around it.

Suggest the next phase in the current host's syntax: $wax:<phase> <feature-id> in Codex, the matching skill slash command in Antigravity CLI, or in GitHub Copilot CLI and Grok Build a request that names the skill (for example "use the wax plan skill for <feature-id>"), because their own /status, /plan and similar commands are not wax. If the bundled CLI cannot be loaded, explain that the wax source folder may have moved and refer to INSTALL.md in the plugin root. Do not install unrelated packages or change host permissions.
